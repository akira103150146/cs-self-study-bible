🔑
這一章的主軸：my-wc

我們將實作一個名叫 my-wc 的命令列工具，模仿 Unix 的 wc 指令——輸入一個檔案路徑，印出行數、字數與字元數。 這個工具小到可以在一章內做完，卻包含了一個真實 Rust 專案的所有關鍵要素：模組拆分、錯誤處理、測試、以及可部署的二進位執行檔。

專案結構與模組系統

用 cargo new my-wc --bin 建立一個新的二進位專案： 

cargo new my-wc --bin
# 產生:
# my-wc/
# ├── Cargo.toml   ← 專案描述與依賴宣告
# └── src/
#     └── main.rs  ← 進入點（binary crate）

一個 Rust 專案（稱為 package）可以同時包含一個函式庫 crate（library crate）和一個二進位 crate（binary crate）。按照慣例，src/main.rs 是二進位進入點，src/lib.rs 是函式庫根（crate root）。我們的 my-wc 採用這個架構：

  • src/lib.rs：定義並公開（pub）統計函式——可被 main.rs 和 tests/ 引用。
  • src/main.rs：解析命令列引數、讀取檔案，呼叫函式庫函式，印出結果。
  • tests/integration_test.rs：整合測試，從外部使用函式庫的公開 API 進行驗證。

模組系統：mod、pub、use

Rust 的模組系統讓你把程式碼組織成樹狀結構（模組樹，module tree）。三個關鍵字分工明確：

  • mod：宣告一個模組。可以是內嵌（mod stats { ... }）或指向同名檔案（mod stats; 會讀取 src/stats.rs）。
  • pub：使項目對外可見。Rust 預設一切是私有的——就連同 crate 的其他模組也看不到私有項目。
  • use：把路徑帶入當前作用域，省去每次都寫全路徑的麻煩。
// src/lib.rs 裡的內嵌子模組示範
mod stats {
    // 子模組內的項目預設私有；pub fn 才對外暴露
    pub fn count_lines(text: &str) -> usize {
        text.lines().count()
    }
}

// 在 crate root 層面重新匯出（re-export）
// 讓使用者可以直接寫 use my_wc::count_lines 而非 use my_wc::stats::count_lines
pub use stats::count_lines;
💡
連字號 → 底線：crate 命名規則

Cargo.toml 的 [package] name 可以用連字號（my-wc），這是 crates.io 的常見慣例。 但 Rust 識別字不允許連字號，所以在程式碼裡引用時要改底線：use my_wc::...。 Cargo 會自動做這個對應，不需要手動設定。

Cargo 生態：依賴管理與語意化版本

Cargo.toml 是 Rust 專案的心臟。它宣告 crate 的名稱、版本，以及最重要的——依賴（dependencies）。 

[package]
name    = "my-wc"        # crate 名稱（程式碼裡寫 my_wc）
version = "0.1.0"        # 語意化版本：major.minor.patch
edition = "2021"         # Rust Edition，建議一律用 2021

[dependencies]
# 本章 CLI 工具只用標準函式庫，不需任何外部 crate
# 若需要解析複雜命令列引數，可加：
# clap = { version = "4", features = ["derive"] }

[dev-dependencies]
# 只在 cargo test 時才需要的 crate；不會打包進最終二進位
# tempfile = "3"   ← 整合測試用的暫存檔工具

加入外部依賴

在 [dependencies] 裡加一行，Cargo 就會在下次 cargo build 時自動從 crates.io 下載並快取： 

[dependencies]
serde      = { version = "1", features = ["derive"] }   # 序列化框架
serde_json = "1"                                         # JSON 支援
tokio      = { version = "1", features = ["full"] }     # 非同步執行時
🔑
語意化版本（Semantic Versioning）與 Cargo.lock

Cargo 遵循 SemVer：major.minor.patch。版本規格 "1"（相當於 "^1"）允許 Cargo 自動升級到 >=1.0.0, <2.0.0 的任意版本，保留相容性升級彈性而不破壞 API（major 版本變更才代表破壞性更新）。 Cargo.lock 記錄每個依賴的確切版本——有了它，不同機器、不同時間點的 build 都能完全重現。二進位專案應 commit Cargo.lock；函式庫則通常不 commit。

常用 cargo 指令

cargo new my-wc --bin    # 建立新的二進位專案（--lib 建函式庫）
cargo build              # 編譯（debug 模式，不最佳化，加 debug symbol）
cargo build --release    # 編譯（release 模式，開啟完整最佳化）
cargo run                # 編譯並立刻執行
cargo run -- hello.txt   # 傳遞引數給程式（-- 之後才是程式自己的引數）
cargo test               # 執行所有測試（單元 + 整合）
cargo test count_lines   # 只執行名稱包含 count_lines 的測試
cargo clean              # 清除 target/ 編譯產物

動手做：my-wc CLI 統計工具

現在開始實作。先寫函式庫（src/lib.rs），再寫二進位進入點（src/main.rs）。這樣的分離有個重要好處：整合測試可以直接呼叫函式庫函式，不需要啟動二進位再解析輸出。

src/lib.rs — 三個統計函式

// src/lib.rs — 函式庫 crate 的根（crate root）
// main.rs 與 tests/ 都能透過 `use my_wc::...` 引用這裡的公開項目

/// 計算行數（基於 str::lines()；尾端換行不計入額外空行）
pub fn count_lines(text: &str) -> usize {
    text.lines().count()
}

/// 計算單詞數（以任何連續空白字元為分隔，包含 Tab、換行）
pub fn count_words(text: &str) -> usize {
    text.split_whitespace().count()
}

/// 計算 Unicode 字元數（碼位數，非位元組數；CJK 字元各算 1 個）
pub fn count_chars(text: &str) -> usize {
    text.chars().count()
}

// ----- 單元測試（只在 cargo test 時編譯） -----
#[cfg(test)]
mod tests {
    use super::*;   // 引入上層模組的所有公開項目

    #[test]
    fn test_count_lines() {
        assert_eq!(count_lines("hello\nworld\nfoo"), 3);    // 3 行（無尾端換行）
        assert_eq!(count_lines("hello\nworld\nfoo\n"), 3);  // 尾端換行不算額外行
        assert_eq!(count_lines("single"), 1);               // 無換行符 → 1 行
        assert_eq!(count_lines(""), 0);                     // 空字串 → 0 行
    }

    #[test]
    fn test_count_words() {
        assert_eq!(count_words("hello world foo"), 3);      // 3 個單詞
        assert_eq!(count_words("  tabs\there  "), 2);       // tab 也算空白，共 2 個單詞
        assert_eq!(count_words(""), 0);                     // 空字串 → 0
    }

    #[test]
    fn test_count_chars() {
        assert_eq!(count_chars("hello"), 5);                // 5 個 ASCII 字元
        assert_eq!(count_chars("你好世界"), 4);             // 4 個 Unicode 碼位（各佔 3 bytes 但算 1 個字元）
        assert_eq!(count_chars(""), 0);                     // 空字串 → 0
    }
}
ℹ️
str::lines() vs split('\n')

lines() 同時處理 \n（Unix）與 \r\n（Windows），且不因尾端換行多算一行： "hello\n" 用 lines().count() 得到 1，用 split('\n').count() 得到 2（產生空字串元素）。 處理使用者上傳的文字檔時，lines() 的行為通常更符合直覺。

src/main.rs — 二進位進入點

// src/main.rs
use std::env;
use std::fs;
use std::process;

// my-wc 的 Cargo.toml name = "my-wc"；程式碼裡用底線 my_wc
use my_wc::{count_chars, count_lines, count_words};

fn main() {
    // args() 回傳迭代器；collect() 蒐集成 Vec<String>
    // args[0] 是程式名稱本身，使用者的引數從 args[1] 開始
    let args: Vec<String> = env::args().collect();

    if args.len() < 2 {
        eprintln!("用法: {} <檔案路徑>", args[0]);   // eprintln! 印到 stderr
        process::exit(1);
    }

    let path = &args[1];

    if let Err(e) = run(path) {
        eprintln!("錯誤: {}", e);
        process::exit(1);
    }
}

fn run(path: &str) -> Result<(), Box<dyn std::error::Error>> {
    // read_to_string 可能失敗（檔案不存在、權限不足等）
    // ? 運算子：若 Err，立刻提早回傳，不繼續執行後面的程式碼
    let text = fs::read_to_string(path)?;

    // {:>8}：右對齊、最小欄位寬度 8 字元
    println!("{:>8} 行   {:>8} 字   {:>8} 字元   {}",
        count_lines(&text),
        count_words(&text),
        count_chars(&text),
        path
    );

    Ok(())
}

分離 lib 與 bin 的三個工程理由

把邏輯放 lib.rs、入口放 main.rs，帶來三個好處： (1) 測試可以直接呼叫函式，不需要啟動整個程式再解析輸出——更快、更精確。 (2) 將來可把函式庫發佈到 crates.io，讓別人引用你的統計函式。 (3) 同一個 package 可以有多個 binary（放在 src/bin/*.rs），全部共用同一個 lib。

錯誤處理整合：Result、? 與自訂錯誤型別

在第 80 章，我們學過 Result<T, E> 與 ? 的基礎。現在把它用在真實的 I/O 場景。

run() 的回傳型別是 Result<(), Box<dyn std::error::Error>>。為什麼要用 Box<dyn std::error::Error>？因為 I/O 操作可能拋出 std::io::Error，路徑解析可能拋出 ParseIntError，這些是不同型別的錯誤。用 trait object Box<dyn Error> 可統一裝入任何實作 Error trait 的型別，方便在 CLI 中快速整合多種錯誤源。 

use std::fs;

// 一個讀取整數設定值並翻倍的小例子
fn read_and_double(path: &str) -> Result<i32, Box<dyn std::error::Error>> {
    let content = fs::read_to_string(path)?;    // io::Error 自動轉成 Box<dyn Error>
    let number: i32 = content.trim().parse()?;  // ParseIntError 也自動轉
    Ok(number * 2)
}

公開 API 應使用具名錯誤型別

對公開的函式庫 API，建議定義具名錯誤型別，而非 Box<dyn Error>——這讓呼叫者能夠對不同錯誤做模式比對： 

use std::{fmt, io};

/// my-wc 可能發生的錯誤
#[derive(Debug)]
pub enum WcError {
    Io(io::Error),   // 檔案讀取失敗
    EmptyPath,       // 傳入空路徑
}

impl fmt::Display for WcError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            WcError::Io(e)     => write!(f, "I/O 錯誤: {}", e),
            WcError::EmptyPath => write!(f, "路徑不得為空"),
        }
    }
}

impl std::error::Error for WcError {}

// From<io::Error>：讓 ? 能自動把 io::Error 轉成 WcError::Io(e)
impl From<io::Error> for WcError {
    fn from(e: io::Error) -> Self { WcError::Io(e) }
}

/// 回傳 (行數, 字數, 字元數) 或 WcError
pub fn count_file(path: &str) -> Result<(usize, usize, usize), WcError> {
    if path.is_empty() {
        return Err(WcError::EmptyPath);
    }
    let text = std::fs::read_to_string(path)?;   // io::Error 由 From impl 自動轉
    Ok((
        crate::count_lines(&text),
        crate::count_words(&text),
        crate::count_chars(&text),
    ))
}
💡
小 CLI 用 Box<dyn Error>，函式庫用具名錯誤型別

Box<dyn std::error::Error> 在 main.rs 這類「只管印錯誤訊息」的場景非常方便，用 ? 統一拋出即可。 但函式庫的公開 API 應該定義具名錯誤型別（如 WcError），讓呼叫者能分情況處理—— 「路徑為空」和「檔案不存在」是不同問題，應該能分別應對。

測試：#[test]、整合測試與 cargo test

Rust 的測試系統直接內建於語言與 Cargo 中，不需要額外框架。在第 46 章我們討論過軟體測試的一般概念；這裡聚焦 Rust 特有的實作方式。

單元測試（Unit Tests）

單元測試放在被測模組的同一個檔案裡，用 #[cfg(test)] 標記的 mod tests { } 包起來。#[test] 標記個別測試函式；assert_eq!、assert_ne!、assert! 是最常用的斷言巨集。 

// src/lib.rs（片段）

#[cfg(test)]    // 只在 `cargo test` 時才編譯此模組，不影響正式 build
mod tests {
    use super::*;   // 引入上層模組（lib.rs）的公開與私有項目

    #[test]
    fn empty_string_gives_zero_lines() {
        assert_eq!(count_lines(""), 0);
    }

    #[test]
    #[should_panic]   // 標記「預期這個函式會 panic」；若沒 panic，測試失敗
    fn this_panics() {
        panic!("刻意觸發");
    }

    #[test]
    fn count_words_with_unicode() {
        // 中英文混合，以空白分隔
        let text = "Hello 世界 Rust";
        assert_eq!(count_words(text), 3);   // "Hello"、"世界"、"Rust" = 3 個單詞
    }
}

整合測試（Integration Tests）

整合測試放在專案根目錄的 tests/ 資料夾，每個 .rs 是獨立的 crate，從外部使用你的函式庫，與函式庫的公開契約完全一致。 

// tests/integration_test.rs
// 整個檔案就是測試環境；不需要 mod tests { } 包裝

#[test]
fn integration_stats_consistency() {
    let text = "hello world\nfoo bar\n";

    // 2 行（"hello world" 和 "foo bar"；尾端 \n 不算額外行）
    assert_eq!(my_wc::count_lines(text), 2);

    // 4 個單詞：hello, world, foo, bar
    assert_eq!(my_wc::count_words(text), 4);

    // 20 個字元（h,e,l,l,o,空白,w,o,r,l,d,\n,f,o,o,空白,b,a,r,\n）
    assert_eq!(my_wc::count_chars(text), 20);
}

#[test]
fn integration_empty_input() {
    assert_eq!(my_wc::count_lines(""), 0);
    assert_eq!(my_wc::count_words(""), 0);
    assert_eq!(my_wc::count_chars(""), 0);
}

#[test]
fn integration_unicode_text() {
    let text = "你好\n世界\n";
    assert_eq!(my_wc::count_lines(text), 2);             // 2 行
    assert_eq!(my_wc::count_chars(text), 6);             // 你,好,\n,世,界,\n = 6 個字元
}

✏️ 練習 83.1 實作

為 src/lib.rs 新增一個 count_bytes(text: &str) -> usize 函式，回傳 UTF-8 位元組數（不是字元數）。 再在 src/main.rs 加入 --bytes 旗標：當使用者輸入 my-wc --bytes <file> 時，只印出位元組數。 最後補寫至少一個單元測試，驗證 ASCII 文字的位元組數等於字元數，而中文字元的位元組數大於字元數。

看解答

src/lib.rs — 新增 count_bytes：

/// 計算 UTF-8 位元組數（str::len() 回傳位元組數，非字元數）
pub fn count_bytes(text: &str) -> usize {
    text.len()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_count_bytes() {
        // ASCII 文字：位元組數 == 字元數
        assert_eq!(count_bytes("hello"), 5);
        assert_eq!(count_chars("hello"), 5);

        // 中文字元：UTF-8 每個佔 3 bytes，但 chars().count() 算 1 個字元
        assert_eq!(count_bytes("你好"), 6);   // 2 個字元 × 3 bytes = 6 bytes
        assert_eq!(count_chars("你好"), 2);   // 2 個 Unicode 碼位
    }
}

src/main.rs — 處理 --bytes 旗標：

use my_wc::{count_bytes, count_chars, count_lines, count_words};

fn main() {
    let args: Vec<String> = env::args().collect();

    match args.as_slice() {
        [_, flag, path] if flag == "--bytes" => {
            match fs::read_to_string(path) {
                Ok(text) => println!("{} bytes  {}", count_bytes(&text), path),
                Err(e)   => { eprintln!("錯誤: {}", e); process::exit(1); }
            }
        }
        [_, path] => {
            if let Err(e) = run(path) {
                eprintln!("錯誤: {}", e);
                process::exit(1);
            }
        }
        _ => {
            eprintln!("用法: {} [--bytes] <檔案路徑>", args[0]);
            process::exit(1);
        }
    }
}

核心重點：str::len() 回傳 UTF-8 位元組數，str::chars().count() 回傳 Unicode 碼位數。 對 ASCII 文字兩者相同；對 CJK 字元（各佔 3 bytes），len() 的結果會是 chars().count() 的 3 倍。

✏️ 練習 83.2 實作

目前 count_lines、count_words、count_chars 都直接定義在 src/lib.rs 的 crate root。 請把這三個函式移進一個名為 stats 的子模組（在 lib.rs 裡用 mod stats { ... }）， 並在 crate root 層用 pub use 重新匯出，讓外部的 use my_wc::count_lines 仍然有效。

// src/lib.rs — 重構後

mod stats {
    /// 計算行數
    pub fn count_lines(text: &str) -> usize {
        text.lines().count()
    }

    /// 計算單詞數
    pub fn count_words(text: &str) -> usize {
        text.split_whitespace().count()
    }

    /// 計算 Unicode 字元數
    pub fn count_chars(text: &str) -> usize {
        text.chars().count()
    }
}

// pub use 讓呼叫者直接寫 use my_wc::count_lines，不需要知道內部是 stats 模組
pub use stats::{count_chars, count_lines, count_words};

mod stats { ... } 預設是私有模組；但透過 pub use，它的公開函式可以在 crate root 層被「再匯出」（re-export）。 對使用者而言，use my_wc::count_lines 完全不需要更改——模組的內部組織是實作細節，公開 API 不受影響。 這是 Rust 函式庫常見的封裝模式：內部隨意重組模組，對外只維持穩定的公開路徑。

進一步：最小 HTTP 服務初探

CLI 工具示範了 Rust 處理檔案 I/O 與錯誤的能力；Rust 在服務端（server-side）同樣強大。 得益於 第 82 章的 async/await 與 tokio，Rust 可以用極少的執行緒承載大量並發 HTTP 連線。 這一節簡介用 axum 框架寫一個最小 HTTP 服務，作為「用 Rust 寫 Web 服務」的鋪路。

ℹ️
axum：建立在 tokio 生態上的輕量 Web 框架

axum 是由 tokio 團隊維護的 HTTP 框架，以型別安全、零樣板、與 tokio 生態深度整合著稱。 除了 axum，Rust 生態還有 actix-web（以效能聞名）和 warp。 本節以 axum 0.7 為例；往後用 Rust 撰寫 MCP server 或 gRPC 服務時，都是以相同的 tokio + axum 架構為基礎。

首先在 Cargo.toml 加入依賴： 

[dependencies]
axum  = "0.7"
tokio = { version = "1", features = ["full"] }

最小 HTTP 服務，只需幾十行： 

// src/main.rs（HTTP 服務版本）
use axum::{routing::get, Router};

#[tokio::main]
async fn main() {
    // Router 把 URL 路徑對應到 handler 函式
    let app = Router::new()
        .route("/",       get(root))      // GET /     → root()
        .route("/health", get(health));   // GET /health → health()

    // tokio::net::TcpListener 在 0.0.0.0:3000 監聽
    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000")
        .await
        .unwrap();
    println!("伺服器啟動：http://localhost:3000");

    // axum::serve 開始接受連線（永久阻塞）
    axum::serve(listener, app).await.unwrap();
}

// handler 函式必須是 async，回傳型別自動轉成 HTTP 回應
async fn root() -> &'static str {
    "Hello from Rust!"
}

async fn health() -> &'static str {
    "ok"
}
cargo run
# 伺服器啟動：http://localhost:3000

curl http://localhost:3000/
# Hello from Rust!

curl http://localhost:3000/health
# ok

這幾行背後發生了什麼？#[tokio::main] 宏展開成一個多執行緒 tokio runtime，在所有 CPU 核心上驅動 async Future；每個進來的 HTTP 連線都是一個輕量任務（task），不佔用 OS 執行緒。理論上，這個最小服務在一台普通機器上可以同時處理數萬條並發連線。

💡
回傳 JSON：加入 axum::Json

把回傳型別改成 axum::Json<T>（其中 T: Serialize），axum 會自動序列化成 JSON 並設定正確的 Content-Type header： 

use axum::Json;
use serde::Serialize;

#[derive(Serialize)]
struct Status { ok: bool, version: &'static str }

async fn status() -> Json<Status> {
    Json(Status { ok: true, version: "0.1.0" })
    // 自動回傳 {"ok":true,"version":"0.1.0"}
}

發佈與工程實務：fmt、clippy、publish

寫出能執行的程式只是第一步；讓程式可維護、可協作、可分享，才是工程實務的核心。Cargo 提供了三個重要工具：

cargo fmt — 統一排版風格

cargo fmt          # 依 Rust 官方風格指南自動排版整個專案
cargo fmt --check  # CI 裡用：若有任何未格式化的程式碼，回傳非零 exit code

rustfmt 是 Rust 的官方格式化工具，規則由社群共識固定（縮排 4 空白、最大行寬 100 字元等），開發者不需要再爭「縮排要不要用 Tab」。讓所有 PR 在合入前都跑 cargo fmt --check，是維持程式碼風格一致的最低成本做法。

cargo clippy — 靜態分析與慣用語提示

cargo clippy              # 執行靜態分析，印出改進建議
cargo clippy -- -D warnings  # 把所有 clippy 警告視為錯誤（CI 嚴格模式）

clippy 是 Rust 的靜態分析工具（linter），能抓出常見的非慣用語寫法、效能問題、以及潛在 bug。例如： 

// clippy 會警告這段程式碼，建議改用 is_empty()
if text.len() == 0 {     // ⚠️ clippy: use `is_empty()` instead of comparing to zero
    return 0;
}

// 改成：
if text.is_empty() {     // ✓ 慣用語，清楚且效能等同
    return 0;
}
🔑
CI 三件套：fmt + clippy + test

成熟的 Rust 專案 CI pipeline 通常包含三道關卡： cargo fmt --check（風格）、 cargo clippy -- -D warnings（靜態分析）、 cargo test（功能正確性）。 三道全過，PR 才能合入。這讓每次合入都有最低限度的品質保證。

cargo publish — 發佈到 crates.io

準備好把函式庫分享給全世界？先確認 Cargo.toml 已填入必要欄位： 

[package]
name        = "my-wc"
version     = "0.1.0"
edition     = "2021"
description = "一個簡單的 CLI 文字統計工具"
license     = "MIT"
repository  = "https://github.com/yourname/my-wc"
readme      = "README.md"
cargo login             # 用 crates.io API token 登入（一次性設定）
cargo publish --dry-run # 模擬發佈，不真正上傳（先確認沒問題）
cargo publish           # 正式發佈到 crates.io

發佈後，全球任何人都能在自己的 Cargo.toml 裡加一行 my-wc = "0.1.0" 來使用你的 crate。版本一旦發佈無法刪除（只能 yank，讓它在搜尋中隱藏，但已有的依賴仍能下載），所以請先確認 API 穩定再發佈。

⚠️
發佈前務必確認的事

(1) 不要發佈包含私密金鑰或 token 的 crate——crates.io 是公開的。 (2) 確認 license 欄位填寫正確（常見選擇：MIT、Apache-2.0、MIT OR Apache-2.0）。 (3) cargo publish --dry-run 會列出所有將被打包的檔案，用 .cargo_ignore 或 [package] exclude 排除不必要的檔案。

✏️ 練習 83.3 實作

在 tests/ 目錄下新增一個整合測試，使用 std::fs 與 std::env::temp_dir() 建立一個暫存檔，寫入兩行已知內容，再呼叫 my_wc::count_lines 與 my_wc::count_words 驗證結果。測試結束後清除暫存檔。

看解答 
// tests/file_io_test.rs
use std::fs;
use std::io::Write;

#[test]
fn integration_with_real_file() {
    // 建立暫存檔路徑
    let mut path = std::env::temp_dir();
    path.push("my_wc_test_83.txt");

    // 寫入已知內容
    let mut file = fs::File::create(&path).expect("建立暫存檔失敗");
    writeln!(file, "line one").expect("寫入失敗");   // "line one\n"
    writeln!(file, "line two").expect("寫入失敗");   // "line two\n"
    drop(file);   // 確保 file handle 關閉、資料刷新到磁碟

    // 讀回並驗證
    let text = fs::read_to_string(&path).expect("讀取暫存檔失敗");
    assert_eq!(my_wc::count_lines(&text), 2);   // "line one" 和 "line two" = 2 行
    assert_eq!(my_wc::count_words(&text), 4);   // line, one, line, two = 4 個單詞

    // 清除暫存檔（失敗也無妨；系統重啟會自動清理 temp_dir）
    let _ = fs::remove_file(&path);
}

注意 drop(file)：Rust 的 File 在 drop 時才保證刷新（flush）並關閉。雖然 File 實作了 Drop，這裡顯式呼叫 drop() 是為了確保在讀取前資料已完全寫入磁碟——在同一個程序內連續寫再讀，偶爾會踩到 OS 快取的競態。

把這一章串起來

這一章是 Rust 部（第二十部）的整合實戰。我們從建立一個真實的 Rust 專案出發，走過了工程師每天都會用到的工作流：

  • 模組系統（mod/pub/use）：Rust 預設一切私有，pub 才對外公開。mod 宣告模組，pub use 在適當層級重新匯出——讓使用者看到簡潔的公開 API，內部實作自由重組。
  • Cargo 生態：Cargo.toml 宣告依賴；SemVer 讓 Cargo 能安全地自動升級相容版本；Cargo.lock 保證完全可重現的 build。cargo run/build/test/clean 是日常節奏。
  • lib + bin 分離架構：把邏輯放 src/lib.rs、入口放 src/main.rs，讓測試能直接呼叫函式庫函式，同時保留未來發佈函式庫或加入多個 binary 的彈性。
  • 錯誤處理整合：CLI 用 Box<dyn std::error::Error> + ? 快速整合多種錯誤源；函式庫 API 用具名錯誤型別（enum WcError）讓呼叫者能分情況處理，並用 From impl 讓 ? 自動轉型。
  • 測試：單元測試放在 #[cfg(test)] mod tests { } 裡，可以存取私有項目；整合測試放在 tests/，從外部驗證公開 API。cargo test 一鍵執行全部。
  • 最小 HTTP 服務：axum + tokio 讓 Rust 以少量執行緒處理大量並發連線，是 Rust Web 服務的主流架構。#[tokio::main]、Router::new().route()、axum::serve() 是最小必知三件套。
  • 工程實務：cargo fmt 統一風格、cargo clippy 靜態分析、cargo publish 發佈到 crates.io。CI pipeline 三件套（fmt + clippy + test）是成熟 Rust 專案的標配。
🔑
Rust 的整合哲學：型別系統是你最忠實的協作夥伴

把前五章放在一起看：所有權保證記憶體安全、型別系統保證錯誤被處理、Send/Sync 保證並行安全、trait 保證介面契約——全部在編譯期，全部零執行時開銷。 模組系統和 Cargo 把這些保證延伸到整個生態系：你依賴的每個 crate 也受到同樣嚴格的靜態檢查。 這就是為什麼許多工程師說，一旦 Rust 程式能編譯通過，它的行為往往就是你預期的。
