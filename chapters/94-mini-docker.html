Docker 拿掉品牌後,核心剩下什麼?

⚠️
誠實標示:教學用最小 container runtime

本章實作的 mydocker 是一個教學用最小 container runtime——目的是把 第 87 章的理論對應到真實的系統呼叫,讓每一行程式碼都能對應到一個機制。 它不處理映像格式(OCI image spec)、registry 拉取、網路 CNI 外掛、安全強化(seccomp profile / capabilities 收縮)、 rootless 模式或任何生產級功能。需要 root 或 CAP_SYS_ADMIN 才能執行。 本章使用 C 語言呈現系統呼叫語義(系統呼叫全部從 C 直接呼叫); 在適當處會標注「也可用 Rust 重寫,呼應第 84 章的 bare-metal 精神」。

在第 87 章，我們拆解了 docker run 背後的四層機制: namespace 隔離視圖、cgroup 資源上限、OverlayFS 聯合掛載、capabilities + seccomp 最小權限。 你現在知道 Docker 的本質是什麼——但「知道」和「親手拼出來」是兩回事。

這一章做的事情就一件:把那四層機制用 C 語言的系統呼叫親手連起來, 做出一個能執行 mydocker run /path/to/rootfs /bin/sh 的最小 container runtime。 大約 200 行 C 程式碼。不依賴任何容器函式庫。每一行都有對應的機制說明。

歷史上第一個做這件事(並公開講解)的人是 Liz Rice——她在 2016 年 DockerCon 的演講 「Containers from Scratch」裡用 Go 語言現場直播寫了一個迷你 runtime。 我們的版本改用 C,因為 C 的系統呼叫語義更直接(Go 的 syscall 套件 做了一層包裝),而且與本書整體語言選擇一致。

🔑
核心等式

一個最小 container runtime = clone()(開 namespace) + pivot_root()(換根) + mount()(掛 /proc) + cgroup v2(寫 /sys/fs/cgroup) + execvp()(執行指令)。 這五個步驟,就是 Docker 的骨架。

目標與全局架構:mydocker run 要做什麼

我們的目標指令介面是: 

sudo ./mydocker /path/to/rootfs /bin/sh
# 在隔離環境裡進入 /bin/sh

執行後,使用者拿到一個 shell。在這個 shell 裡:

  • echo $$ 輸出 1——它是新 PID namespace 的 PID 1
  • hostname 輸出 mycontainer——獨立的 UTS namespace
  • ps aux 只看到容器內的行程——mount namespace + /proc 隔離
  • ls / 看到的是 rootfs 的根目錄,而不是主機的 /——pivot_root 換根

要達到這個效果,mydocker 需要完成以下六個步驟,如下圖所示:

在動手寫程式之前,先準備一個 rootfs。最簡單的方法是用 debootstrap 從頭建立一個最小 Ubuntu 環境: 

# 安裝 debootstrap(若尚未安裝)
sudo apt install debootstrap

# 建立最小 Ubuntu 22.04 rootfs(約 300MB)
sudo debootstrap --arch=amd64 jammy /tmp/myrootfs

# 確認結構
ls /tmp/myrootfs   # bin  etc  lib  proc  tmp  usr  var ...

有了 rootfs,我們就可以開始一步一步拼這個 runtime。

第一步:用 clone() 同時開啟四個 namespace

在第 87 章我們看到 clone() 如何接受一組 CLONE_NEW* 旗標,一次建立多個新 namespace。現在把它放進 main(): 

#define _GNU_SOURCE
#include <sched.h>      /* CLONE_NEWPID, CLONE_NEWNS, CLONE_NEWUTS, CLONE_NEWIPC */
#include <stdlib.h>     /* malloc, free */
#include <sys/wait.h>   /* waitpid */
#include <stdio.h>      /* perror */

#define STACK_SIZE (8 * 1024 * 1024)   /* 子行程堆疊 8 MB */

/* 容器設定:rootfs 路徑 + 要執行的指令 */
struct cfg {
    char  *rootfs;   /* 容器根目錄 */
    char **argv;     /* 指令與參數 */
};

/* 子行程函式(見下一節) */
static int container_fn(void *arg);

int main(int argc, char *argv[]) {
    if (argc < 3) {
        fprintf(stderr, "用法: mydocker <rootfs> <cmd> [args...]\n");
        return 1;
    }

    /* 把 rootfs 路徑與指令打包成 cfg */
    struct cfg cfg = { .rootfs = argv[1], .argv = &argv[2] };

    /* 分配子行程堆疊 */
    char *stack = malloc(STACK_SIZE);
    if (!stack) { perror("malloc"); return 1; }

    /* ── clone():一次建立四個新 namespace ── */
    pid_t pid = clone(
        container_fn,            /* 子行程從此函式開始執行           */
        stack + STACK_SIZE,      /* 堆疊頂端(x86 堆疊向下成長)       */
        CLONE_NEWPID |           /* 新 PID ns:容器 PID 從 1 開始     */
        CLONE_NEWNS  |           /* 新 mount ns:獨立掛載點視圖        */
        CLONE_NEWUTS |           /* 新 UTS ns:可設定獨立 hostname     */
        CLONE_NEWIPC |           /* 新 IPC ns:隔離 SHM / MQ           */
        SIGCHLD,                 /* 子行程退出時父行程收到 SIGCHLD     */
        &cfg);

    if (pid < 0) { perror("clone"); free(stack); return 1; }

    /* 父行程:設定 cgroup,然後等容器結束 */
    setup_cgroup(pid, 256L * 1024 * 1024);   /* 256 MB 記憶體上限 */
    waitpid(pid, NULL, 0);
    free(stack);
    return 0;
}
🔑
clone() 的旗標語義

CLONE_NEWPID:子行程在新 PID namespace 內是 PID 1。 從主機看到的真實 PID 仍是一個正常數字,但容器內看到的是 1。
CLONE_NEWNS:「NS」是最早的 namespace 旗標(2002 年,當時只有一種 namespace), 現在代表 mount namespace——容器有自己的掛載點視圖。
CLONE_NEWUTS:UTS(Unix Timesharing System)namespace, 讓容器可用 sethostname() 設定獨立的主機名稱。
CLONE_NEWIPC:隔離 System V 共享記憶體(SHM)與訊息佇列(MQ)。

ℹ️
為何不加 CLONE_NEWNET?

加入 CLONE_NEWNET 會讓容器進入一個全空的 net namespace—— 只有一個無法通訊的 loopback 介面。要讓容器有網路, 需要在主機上建立 veth pair 並連上 bridge。 這部分留到第八節「最簡網路」說明。本節先跳過 CLONE_NEWNET, 讓容器暫時與主機共用 net namespace——足夠示範其他機制。

第二步:pivot_root — 比 chroot 更安全的換根

在第 87 章我們看到 chroot 的限制:它只改變了「根目錄的視圖」, 但一個擁有 root 權限的行程可以透過巢狀 chroot 或存取 /proc 逃逸。 pivot_root(2) 系統呼叫是更徹底的解決方案——它真正地把 整個掛載樹的根換掉,配合卸載舊根,讓容器完全看不到主機的原始檔案系統。

pivot_root 的正確操作步驟如下:

  1. 把 new_root bind-mount 到自身(mount --bind new_root new_root)—— 這是必要條件,因為 pivot_root 要求目標必須是一個掛載點。
  2. 在 new_root 內建立一個暫存目錄 .pivot_old,作為舊根的「停車場」。
  3. 呼叫 pivot_root(new_root, new_root/.pivot_old)—— 核心把 new_root 提升為 /,舊的 / 掛進 /.pivot_old。
  4. chdir("/") 更新當前工作目錄到新根。
  5. umount2("/.pivot_old", MNT_DETACH) 懶卸載舊根——容器從此看不到主機的原始 /。
  6. rmdir("/.pivot_old") 移除暫存目錄。
#define _GNU_SOURCE
#include <unistd.h>      /* chdir, rmdir */
#include <sys/mount.h>   /* mount, umount2, MS_BIND, MS_REC, MNT_DETACH */
#include <sys/stat.h>    /* mkdir */
#include <sys/syscall.h> /* SYS_pivot_root */
#include <stdio.h>       /* perror, snprintf */
#include <string.h>      /* snprintf */

static int do_pivot_root(const char *new_root)
{
    /* ① bind-mount new_root 到自身:讓它成為掛載點 */
    if (mount(new_root, new_root, NULL, MS_BIND | MS_REC, NULL) < 0) {
        perror("bind-mount rootfs");
        return -1;
    }

    /* ② 在 new_root 內建立舊根的暫存目錄 */
    char old[512];
    snprintf(old, sizeof(old), "%s/.pivot_old", new_root);
    mkdir(old, 0700);   /* 若已存在也無妨 */

    /* ③ pivot_root:glibc 無封裝,直接用 syscall()
     *    SYS_pivot_root 在 x86-64 上是 syscall 155        */
    if (syscall(SYS_pivot_root, new_root, old) < 0) {
        perror("pivot_root");
        return -1;
    }

    /* ④ 更新 CWD 到新根 */
    chdir("/");

    /* ⑤ 懶卸載舊根(MNT_DETACH:等待無行程使用後完成) */
    if (umount2("/.pivot_old", MNT_DETACH) < 0) {
        perror("umount2 .pivot_old");
        return -1;
    }

    /* ⑥ 清理暫存目錄 */
    rmdir("/.pivot_old");
    return 0;
}
⚠️
為何是 MNT_DETACH 而不是 MNT_FORCE?

MNT_DETACH(懶卸載)立刻把掛載點從掛載樹分離,讓新行程無法存取—— 但對於已開啟檔案的現有行程,卸載動作會等到它們關閉後才真正完成。 MNT_FORCE 是強制卸載,可能中斷 NFS 等網路掛載的 I/O。 對 pivot_old 舊根使用 MNT_DETACH 是標準做法: 容器初始化時不會有任何行程在使用舊根,卸載實際上立即完成。

🔑
pivot_root vs chroot 的根本差異

chroot 只改變了行程的「根目錄視圖」(fs->root), 但行程仍然在同一個 mount namespace 裡——所以擁有 root 的行程可以用巢狀 chroot 逃逸。 pivot_root 配合 mount namespace(CLONE_NEWNS)和 umount2 舊根, 才是真正的隔離:容器行程活在一個全新的掛載樹裡,主機的原始 / 已被卸載, 根本不存在於這個 mount namespace 的任何位置。

第三步:掛載 /proc 與設定容器 hostname

換根之後,容器的 / 已經是 rootfs 的根目錄。 但如果現在在容器裡執行 ps aux,會看到奇怪的結果—— 因為 /proc 還沒有掛載。 ps、top、/proc/self/ 等都依賴 /proc 偽檔案系統。

同時,我們在 CLONE_NEWUTS namespace 裡,可以呼叫 sethostname() 設定容器自己的主機名稱, 讓 hostname 指令在容器內顯示正確的值。 

/* 在 container_fn 裡,do_pivot_root 成功後接著做: */

/* ① 設定容器 hostname(在 UTS namespace 內,不影響主機) */
sethostname("mycontainer", 11);

/* ② 掛載 /proc 偽檔案系統
 *    source : "proc"  (proc 掛載的「裝置名稱」,只是慣例字串)
 *    target : "/proc" (rootfs 裡必須有這個目錄)
 *    type   : "proc"  (檔案系統類型)
 *    flags  : 0       (無特殊旗標)
 *    data   : NULL    (無額外掛載選項)
 */
if (mount("proc", "/proc", "proc", 0, NULL) < 0) {
    perror("mount /proc");
    /* 非致命:容器仍可執行,只是 ps 會看到舊 /proc */
}

sethostname() 必須在 CLONE_NEWUTS namespace 裡才有意義—— 在新的 UTS namespace 裡呼叫它只影響容器自己的 hostname,主機的 hostname 完全不受影響。 如果不在 UTS namespace 裡(例如沒有 CLONE_NEWUTS), 呼叫 sethostname() 就真的會改掉主機的 hostname。 

# 驗證:進入容器後
hostname          # 輸出: mycontainer
echo $$           # 輸出: 1  (新 PID namespace 的 PID 1)
ps aux            # 只看到容器內的行程(因為 /proc 是新掛載的)
cat /proc/1/comm  # 輸出: sh (容器內 PID 1 的指令名稱)

第四步:cgroup v2 限制記憶體與行程數

Namespace 解決了「看到什麼」的問題; cgroup v2 解決的是「能用多少」的問題。 在父行程呼叫 clone() 得到子行程的 PID 之後、在子行程執行 execvp() 之前,父行程有一個視窗可以設定 cgroup—— 把子行程的 PID 寫入 cgroup 的 cgroup.procs 介面。 

#include <sys/stat.h>  /* mkdir */
#include <stdio.h>     /* fopen, fprintf, fclose */

static void setup_cgroup(pid_t pid, long mem_max)
{
    const char *cg = "/sys/fs/cgroup/mydocker";
    char p[256];
    FILE *f;

    /* ① 建立 cgroup 子目錄 */
    mkdir(cg, 0755);

    /* ② 在父 cgroup 啟用子控制器
     *    只有父 cgroup 的 cgroup.subtree_control 允許的控制器
     *    才能在子目錄中使用                                    */
    f = fopen("/sys/fs/cgroup/cgroup.subtree_control", "w");
    if (f) { fprintf(f, "+memory +pids"); fclose(f); }

    /* ③ 設定記憶體上限(memory.max)
     *    超過此值 → OOM killer 在 cgroup 範圍內 SIGKILL 行程  */
    snprintf(p, sizeof(p), "%s/memory.max", cg);
    f = fopen(p, "w");
    if (f) { fprintf(f, "%ld", mem_max); fclose(f); }

    /* ④ 設定最大行程數(pids.max),防止 fork bomb */
    snprintf(p, sizeof(p), "%s/pids.max", cg);
    f = fopen(p, "w");
    if (f) { fprintf(f, "64"); fclose(f); }

    /* ⑤ 把容器行程加入 cgroup(寫入 PID)
     *    之後容器的所有子行程也會自動繼承此 cgroup             */
    snprintf(p, sizeof(p), "%s/cgroup.procs", cg);
    f = fopen(p, "w");
    if (f) { fprintf(f, "%d", (int)pid); fclose(f); }
}

以下是等效的 bash 示範,方便驗證 cgroup 行為: 

# ── cgroup v2 操作示範(需要 root) ──

# 建立 cgroup
mkdir /sys/fs/cgroup/mydocker

# 啟用記憶體與 PID 控制器
echo "+memory +pids" > /sys/fs/cgroup/cgroup.subtree_control

# 記憶體上限:256 MB = 268435456 bytes
echo 268435456 > /sys/fs/cgroup/mydocker/memory.max

# PID 上限:最多 64 個行程
echo 64 > /sys/fs/cgroup/mydocker/pids.max

# 把當前 shell 加入 cgroup(用 $$ 取得目前 PID)
echo $$ > /sys/fs/cgroup/mydocker/cgroup.procs

# 驗證:查看目前記憶體用量
cat /sys/fs/cgroup/mydocker/memory.current

# 確認行程已加入
cat /proc/$$/cgroup
⚠️
父 cgroup 的 subtree_control 必須先啟用

cgroup v2 採用「委派」模型:子 cgroup(/sys/fs/cgroup/mydocker/)能使用的控制器, 必須先在父 cgroup(/sys/fs/cgroup/)的 cgroup.subtree_control 中明確開啟。 若父 cgroup 沒有 +memory,在子目錄寫 memory.max 會回傳 ENOENT 或寫入無效。 另:若系統上 systemd 已獨佔使用 cgroup v2 的某些控制器, 可能需要先調整 systemd 設定(或在容器 / VM 環境中測試)。

ℹ️
加入 CPU 配額

要加上 CPU 配額限制,先在 subtree_control 啟用 +cpu, 然後寫 cpu.max:格式是 $MAX $PERIOD(微秒)。 例如 echo "50000 100000" > cpu.max 表示每 100ms 最多用 50ms, 相當於 50% 一顆 CPU。練習 88.1 會帶你實驗這個配額。

第五步:OverlayFS — 疊一個可寫層

目前我們的 mydocker 讓容器直接在 rootfs 上讀寫——容器任何寫入動作 都會修改原始的 rootfs 目錄。要做到「多個容器共用同一個唯讀 rootfs,每個容器有自己的可寫層」, 就需要 OverlayFS。

在第 87 章我們已詳細解釋 OverlayFS 的原理(lowerdir/upperdir/workdir/merged)。 這裡直接看如何在 mydocker 使用前設定 OverlayFS 掛載: 

#!/bin/bash
# setup-overlay.sh — 為 mydocker 建立 OverlayFS 可寫層
# 用法: source setup-overlay.sh /path/to/rootfs
# 執行後 $MERGED 指向容器看到的根目錄

ROOTFS="${1:-/tmp/myrootfs}"    # 唯讀 rootfs(lowerdir)
WORKDIR="/tmp/mydocker"

UPPER="$WORKDIR/upper"          # 容器可寫層
WORK="$WORKDIR/work"            # OverlayFS 核心暫存(必須與 upper 同一檔案系統)
MERGED="$WORKDIR/merged"        # 容器看到的統一視圖

# 建立目錄
mkdir -p "$UPPER" "$WORK" "$MERGED"

# 掛載 OverlayFS
sudo mount -t overlay overlay \
    -o lowerdir="$ROOTFS",upperdir="$UPPER",workdir="$WORK" \
    "$MERGED"

echo "OverlayFS 已掛載:"
echo "  lowerdir(唯讀): $ROOTFS"
echo "  upperdir(可寫): $UPPER"
echo "  merged(容器的 /): $MERGED"

# 現在把 $MERGED 傳給 mydocker
sudo ./mydocker "$MERGED" /bin/sh

卸載 OverlayFS 時: 

# 容器退出後卸載
sudo umount /tmp/mydocker/merged

# 查看容器在 upper 層做了哪些修改
ls -la /tmp/mydocker/upper/   # 容器建立或修改的檔案都在這裡

第六步(進階):最簡網路 — veth pair 連到主機 bridge

ℹ️
本節為進階選讀

這一節要在 main() 裡加入 CLONE_NEWNET,並在容器外建立 veth pair 連到 bridge。 概念層次偏複雜,初次閱讀可跳過,先看第九節的完整程式。 生產環境的容器網路由 CNI(Container Network Interface)外掛負責, Docker 用的是 bridge 模式的 CNI 實作。

要讓容器有自己的網路介面,需要在 clone() 加入 CLONE_NEWNET, 然後在容器外建立一個 veth pair(虛擬乙太網路對)—— 想像成一條兩端都有插頭的虛擬網路線:一端留在主機,另一端插進容器的 net namespace。 

#!/bin/bash
# net-setup.sh — 為 mydocker 容器設定最簡網路
# 用法: bash net-setup.sh $CONTAINER_PID
CONTAINER_PID=$1

# ① 建立 veth pair: veth0(主機端) - ctr-eth0(容器端)
ip link add veth0 type veth peer name ctr-eth0

# ② 把 ctr-eth0 移入容器的 net namespace
ip link set ctr-eth0 netns $CONTAINER_PID

# ③ 主機側:建立 bridge br0 並掛上 veth0
ip link add br0 type bridge
ip link set veth0 master br0
ip link set veth0 up
ip link set br0 up
ip addr add 172.20.0.1/24 dev br0

# ④ 容器側:透過 nsenter 進入容器 net namespace 設定
nsenter -t $CONTAINER_PID -n -- ip addr add 172.20.0.2/24 dev ctr-eth0
nsenter -t $CONTAINER_PID -n -- ip link set ctr-eth0 up
nsenter -t $CONTAINER_PID -n -- ip link set lo up
nsenter -t $CONTAINER_PID -n -- ip route add default via 172.20.0.1

echo "容器網路已設定: 172.20.0.2 <-- veth --> bridge 172.20.0.1"

主機要開啟 IP forwarding 並設定 NAT,容器才能存取外部網路: 

# 開啟 IP forwarding
echo 1 > /proc/sys/net/ipv4/ip_forward

# NAT:讓容器流量從主機網卡出去(eth0 替換為實際介面名稱)
iptables -t nat -A POSTROUTING -s 172.20.0.0/24 -o eth0 -j MASQUERADE
⚠️
時序問題:先建立容器再設定網路

veth pair 移入容器 net namespace 必須在容器行程存在之後(clone 之後)、 但在容器使用網路之前。實際做法:在 clone() 後、setup_cgroup() 之後, fork 一個子行程執行 net-setup.sh $pid, 然後再 waitpid 等容器結束。 Docker 用 containerd 的 goroutine 協調這個時序;我們的 runtime 用 shell script 示意。

串在一起:完整的 mydocker 主程式

把前面各節的片段整合成一個完整的 C 程式。這就是我們的最小 container runtime: 

/* mydocker.c — 教學用最小 container runtime
 * 需要 root / CAP_SYS_ADMIN。非生產級,僅供學習。
 * 編譯: gcc -o mydocker mydocker.c
 * 執行: sudo ./mydocker /path/to/rootfs /bin/sh
 */
#define _GNU_SOURCE
#include <sched.h>       /* CLONE_NEWPID, CLONE_NEWNS, CLONE_NEWUTS, CLONE_NEWIPC */
#include <stdio.h>       /* printf, fprintf, perror, fopen, fclose */
#include <stdlib.h>      /* malloc, free */
#include <unistd.h>      /* sethostname, chdir, rmdir, execvp */
#include <sys/mount.h>   /* mount, umount2, MS_BIND, MS_REC, MNT_DETACH */
#include <sys/stat.h>    /* mkdir */
#include <sys/syscall.h> /* SYS_pivot_root */
#include <sys/wait.h>    /* waitpid */

#define STACK_SIZE (8 * 1024 * 1024)   /* 子行程堆疊 8 MB */

/* ── 容器設定 ───────────────────────────────────── */
struct cfg {
    char  *rootfs;   /* 容器根目錄路徑 */
    char **argv;     /* 要 exec 的指令與參數 */
};

/* ── ① pivot_root:換根並卸載舊根 ─────────────────── */
static int do_pivot_root(const char *new_root)
{
    char old[512];
    snprintf(old, sizeof(old), "%s/.pivot_old", new_root);

    /* bind-mount new_root 到自身,使其成為掛載點 */
    if (mount(new_root, new_root, NULL, MS_BIND | MS_REC, NULL) < 0) {
        perror("bind-mount rootfs"); return -1;
    }
    mkdir(old, 0700);   /* 建立舊根的停車場目錄 */

    /* pivot_root:glibc 未提供 wrapper,直接呼叫 syscall */
    if (syscall(SYS_pivot_root, new_root, old) < 0) {
        perror("pivot_root"); return -1;
    }
    chdir("/");   /* 更新 CWD 到新根目錄 */

    /* 懶卸載舊根:容器從此看不到主機的原始 / */
    if (umount2("/.pivot_old", MNT_DETACH) < 0) {
        perror("umount2 .pivot_old"); return -1;
    }
    rmdir("/.pivot_old");
    return 0;
}

/* ── ② cgroup v2:限制資源 ────────────────────────── */
static void setup_cgroup(pid_t pid, long mem_max)
{
    const char *cg = "/sys/fs/cgroup/mydocker";
    char p[256]; FILE *f;

    mkdir(cg, 0755);

    /* 在父 cgroup 啟用子控制器 */
    f = fopen("/sys/fs/cgroup/cgroup.subtree_control", "w");
    if (f) { fprintf(f, "+memory +pids"); fclose(f); }

    /* 記憶體上限 */
    snprintf(p, sizeof(p), "%s/memory.max", cg);
    f = fopen(p, "w");
    if (f) { fprintf(f, "%ld", mem_max); fclose(f); }

    /* PID 上限(防止 fork bomb) */
    snprintf(p, sizeof(p), "%s/pids.max", cg);
    f = fopen(p, "w");
    if (f) { fprintf(f, "64"); fclose(f); }

    /* 把容器行程加入 cgroup */
    snprintf(p, sizeof(p), "%s/cgroup.procs", cg);
    f = fopen(p, "w");
    if (f) { fprintf(f, "%d", (int)pid); fclose(f); }
}

/* ── ③ 子行程:在新 namespace 內執行 ─────────────── */
static int container_fn(void *arg)
{
    struct cfg *c = (struct cfg *)arg;

    /* 設定容器 hostname(在 UTS namespace 內,不影響主機) */
    sethostname("mycontainer", 11);

    /* 換根:pivot_root 到指定 rootfs */
    if (do_pivot_root(c->rootfs) < 0) return 1;

    /* 掛載 /proc:讓 ps、top、/proc/self 正常運作 */
    if (mount("proc", "/proc", "proc", 0, NULL) < 0)
        perror("mount /proc");   /* 非致命,繼續執行 */

    /* exec 容器指令:替換子行程映像 */
    execvp(c->argv[0], c->argv);
    perror("execvp");   /* 只有 exec 失敗才執行到此 */
    return 1;
}

/* ── ④ 主程式:父行程 ──────────────────────────── */
int main(int argc, char *argv[])
{
    if (argc < 3) {
        fprintf(stderr,
            "用法: mydocker <rootfs> <cmd> [args...]\n"
            "範例: sudo ./mydocker /tmp/myrootfs /bin/sh\n");
        return 1;
    }

    struct cfg cfg = {
        .rootfs = argv[1],
        .argv   = &argv[2],
    };

    /* 分配子行程的堆疊空間 */
    char *stack = malloc(STACK_SIZE);
    if (!stack) { perror("malloc"); return 1; }

    /* clone():一次建立四個 namespace 並 fork 子行程 */
    pid_t pid = clone(
        container_fn,
        stack + STACK_SIZE,      /* 堆疊頂端,向下成長 */
        CLONE_NEWPID |           /* 新 PID namespace   */
        CLONE_NEWNS  |           /* 新 mount namespace */
        CLONE_NEWUTS |           /* 新 UTS namespace   */
        CLONE_NEWIPC |           /* 新 IPC namespace   */
        SIGCHLD,                 /* 子行程結束發 SIGCHLD */
        &cfg);

    if (pid < 0) { perror("clone"); free(stack); return 1; }

    /* 父行程:在子行程 exec 之前設定 cgroup */
    setup_cgroup(pid, 256L * 1024 * 1024);   /* 256 MB 記憶體上限 */

    /* 等待容器行程結束 */
    waitpid(pid, NULL, 0);
    free(stack);
    return 0;
}
/* ═══════════════════════════════════════════════════
 * 編譯與執行:
 *   gcc -o mydocker mydocker.c
 *   sudo ./mydocker /tmp/myrootfs /bin/sh
 *
 * 在容器內驗證:
 *   echo $$        # 應輸出 1
 *   hostname       # 應輸出 mycontainer
 *   ps aux         # 只看到容器內的行程
 *   ls /           # 看到 rootfs 的根目錄
 * ═══════════════════════════════════════════════════ */
💡
也可以用 Rust 重寫

上述 C 程式的每一個系統呼叫,在 Rust 裡都有對應的 libc crate 繫結(或 nix crate 的安全包裝)。 呼應第 84 章的 bare-metal 精神: libc::clone()、nix::mount::mount()、nix::unistd::sethostname()—— Rust 的 borrow checker 甚至能幫你在編譯期抓出部分未初始化堆疊的問題。 唯一需要 unsafe 的地方是 clone() 的函式指標和堆疊指標操作, 其餘都可以包在安全的 Rust API 裡。

✏️ 練習 88.1 實作

在 setup_cgroup() 函式中加入 CPU 配額限制: 每 100ms 最多使用 50ms(相當於 50% 一顆 CPU)。 然後在容器內執行 stress --cpu 1 --timeout 10(需安裝 stress 套件), 同時在主機上用 top 觀察該行程的 CPU 使用率是否被限制在 50% 以下。 提示:需要先在 cgroup.subtree_control 啟用 +cpu。

看解答

在 setup_cgroup() 中,先把 subtree_control 改為同時啟用三個控制器, 然後寫入 cpu.max:

/* 1. 啟用 memory + cpu + pids 三個控制器 */
f = fopen("/sys/fs/cgroup/cgroup.subtree_control", "w");
if (f) { fprintf(f, "+memory +cpu +pids"); fclose(f); }

/* 2. CPU 配額:每 100ms 最多用 50ms = 50% 一顆 CPU */
snprintf(p, sizeof(p), "%s/cpu.max", cg);
f = fopen(p, "w");
if (f) { fprintf(f, "50000 100000"); fclose(f); }

等效的 bash 指令:

echo "+memory +cpu +pids" > /sys/fs/cgroup/cgroup.subtree_control
echo "50000 100000" > /sys/fs/cgroup/mydocker/cpu.max

cpu.max 格式是 $MAX $PERIOD(單位微秒)。 50000 100000 = 每個 100ms 週期最多使用 50ms CPU 時間。 在主機上執行 top 時,容器內的 stress 行程的 %CPU 應穩定在 50% 左右, 即使主機有空閒 CPU 也不會更高。

✏️ 練習 88.2 實作

執行 mydocker 進入容器後,分別在容器內和主機上執行以下指令並記錄結果:

# 容器內
echo $$      # 容器認為自己的 PID 是?
ps aux       # 看到幾個行程?

# 主機上(另開一個終端)
ps aux | grep sh          # 看到容器的 sh 行程了嗎?它的 PID 是多少?
ls /proc/$(pgrep -n sh)/ns/pid   # 容器的 PID namespace inode 是多少?
ls /proc/$$/ns/pid               # 主機 shell 的 PID namespace inode 是多少?

解釋:為什麼容器內看到的 PID 是 1,但從主機上看到的是一個不同的 PID? 這說明了 PID namespace 的什麼特性?

看解答

容器內: echo $$ 輸出 1。ps aux 只看到 2–3 個行程(sh + ps 本身)。 這是因為 CLONE_NEWPID 建立了一個新的 PID namespace, container_fn 是新 namespace 的第一個行程,所以被分配到 PID 1。 /proc 是在新 mount namespace 裡重新掛載的, 只反映新 PID namespace 裡的行程,因此 ps 看不到主機上的其他行程。

主機上: ps aux 能看到容器的 sh 行程,但 PID 是一個比 1 大的正常數字 (例如 3847)——這是它在主機 PID namespace 裡的「真實 PID」。 PID namespace 的核心特性:每個行程在每個可見的 PID namespace裡都有一個 PID。 容器 sh 在自己的 namespace 裡是 PID 1,但在主機的 namespace 裡是 3847。 這兩個數字同時存在——只是視角不同。

namespace inode: ls /proc/.../ns/pid 會顯示像 pid:[4026532132] 的符號連結。 容器 sh 的 PID namespace inode 與主機 shell 的不同,證明它們確實在不同的 PID namespace 裡。

✏️ 練習 88.3 思考

我們在第四節說明了為什麼 pivot_root 比 chroot 更安全。 現在請具體回答:

  1. 一個在 chroot 環境裡擁有 root 權限的行程, 可以透過什麼方式「逃逸」回到主機的根目錄?
  2. 在 pivot_root 之後執行 umount2("/.pivot_old", MNT_DETACH) 是整個安全鏈的哪個環節?如果省略這一步,容器是否真的隔離了?
  3. 就算 pivot_root + umount 做好了,為什麼我們還需要 CLONE_NEWNS? 如果沒有 CLONE_NEWNS,pivot_root 還能執行嗎?
看解答

1. chroot 逃逸的方法: 一個擁有 root 的行程可以在 chroot 環境裡用 mkdir + chroot 建立一個巢狀的 chroot 環境,然後多次向上 cd .. 回到真實的 /。 也可以用 open("/proc/1/root")(若 /proc 仍可存取)直接存取主機根目錄。 根本原因是 chroot 只改變了行程的根目錄視圖, 行程仍在同一個 mount namespace 裡,仍然可以透過各種方式存取主機的掛載點。

2. umount2 的安全意義: pivot_root 之後,舊根仍然可從 /.pivot_old 存取—— 這個時候容器其實還能看到主機的整個檔案系統! umount2("/.pivot_old", MNT_DETACH) 才是真正把舊根從容器的 mount namespace 裡「消失」的那一步。 如果省略這步,攻擊者在容器內找到 /.pivot_old 就可以讀寫主機的所有檔案—— 隔離完全失效。umount2 + rmdir 是安全鏈不可省略的最後一步。

3. CLONE_NEWNS 的必要性: pivot_root 要求呼叫行程必須在一個獨立的 mount namespace 裡—— 在 Linux 手冊頁(man 2 pivot_root)中明確規定: 「The calling process must have the CAP_SYS_ADMIN capability, and new root and put old must not be on the same filesystem as the current root.」 實際上,若沒有 CLONE_NEWNS,pivot_root 在主機共用的 mount namespace 裡 會影響整個系統的根目錄——這非常危險。 CLONE_NEWNS 讓 pivot_root 的效果侷限在容器自己的 mount namespace 裡, 主機的根目錄完全不受影響。沒有 CLONE_NEWNS,pivot_root 實際上無法安全執行。

把這一章串起來

從一個空白的 C 檔開始,我們一步一步拼出了一個能跑命令的 container runtime。 回顧一下每個機制對應的程式碼:

步驟機制程式碼作用
① namespace 隔離 clone(CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC | SIGCHLD, ...) 一次建立四個隔離視圖
② 換根 mount(bind) → syscall(SYS_pivot_root) → umount2(MNT_DETACH) 容器看不到主機的原始 /
③ /proc 掛載 mount("proc", "/proc", "proc", 0, NULL) ps / top / /proc/self 正常運作
④ hostname sethostname("mycontainer", 11) 容器有獨立的主機名稱
⑤ 資源限制 /sys/fs/cgroup/mydocker/memory.max 等 防止容器耗光主機資源
⑥ 可寫層 mount -t overlay ... merged 容器寫入不污染唯讀 rootfs

這 ~200 行程式碼就是「Docker 的骨架」。但它還缺少很多東西—— 而且這些缺少的部分正是 Docker 複雜度的所在:

  • 映像格式與 registry:OCI image spec 定義了映像的 JSON manifest、layer tarball 格式與 digest 校驗。 Docker Hub 的 registry API 讓 docker pull 能下載、快取、驗證映像。我們的 runtime 需要你自己準備 rootfs。
  • seccomp 與 capabilities 收縮:我們的 runtime 讓容器繼承了父行程的全部 capabilities。 生產級 runtime(runc)套用一個預設 seccomp profile,並把 capabilities 收縮到最小集合—— 這是第 34 章最小權限原則的直接體現。
  • rootless 模式:加入 CLONE_NEWUSER 並設定 uid_map / gid_map, 讓容器在不需要 Host root 的情況下模擬 root——我們的 runtime 需要 sudo。
  • 網路 CNI 外掛:正式的容器網路由 CNI spec 規範, 每個 plugin(bridge、macvlan、host-local IPAM)負責不同面向的網路設定。 我們只展示了最基本的 veth pair + bridge 手動設定。
  • OCI runtime spec / runc:標準化的 config.json 讓 containerd、Podman、cri-o 都能呼叫同一個 runtime binary——interoperability 的基礎。

下一章(Docker 實戰:映像、網路、Compose)將站在這一章的骨架上, 補全映像生命週期、網路驅動和 Compose 多服務編排。 而 MCP 沙箱(後面的章節)會把容器技術用於大型語言模型工具執行的安全隔離—— 也就是說,你在這裡親手拼出的這幾個系統呼叫,未來會在 AI 工具鏈的安全邊界裡繼續發揮作用。

⚠️
教學 runtime 不等於生產安全邊界

本章的 mydocker 缺少:seccomp syscall 過濾、capabilities 收縮、 user namespace(rootless)、AppArmor / SELinux LSM profile、 映像 digest 校驗、網路策略等。 在第 34 章我們看過縱深防禦的原則—— 容器的安全是這些機制的疊加,缺少任何一層都意味著更大的攻擊面。 在生產環境中,請使用 Docker / Podman / containerd 等經過嚴格稽核的 runtime, 而不是本章的教學版本。
