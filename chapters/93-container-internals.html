容器的真相:namespaces、cgroups 與 OverlayFS

一個「docker run」背後,Linux 核心悄悄拉起了六道門、掛上一把資源鎖、疊起了幾層透明薄膜——你以為你在用魔法,其實全是精密的工程。

docker run 之後,核心到底做了什麼?

你打了一行指令:docker run --rm -it ubuntu bash。不到一秒, 一個 Ubuntu 的 Bash 提示符出現了。你執行 echo $$,看到 PID 是 1—— 彷彿這個 Bash 是整台機器的第一個行程。 你執行 hostname,得到的不是你主機的名稱,而是一串隨機 hash。 你執行 ls /,看到一個乾淨的 Ubuntu 根目錄,而不是你的 Host 根目錄。

這一切都是同一個 Linux 核心製造的幻象。容器不是虛擬機(VM): 它沒有自己的 Guest OS、沒有 Hypervisor、沒有虛擬硬體。 它是一組普通的 Linux 行程,只是被精心地包裝進一個「隔離的視圖」裡。 在第 85 章我們看過虛擬化的全景光譜—— 現在是拆開容器這個魔術箱的時候了。

Docker(或更底層的 runc、containerd)為你做的事, 大致可以分解成以下四個核心步驟:

  1. 呼叫 clone() 系統呼叫,傳入一組 CLONE_NEW* 旗標, 在新的一組 namespace(命名空間) 裡建立容器的初始行程
  2. 在 /sys/fs/cgroup/ 下建立一個 cgroup, 把容器行程加入其中,設定 CPU / 記憶體 / I/O 的資源上限
  3. 用 OverlayFS 把映像層(唯讀)與容器可寫層疊加成一個完整的根目錄
  4. 套用 capabilities 收縮與 seccomp 過濾器, 限制容器能使用的系統呼叫與特權
🔑
容器的本質公式

容器 = 有隔離視圖(namespace)+ 有資源上限(cgroup)+ 有獨立根目錄(OverlayFS) + 有縮減特權(capabilities + seccomp)的 Linux 行程。 它們直接共用 Host 的 Linux 核心——這是容器輕量、快速的根本原因, 也是它與 VM 安全邊界最本質的差異。

chroot:隔離的起點,也是第一道不夠的牆

容器思想的最早源頭是 chroot(change root)—— 一個 1979 年在 Unix V7 中出現的系統呼叫(由 Bill Joy 設計), 目標是讓一個行程和它的子行程只能看到指定子目錄以下的檔案系統, 以此製造一個「假根目錄」環境。 BSD jail(2000 年)、Linux vserver、早期的 LXC 都在 chroot 的基礎上演化而來。

用 chroot 建立一個簡易隔離環境的操作如下: 

# 準備一個最小 rootfs(以 Ubuntu 22.04 為例)
sudo debootstrap --arch=amd64 jammy /mycontainer

# 切換根目錄進入「容器」
sudo chroot /mycontainer /bin/bash

# 在「容器」內:
ls /            # 只看得到 /mycontainer 下的內容
cat /etc/os-release    # Ubuntu 22.04 Jammy

在第 24 章我們看過行程與檔案系統(VFS)如何運作—— 容器正是用核心機制把這些「視圖」隔離開來。 聽起來不錯——但 chroot 只改變了檔案系統的根目錄,其他什麼都沒有隔離:

  • 行程可見性:在 chroot 環境裡執行 ps aux,你仍然看得到 Host 上所有行程。
  • 網路:共用 Host 的所有網路介面和 IP 地址。
  • 主機名稱:共用 Host 的 hostname。
  • 資源限制:完全沒有——chroot 環境可以把 Host 的記憶體全部耗光。
  • IPC:共用 Host 的 System V IPC(共享記憶體、訊息佇列)。
⚠️
chroot 可以逃逸,不是安全邊界

一個在 chroot 環境裡擁有 root 權限的行程,可以透過建立巢狀 chroot 並向上穿越目錄, 或掛載 /proc、存取裝置檔案等方式逃脫隔離、影響 Host 系統。 chroot 從未被設計成安全隔離機制——它只是一個方便的工具, 讓行程在受限的目錄視圖中執行。Linux namespace 才是真正的隔離原語。

📜
容器的演化時間線

1979: chroot(Unix V7) → 2000: BSD jail → 2002: Linux mount namespace → 2006: cgroup 提案 → 2008: LXC / cgroup 合入 Linux 2.6.24 → 2013: Docker 開源(0.x)、user namespace 合入核心 3.8 → 2014: Docker 1.0 發布、OverlayFS 合入核心 3.18 → 2015: OCI 標準成立、runc 發布 → 2016: containerd 獨立。

namespace(命名空間):六道隔離的門

Linux namespace(命名空間)是核心機制,讓一組行程看到的系統資源視圖 與另一組行程完全隔離——彷彿它們活在不同的 OS 裡,但實際上共用同一個核心。 目前容器技術常用的六大 namespace 如下:

Namespace 類型 CLONE_* 旗標 加入核心版本 隔離的資源
pid CLONE_NEWPID 2.6.24 (2008) 行程 ID 空間;容器內 PID 從 1 開始,看不到 Host 的其他行程
mount CLONE_NEWNS 2.4.19 (2002,最早) 掛載點視圖;容器有自己的根目錄 / 與掛載樹
net CLONE_NEWNET 2.6.29 (2009) 網路介面、路由表、防火牆規則、socket;容器有自己的 eth0
uts CLONE_NEWUTS 2.6.19 (2006) hostname 與 NIS domain name;容器可有獨立的主機名稱
ipc CLONE_NEWIPC 2.6.19 (2006) System V IPC(共享記憶體 SHM、訊息佇列 MQ)與 POSIX MQ
user CLONE_NEWUSER 3.8 (2013) UID/GID 映射;容器內 root(uid=0)可對應到 Host 的非特權使用者
ℹ️
為什麼 mount namespace 的旗標叫 CLONE_NEWNS?

CLONE_NEWNS 是 mount namespace 的旗標,「NS」是 namespace 的縮寫。 它是 Linux 加入的第一個 namespace(2002 年),當時還沒有「各種 namespace」的構想, 所以直接叫「新的 namespace」。後來加入的 namespace 才有了各自的描述性名稱。

用 unshare 與 lsns 觀察 namespace

unshare 指令讓你不需要寫程式碼就能手動建立新的 namespace: 

# 建立新的 PID + mount namespace,自動重掛 /proc
# --fork: unshare 本身 fork 一個子行程再 exec /bin/bash
# --mount-proc: 在新 mnt ns 裡重新掛載 /proc
sudo unshare --pid --fork --mount-proc /bin/bash

# 進入新 namespace 後:
echo $$        # 輸出: 1   (這個 bash 是容器內的 PID 1)
ps aux         # 只看到兩個行程: bash(1) 與 ps(2)
exit           # 回到 Host
# 列出系統中所有 namespace
lsns

# 觀察當前 Shell 的 namespace(符號連結 → inode 號)
ls -la /proc/$$/ns/
# 範例輸出:
# ipc  -> ipc:[4026531839]
# mnt  -> mnt:[4026531840]
# net  -> net:[4026531992]
# pid  -> pid:[4026531836]
# user -> user:[4026531837]
# uts  -> uts:[4026531838]
#
# 兩個不同容器的 pid namespace 的 inode 號不同;相同 namespace 共用相同 inode

用 clone() 建立 namespace

底層 container runtime(如 runc)實際上是呼叫 clone() 系統呼叫, 一次傳入所有 CLONE_NEW* 旗標: 

#define _GNU_SOURCE
#include <sched.h>      /* CLONE_NEWPID, CLONE_NEWNS, CLONE_NEWNET ... */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

#define STACK_SIZE (8 * 1024 * 1024)   /* 子行程堆疊 8 MB */

/* 子行程:在新 namespace 裡執行的「容器 init」 */
static int container_init(void *arg) {
    printf("容器內 PID = %d\n", getpid());   /* 應印出 1 */
    execvp("/bin/sh", (char *[]){ "/bin/sh", NULL });
    return 1;
}

int main(void) {
    char *stack = malloc(STACK_SIZE);
    if (!stack) { perror("malloc"); return 1; }

    /* clone() 同時建立六個新 namespace */
    int pid = clone(container_init,
                    stack + STACK_SIZE,           /* 堆疊頂(向下成長) */
                    CLONE_NEWPID | CLONE_NEWNS  | /* PID + mount      */
                    CLONE_NEWNET | CLONE_NEWUTS | /* net  + uts       */
                    CLONE_NEWIPC | CLONE_NEWUSER| /* ipc  + user      */
                    SIGCHLD, NULL);
    if (pid < 0) { perror("clone"); return 1; }

    waitpid(pid, NULL, 0);
    free(stack);
    return 0;
}
/* 編譯: gcc -o minicontainer minicontainer.c */
🔑
namespace 只隔離「視圖」,不隔離「核心」

namespace 讓容器裡的行程看不到 Host 的行程樹、網路、檔案系統—— 但它們仍然在呼叫同一個 Host Linux 核心的系統呼叫介面。 若攻擊者能利用核心漏洞(如 CVE 級別的 privilege escalation), 就能從任何一個容器「逃逸」到 Host,影響同主機上的所有容器。

user namespace 與 rootless 容器

user namespace(使用者命名空間)是六大 namespace 中最複雜、 也最具安全意義的一個。它允許在容器內部使用一套 UID/GID 數字, 並在核心層由 uid_map / gid_map 翻譯到 Host 的真實 UID/GID。

最典型的用法是:容器內的 root(uid=0)映射到 Host 的一個普通使用者(如 uid=1000)。 容器內的行程以為自己是 root——但脫離容器視圖後,它在 Host 眼中只是一個普通使用者。 

# 建立新的 user + pid + mount namespace(不需要 sudo!)
unshare --user --pid --fork --mount-proc /bin/bash

# 在新 namespace 內:
id                          # uid=0(root) gid=0(root)  ← 容器內看起來是 root
cat /proc/self/uid_map      # 0  1000  1  ← 容器 uid 0 對應 Host uid 1000
exit

/proc/self/uid_map 的格式是三欄: 容器內起始 UID → Host 起始 UID → 映射長度。 上例的 0 1000 1（三欄以空格分隔）表示容器內 uid=0 映射到 Host uid=1000,共 1 個 UID。

🔑
rootless 容器的安全意義

rootless container(無 root 容器)指整個容器 runtime 以普通使用者身分執行, 容器內的 root 靠 user namespace 映射實現。好處:即使容器逃逸, 攻擊者在 Host 上只有普通使用者權限,無法安裝核心模組或修改系統級設定。 Podman 默認即為 rootless;Docker 自 19.03 起也支援 rootless mode。

cgroups(控制群組):資源的韁繩

Namespace 解決了「能看到什麼」的問題; cgroups(control groups,控制群組)解決的是「能用多少」的問題。 cgroups 是 Google 工程師 Paul Menage 與 Rohit Seth 於 2006 年提交的功能, 2008 年合入 Linux 2.6.24。

現代 Linux 系統(systemd 240+ 起預設)主要使用 cgroup v2—— 統一階層(unified hierarchy):所有資源控制器掛載在同一個根 /sys/fs/cgroup/ 下。每個 cgroup 是一個目錄, 其中的虛擬檔案就是控制介面。

cgroup v2 的主要資源控制器

  • memory:記憶體用量上限(memory.max)、軟限(memory.high)、當前用量(memory.current)
  • cpu:CPU 時間配額——cpu.max 格式為 $MAX $PERIOD, 如 50000 100000 = 每 100ms 最多用 50ms ≈ 50% 一顆 CPU
  • io:磁碟 I/O 速率上限(io.max,格式按設備 major:minor 指定)
  • pids:最大行程/執行緒數量(pids.max),防止 fork bomb

動手操作:用 cgroup v2 限制記憶體

# 1. 建立 cgroup(需要 root 或 sudo)
mkdir /sys/fs/cgroup/mycontainer

# 2. 在父 cgroup 啟用子控制器
echo "+memory +cpu +pids" > /sys/fs/cgroup/cgroup.subtree_control

# 3. 設定記憶體上限:256 MB
echo 268435456 > /sys/fs/cgroup/mycontainer/memory.max

# 4. 設定 CPU 配額:每 100ms 最多用 50ms(= 50% 一顆 CPU)
echo "50000 100000" > /sys/fs/cgroup/mycontainer/cpu.max

# 5. 設定 PID 上限,防止 fork bomb
echo 100 > /sys/fs/cgroup/mycontainer/pids.max

# 6. 把當前 Shell 加入這個 cgroup
echo $$ > /sys/fs/cgroup/mycontainer/cgroup.procs

# 7. 驗證
cat /sys/fs/cgroup/mycontainer/memory.current   # 目前用量(bytes)
cat /proc/$$/cgroup                               # 確認行程已加入
⚠️
超過 memory.max 會觸發 OOM killer

超過 memory.max 時,Linux 的 OOM killer(Out-Of-Memory Killer) 會選擇 cgroup 內最耗記憶體的行程並發送 SIGKILL 強制終止。 Docker 日誌中會出現 OOMKilled: true。 超過 memory.high(軟限)時則只會節流、回收快取,不立刻 kill。 正確的做法:在應用程式中加入記憶體用量監控,或適當調高 memory.max。

OverlayFS:聯合掛載與寫時複製

想像你下載了一個 1 GB 的 Ubuntu Docker 映像,然後啟動了 10 個容器。 如果每個容器都需要一份完整的磁碟副本,那就需要 10 GB 的儲存空間。 實際上這 10 個容器共用了同一份映像資料,每個容器只儲存了自己修改的部分—— 這靠的是 OverlayFS(覆蓋式檔案系統)。

OverlayFS 是 Linux 3.18(2014 年)正式合入主線的聯合掛載(union mount)實作。 它把多個目錄疊加成一個統一視圖,靠四種目錄完成:

  • lowerdir(下層/唯讀層):一個或多個唯讀目錄,通常是 Docker 映像的各層(Layer)。多層 lowerdir 從右到左疊加,最右側是最底層。
  • upperdir(上層/可寫層):容器的可寫層——修改和新增的檔案都放這裡。
  • workdir(工作目錄):核心用的暫存目錄,必須與 upperdir 在同一個檔案系統,使用者不應直接存取。
  • merged(合併視圖):掛載點——這是容器看到的根目錄,是 lowerdir + upperdir 的統一視圖。

copy-on-write(寫時複製)的工作原理

當容器行程讀取一個檔案(如 /etc/passwd)時, OverlayFS 先在 upperdir 找,找不到就去 lowerdir 找——讀取的是 lowerdir 的版本,沒有複製。

當容器行程修改一個 lowerdir 的檔案時,copy-on-write 啟動: (1) 核心把 lowerdir 的原始檔案完整複製到 upperdir; (2) 後續所有讀寫都針對 upperdir 的副本; (3) lowerdir 的原始檔案永遠不被動到。 刪除一個 lowerdir 的檔案時,OverlayFS 在 upperdir 建立一個 whiteout 檔案(特殊的字元裝置節點),讓 merged 視圖「看不到」它。 

# 手動建立 OverlayFS 掛載(示範結構)
mkdir -p /tmp/lower1 /tmp/lower2 /tmp/upper /tmp/work /tmp/merged

echo "base file from lower1" > /tmp/lower1/base.txt
echo "app config from lower2" > /tmp/lower2/app.conf

# 掛載 OverlayFS(lowerdir 用 : 分隔,左側優先蓋右側)
sudo mount -t overlay overlay \
  -o lowerdir=/tmp/lower2:/tmp/lower1,upperdir=/tmp/upper,workdir=/tmp/work \
  /tmp/merged

ls /tmp/merged           # base.txt  app.conf  (兩層 lower 都看得到)

# 修改 app.conf(copy-on-write 啟動!)
echo "modified" >> /tmp/merged/app.conf

# lower2 的原始檔案不變;修改後副本在 upper
cat /tmp/lower2/app.conf   # app config from lower2   (未動)
cat /tmp/upper/app.conf    # app config from lower2\nmodified

capabilities 與 seccomp:收縮權力邊界

Namespace + cgroup + OverlayFS 解決了「隔離視圖」和「資源上限」的問題, 但還有一個關鍵安全層:容器的行程能呼叫哪些系統呼叫?能擁有哪些特權? 這由 capabilities 與 seccomp 控制—— 也是第 34 章 最小權限原則(principle of least privilege)的直接體現。

Linux capabilities:把 root 切成細粒度特權

傳統 Unix 是二元的:你要麼是 root(uid=0,無所不能),要麼是普通使用者(受限)。 Linux capabilities(自 2.2 起)把「root 的能力」分解成數十個獨立的細粒度特權:

  • CAP_NET_ADMIN:設定網路介面、路由、防火牆規則
  • CAP_SYS_ADMIN:掛載檔案系統、設定 namespace 等(最廣泛,接近全能)
  • CAP_SYS_PTRACE:使用 ptrace() 除錯/追蹤其他行程
  • CAP_NET_RAW:使用 raw socket(可 sniff 封包)
  • CAP_KILL:向任意行程發 signal

Docker 預設的容器只保留一個很小的 capability 集合, CAP_SYS_ADMIN、CAP_SYS_PTRACE、CAP_NET_RAW 等危險 capability 均被移除。即使容器內行程以 uid=0 執行, 它也沒有辦法做真正的 root 才能做的大多數事——例如載入核心模組。 

# 查看一般容器的 capability 集合
docker run --rm ubuntu:22.04 capsh --print
# 只有 cap_chown, cap_dac_override, cap_fowner, cap_kill 等少數幾個

# 查看當前 Shell 的 capability(Host)
cat /proc/$$/status | grep Cap

# --privileged 旗標授予所有 capability(非常危險,僅用於特殊場景!)
docker run --rm --privileged ubuntu:22.04 capsh --print

seccomp:系統呼叫的白名單

seccomp(Secure Computing Mode) 在 Linux 2.6.12(2005)以 strict mode 登場 (只允許極少數系統呼叫);Linux 3.5(2012)加入以 BPF(Berkeley Packet Filter) 程式過濾系統呼叫的 filter 模式, 這才是 Docker 等容器實際使用的機制。 Docker 預設啟用一個包含約 300 個允許 syscall 的 seccomp profile, 阻止約 44 個危險 syscall——例如 reboot、kexec_load、 create_module、ptrace 等。 

# 在容器中嘗試被 seccomp 阻止的 syscall
docker run --rm ubuntu:22.04 sh -c "reboot"
# 輸出: sh: reboot: Operation not permitted
# seccomp 攔截了 reboot syscall(syscall number 169 on x86-64)

# 以自訂 seccomp profile 啟動
docker run --rm --security-opt seccomp=/path/to/profile.json ubuntu:22.04 sh

在 C 中使用 libseccomp 加入 seccomp 過濾: 

#include <seccomp.h>   /* 需要 apt install libseccomp-dev / gcc ... -lseccomp */

/* 初始化 seccomp:預設允許所有 syscall */
scmp_filter_ctx ctx = seccomp_init(SCMP_ACT_ALLOW);

/* 禁止 reboot(169),任何試圖呼叫者會被 SIGKILL */
seccomp_rule_add(ctx, SCMP_ACT_KILL, SCMP_SYS(reboot), 0);
/* 禁止 ptrace(101) */
seccomp_rule_add(ctx, SCMP_ACT_KILL, SCMP_SYS(ptrace), 0);

/* 載入過濾器到核心;此後本行程及子行程均受約束 */
seccomp_load(ctx);
seccomp_release(ctx);
🔑
capabilities + seccomp = 最小攻擊面

capabilities 限制「擁有哪些特權」;seccomp 限制「能呼叫哪些系統呼叫」。 兩者都是縱深防禦(defense in depth)的一環: 即使攻擊者能在容器內執行任意程式碼,受限的 capability 集合與嚴格的 syscall 白名單 會大幅限制其橫向移動與提權的能力。 但核心本身的漏洞仍然是共同的天花板。

把六個機制拼成一個容器

現在把各個機制放在一起,看看它們如何協同工作——以及缺少任何一個會發生什麼:

核心機制 解決的問題 如果沒有它
mount namespace
CLONE_NEWNS		 獨立根目錄視圖(容器有自己的 /) 容器能看到並修改 Host 的整個檔案系統
pid namespace
CLONE_NEWPID		 隔離行程 ID 空間(容器有自己的 PID 1) 容器內行程能看到並 kill Host 上的其他行程
net namespace
CLONE_NEWNET		 隔離網路介面、路由、socket 容器共用 Host 的 IP,任意監聽 Host 埠號
uts namespace
CLONE_NEWUTS		 隔離 hostname / domain name 所有容器共用 Host hostname,日誌混淆難追蹤
ipc namespace
CLONE_NEWIPC		 隔離 System V SHM / MQ 不同容器可透過共享記憶體或訊息佇列互相通訊洩密
user namespace
CLONE_NEWUSER		 UID/GID 映射,支援 rootless 容器 容器 root = Host root,逃逸即獲得完整 root 權限
cgroup v2 限制 CPU / 記憶體 / I/O / PID 數量 一個容器可耗光 Host 所有資源(DoS 攻擊)
OverlayFS 聯合掛載映像層,copy-on-write 可寫層 每個容器需完整磁碟副本,磁碟佔用與啟動時間爆增
capabilities 移除危險 root 特權 容器可載入核心模組、修改網路設定、kill 任意行程
seccomp BPF 過濾危險系統呼叫 容器可呼叫 reboot、kexec_load 等影響整台 Host 的 syscall

在 Linux 上,runc(OCI container runtime 的參考實作) 就是把上述步驟串聯起來的程式。它讀取 OCI 格式的 config.json, 依序建立 namespace、設定 cgroup、掛載 rootfs(OverlayFS)、 套用 capabilities 與 seccomp profile,然後 exec 容器的入口程式。 Docker 的 containerd 負責管理映像生命週期,最後呼叫 runc 完成真正的建立動作。

⚠️
容器隔離 ≠ VM 等級的安全邊界

不管疊了多少層機制,容器的根本弱點是: 所有容器共用同一個 Host Linux 核心的系統呼叫介面。 若攻擊者能利用核心的 CVE 漏洞(如 CVE-2022-0185 的 namespace 越界寫入、 CVE-2019-5736 的 runc symlink 漏洞),就能從容器「逃逸」到 Host, 影響同主機上的所有容器。 VM 有獨立的 Guest OS 核心,Hypervisor 介面比 Linux syscall 介面小得多—— 這是 VM 安全邊界比容器更強的根本原因。 多租戶的高安全場景(如公有雲執行不受信任的程式碼) 應考慮 VM 或 VM + 容器(如 kata-containers、Firecracker)的組合。

✏️ 練習 87.1 實作

在 Linux 機器(或 WSL2)上執行:

sudo unshare --pid --fork --mount-proc /bin/bash

進入後分別執行 echo $$、ps aux、ls /proc/。 觀察並解釋:(1) 為什麼 PID 是 1?(2) 為什麼 ps aux 只看到少數行程? (3) --mount-proc 旗標的作用是什麼?如果不加這個旗標會怎樣?

看解答

(1) PID 是 1 的原因: --pid 建立了新的 PID namespace,行程 ID 在新 namespace 裡從 1 開始重新編號。 --fork 讓 unshare 先 fork 一個子行程, 讓該子行程成為新 namespace 的第一個行程再 exec /bin/bash。 因此 bash 的 PID 在容器視圖裡就是 1。

(2) ps 只看到少數行程: ps 讀取 /proc 目錄來列出行程。 --mount-proc 在新的 mount namespace 裡重新掛載了 /proc—— 這個 /proc 只反映新 PID namespace 裡的行程, 所以 ps aux 只看到 bash 和 ps 兩個行程。

(3) 不加 --mount-proc 的結果: 新 namespace 裡仍然掛著 Host 的 /proc。 ps aux 會看到 Host 的所有行程——雖然 PID namespace 已隔離, 但 /proc 仍反映 Host 真實行程樹。 這正是為什麼 Docker 必須同時隔離 mount namespace 並重新掛載 /proc。

✏️ 練習 87.2 思考

解釋 user namespace 如何讓 rootless 容器更安全。具體地說:如果容器發生逃逸(container escape), 有 user namespace(rootless)與沒有 user namespace(傳統 Docker,以 Host root 執行 daemon)的情況下, 攻擊者在 Host 上的權限有什麼不同?

看解答

有 user namespace(rootless): 容器內行程以 uid=0 執行,但核心的 user namespace 把這個 uid=0 映射到 Host 上的普通使用者(例如 uid=1001)。 攻擊者成功逃逸後,在 Host 的真實 UID 仍然是 1001—— 無法安裝核心模組、無法修改 /etc/passwd、無法存取其他使用者的檔案。

沒有 user namespace(傳統容器,Docker daemon 以 root 執行): 容器內 uid=0 就是 Host 的真實 root。 攻擊者逃逸後在 Host 直接是 root,可以安裝惡意核心模組、讀取所有檔案、 影響同主機上的所有容器和服務。

結論: user namespace 是容器安全的重要縱深防禦—— 把「容器逃逸」的最壞結果從「完全接管 Host root」降低到「只有普通使用者權限」。 這就是為什麼 Podman 默認 rootless、Docker 的 rootless mode 被積極推廣。

✏️ 練習 87.3 思考

一個容器設定了 memory.max = 256MB 的 cgroup 限制。 容器內的應用程式嘗試分配 300MB 的記憶體。 請描述從 malloc() 呼叫到最終結果的完整流程: 核心在哪個環節介入?OOM killer 如何決定要 kill 哪個行程? 應用程式會看到什麼?Docker 接下來會怎麼做?

看解答

記憶體分配流程: malloc(300MB) 最終會呼叫 mmap() 系統呼叫請求核心分配記憶體頁。 核心在分配時檢查行程所屬 cgroup 的 memory.current(目前用量); 若加上新分配會超過 memory.max(268435456 bytes), 核心觸發 cgroup OOM 機制。

OOM killer 的決策: OOM killer 在 cgroup 範圍內計算每個行程的 OOM score (主要依據記憶體用量、是否已被標記),選擇得分最高的行程發送 SIGKILL。 單行程容器中,通常就是那個應用程式本身被 kill。 OOM 事件會記錄在核心日誌(dmesg)中。

應用程式看到的: 被 kill 的行程直接終止,不會收到任何從 malloc() 的返回值。 Docker 日誌中會出現 OOMKilled: true(docker inspect 可查)。 若容器的 restart policy 是 always 或 on-failure, Docker 會自動重啟容器。正確對應方式:加入記憶體用量監控,或適當調高 memory.max。

把這一章串起來

從一個 docker run 出發,我們拆解了 Linux 容器的完整底層實作。 幾個值得帶走的核心觀念:

  • 容器不是 VM:沒有 Guest OS、沒有 Hypervisor。 它是有隔離視圖(namespace)+ 資源上限(cgroup) + 獨立根目錄(OverlayFS)+ 縮減特權(capabilities + seccomp)的 Linux 行程。
  • 六大 namespace 各司其職: pid / mount / net / uts / ipc / user——每個解決一個維度的隔離需求。 CLONE_NEWPID、CLONE_NEWNS、CLONE_NEWNET、 CLONE_NEWUTS、CLONE_NEWIPC、CLONE_NEWUSER 是核心提供的原語,container runtime 把它們組合起來。
  • cgroup v2 是資源的韁繩: /sys/fs/cgroup/ 下的虛擬介面讓你精確控制容器的 CPU、記憶體、I/O、PID—— 沒有它,一個容器就能把整台 Host 拖垮。
  • OverlayFS 讓多容器共用映像層: lowerdir 唯讀、upperdir 可寫、merged 統一視圖—— copy-on-write 讓修改只影響 upper 層,不碰 lower 的原始映像,大幅節省磁碟。
  • capabilities + seccomp 是最後一道防線: 即使 namespace 被突破,收縮過的 capability 集合與 syscall 白名單 仍然限制攻擊者能做的事。但它們都依賴核心的正確性——核心漏洞是共同的天花板。
  • 誠實面對安全邊界: 容器是「同核心隔離」,VM 是「不同核心隔離」。 高安全多租戶場景應選擇 VM 或 kata-containers / Firecracker 等混合方案。

下一章將把這些理論付諸實踐——用 C 語言直接呼叫 clone()、 設定 cgroup、掛載 OverlayFS、套用 seccomp 過濾器, 親手從零拼出一個迷你 Docker runtime。 理解了本章的原理,那裡的每一行程式碼你都能對應到「它在實作哪個機制」。
