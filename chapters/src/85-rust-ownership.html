C 的記憶體之痛

讓我們從一段看起來無害的 C 程式開始。它做的事很簡單:在函式裡建立一個字串, 然後把它回傳給呼叫者。 

/* dangling_ptr.c — 懸空指標示範 */
#include <stdio.h>
#include <string.h>

char *make_greeting(const char *name) {
    char buf[64];
    snprintf(buf, sizeof(buf), "Hello, %s!", name);
    return buf;   /* ⚠️ 錯誤:回傳局部變數的位址 */
}

int main(void) {
    char *msg = make_greeting("Alice");
    printf("%s\n", msg);   /* 未定義行為:buf 已在函式返回時消失 */
    return 0;
}

這段程式在某些編譯器上能印出看起來「正確」的字串,在另一些環境下 卻印出亂碼,甚至直接崩潰。問題在哪裡?buf 是 make_greeting 函式的局部陣列,住在 stack 上。 函式返回的瞬間,buf 所佔用的 stack 空間就被系統收回—— 可能下一個函式呼叫就覆蓋掉它。我們把這種「指向已無效記憶體的指標」 叫做懸空指標(dangling pointer)。

這還只是開胃菜。接下來看 double free(重複釋放): 

/* double_free.c — double free 示範 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    char *p = (char *)malloc(32);
    if (!p) return 1;

    strcpy(p, "hello");
    free(p);   /* 第一次釋放 */

    /* ... 程式邏輯龐大,某處忘了 p 已被 free ... */
    free(p);   /* ⚠️ 第二次釋放:未定義行為,可能崩潰或成安全漏洞 */
    return 0;
}

malloc / free 的原則是「誰配置、誰釋放、只釋放一次」。 但在複雜程式中,一塊記憶體可能被多個指標「共享」地指著, 其中一個把它釋放了,其他指標就變成懸空指標;若再次釋放,就是 double free。 結果輕則程式崩潰,重則被攻擊者利用成安全漏洞——CVE 資料庫裡每年都有上百個這樣的案例。

第三個地雷是記憶體洩漏(memory leak): 

/* leak.c — 記憶體洩漏示範 */
#include <stdlib.h>

char *load_data(void) {
    char *buf = (char *)malloc(1024);
    if (!buf) return NULL;
    /* 填入資料 ... */
    return buf;   /* 呼叫者必須記得 free,但常常忘 */
}

int main(void) {
    for (int i = 0; i < 100000; i++) {
        char *data = load_data();
        /* 使用 data ... */
        /* ⚠️ 忘了 free(data):每次迴圈洩漏 1024 bytes */
    }
    return 0;
}

以上三種 bug 有一個共同根源:記憶體的「誰負責、何時釋放」 完全靠程式設計師的大腦追蹤。C 語言假設你能做到完美—— 而人類做不到。

⚠️
「加個 GC 不就解決了?」

Java、Python、Go 等語言用垃圾回收(garbage collection, GC)解決了記憶體安全問題, 但代價是:執行時的額外開銷、不可預測的 GC pause、以及更高的記憶體用量。 對需要和 OS 爭奪微秒級延遲的系統程式(驅動程式、遊戲引擎、嵌入式韌體)而言, GC 是不可接受的奢侈品。我們需要一個第三條路。

為什麼是 Rust:無 GC 卻保證記憶體安全

2006 年,Mozilla 工程師 Graydon Hoare 開始業餘時間設計一門新語言, 目標是「比 C++ 更安全,但一樣快」。Mozilla 從 2009 年正式贊助這個專案, 2015 年 Rust 1.0 正式釋出。如今,Rust 連續多年蟬聯 Stack Overflow「最受開發者喜愛的程式語言」第一名, Linux 核心、Windows 核心、Android、Chromium 已陸續引入 Rust 撰寫安全關鍵模組。

Rust 的核心承諾是:在編譯期消除記憶體錯誤,不需要 GC, 執行時幾乎零額外成本(zero-cost abstractions)。 它靠的不是魔法,而是一套精心設計的型別系統—— 所有權系統(ownership system)。

🔑
Rust 的三把鑰匙

所有權(ownership):每一塊記憶體都有且只有一個「主人」,主人離開作用域時記憶體自動釋放。
借用(borrowing):暫時取用別人的資料,但規則嚴格——不能在借用期間讓主人消失。
生命週期(lifetime):編譯器追蹤每個參考(reference)的「有效期」,確保參考不會活得比它指向的資料更久。

ℹ️
連結:型別系統與編譯器

Rust 的所有權系統是第 9 章討論的靜態型別系統的延伸—— 它不只追蹤「這個值是整數還是字串」,還追蹤「這個值現在歸誰所有、能不能被修改」。 第 42 章介紹的編譯器在語意分析階段做型別檢查, Rust 的 borrow checker 就是這個型別檢查的一部分。

cargo 與你的第一支 Rust 程式

Rust 的生態系圍繞著官方工具鏈 rustup(管理版本)與 cargo(建置、測試、套件管理)展開。 安裝方式(Linux/macOS/WSL): 

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh

安裝完成後,建立第一個 Rust 專案:

cargo new hello_rust    # 建立新專案目錄
cd hello_rust
cargo run               # 編譯並執行

cargo new 會生成以下結構:

hello_rust/
├── Cargo.toml          # 套件設定(相當於 package.json)
└── src/
    └── main.rs         # 程式進入點

src/main.rs 的初始內容:

fn main() {
    println!("Hello, world!");    // println! 是巨集(macro),不是函式
}

稍微豐富一下,感受 Rust 的基本語法與借用: 

fn main() {
    let name = String::from("Alice");    // 在 heap 上配置字串
    let greeting = greet(&name);         // &name:借用 name,不轉移所有權
    println!("{}", greeting);
    // name 在這裡依然有效——因為只是借用
    println!("name 還活著: {}", name);
}

fn greet(s: &String) -> String {         // &String:接受借用
    format!("Hello, {}!", s)             // format! 回傳一個全新的 String
}

這段程式能跑,但有個值得注意的細節:我們把 &name 傳給 greet,而不是 name——這就是「借用」。 接下來幾節,我們要把這個直覺變成精確的規則。

所有權三規則與 move 語意

Rust 所有權系統的核心只有三條規則。乍看很簡單, 但後果可以讓第一次學習的人抓狂好幾天—— 因為你從 Python/Java 帶來的直覺在這裡幾乎都是錯的。

🔑
所有權三規則

1. Rust 中每個值都有一個擁有者(owner)。
2. 同一時間只能有一個擁有者。
3. 當擁有者離開作用域(scope),該值立即被丟棄(dropped)。

規則三用程式碼最直觀:

fn main() {
    {
        let s = String::from("hello");   // s 成為這個 String 的擁有者
        // 可以使用 s ...
    }  // ← 作用域結束,s 被 drop:heap 記憶體在此自動釋放
    // println!("{}", s);  // ✗ s 已不存在
}

這就是 Rust 的確定性解構(deterministic destruction)—— 不是 GC 在某個不確定的時間點回收,而是在作用域結束的瞬間立即釋放。 C++ 也有類似的 RAII(Resource Acquisition Is Initialization)慣用法, Rust 把它提升為語言的基礎機制。

ℹ️
Stack 與 Heap 複習

第 24 章介紹了作業系統的記憶體管理: stack 隨函式呼叫自動成長縮短,heap 由程式動態配置與釋放。 Rust 的所有權系統正是建立在此之上——它讓 heap 記憶體的釋放也能像 stack 一樣「自動且確定」。

move 語意的程式碼

fn main() {
    let s1 = String::from("hello");
    let s2 = s1;              // s1 的所有權「移交」給 s2(move)
    // println!("{}", s1);   // ✗ 編譯錯誤:s1 的值已被 move
    println!("{}", s2);      // ✓ s2 是現在的擁有者
}  // s2 離開作用域 → drop 被呼叫 → heap 記憶體釋放(一次且僅一次)

這和 Python/Java 的語意完全不同:在那些語言,s2 = s1 只是讓兩個變數指向同一個物件。在 Rust,這個動作轉移了所有權——s1 不再有效。 為什麼?因為如果兩個變數都認為自己是那塊 heap 記憶體的主人, 作用域結束時兩者都會嘗試 free——這就是 double free。 Rust 從根本上杜絕了這個可能性。

Copy 型別:住在 stack 上的例外

整數、浮點數、布林、char、以及只由這些型別組成的元組(tuple), 都實作了 Copy trait——它們住在 stack 上,複製成本極低, Rust 對它們執行複製(copy)而非 move: 

fn main() {
    let x = 5;
    let y = x;                          // x 被複製到 y(不是 move)
    println!("x = {}, y = {}", x, y);  // ✓ 兩者都有效
}
✏️ 練習 79.1 思考

下面這段 Rust 程式為什麼無法編譯?請解釋原因,並說明哪條所有權規則被違反了:

fn main() {
    let s1 = String::from("hello");
    let s2 = s1;
    println!("{}", s1);   // 這一行錯在哪裡?
}
看解答

let s2 = s1; 把 s1 的所有權移交(move)給了 s2, 此後 s1 不再有效。println!("{}", s1) 試圖使用已被 move 的值, 違反所有權規則二:同一時間只能有一個擁有者。

編譯器回報:

error[E0382]: borrow of moved value: `s1`
 --> src/main.rs:4:20
  |
2 |     let s1 = String::from("hello");
  |         -- move occurs because `s1` has type `String`
3 |     let s2 = s1;
  |              -- value moved here
4 |     println!("{}", s1);
  |                    ^^ value borrowed here after move

修正方式:若要兩者都使用,改為 let s2 = s1.clone();; 若只要讀取,傳 &s1 參考即可。

借用 & 與可變借用 &mut

如果每次把值傳進函式都要放棄所有權,那程式設計將是一場噩夢—— 你永遠拿不回自己的東西。這就是借用(borrowing)的用途。 借用讓你能暫時使用某個值,卻不取得它的所有權。 

fn main() {
    let s = String::from("hello");
    let len = calculate_length(&s);      // &s:建立指向 s 的參考,不轉移所有權
    println!("'{}' 的長度是 {}", s, len); // s 依然有效!
}

fn calculate_length(s: &String) -> usize { // 接受 String 的參考
    s.len()
}   // s 在這裡離開作用域,但因為只是借用,不會 drop 原始資料

&s 建立一個指向 s 的共享參考(shared reference)。 你可以讀取值,但不能修改它——就像你借了朋友的書,只能看、不能塗鴉。

可變借用:&mut T

想修改借來的值?需要可變參考(mutable reference):

fn main() {
    let mut s = String::from("hello");  // 先讓 s 本身是可變的(mut)
    change(&mut s);                     // 傳可變參考
    println!("{}", s);                  // 印出 "hello, world"
}

fn change(s: &mut String) {            // 接受可變參考
    s.push_str(", world");              // 可以修改!
}

別名 XOR 可變:最重要的規則

Rust 對參考有一條嚴格的規則,這條規則消除了一整類的資料競爭 bug:

🔑
別名 XOR 可變(Aliasing XOR Mutability)

在同一個作用域裡,你可以有:
任意多個共享參考 &T(多個讀取者),
或者恰好一個可變參考 &mut T(一個修改者),
但不能同時擁有兩者。

為什麼這條規則能消除資料競爭?考慮多執行緒環境: 如果一個執行緒在讀取(&T),另一個在修改(&mut T),就是經典的資料競爭。 Rust 的規則在單執行緒時就已嚴格禁止這種「同時存在」的可能性—— 多執行緒時,Send 和 Sync trait 繼續保衛這道防線。

⚠️
常見新手陷阱

新手常在迴圈裡試圖同時以不可變方式讀取一個集合,又試圖修改它。Rust 一律拒絕。 解決辦法通常是:先把需要的資訊複製出來,再統一修改;或者改用 index 存取而非參考。

✏️ 練習 79.2 實作

下面這段程式有 borrow checker 錯誤。找出錯誤原因,說明為何這樣不安全,並修正它:

fn main() {
    let mut s = String::from("hello");
    let r1 = &s;
    let r2 = &s;
    s.push_str(", world");    // 這行造成什麼問題?
    println!("{} {}", r1, r2);
}
看解答

r1 和 r2 是 s 的共享參考(不可變借用)。 s.push_str() 需要對 s 進行可變借用。 根據別名 XOR 可變規則,當 r1、r2 還活著時,不能同時有可變借用。 此外,String 的內部緩衝區(一個 Vec<u8>)可能因 push_str 而重新配置記憶體, 使 r1、r2 成為懸空指標——這正是 Rust 要防止的。

修正:先用完不可變借用,再修改。自 Rust 2018 edition 起引入 Non-Lexical Lifetimes(NLL,非詞法生命週期),其實只需把最後一次使用 r1、r2 的 println! 移到 push_str 之前,就能解除衝突,不需額外的 block;下方的 block 只是更顯式的寫法:

fn main() {
    let mut s = String::from("hello");
    {
        let r1 = &s;
        let r2 = &s;
        println!("{} {}", r1, r2);   // 借用在這裡結束
    }
    s.push_str(", world");           // ✓ 借用已結束,可以修改
    println!("{}", s);
}

生命週期初步

生命週期(lifetime)是 Rust 最讓新手頭痛的特性。 但它解決的問題很真實:如何確保參考不會活得比它指向的資料更久?

先看一個在 C 裡會靜默出錯、在 Rust 裡會被擋下的情境:

fn main() {
    let r;
    {
        let x = 5;
        r = &x;         // r 借用 x
    }                   // x 在這裡被 drop!
    println!("{}", r);  // ✗ r 現在是懸空參考
}

Rust 編譯器直接拒絕,並清楚指出問題所在:

error[E0597]: `x` does not live long enough
 --> src/main.rs:5:13
  |
5 |         r = &x;
  |             ^^ borrowed value does not live long enough
6 |     }
  |     - `x` dropped here while still borrowed
7 |     println!("{}", r);
  |                    - borrow later used here

這正是我們在 C 裡被懸空指標燒到的那類 bug—— 現在被 Rust 在編譯時完全消滅了。

生命週期標注:告訴編譯器「誰活得更久」

大多數情況,Rust 能自動推斷生命週期(lifetime elision 規則), 你不用手動標注。但當函式回傳參考,且參考可能來自多個輸入時, 編譯器需要你明確說明參考之間的關係: 

// 接受兩個字串 slice,回傳較長的那個
// 'a 是生命週期參數:確保輸出的生命週期不超過兩個輸入中較短的那個
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}

fn main() {
    let s1 = String::from("long string is long");
    let result;
    {
        let s2 = String::from("xyz");
        result = longest(s1.as_str(), s2.as_str());
        println!("較長的字串是: {}", result);  // ✓ 在 s2 的作用域內使用
    }
    // println!("{}", result);  // ✗ s2 已 drop,result 可能指向它
}

'a 不是一個固定的時間長度——它是個佔位符, 代表「無論 x 和 y 的生命週期是多長,我保證輸出不會活得比其中較短的那個更久」。 編譯器用它來驗算所有使用這個函式的呼叫點是否安全。

💡
生命週期標注的直覺

你不是在告訴 Rust「這個參考能活多久」——你是在描述不同參考之間的相對關係。 當 Rust 說「需要生命週期標注」,通常意味著它無法靠推斷確認回傳的參考一定比某個輸入活得短。 你的標注給了它這個資訊。大多數日常程式碼遇不到這種情況。

borrow checker 實戰:讀懂錯誤,修正程式

理論說夠了。最好的學習方式是故意寫出會被 borrow checker 擋下的程式, 然後學會讀懂錯誤訊息並修正它。

場景一:借用後修改導致懸空指標

fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0];    // 不可變借用 v
    v.push(4);             // ✗ 可變借用 v,但 first 還活著!
    println!("{}", first);
}

編譯器的錯誤訊息(精簡版):

error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
 --> src/main.rs:4:5
  |
3 |     let first = &v[0];
  |                  - immutable borrow occurs here
4 |     v.push(4);
  |     ^^^^^^^^^ mutable borrow occurs here
5 |     println!("{}", first);
  |                    ----- immutable borrow later used here

為什麼這很危險?Vec 在 push 時可能需要重新配置更大的 heap 記憶體, 把所有元素搬到新位置——first 指向的舊位置就成了懸空指標! Rust 阻止了這個問題。

修正方式一:複製值出來,不借用:

fn main() {
    let mut v = vec![1, 2, 3];
    let first_val = v[0];    // 複製 i32(Copy 型別),不是借用
    v.push(4);               // ✓ 現在可以修改
    println!("第一個元素: {}", first_val);
    println!("現在的 v: {:?}", v);
}

場景二:C 懸空指標問題在 Rust 的對應情境

回到本章開頭的 C 懸空指標。如果用 Rust 重寫,borrow checker 直接擋下來:

fn make_greeting(name: &str) -> &str {
    let greeting = format!("Hello, {}!", name);   // 在函式內建立新 String
    &greeting   // ✗ 回傳局部變數的參考
}               // greeting 在這裡被 drop,參考立即失效

編譯器錯誤:

error[E0515]: cannot return reference to local variable `greeting`
 --> src/main.rs:3:5
  |
3 |     &greeting
  |     ^^^^^^^^^ returns a reference to data owned by the current function

正確修法:回傳 String(轉移所有權),不回傳參考:

fn make_greeting(name: &str) -> String {
    format!("Hello, {}!", name)   // 把所有權移交給呼叫者
}

fn main() {
    let msg = make_greeting("Alice");   // msg 成為 String 的新擁有者
    println!("{}", msg);
}
🔑
Rust 編譯器的錯誤訊息很友善

Rust 的編譯器(rustc)以「錯誤訊息清楚有用」聞名。每個錯誤都有 E0XXX 編號和詳細說明, 通常還附上修正建議。遇到 borrow checker 報錯,先讀懂「哪裡借用、哪裡衝突」, 八成問題就解了。不要跳過錯誤訊息——它是你最好的老師。

✏️ 練習 79.3 實作

把這個 C 函式改寫成 Rust 慣用版本。C 版本有潛在的 buffer overflow(當 n 為 0 時)問題,Rust 版本應該安全且慣用:

/* 找出陣列中的最大值 */
int find_max(int *arr, int n) {
    int max = arr[0];
    for (int i = 1; i < n; i++) {
        if (arr[i] > max) max = arr[i];
    }
    return max;
}
看解答

Rust 慣用版本使用切片(&[i32])取代指標+長度,以 Option 處理空陣列:

// 方法一:手動迴圈
fn find_max(arr: &[i32]) -> Option<i32> {
    if arr.is_empty() { return None; }  // 明確處理空陣列
    let mut max = arr[0];
    for &val in &arr[1..] {             // &arr[1..] 是從第二個元素開始的借用切片
        if val > max { max = val; }
    }
    Some(max)
}

// 方法二:使用標準庫迭代器(更 Rust 慣用)
fn find_max_iter(arr: &[i32]) -> Option<&i32> {
    arr.iter().max()   // 標準庫已有 max()
}

fn main() {
    let data = vec![3, 9, 2, 7, 5];
    println!("{:?}", find_max(&data));       // Some(9)
    println!("{:?}", find_max_iter(&data));  // Some(9)
    println!("{:?}", find_max(&[]));         // None,空切片安全處理
}

與 C 版本的差異:① 輸入是 &[i32](借用的切片),不需要額外傳長度參數; ② 空陣列的情況以 Option 明確表達,不會有未定義行為; ③ 索引存取時 Rust 自動做邊界檢查,不可能越界讀取。

何時 clone、何時借用

學了借用之後,新手常陷入另一個極端:到處加 .clone() 讓程式能編譯, 卻不理解這樣做的代價。.clone() 會複製整塊 heap 資料—— 對大型字串或容器而言,代價可觀。 

// ✗ 反模式:不必要的所有權轉移與 clone
fn print_length(s: String) -> usize {   // 吞掉所有權(不必要!)
    s.len()
}

fn main() {
    let name = String::from("Alice");
    println!("{}", print_length(name.clone()));  // clone 了但根本不需要
    println!("{}", name);
}
// ✓ 正確做法:借用
fn print_length(s: &str) -> usize {    // &str:最通用的字串借用形式
    s.len()
}

fn main() {
    let name = String::from("Alice");
    println!("{}", print_length(&name));  // 借用,不轉移所有權
    println!("{}", name);                 // name 依然有效
}
💡
實用的決策流程

1. 函式只需要讀取資料?→ 用 &T(借用)。
2. 函式需要修改資料?→ 用 &mut T(可變借用)。
3. 函式需要取得所有權(例如把它存進 struct 或傳給執行緒)?→ 用 T(move)。
4. 需要所有權,但又要保留原始資料?→ .clone()(有成本,謹慎使用)。

&str vs String:最常見的型別混淆

型別 儲存位置 擁有資料 可否修改 常見用途
&str 借用的 slice(可指向任何地方) 否 否 函式參數、字串常數
String heap 上的可成長緩衝區 是 是(若 mut) 動態建立字串、需要所有權

經驗法則:函式參數優先用 &str—— 它比 &String 更通用(可以接受字串常數和 String 的借用); 回傳值如果是新建立的字串,用 String。

✏️ 練習 79.4 挑戰

下面這段程式嘗試把 String 中的單詞順序反轉。它有兩個問題:一個是 borrow checker 問題,一個是邏輯問題。找出這兩個問題並修正:

fn reverse_words(s: &mut String) {
    let words: Vec<&str> = s.split_whitespace().collect();
    s.clear();                              // 問題在這裡?
    for word in words.iter().rev() {
        s.push_str(word);
        s.push(' ');                        // 邏輯問題在哪裡?
    }
}

fn main() {
    let mut sentence = String::from("hello world foo");
    reverse_words(&mut sentence);
    println!("{}", sentence);
}
看解答

Borrow checker 問題:words 中每個 &str 都借用了 s 的記憶體。 s.clear() 試圖可變借用並修改 s,但 words 的不可變借用還活著。 根據別名 XOR 可變規則,這被編譯器拒絕。

邏輯問題:最後一個單詞後面會多一個多餘的空格。

修正方式:先把單詞複製成獨立的 String,打破對 s 的借用:

fn reverse_words(s: &mut String) {
    // 先把單詞複製成獨立的 String,解除對 s 的借用
    let words: Vec<String> = s.split_whitespace()
                               .map(|w| w.to_string())
                               .collect();
    // words 是獨立所有者,不再借用 s,現在可以安全修改 s
    *s = words.iter()
              .rev()
              .cloned()
              .collect::<Vec<String>>()
              .join(" ");   // join 不產生尾隨空格
}

fn main() {
    let mut sentence = String::from("hello world foo");
    reverse_words(&mut sentence);
    println!("{}", sentence);   // "foo world hello"
}

把這一章串起來

從 C 的記憶體地雷,到 Rust 的所有權系統,我們走過了一段令人驚嘆的旅程。 回顧這趟旅程的幾個路標:

  • C 的問題根源:懸空指標、double free、記憶體洩漏——全都源自「記憶體的責任由人腦追蹤」。
  • Rust 的解法:不靠 GC,靠所有權三規則在編譯期強制正確性。每個值有唯一擁有者;擁有者離開作用域,值立即且確定地釋放。
  • Move 語意:let s2 = s1 是所有權轉移,不是複製;實作了 Copy trait 的 stack-only 型別(整數等)是唯一例外。
  • 別名 XOR 可變:可以有多個 &T,或一個 &mut T,但不能同時有兩者——這條規則是零成本並行安全的基礎。
  • 生命週期:確保參考不會活得比它指向的資料更久。大多數時候 Rust 自動推斷,偶爾需要 'a 標注。
  • 實戰策略:優先借用(&str/&T),需要修改用 &mut T,需要所有權才 move,最後手段才 .clone()。

所有權系統起初讓人痛苦——「為什麼這段在 Python 完全沒問題的程式,Rust 不讓我這樣寫?」 但當你過了這道坎,你會發現:borrow checker 其實是你最嚴格也最友善的程式碼審查者, 它把你過去在 GDB 或 Valgrind 裡苦苦追查的那些 bug,全都提前到編譯時報告給你。 能通過編譯的 Rust 程式,記憶體安全這件事可以幾乎打勾。
