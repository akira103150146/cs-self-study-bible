🔑
映像(image)vs 容器(container)

映像是唯讀的模板——就像第 87 章的 OverlayFS lowerdir: 一疊唯讀層,每一層對應 Dockerfile 的一條指令。 容器是映像的執行實例——在映像的唯讀層上加了一個可寫層(upperdir), 讓容器可以寫入檔案,但不影響原始映像。 刪除容器,可寫層隨之消失;映像本身仍保持不變。

Dockerfile 基礎:FROM / RUN / COPY / CMD / ENTRYPOINT / EXPOSE

Dockerfile 是一份「如何建置映像」的食譜——每條指令告訴 Docker daemon 一個建置步驟。 讓我們從一個真實的 Node.js 應用程式 Dockerfile 出發,逐行解釋: 

# ── Node.js 應用程式 Dockerfile 範例 ──────────────────
# FROM:指定基礎映像。alpine 是極小的 Linux 發行版(~5 MB)。
FROM node:18-alpine

# WORKDIR:設定容器內的工作目錄(不存在則自動建立)。
# 後續所有 RUN / COPY / CMD 指令都在這個目錄下執行。
WORKDIR /app

# COPY:把 host 上的 package.json 與 package-lock.json 複製進映像。
# 注意:先複製 package*.json,再 RUN npm ci,
# 這樣只有 package.json 改變時才需要重新 npm install(快取優化,見下節)。
COPY package*.json ./

# RUN:在建置階段執行指令,結果固化成一個映像層。
# --omit=dev 只安裝 production 依賴(等同舊版 --only=production)。
RUN npm ci --omit=dev

# 把應用程式碼複製進去(改了程式碼但沒改 package.json 時,此層重建而上層快取仍有效)
COPY . .

# EXPOSE:宣告容器監聽的埠。這只是文件說明,不自動對外公開——
# 需要 docker run -p 才真正把 host 埠對應到容器埠。
EXPOSE 3000

# CMD:容器啟動時預設執行的指令(exec 格式,不透過 shell)。
# 若 docker run 後面傳了指令,CMD 會被覆蓋。
CMD ["node", "app.js"]
ℹ️
CMD vs ENTRYPOINT

CMD 是「預設指令」——docker run myapp 時執行 node app.js, 但 docker run myapp sh 會覆蓋 CMD 改為執行 sh。
ENTRYPOINT 是「主程式骨幹」——docker run myapp --port 4000 會把 --port 4000 當作 ENTRYPOINT 的參數傳入,而不是替換它;若要替換 ENTRYPOINT 本身,需明確加上 --entrypoint 旗標,例如 docker run --entrypoint sh myapp。
常見模式:ENTRYPOINT 設主程式,CMD 設預設參數。例如: ENTRYPOINT ["node"] 配上 CMD ["app.js"]。

其他常用 Dockerfile 指令:

  • ENV NODE_ENV=production:設定環境變數,建置期與執行期都有效。
  • ARG VERSION=1.0:僅建置期有效的參數,可用 docker build --build-arg VERSION=2.0 覆蓋。
  • USER appuser:切換執行身份(安全章節詳述)。
  • VOLUME ["/data"]:宣告一個 volume 掛載點(啟動容器時自動建立匿名 volume)。
  • HEALTHCHECK CMD curl -f http://localhost:3000/health || exit 1:定義健康檢查指令。

映像分層與快取:加速建置的關鍵

Docker 映像是由多個「層(layer)」堆疊而成的——每條 RUN、COPY、ADD 指令都會產生一個新層。層是內容定址(content-addressed)的: Docker 用每層的內容 SHA256 雜湊作為快取鍵。 只要輸入內容不變,同一層就可以從快取直接取用,不需要重新執行。

但快取有一個關鍵規則:某層快取失效,它之後的所有層都必須重建。 這就是為什麼 Dockerfile 的指令順序至關重要。

🔑
快取友善 Dockerfile 的黃金規則

「變動頻率低的放前面,變動頻率高的放後面。」
FROM 基礎映像 → 安裝系統工具 → 複製依賴清單(package.json / requirements.txt / go.mod) → 安裝依賴 → 複製應用程式碼。
依賴通常很少改,快取可長期有效;程式碼改動頻繁,但它後面沒有耗時步驟,重建成本低。

另一個常見的「肥層」問題:在 RUN 安裝工具後忘記清除快取:

# ❌ 錯誤:apt 快取被永遠固化在層裡,映像變大
RUN apt-get update
RUN apt-get install -y curl

# ✓ 正確:在同一條 RUN 指令內清除,快取不進入層
RUN apt-get update && \
    apt-get install -y curl && \
    rm -rf /var/lib/apt/lists/*
⚠️
為何要在同一條 RUN 清除快取?

每條 RUN 生成一個獨立的層。如果在第一條 RUN 安裝後留下 apt 快取, 即使在後面一條 RUN rm -rf /var/lib/apt/lists/* 清掉, 快取的位元組仍存在於先前那個層裡——映像的總大小不縮小。 OverlayFS 的「刪除」只是在上層建立 whiteout 節點(第 87 章解釋過), 底層資料還在。把安裝和清除放在同一條 RUN 才能讓層不含快取。

多階段建置:把映像從幾百 MB 縮到幾十 MB

編譯型語言(Go、Rust、Java、TypeScript)有一個尷尬的問題: 建置工具只有建置時需要,但如果用同一個映像執行應用程式, 那些編譯器、linker、dev dependencies 就永遠跟著映像走——徒增映像大小和攻擊面。

多階段建置(multi-stage build) 讓你在同一份 Dockerfile 裡使用多個 FROM, 每個 FROM 是一個獨立的建置階段。最終映像只包含最後一個階段——用 COPY --from 把前面階段的產出物(binary、bundle)複製進來,整個編譯工具鏈都留在中間階段,不進最終映像。 

# ── Go 應用程式多階段建置範例 ────────────────────────────
# 第一階段:build stage — 用完整的 Go 工具鏈編譯
FROM golang:1.22-alpine AS builder

WORKDIR /src
# 先複製 go.mod / go.sum,快取 go mod download
COPY go.mod go.sum ./
RUN go mod download

# 複製程式碼並編譯靜態 binary
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /app/server ./cmd/server

# ──────────────────────────────────────────────────────────
# 第二階段:final stage — 用極小的 distroless 映像
FROM gcr.io/distroless/static:nonroot AS final

# 從 builder 複製編譯好的 binary
COPY --from=builder /app/server /server

# distroless/nonroot 預設以非 root 使用者執行
EXPOSE 8080
ENTRYPOINT ["/server"]

效果對比:完整 Go 工具鏈映像約 350 MB;最終 distroless 映像通常在 10–20 MB 之間。 攻擊面大幅縮小——distroless 連 shell 都沒有。

💡
AS 命名讓 COPY --from 更清晰

FROM golang:1.22-alpine AS builder 中的 AS builder 給這個階段取了名字,之後可用 COPY --from=builder 引用。 也可用數字 COPY --from=0(第一個 FROM)——但用名字更易維護。 docker build --target builder . 可只建置到指定階段,方便除錯中間產物。

容器生命週期:run / ps / exec / logs / stop / rm

映像建好之後,真正的工作才開始。以下是容器日常操作的完整指令圖鑑: 

# ── 建置映像 ───────────────────────────────────────────
docker build -t myapp:latest .
# -t myapp:latest  為映像打標籤(name:tag)
# .               Dockerfile 所在目錄(build context)

# ── 執行容器 ───────────────────────────────────────────
docker run -d -p 3000:3000 --name web myapp:latest
# -d              背景執行(detached)
# -p 3000:3000    host:container 埠對應
# --name web      為容器命名(方便後續引用)

# 互動模式(進入容器 shell 除錯)
docker run --rm -it myapp:latest sh
# --rm            容器停止後自動刪除
# -it             分配 TTY 並保持 stdin 開啟

# ── 查看執行中的容器 ────────────────────────────────────
docker ps             # 執行中的容器
docker ps -a          # 所有容器(含已停止)

# ── 進入執行中的容器 ────────────────────────────────────
docker exec -it web sh
# exec 不建立新容器,而是在現有容器的 namespace 裡開 shell

# ── 查看日誌 ────────────────────────────────────────────
docker logs web             # 查看容器輸出
docker logs -f web          # 持續追蹤(-f = follow)
docker logs --tail 50 web   # 只看最後 50 行

# ── 停止與刪除 ──────────────────────────────────────────
docker stop web       # 發送 SIGTERM,等 10 秒後 SIGKILL
docker kill web       # 立即發送 SIGKILL
docker rm web         # 刪除已停止的容器
docker rm -f web      # 強制刪除執行中的容器(stop + rm)

# ── 映像管理 ────────────────────────────────────────────
docker images            # 列出本地映像
docker rmi myapp:latest  # 刪除映像
docker pull nginx:alpine # 從 registry 拉取映像
docker push myapp:latest # 推送映像到 registry
ℹ️
docker exec 的底層原理

docker exec -it web sh 的底層是:找到容器 web 的各個 namespace inode, 然後用 setns() 系統呼叫加入那些 namespace,再 exec sh。 因此 exec 開的 shell 和容器的 PID 1 在同一個 namespace 集合裡—— 能看到同樣的行程、網路、檔案系統。這是在第 87 章 介紹過的 setns() 的實際應用。

資料持久化:volume 與 bind mount

你已經知道容器有一個可寫層(OverlayFS upperdir)——但在第 87 章 我們看到,這個可寫層是容器的一部分。容器刪除,可寫層隨之消失。 對於需要持久化的資料(資料庫、上傳的檔案、日誌),我們需要把儲存移到容器的 namespace 外面。

Docker 提供兩種持久化方案:

VolumeBind Mount
儲存位置 /var/lib/docker/volumes/名稱/_data(由 Docker 管理) Host 上任意路徑(由你指定)
建立方式 docker volume create mydata 或 -v mydata:/app/data -v /host/path:/container/path
適合場景 資料庫持久化、container 間共享資料 開發時把 host 原始碼掛進容器(hot reload)
可攜性 跨 OS 一致(Docker 管理路徑) 依 host 路徑,Windows/Mac 路徑不同 
# ── Volume 操作 ─────────────────────────────────────────
# 建立命名 volume
docker volume create pgdata

# 使用 volume 跑 PostgreSQL(資料庫資料持久化)
docker run -d \
  --name postgres \
  -e POSTGRES_PASSWORD=secret \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16-alpine

# 列出所有 volume
docker volume ls

# 查看 volume 詳情(包含實際路徑)
docker volume inspect pgdata

# 刪除容器後 volume 仍然保留
docker rm -f postgres
docker volume ls      # pgdata 還在

# 刪除 volume
docker volume rm pgdata

# ── Bind Mount(開發用途)──────────────────────────────
# 把 host 的 ./src 掛進容器 /app/src,方便即時看到程式碼改動
docker run -d \
  -p 3000:3000 \
  -v "$(pwd)/src:/app/src" \
  myapp:dev
⚠️
匿名 volume 的陷阱

如果 Dockerfile 裡有 VOLUME ["/data"],或 docker run -v /data 沒有指定名稱,Docker 會建立一個匿名 volume——名稱是一串 UUID。 容器刪除後,匿名 volume 預設不自動清除(除非 docker rm -v), 隨時間累積會佔用大量磁碟空間。定期執行 docker volume prune 清除無主 volume。

網路:bridge / host / none、埠對應、容器間互連

在第 88 章的 mydocker 裡, 我們手動用 veth pair + bridge 搭建了容器網路。Docker 把這個流程自動化了, 並提供三種預設的網路驅動:

  • bridge(預設):Docker 在主機上建立虛擬網橋 docker0, 容器加入這個網橋——和第 88 章手動建的 br0 是同一個概念。 容器有自己的 IP(預設 172.17.0.0/16),靠 -p 把埠公開給主機。
  • host:容器直接使用主機的網路 namespace——沒有網路隔離, 容器監聽 80 埠就是主機的 80 埠。效能最好,但隔離最差。
  • none:容器只有 loopback,完全沒有外部網路。 適合不需要網路的計算容器。
# ── 預設 bridge 網路 ────────────────────────────────────
docker run -d -p 8080:80 nginx
# -p 8080:80:把 host 的 8080 埠對應到容器的 80 埠
# curl http://localhost:8080 可以打到容器內的 nginx

# ── host 網路 ───────────────────────────────────────────
docker run -d --network host nginx
# 直接用主機網路,nginx 監聽 host 的 80 埠

# ── none 網路 ───────────────────────────────────────────
docker run --rm --network none alpine ping google.com
# ping: google.com: Name or service not known (無網路)

# ── 查看網路 ────────────────────────────────────────────
docker network ls
docker network inspect bridge

容器間以名稱互連:user-defined bridge

預設的 docker0 bridge 有一個限制:容器只能靠 IP 位址互相存取, 不支援以容器名稱解析。要讓 web 容器直接用 db 這個名稱連到資料庫, 需要建立一個 user-defined bridge network: 

# 建立自訂網路
docker network create mynet

# 把兩個容器都加入這個網路
docker run -d --name db --network mynet postgres:16-alpine
docker run -d --name web --network mynet -p 3000:3000 myapp:latest

# 現在 web 容器可以用 db 這個名稱連到 PostgreSQL
docker exec -it web sh
# /app # psql -h db -U postgres   (用容器名稱解析!)
🔑
User-defined bridge 的 DNS 解析

Docker 在 user-defined bridge 上啟動了一個內嵌的 DNS 解析器(通常在 127.0.0.11)。 容器的 /etc/resolv.conf 指向這個 DNS, 所以容器名稱可以直接解析成 IP 位址。 預設的 docker0 不支援這個功能——這是建議用 Compose 或手動建 user-defined network 的主要原因之一。

Docker Compose:用 YAML 宣告多容器服務

當你的應用程式有多個容器(web、db、cache、worker……), 每次手動 docker run 一個一個啟動既繁瑣又容易出錯。 Docker Compose 讓你把整個多容器環境宣告在一份 docker-compose.yml 裡, 一個指令啟動、停止或重建所有服務。 

# docker-compose.yml — web app + PostgreSQL 資料庫範例
services:
  web:
    build: .                # 從當前目錄的 Dockerfile 建置
    ports:
      - "3000:3000"         # host:container
    environment:
      - NODE_ENV=production
      - DATABASE_URL=postgres://postgres:secret@db:5432/mydb
    depends_on:
      db:
        condition: service_healthy   # 等 db 健康檢查通過才啟動 web
    networks:
      - appnet

  db:
    image: postgres:16-alpine
    environment:
      - POSTGRES_PASSWORD=secret
      - POSTGRES_DB=mydb
    volumes:
      - pgdata:/var/lib/postgresql/data   # 持久化資料庫資料
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5
    networks:
      - appnet

volumes:
  pgdata:          # 命名 volume,由 Docker 管理

networks:
  appnet:
    driver: bridge
ℹ️
Docker Compose V2 不再需要 version 欄位

現代 Docker Compose V2 已把 version 視為純資訊性、官方建議省略。 舊版 schema 標記寫了也只是資訊性,直接從 services: 開始即可。 本章其他 Compose 範例也都移除了 version 欄位。 

# ── Compose 常用指令 ────────────────────────────────────
docker compose up -d           # 在背景啟動所有服務
docker compose up --build      # 強制重新 build 後啟動
docker compose down            # 停止並刪除容器(volume 保留)
docker compose down -v         # 同上,並刪除 volume(資料會消失!)
docker compose ps              # 查看服務狀態
docker compose logs -f web     # 追蹤 web 服務的日誌
docker compose exec web sh     # 進入 web 容器的 shell
docker compose restart web     # 重啟 web 服務
ℹ️
docker compose vs docker-compose

較新版本的 Docker Desktop 和 Docker Engine 把 Compose 整合進 Docker CLI, 指令是 docker compose(中間沒有 hyphen)。 舊版的獨立安裝是 docker-compose(V1,用 Python 寫)。 V2 版本(docker compose)效能更好,語法相容,建議優先使用 V2。

⚠️
depends_on 不等於等待服務就緒

depends_on 預設只保證容器的啟動順序——db 容器啟動後 web 才啟動。 但「容器啟動」不等於「PostgreSQL 就緒可以接受連線」。 加上 condition: service_healthy 搭配 healthcheck 才能確保 web 在 db 真正就緒後才開始。 若應用程式沒有此機制保護,應在程式內加入連線失敗重試邏輯。

動手:把 Flask + Redis 應用容器化並用 Compose 一鍵起

現在把前面學到的所有工具組合起來,實際容器化一個「有 web 服務和快取」的小型應用。 範例包含:Flask web app(Python)+ Redis(計數器)。

Step 1:應用程式程式碼

# app.py — 計次器 API,每次 GET / 把 Redis 的 counter 加 1
from flask import Flask
import redis
import os

app = Flask(__name__)

# 從環境變數取得 Redis 主機名稱(預設 redis,對應 compose service 名稱)
r = redis.Redis(host=os.getenv("REDIS_HOST", "redis"), port=6379, decode_responses=True)

@app.route("/")
def index():
    count = r.incr("counter")   # INCR 是原子操作,執行緒安全
    return f"你好!這個頁面已被訪問 {count} 次。\n"

if __name__ == "__main__":
    # app.run() 是 Flask 內建的開發伺服器
    # 生產環境應改用 gunicorn 或 uvicorn 等 WSGI/ASGI 伺服器
    app.run(host="0.0.0.0", port=5000)
# requirements.txt
flask==3.0.3
redis==5.0.4

Step 2:Dockerfile(快取友善 + 非 root)

FROM python:3.12-slim

# 建立非 root 使用者(安全最佳實踐)
RUN groupadd -r appgroup && useradd -r -g appgroup appuser

WORKDIR /app

# 先複製依賴清單,充分利用層快取
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

# 複製應用程式碼
COPY app.py ./

# 切換到非 root 使用者
USER appuser

EXPOSE 5000
CMD ["python", "app.py"]

💡
開發 vs 生產的 Compose 分層

生產與開發環境通常有不同設定(開發時掛 bind mount 熱重載,生產時用建置好的映像)。 常見做法:用 docker-compose.yml(基礎設定)+ docker-compose.override.yml(開發覆蓋)。 docker compose up 會自動合併兩個檔案。 生產環境用 docker compose -f docker-compose.yml -f docker-compose.prod.yml up 明確指定。

最佳實踐與安全:小映像、非 root、.dockerignore、別把祕密寫進映像

容器化的生產環境有幾個安全紀律是必須遵守的。

1. 用最小基礎映像

映像越小,攻擊面越小、掃描速度越快、部署越快。 選擇優先順序:scratch(最小,僅適合靜態 binary)、 distroless(無 shell,適合靜態語言)、 alpine(~5 MB,適合動態語言)、 slim 變體,最後才是完整發行版。

2. 非 root 使用者(USER 指令)

⛔
別讓容器以 root 身份執行應用程式

預設情況下,容器內的行程以 root(uid=0)執行。 雖然有 namespace 隔離,但容器逃逸漏洞一旦發生(如第 87 章所說, namespace 不等於 VM 等級安全邊界),容器內的 root 可能等同主機 root。 一定要在 Dockerfile 建立並切換到非 root 使用者。 

# ✓ 正確做法:建立並切換到非 root 使用者
RUN groupadd -r appgroup && useradd -r -g appgroup --no-create-home appuser
USER appuser

3. .dockerignore

.dockerignore 的作用類似 .gitignore:告訴 Docker daemon 在 build context 傳輸時忽略哪些檔案。常見必排除的項目: .git/、.env、node_modules/、*.log、 測試目錄、IDE 設定等。好的 .dockerignore 可以讓 build context 從幾 GB 縮到幾十 MB, 大幅加速 docker build。

4. 絕對不要把祕密(secret)寫進映像

⛔
映像層是永久記錄——祕密一旦進入,很難完全清除

ENV API_KEY=sk-prod-abc123 會把 API key 永遠固化在映像層裡—— 即使後面的層用 unset 清掉,也可以用 docker history 或直接解開層 tarball 挖出來。
正確做法:祕密在執行時透過環境變數注入(docker run -e API_KEY=... 或 Compose 的 env_file: .env),或使用 Docker secrets / HashiCorp Vault 等祕密管理系統。 建置期確實需要祕密(如私有 npm registry token)時,用 docker build --secret(BuildKit) 掛載臨時檔案,不進任何層。

5. 定期掃描映像漏洞

# Docker Scout(官方,需登入 Docker Hub)
docker scout cves myapp:latest

# 開源替代:Trivy(Aqua Security)
trivy image myapp:latest

6. 預告:Kubernetes 與更大的編排世界

Compose 適合單機的多容器環境。當你的服務需要跨多台主機、自動水平擴展、 滾動更新、自我修復——這就是第 90 章 Kubernetes 登場的時機。 Kubernetes 把 Pod(一組容器)作為最小調度單位, 用 Deployment、Service、Ingress 等資源描述你的整個雲原生架構。 你在這一章學到的 Dockerfile 和映像技能在 Kubernetes 裡完全適用—— 只是容器的「管理者」從 Compose 換成了 K8s 的 control plane。

在後面的章節,容器化技術也會應用到 AI agent 的工具執行隔離—— 讓大型語言模型呼叫工具時,每次執行都在一個全新的容器沙箱裡安全運行, 實現第 106 章容器化 agent 的核心安全機制。

✏️ 練習 89.1 實作

為以下 Python 程式寫一份 Dockerfile,要求:
(a) 使用 python:3.12-slim 作為基礎映像;
(b) 指令順序要能充分利用層快取——改 hello.py 不觸發 pip install;
(c) 以非 root 使用者執行。
完成後,用 docker build 建置,修改 hello.py 後再次建置, 觀察哪些層顯示 CACHED。 

# hello.py
print("Hello from container!")
# requirements.txt
requests==2.32.3
看解答 
FROM python:3.12-slim

# 建立非 root 使用者
RUN groupadd -r app && useradd -r -g app appuser

WORKDIR /app

# 先複製依賴清單(快取友善:改 hello.py 不影響這層)
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

# 複製程式碼
COPY hello.py ./

USER appuser
CMD ["python", "hello.py"]

建置與驗證:

docker build -t hello:v1 .
# 修改 hello.py 的輸出文字
docker build -t hello:v2 .
# 觀察:RUN pip install 那層仍顯示 CACHED
# 只有 COPY hello.py ./ 和之後的層重建

這驗證了「先 COPY requirements.txt → RUN pip install → COPY 程式碼」 的快取友善順序——pip install 只在 requirements.txt 改變時才重跑。

寫一份 docker-compose.yml,跑起以下三個服務:
(a) nginx(nginx:alpine)作為反向代理,監聽 host 的 8080 埠;
(b) app(用你自己的 Dockerfile 建置,監聽 5000 埠,只在內網公開,不直接對外);

三個服務都在同一個 appnet 網路裡;app 需要在 redis 之後啟動。

services:

    image: nginx:alpine

  app:

✏️ 練習 89.3 思考

你的同事把以下 Dockerfile 交給你 review: 

FROM node:20

COPY . .
RUN npm install
ENV API_KEY=sk-prod-abc123secretkey
RUN npm run build
CMD ["node", "dist/server.js"]

列出這份 Dockerfile 至少五個問題,說明每個問題的原因與修正方式。

看解答
  1. 基礎映像太肥:使用 node:20 而非 node:20-alpine。 完整 Debian 映像約 1 GB;alpine 版本約 120 MB。修正:改用 FROM node:20-alpine。
  2. 快取順序錯誤:COPY . . 在 RUN npm install 之前。 每次修改任何程式碼都導致 npm install 重跑。 修正:先 COPY package*.json ./ 再 RUN npm install,最後 COPY . .。
  3. 祕密寫進映像:ENV API_KEY=sk-prod-abc123secretkey。 API key 被固化在映像層裡,docker history 就能看到。 修正:移除這行,改在 docker run -e API_KEY=... 或 Compose 的 env_file 注入。
  4. 沒有切換到非 root 使用者。 容器以 root 執行應用程式有安全風險。 修正:加入 RUN groupadd -r app && useradd -r -g app appuser 並在 CMD 前加 USER appuser。
  5. 沒有多階段建置。 node_modules、npm、build 工具等都進了最終映像,徒增大小與攻擊面。 修正:用多階段建置——build 階段編譯,final 階段只複製 dist/ 和 production node_modules。
  6. 沒有 .dockerignore。 COPY . . 會把 node_modules/、.git/、.env 一起複製進去,既肥又有安全風險。 修正:建立 .dockerignore 排除這些目錄與檔案。

把這一章串起來

這一章從「你已手寫過 runtime」出發,把工具鏈的每一層都對應到底層機制:

工具 / 概念底層機制(§87/§88)本章關鍵重點
映像層 OverlayFS lowerdir — 唯讀疊層 快取友善排序:變動少的放前面
容器 namespace + cgroup + OverlayFS upperdir run / exec / logs / stop / rm 完整生命週期
Volume 繞過 upperdir,直接掛載到 Docker 管理路徑 命名 volume vs bind mount;不要用匿名 volume
網路 bridge veth pair + 虛擬 bridge + iptables NAT user-defined network 才支援名稱 DNS 解析
Compose 宣告式描述多容器環境 depends_on + healthcheck;volumes;networks
安全 capabilities 收縮、namespace 不等於 VM 安全 非 root、.dockerignore、祕密不進映像

Docker 把第 88 章手寫的那兩百行系統呼叫包裝成友善的 CLI—— 但你現在知道每條指令背後在做什麼: docker run 是 clone() + pivot_root + execvp; docker build 是把每條 Dockerfile 指令固化成 OverlayFS 的一個唯讀層; 容器間的 DNS 解析是 Docker 在 user-defined bridge 上植入的 DNS server。 有了這層理解,你排查問題、調效能、評估安全的能力都比只會用 CLI 的人強得多。
