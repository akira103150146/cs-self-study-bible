⚠️
誠實標示：這是教學用最小版本（non-production OS）

這一章是導引式精簡核心，教學用最小版本，非生產級作業系統。我們不從頭造完整的 OS——那需要幾年、數十萬行程式碼、嚴格的硬體測試。我們的目標是：跟著 blog_os（Philipp Oppermann 的《Writing an OS in Rust》）的路線，理解「一顆核心如何從開機到印出第一行字」的關鍵骨幹。本章節錄關鍵程式碼讓你看見形狀；完整的可跑專案請移步 os.phil-opp.com。

在前五章的 Rust 旅程裡——第 79 章的所有權、第 80 章的型別、第 81 章的資料結構、第 82 章的無懼並行、第 83 章的實戰 CLI——你的程式都站在一個「溫暖的環境」裡：有作業系統幫你管記憶體、有標準函式庫幫你做 I/O、有執行環境幫你設好 heap 分配器。

現在，我們要把這一切抽掉。

想像你剛按下開機鍵，CPU 醒來，執行的第一行程式碼是韌體（BIOS 或 UEFI）；韌體跑完它的初始化，把控制權交給 bootloader；bootloader 載入你的核心，然後……跳進 _start。你的程式就從那個跳躍點開始。

這個跳躍點的環境是：

  • 沒有作業系統（因為你就是作業系統）
  • 沒有 C 標準函式庫、沒有 Rust 標準函式庫（std）
  • 沒有 heap 分配器——你必須自己架設，或者根本不用 heap
  • 沒有 stack 溢出保護、沒有 ASLR、沒有任何 OS 的安全網
  • 但你有：全部的 CPU 暫存器、全部的記憶體，以及完全的掌控

這就是 bare-metal（裸機）程式設計，或稱 freestanding（獨立式）程式——你的程式不依賴任何作業系統或執行環境。Rust 的類型系統和 no_std 機制，讓這件事比在 C 裡做要安全得多，但仍然需要你非常小心。

🔑
OS 也是程式，只是沒有 OS 幫它

作業系統核心的本質，是一個在開機後第一個取得 CPU 控制權的程式。它不能呼叫 println!，不能用 malloc，不能呼叫系統呼叫——因為這些東西都是 OS 才能提供的，而 OS 就是它自己。這是整個 OS 設計最根本的遞迴：核心必須先架好自己需要的一切，才能提供給別人用。

#![no_std]：核心不能用標準庫，只能用 core

Rust 的標準函式庫（std）依賴作業系統——它使用 OS 的系統呼叫（syscalls）來做執行緒、I/O、記憶體分配等。在 bare-metal 環境裡，根本沒有 OS，所以 std 裡的大多數東西都無法使用。我們在檔案頂端加一行宣告，告訴 Rust 編譯器不要連結 std： 

// src/main.rs — 最小 no_std 核心骨架
#![no_std]    // 不連結 Rust 標準函式庫（std）
#![no_main]   // 停用 Rust 的 main 包裝入口（它依賴 std 的初始化）

去掉 std 之後，你仍然有 core——Rust 標準函式庫的「純語言子集」。core 不依賴 OS，提供基本型別（Option、Result、切片、迭代器等），是 bare-metal 程式設計的基石。

強制要求：自訂 panic handler

當你去掉 std，Rust 就失去了預設的 panic 處理器（它通常會印出訊息然後結束行程）。你必須提供自己的 panic_handler，否則程式根本不能編譯： 

use core::panic::PanicInfo;

/// panic handler：no_std 的強制要求
/// 當程式碼發生 panic 時，Rust 編譯器會呼叫這個函式
/// -> ! 表示這個函式「永遠不會回傳」（diverging function）
#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {
    // 在最小核心裡：進入無限迴圈（bare metal 沒有 OS 可以 exit）
    // 正式核心通常會：印出 panic 訊息到序列埠、停機（hlt 指令）
    loop {}
}

停用 main，改用 _start 入口

Rust 的 main 函式其實不是真正的程式進入點——它被 Rust 執行環境（runtime）包了一層，負責設定 stack、初始化 std、呼叫 main、再做善後清理。這個包裝層依賴 std，我們用 #![no_main] 把它關掉，然後直接定義連結器（linker）真正要找的進入點 _start： 

/// 核心真正的入口點
/// 連結器（linker）預設尋找名為 _start 的符號作為程式入口
///
/// #[no_mangle]：禁止 Rust 對這個函式的名稱做任何修改（name mangling）
///   Rust 預設會把函式名稱改成類似 _ZN4main4core5_start7h1a2b3c 的形式
///   加上 #[no_mangle] 才能讓連結器找到「_start」這個名稱
///
/// extern "C"：使用 C 語言的呼叫約定（calling convention）
///   確保與 bootloader 傳來的呼叫方式相容
#[no_mangle]
pub extern "C" fn _start() -> ! {
    // 這裡就是核心的起點：什麼都還沒準備好
    // 後面幾節會在這裡逐步加入 VGA 輸出、中斷初始化等
    loop {}
}
🔑
三個必知屬性：no_mangle、extern "C"、panic_handler

#[no_mangle] 讓連結器能找到你的函式；extern "C" 確保 ABI（應用程式二進位介面）相容；#[panic_handler] 告訴 Rust 運行時「panic 時呼叫我」。這三個屬性在 bare-metal Rust 裡無處不在——每次看到，都要記住它們解決的是「在沒有 OS 的世界裡如何讓函式能被找到並被正確呼叫」這個基礎問題。

cargo 設定：自訂目標與 panic 策略

bare-metal 核心需要告訴 Cargo 「編譯給哪個目標」，以及 panic 時採「立即中止」而非「堆疊展開」（stack unwinding）——因為展開需要 OS 支援： 

# Cargo.toml（片段）
[profile.dev]
panic = "abort"     # panic 時直接中止；不做 stack unwinding（需要 OS）

[profile.release]
panic = "abort"     # release build 同樣中止

# .cargo/config.toml
[build]
target = "x86_64-unknown-none"   # 編譯目標：x86_64 架構、沒有 OS（none）

x86_64-unknown-none 是 Rust 的「裸機 x86_64 目標」：x86_64 架構（64-bit Intel/AMD）、廠商未知、沒有作業系統（none）。這讓 Rust 工具鏈知道：不要連結任何 OS 相關的程式庫。

開機流程：從韌體到核心入口

你按下電源鍵，到你的核心的 _start 被呼叫，中間發生了一系列精心設計的「接力」。理解這個接力，是理解「為何 bare-metal 程式必須做那麼多準備工作」的前提。

BIOS 時代的開機（x86 傳統）

在傳統 BIOS 模式下，韌體在 POST 後讀取磁碟第一個磁區（512 bytes，稱為 MBR——主開機記錄 Master Boot Record），載入到實體位址 0x7c00，然後跳轉執行。這 512 bytes 就是 bootloader 的第一段，它的工作是：把 CPU 從 16-bit real mode 切換到 32-bit protected mode，再切換到 64-bit long mode，設好基本分頁表，然後把核心從磁碟讀進來並跳過去。

在第 21 章，我們看過 CPU 的取指-解碼-執行週期。這個過程從開機的那一刻就開始了——只是一開始的指令是韌體的，而不是你的。

blog_os 的簡化：bootimage crate

把 bootloader 從零寫起本身就是一個大工程（需要 16-bit 組合語言）。blog_os 提供了 bootloader crate 和 bootimage 工具，幫我們把這層封裝好。cargo bootimage 指令會把你的核心和 bootloader 合併成一個可開機的磁碟映像（disk image），你只需要用 QEMU 載入它就能跑。這讓我們能直接聚焦在 _start 之後的部分——那才是真正的核心邏輯。

印出第一行字：VGA 文字緩衝區

在 bare-metal 環境裡，沒有 println!，沒有標準輸出（stdout）。最早、最簡單的輸出方式，是直接寫入 VGA 文字緩衝區（VGA text buffer）——一塊在 x86 架構上位於實體位址 0xb8000 的記憶體，顯示卡會定期讀取這塊記憶體的內容，然後顯示在螢幕上。

VGA text buffer 的格式

VGA 文字模式的螢幕是 80 欄 × 25 列 = 2000 個字元格。每個字元格佔 2 bytes：

  • 位元組 0（低位元組）：字元的 ASCII 碼（例如 0x48 = 'H'）
  • 位元組 1（高位元組）：屬性位元組（attribute byte）
    • Bits 3–0：前景色（foreground color），16 種顏色
    • Bits 6–4：背景色（background color），8 種顏色
    • Bit 7：閃爍 blink（或高亮背景，視模式而定）

因此，整個 VGA 文字緩衝區的大小是 80 × 25 × 2 = 4000 bytes。要在第 row 列、第 col 欄印出一個字元，位元組偏移量（offset）是 (row * 80 + col) * 2。

常用屬性值：0x0f = 黑底（背景色 0 = black）白字（前景色 0xf = white）；0x0a = 黑底亮綠字；0x4f = 紅底白字。

直接寫記憶體：unsafe 是必要的

// src/vga.rs — VGA 文字輸出的最小實作（節錄自 blog_os 路線）

/// VGA 文字緩衝區的實體位址（x86 傳統映射）
/// 在 bootloader 設好分頁後，這個位址在核心的虛擬位址空間中也能直接存取
const VGA_BUFFER: *mut u8 = 0xb8000 as *mut u8;

/// 在螢幕第 row 列、第 col 欄，寫入字元 byte，顏色屬性 attr
///
/// # Safety
/// - VGA_BUFFER 是原始指標（raw pointer），沒有 Rust 的借用檢查保護
/// - 呼叫者必須確保 row < 25、col < 80（否則會越界寫入其他記憶體）
/// - write_volatile 告訴編譯器「此寫入有硬體副作用，不可最佳化掉」
pub unsafe fn vga_write_char(row: usize, col: usize, byte: u8, attr: u8) {
    let offset = (row * 80 + col) * 2; // 每字元 2 bytes；第 row 列第 col 欄
    // write_volatile：確保每次寫入都真正送出，不被編譯器的最佳化省略
    VGA_BUFFER.add(offset).write_volatile(byte);        // 位元組 0：ASCII 碼
    VGA_BUFFER.add(offset + 1).write_volatile(attr);    // 位元組 1：顏色屬性
}

/// 從第 0 列印出一條訊息（最多 80 個字元）
pub fn print_hello() {
    let msg = b"Hello, Kernel!";   // b"..." 是 byte string literal，型別 &[u8; N]
    for (col, &byte) in msg.iter().enumerate() {
        // SAFETY：row=0, col < 14 < 80，位址合法
        unsafe { vga_write_char(0, col, byte, 0x0f); }  // 0x0f = 黑底白字
    }
}

// 在 _start 中呼叫：
// #[no_mangle]
// pub extern "C" fn _start() -> ! {
//     print_hello();
//     loop {}
// }
⚠️
為何一定要用 write_volatile？

Rust（以及 C/C++）的編譯器可能「最佳化掉」看起來沒有被讀回的記憶體寫入——它不知道 VGA 顯示卡會從那個位址讀資料。write_volatile 告訴編譯器：「這個寫入有外部副作用（side effect），請保留每一次寫入，不要合併或省略。」若改用普通的指標解參考 *ptr = byte，編譯器在 --release 最佳化下可能把所有寫入都省略掉，螢幕一片空白。

整段 VGA 寫入程式碼用了 unsafe，因為：

  1. 原始指標解參考（raw pointer dereference）：*mut u8 指標不受 borrow checker 保護，越界就寫壞記憶體。
  2. 無任何對應分配（no allocation）：這個位址是硬體映射，不是 Rust 的記憶體分配器管的——呼叫者必須自己保證位址正確。
  3. 可能的別名（aliasing）：多段程式碼可能同時持有指向同一塊 VGA 緩衝區的 *mut u8，違反 Rust 的「同一時間只能有一個可變參考」規則，但硬體限制讓我們別無選擇，只能用 unsafe 並自己管理存取順序。

呼應第 79 章的 borrow checker 概念：在安全 Rust 裡，編譯器幫你確保不會有懸空指標或別名問題。但在核心的 bare-metal 層，硬體世界裡這些規則本來就不存在，unsafe 區塊是你對編譯器說「我知道我在做什麼，請讓我做」的聲明。

✏️ 練習 84.1 思考

在 no_std 的核心程式碼裡，無法使用 println! 巨集。請解釋：

  1. 為何 println! 在 no_std 環境不可用？它依賴了哪些 OS 功能？
  2. 在最小 Rust 核心裡，若想「印出一段訊息」，有哪些替代方案？請舉出至少兩種。
看解答

1. println! 依賴 std 的原因：

println! 最終呼叫 std::io::stdout().write()，而 stdout() 是透過作業系統的 write 系統呼叫（syscall）把資料送到檔案描述符 1（standard output）。在 bare-metal 核心裡，根本沒有 OS，也沒有檔案描述符的概念，std::io 無從使用，所以 println! 無法存在。#![no_std] 宣告後，println! 連定義都沒有，直接編譯錯誤。

2. 替代方案：

  • VGA 文字緩衝區（本章的做法）：直接用 unsafe 寫入 0xb8000，顯示卡會把這塊記憶體顯示在螢幕上。速度快、不需任何初始化，但只支援 80×25 字元的文字模式。
  • 序列埠輸出（serial port/UART）：透過 x86 的 I/O 指令（out 指令）寫入序列埠暫存器（如 COM1 的基址 0x3f8），可以把文字傳到外部終端機或 QEMU 的 serial console。blog_os 後期章節採用這個方式，因為序列埠輸出更可靠、不受 VGA 文字模式限制。

兩種方式都需要 unsafe，因為都是直接操作硬體位址或 I/O 指令。

中斷與例外（Interrupts & Exceptions）：IDT 概念

核心不能只是一個「從頭到尾跑一遍的程式」——它必須能回應外部事件（鍵盤按下、網路封包到達、硬碟讀完）和 處理程式錯誤（除以零、存取非法位址）。這靠的是 CPU 的中斷與例外機制。

CPU 例外（CPU Exceptions）

x86_64 架構定義了一系列由 CPU 自動觸發的「例外（exceptions）」——程式做了 CPU 不允許的事時，CPU 會停止目前的執行，跳到一個預先設好的處理函式去執行。常見例外：

  • #DE（向量 0）除以零（Divide Error）：整數除法分母為零時觸發
  • #BP（向量 3）中斷點（Breakpoint）：執行到 int3 指令時觸發；除錯器用這個
  • #DF（向量 8）雙重錯誤（Double Fault）：處理其他例外時又發生例外
  • #GP（向量 13）一般保護錯誤（General Protection Fault）：各種非法操作
  • #PF（向量 14）分頁錯誤（Page Fault）：存取未映射或無權存取的位址

中斷描述符表（IDT）

CPU 怎麼知道「發生例外時要跳到哪裡」？靠一張叫做 中斷描述符表（Interrupt Descriptor Table，IDT） 的表格。IDT 有 256 個項目（entry），每個項目儲存一個處理函式的位址（以及一些旗標）。當例外或中斷發生時，CPU 用例外/中斷的向量號（0–255）當索引，從 IDT 取出對應處理函式的位址，然後跳過去執行。 

// 使用 x86_64 crate（blog_os 使用的輔助函式庫）設置 IDT
// Cargo.toml: x86_64 = "0.14"
use x86_64::structures::idt::{InterruptDescriptorTable, InterruptStackFrame};

// 靜態 IDT（核心只有一個）
// 注意：在真實 blog_os 中，需要用 lazy_static! 確保靜態初始化安全
static mut IDT: InterruptDescriptorTable = InterruptDescriptorTable::new();

/// 設置 IDT 並載入（在 _start 裡呼叫）
pub fn init_idt() {
    unsafe {
        // 設置 #BP（中斷點）的處理函式
        IDT.breakpoint.set_handler_fn(breakpoint_handler);
        // 設置 #DF（Double Fault）的處理函式
        IDT.double_fault.set_handler_fn(double_fault_handler);
        // lidt 指令：把 IDT 的位址載入 IDTR 暫存器
        IDT.load();
    }
}

/// 中斷點例外處理函式
/// InterruptStackFrame 包含例外發生時的 CPU 狀態（RIP、CS、RFLAGS、RSP、SS）
extern "x86-interrupt" fn breakpoint_handler(stack_frame: InterruptStackFrame) {
    // 在實際 blog_os 中，這裡會把資訊印到序列埠
    // 教學版本：只是在此標示「例外被處理了」
    let _ = stack_frame;
}

extern "x86-interrupt" fn double_fault_handler(
    stack_frame: InterruptStackFrame, _error_code: u64) -> !
{
    // Double Fault 是不可恢復的錯誤，只能停機
    panic!("Double Fault 發生！");
}
ℹ️
extern "x86-interrupt" 呼叫約定

中斷處理函式有特殊的呼叫約定（calling convention）：CPU 在跳入處理函式前，會自動把部分暫存器推到 stack（push to stack），函式結束時用 iretq 指令恢復，而不是普通的 ret。extern "x86-interrupt" 告訴 Rust 編譯器遵守這個約定，讓 Rust 生成正確的 prologue/epilogue。

✏️ 練習 84.2 思考

解釋下列程式碼中，為何 unsafe 是必要的，以及各個屬性的作用： 

const VGA_BUFFER: *mut u8 = 0xb8000 as *mut u8;

#[no_mangle]
pub extern "C" fn _start() -> ! {
    unsafe {
        VGA_BUFFER.write_volatile(b'H');          // 寫入字元 'H'
        VGA_BUFFER.add(1).write_volatile(0x0f);   // 寫入屬性：黑底白字
    }
    loop {}
}

具體回答：

  1. 為何 VGA_BUFFER.write_volatile(b'H') 需要在 unsafe 區塊裡？
  2. #[no_mangle] 的作用是什麼？若沒有它，會發生什麼？
  3. 為何使用 write_volatile 而非普通的指標解參考 *ptr = value？
看解答

1. 為何需要 unsafe：

VGA_BUFFER 是一個原始指標（raw pointer，*mut u8）。在 Rust 中，解參考原始指標（讀或寫其指向的記憶體）必須在 unsafe 區塊裡，因為：

  • 原始指標可能是 null（空指標）
  • 原始指標可能未對齊
  • 原始指標可能指向非法位址（在這裡是 0xb8000，但 Rust 無法靜態驗證這個位址是合法的）
  • 對同一位址可能有多個 *mut 指標同時存在（違反排他可變借用規則）

我們用 unsafe 告訴編譯器：「我知道這些風險，我保證這個位址是有效的 VGA 緩衝區位址。」

2. #[no_mangle] 的作用：

Rust 為了支援泛型、模組、crate 等功能，預設會對函式名稱做「名稱修飾（name mangling）」，把 _start 變成類似 _ZN4mini_kernel6_start17h3a2b4c... 的字串。連結器（linker）在查找程式進入點時，找的是「_start」這個確切名稱；若有名稱修飾，連結器就找不到，程式無法連結。#[no_mangle] 禁止名稱修飾，確保函式名稱保持為 _start。

3. write_volatile vs 普通解參考：

普通的 *ptr = value 寫入，若編譯器判斷「這個值之後沒有被讀取」，可能在 --release 最佳化模式下把它省略掉（dead store elimination）。VGA 緩衝區的寫入是由顯示卡從外部「讀取」的，Rust 編譯器不知道這件事，可能認為這個寫入沒有用處而省略。write_volatile 明確告訴編譯器：「這個寫入有外部副作用，必須保留每一次，不可最佳化掉。」

分頁與虛擬記憶體：核心如何看待位址空間

在第 24 章，我們從 OS 使用者的視角看分頁（paging）——每個行程（process）看到的是一個連續的「虛擬位址空間」，OS 偷偷把虛擬位址對應到實體記憶體的不同地方。這一節，我們從核心開發者的視角看：核心自己是怎麼建立和使用這套分頁機制的。

x86_64 的四層分頁表

x86_64 架構使用四層分頁表（4-level page tables）把 64-bit 虛擬位址對應到實體位址：

  • 虛擬位址共 64 bits，但 x86_64 實際只用低 48 bits（63:48 bits 必須是 bit 47 的符號延伸）
  • 低 48 bits 分成 5 個欄位：PML4 index（9 bits）| PDPT index（9 bits）| PD index（9 bits）| PT index（9 bits）| 頁內偏移（12 bits）
  • 每個 9-bit index = 512 個項目（entry），每個項目 8 bytes = 4096 bytes = 1 個頁面大小
  • 頁面大小：4 KiB（4096 bytes），2^12 = 4096

核心如何建立分頁表

bootloader 在把控制權交給核心之前，已經設好了一個最基本的恆等映射（identity mapping）：虛擬位址 = 實體位址。核心接手後，通常會：

  1. 建立自己的分頁表，把核心程式碼映射到高位址（如 0xffffffff80000000）
  2. 設定 VGA 緩衝區的映射（0xb8000 的虛擬位址對應實體位址 0xb8000）
  3. 為使用者行程的每個 virtual address space 維護各自的分頁表，實現隔離

分頁表項目（page table entry，PTE）除了儲存實體頁框號，還有旗標欄位：Present（此映射是否有效）、Writable（是否可寫）、User Accessible（使用者模式是否能存取）等。核心透過設定這些旗標來實現記憶體保護——使用者行程嘗試存取核心空間，就會觸發 #PF（Page Fault）例外，核心可以安全地終止該行程。

🔑
分頁是 OS 隔離機制的根基

分頁表讓每個行程「以為自己擁有整個位址空間」，而實際上各行程的虛擬位址對應的是不同的實體頁框。這就是第 24 章提到的「虛擬記憶體」——OS 是魔術師，分頁表是那頂帽子。核心開發者要做的，就是親手設計那頂帽子裡的結構。

一個玩具排程器：合作式與搶佔式

作業系統最重要的工作之一，是讓多個程式「同時」跑在有限的 CPU 核心上。這靠的是排程器（scheduler）和 context switch（上下文切換）。

合作式排程（Cooperative Scheduling）

最簡單的排程策略：每個任務自願讓出 CPU。任務呼叫 yield() 函式，告訴排程器「我現在不急，讓別人先跑」；排程器選下一個任務繼續執行。 

任務 A 跑 ... yield() → 排程器 → 任務 B 跑 ... yield() → 排程器 → 任務 A 跑 ...

優點：實作簡單，context switch 只在 yield 點發生，沒有競態問題。 缺點：如果任務 A 進入了一個永無止境的迴圈而忘了 yield，整台機器就卡死——其他任務永遠不會得到 CPU。早期的 Windows（3.x）和 macOS（9 以前）就是合作式排程，因此一個瘋狂的應用程式能凍結整個系統。

搶佔式排程（Preemptive Scheduling）

現代作業系統用的是搶佔式排程：硬體計時器（hardware timer）每隔固定時間（如 10 ms）發出一個中斷，強制切換任務，不管任務願不願意讓出 CPU。 

任務 A 跑 ... [計時器中斷！] → 排程器 → 任務 B 跑 ... [計時器中斷！] → 排程器 → 任務 A 跑 ...

任務感受不到這個切換——切換發生在中斷處理的瞬間，對任務來說好像時間靜止了一下又繼續。

Context Switch：切換任務時發生什麼

切換任務時，排程器必須完整儲存目前任務的「執行狀態」，再載入下一個任務的狀態，讓它從上次停下來的地方繼續。這份狀態稱為 context（上下文），最少包含：

  • 通用暫存器（x86_64 有 16 個：RAX、RBX、RCX、RDX、RSI、RDI、RBP、RSP、R8–R15）
  • 程式計數器（RIP）：下一條要執行的指令位址
  • 旗標暫存器（RFLAGS）：進位、零、符號等條件旗標
  • stack 指標（RSP）：每個任務有自己的 stack
  • CR3 暫存器（若切換到不同行程）：各行程有各自的分頁表

blog_os 的 async/await 排程器

blog_os 後期章節使用 Rust 的 async/await 機制實作了一個簡單的合作式任務排程器（cooperative task executor）——利用 Future 的 poll 機制，讓任務在「等待」時（如等待鍵盤輸入）自動 yield，不需要 OS 級的 context switch 硬體支援。這是在 bare-metal 環境裡嘗試非同步的有趣方法，呼應了第 82 章的 async/await 概念。

在 QEMU 跑起來：工具鏈概觀

在真實硬體上跑自己寫的核心又慢又危險（一個 bug 就能磚掉機器）。開發核心時，標準做法是用 QEMU——一個開源的硬體模擬器——在你的電腦上跑一個「虛擬 x86_64 機器」。

所需工具

# 1. 安裝 Rust nightly（bare-metal 開發需要 nightly 特性）
rustup toolchain install nightly
rustup default nightly

# 2. 加入 x86_64 bare-metal 目標
rustup target add x86_64-unknown-none

# 3. 安裝 bootimage 工具（幫你把核心包成可開機磁碟映像）
cargo install bootimage

# 4. 安裝 QEMU（macOS 用 brew，Ubuntu 用 apt，Windows 用官網安裝包）
brew install qemu           # macOS
apt install qemu-system-x86 # Ubuntu/Debian

Cargo.toml 依賴設定（節錄）

[package]
name    = "mini-kernel"
version = "0.1.0"
edition = "2021"

[dependencies]
bootloader = "0.9"    # 提供 bootloader，讓 bootimage 把它和核心合併

[profile.dev]
panic = "abort"

[profile.release]
panic = "abort"

建置與執行

# 建置：把核心 + bootloader 合併成可開機磁碟映像（.bin）
cargo bootimage

# 用 QEMU 執行（-nographic 把 VGA 輸出重導到終端機，方便 CI）
qemu-system-x86_64 \
  -drive format=raw,file=target/x86_64-unknown-none/debug/bootimage-mini-kernel.bin \
  -nographic

# 或者：在 .cargo/config.toml 設置 runner，之後只需 cargo run
# [target.x86_64-unknown-none]
# runner = "bootimage runner"

執行後，你應該會在 QEMU 視窗（或 -nographic 模式下的終端機）看到： 

Hello, Kernel!

這 14 個字元，是你的程式在「裸機」上，不靠任何作業系統，直接對硬體說的第一句話。感受一下這件事的重量。

💡
除錯技巧：QEMU + GDB

QEMU 支援 GDB remote debugging：加上 -s -S 旗標啟動 QEMU，它會在 TCP port 1234 等待 GDB 連入，並在開機時暫停。然後在另一個終端機用 gdb target/x86_64-unknown-none/debug/mini-kernel 連入，就能設中斷點、單步執行、查看暫存器，像偵測一般程式一樣偵測你的核心。bare-metal 除錯難就難在這裡——你需要的工具，全都要自己架設。

✏️ 練習 84.3 實作

跟著 blog_os（os.phil-opp.com）的前三篇文章，在本地建立一個能在 QEMU 中印出「Hello World」的最小 Rust 核心。請依序回答以下步驟問題：

  1. 你需要在 .cargo/config.toml 裡指定什麼，才能讓 Cargo 編譯到 bare-metal 目標？
  2. src/main.rs 需要哪三個東西（屬性 + 函式）才能通過編譯？
  3. cargo bootimage 和一般的 cargo build 差別在哪裡？
看解答

1. .cargo/config.toml 設定：

# .cargo/config.toml
[build]
target = "x86_64-unknown-none"  # bare-metal x86_64，沒有 OS

[unstable]
# 讓 Cargo 從原始碼重新建置 core 與 compiler_builtins
# 針對我們的裸機目標做最佳化（需要 nightly）
build-std = ["core", "compiler_builtins"]
build-std-features = ["compiler-builtins-mem"]

2. src/main.rs 三個必要元件：

#![no_std]   // ① 屬性：不連結 std
#![no_main]  // ② 屬性：停用 main 包裝

use core::panic::PanicInfo;

// ③-a：panic handler（強制要求）
#[panic_handler]
fn panic(_info: &PanicInfo) -> ! { loop {} }

// ③-b：_start 入口（連結器的進入點）
#[no_mangle]
pub extern "C" fn _start() -> ! {
    // 這裡印出 Hello World（用 VGA 緩衝區寫入）
    loop {}
}

三個必要元件：#![no_std]、#![no_main]、panic_handler。再加上 _start 作為真正的進入點（否則連結器找不到入口）。

3. cargo bootimage vs cargo build 的差別：

cargo build 只把你的 Rust 核心程式碼編譯成一個 ELF 執行檔（或目標碼），但這個 ELF 不能直接開機——它沒有 bootloader，沒有 MBR，x86 韌體不知道怎麼把它載入。

cargo bootimage 做了兩件事：

  1. 先用 cargo build 編譯你的核心
  2. 把 bootloader crate 提供的 bootloader（包含 16-bit 組語、模式切換、基本分頁設定）和你的核心合併，打包成一個可開機的磁碟映像（raw binary，.bin）

最終的 .bin 映像可以直接用 QEMU 的 -drive format=raw 載入，或者 dd 燒到 USB 隨身碟在真實硬體上開機。

把這一章串起來

這一章，我們走過了「一顆 Rust 核心從開機到印出第一行字」的最小骨幹。讓我們把各層的技術棧整理一遍：

  • #![no_std] 與 bare-metal：核心不能依賴作業系統，因為它就是作業系統。#![no_std] 去掉 std，只留 core；#[panic_handler] 和 #[no_mangle] extern "C" fn _start() -> ! 是最小的 bare-metal 骨架。
  • 開機接力：韌體（BIOS/UEFI）→ Bootloader（切換 long mode、設分頁）→ 核心 _start。blog_os 的 bootimage crate 封裝了 Bootloader，讓我們能專注在核心邏輯。
  • VGA 文字緩衝區：實體位址 0xb8000，80×25 字元，每字元 2 bytes（ASCII + 屬性）。直接寫這個位址就能讓螢幕顯示文字——write_volatile 防止編譯器最佳化掉寫入，unsafe 因為這是原始指標操作。
  • 中斷與 IDT：CPU 例外（除以零、分頁錯誤等）靠中斷描述符表（IDT）導引到核心的處理函式。extern "x86-interrupt" 呼叫約定讓 Rust 生成正確的中斷處理框架。
  • 分頁：x86_64 四層分頁表把虛擬位址對應到實體位址，實現隔離與保護。核心建立並維護這張對應表；使用者行程看到的「連續位址空間」是核心施的魔法。
  • 排程：合作式排程（任務自願 yield）實作簡單但脆弱；搶佔式排程（計時器中斷強制切換）是現代 OS 的標配。Context switch 儲存並恢復任務的完整 CPU 狀態。
  • 工具鏈：Rust nightly + x86_64-unknown-none 目標 + bootimage + QEMU——這四件套讓你能在桌機上開發和測試核心，而不必冒著磚掉真實硬體的風險。
「沒有一層抽象是理所當然的。println!、malloc、行程、檔案——這一切都是有人坐下來，從 bare-metal 開始，一層一層疊起來的。」

從 NAND 到 OS 到容器：一條縱向的線

這本書從第 1 部的「計算是什麼」出發，到第 21 章的 CPU 機器語言，到第 24 章的作業系統，再到現在——你用 Rust 親手搭了一個能開機、能印字、能初步理解中斷和分頁的最小核心。這條線，從 NAND 閘到 CPU 到 OS，你已經親眼走了大半。

下一步是什麼？作業系統之上，有容器（container）——Linux namespace 和 cgroup 讓行程「以為自己是獨立的機器」。在未來的第 88 章「手寫迷你 Docker」中，我們將在 OS 之上，用類似的精神手刻容器隔離的骨幹：用 Linux 核心的 clone 系統呼叫建立 namespace，限制資源，讓一個行程活在自己的小宇宙裡——正如分頁讓行程以為自己擁有整個位址空間。

從裸機到 OS 到容器，每一層都在做同樣一件事：把複雜的硬體資源，變成對上層更乾淨、更安全、更好用的抽象。Rust 的角色，是讓這件事在沒有 GC 的前提下，盡可能有保證地做到。

🔑
Rust 在系統程式設計的位置

這一章展示了 Rust 的終極適用場景：在沒有 OS、沒有執行環境、沒有任何安全網的地方，用型別系統和所有權模型把「容易出錯的 unsafe 操作」約束在最小的邊界內，讓其他程式碼能安全地使用。unsafe 不是「Rust 放棄了」，而是「Rust 在這裡信任了你，你要把它的信任用在刀口上」。
