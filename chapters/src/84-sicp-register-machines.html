從高階到機器:暫存器機器模型

「我要說明:天上的機器並非什麼神聖的活物,而是一種鐘錶機構——」——Johannes Kepler,1605(SICP 第五章引言)

第 77 章的後設循環求值器是精彩的:用不到三百行 Scheme,就把整個語言的語意表達清楚了。但它有一個關鍵盲點:它繼承了底層 Scheme 的所有控制機制——呼叫棧、返回位址、引數傳遞——卻對此隻字不提。「為什麼尾遞迴不耗棧？」「過程呼叫時,返回位址存在哪裡？」這些問題,後設循環求值器一律迴避。

SICP 第五章的答案是:我們再往下一層,把求值器降(lower)到暫存器機器(register machine)層。在暫存器機器中,每一步計算都精確到「把某個暫存器的值放進另一個暫存器」這樣的粒度。那時,尾遞迴、垃圾回收、過程呼叫的每一個機制都無所遁形。

讓我們從最簡單的例子開始:用暫存器機器計算最大公因數(GCD, greatest common divisor)。Euclid 演算法的 Scheme 過程如下: 

(define (gcd a b)
  (if (= b 0)
      a
      (gcd b (remainder a b))))

這是一個迭代過程——每次遞迴只需要「新的 a 和 b」,不需要記住舊的計算狀態。一台只有三個暫存器 a、b、t(臨時暫存器)的機器就可以執行它。

暫存器機器的設計需要兩樣東西:資料路徑(data paths)——哪些暫存器、哪些運算、它們如何連接；以及控制器(controller)——按什麼順序驅動資料路徑。下圖展示 GCD 機器的完整結構:

暫存器機器的兩個組件

資料路徑定義「能做什麼」(哪些暫存器、哪些運算),控制器定義「按什麼順序做」(指令序列)。兩者合起來完整描述一台計算機器,就像 CPU 的 datapath 與 FSM 控制器。

描述暫存器機器的語言；用堆疊實作遞迴

用圖表描述複雜機器很不方便。SICP 設計了一種文字語言來描述暫存器機器。GCD 機器用這種語言寫成: 

; GCD 暫存器機器——文字描述語言
(controller
  test-b
    (test (op =) (reg b) (const 0))       ; 測試 b 是否為 0
    (branch (label gcd-done))              ; 是 → 跳到 gcd-done
    (assign t (op rem) (reg a) (reg b))    ; t ← remainder(a, b)
    (assign a (reg b))                     ; a ← b
    (assign b (reg t))                     ; b ← t
    (goto (label test-b))                  ; 回到 test-b 繼續
  gcd-done)

這種語言的完整指令集:

  • (assign reg (reg src)):把 src 暫存器的值搬到 reg
  • (assign reg (const val)):把常數 val 存入 reg
  • (assign reg (op name) inputs...):對輸入做運算,結果存入 reg
  • (perform (op name) inputs...):執行有副作用的動作(如 print)
  • (test (op name) inputs...):執行測試,結果存入內部 flag 暫存器
  • (branch (label L)):若 flag 為真,跳到標籤 L
  • (goto (label L)):無條件跳到標籤 L
  • (goto (reg r)):跳到 r 暫存器所存的位址(用於返回子程式)
  • (save reg):把 reg 的值推入堆疊
  • (restore reg):從堆疊頂端彈出值存入 reg

迭代 vs. 遞迴:堆疊的作用

GCD 是迭代過程,一台沒有堆疊的機器就夠用。但遞迴呢？考慮遞迴階乘(factorial): 

(define (factorial n)
  (if (= n 1)
      1
      (* (factorial (- n 1)) n)))

計算 n! 需要先算 (n-1)!,而計算 (n-1)! 又需要 n 的舊值乘回來。這不像 GCD 可以「原地覆蓋暫存器」——我們需要在遞迴期間保存 n 的舊值。解法:用堆疊(stack)。每次進入遞迴之前,把需要保存的暫存器 push 到堆疊；遞迴返回後,restore 回來: 

; 遞迴階乘暫存器機器
(controller
  (assign continue (label fact-done))    ; 設定最終返回地址
  fact-loop
    (test (op =) (reg n) (const 1))      ; 測試 n = 1？
    (branch (label base-case))
    ; 遞迴呼叫前:保存 n 與 continue
    (save continue)
    (save n)
    (assign n (op -) (reg n) (const 1))  ; n ← n-1
    (assign continue (label after-fact)) ; 設定遞迴返回地址
    (goto (label fact-loop))             ; 執行遞迴呼叫
  after-fact
    (restore n)                          ; 恢復 n
    (restore continue)                   ; 恢復返回地址
    (assign val (op *) (reg n) (reg val)); val ← n * (n-1)!
    (goto (reg continue))                ; 返回呼叫者
  base-case
    (assign val (const 1))               ; 基本情形:1! = 1
    (goto (reg continue))                ; 返回
  fact-done)
🔑
遞迴 = 迭代 + 堆疊

任何遞迴過程都可以在一台有限的暫存器機器上執行,只要加上一個堆疊。堆疊的「後進先出」結構正好對應遞迴的「最後呼叫的最先返回」。save 是呼叫前保存現場,restore 是返回後恢復現場。

計算 (factorial 3) 時,堆疊的動態變化可以清楚追蹤: 

進入 fact-loop (n=3):
  save continue=fact-done → 堆疊: [fact-done]
  save n=3                → 堆疊: [3, fact-done]
  n←2, continue←after-fact

進入 fact-loop (n=2):
  save continue=after-fact → 堆疊: [after-fact, 3, fact-done]
  save n=2                 → 堆疊: [2, after-fact, 3, fact-done]
  n←1, continue←after-fact

n=1 → 到 base-case:
  val ← 1
  goto (reg continue) → 跳到 after-fact

after-fact(第一層返回):
  restore n → n=2, 堆疊: [after-fact, 3, fact-done]
  restore continue → continue=after-fact, 堆疊: [3, fact-done]
  val ← 2*1 = 2
  goto after-fact

after-fact(第二層返回):
  restore n → n=3, 堆疊: [fact-done]
  restore continue → continue=fact-done, 堆疊: []
  val ← 3*2 = 6
  goto fact-done  →  完成！

雙重遞迴:費氏數列機器

費氏數列(Fibonacci)需要兩次遞迴——先算 fib(n-1),再算 fib(n-2),最後相加。每次遞迴都多一組 save/restore: 

; 費氏數列暫存器機器(控制器序列)
(controller
  (assign continue (label fib-done))
  fib-loop
    (test (op <) (reg n) (const 2))      ; n < 2？(基本情形)
    (branch (label immediate-answer))
    ; 計算 fib(n-1)
    (save continue)
    (assign continue (label afterfib-n-1))
    (save n)
    (assign n (op -) (reg n) (const 1))   ; n ← n-1
    (goto (label fib-loop))
  afterfib-n-1                            ; val 現在是 fib(n-1)
    (restore n)
    (restore continue)
    ; 計算 fib(n-2)
    (assign n (op -) (reg n) (const 2))   ; n ← n-2
    (save continue)
    (assign continue (label afterfib-n-2))
    (save val)                            ; 保存 fib(n-1)
    (goto (label fib-loop))
  afterfib-n-2                            ; val 現在是 fib(n-2)
    (assign n (reg val))                  ; n ← fib(n-2)
    (restore val)                         ; val ← fib(n-1)
    (restore continue)
    (assign val (op +) (reg val) (reg n)) ; val ← fib(n-1)+fib(n-2)
    (goto (reg continue))
  immediate-answer
    (assign val (reg n))
    (goto (reg continue))
  fib-done)
ℹ️
continue 暫存器 = CPU 的連結暫存器(link register)

在呼叫子程式前,先把返回位址存入 continue((assign continue (label ...)))；子程式結束時,(goto (reg continue)) 跳回。這正是 ARM 架構的 LR(link register)或 x86 的 call/ret 機制的精確類比。

暫存器機器模擬器

SICP 第 5.2 節用 Scheme 建了一個完整的暫存器機器模擬器,讓我們能實際執行上面設計的機器。核心介面是 make-machine: 

; 建立 GCD 機器並執行
(define gcd-machine
  (make-machine
    '(a b t)                                      ; 暫存器列表
    (list (list 'rem remainder) (list '= =))      ; 運算表
    '(test-b                                      ; 控制器序列
        (test (op =) (reg b) (const 0))
        (branch (label gcd-done))
        (assign t (op rem) (reg a) (reg b))
        (assign a (reg b))
        (assign b (reg t))
        (goto (label test-b))
      gcd-done)))

(set-register-contents! gcd-machine 'a 206)      ; 設定輸入
(set-register-contents! gcd-machine 'b 40)
(start gcd-machine)                              ; 執行
(get-register-contents gcd-machine 'a)           ; → 2

模擬器的內部結構

make-machine 內部建立的「機器物件」包含:

  • make-register:每個暫存器是一個封裝局部狀態的過程物件(message-passing 風格)
  • make-stack:堆疊同樣用過程物件封裝(支援 push/pop/initialize)
  • 內建暫存器 pc(程式計數器)與 flag:pc 指向下一條要執行的指令,flag 存測試結果
  • 組譯器(assembler):把控制器文字轉成可呼叫的「執行過程」列表
; 暫存器的實作
(define (make-register name)
  (let ((contents '*unassigned*))
    (define (dispatch message)
      (cond ((eq? message 'get) contents)
            ((eq? message 'set)
             (lambda (value) (set! contents value)))
            (else (error "Unknown request: REGISTER" message))))
    dispatch))

; 堆疊的實作(後進先出)
(define (make-stack)
  (let ((s '()))
    (define (push x) (set! s (cons x s)))
    (define (pop)
      (if (null? s)
          (error "Empty stack: POP")
          (let ((top (car s)))
            (set! s (cdr s))
            top)))
    (define (initialize) (set! s '()) 'done)
    (define (dispatch message)
      (cond ((eq? message 'push) push)
            ((eq? message 'pop) (pop))
            ((eq? message 'initialize) (initialize))
            (else (error "Unknown request: STACK" message))))
    dispatch))

組譯器:把文字化為執行過程

組譯器(assembler)的工作分兩步:

  1. 掃描標籤(extract-labels):掃描控制器序列,找出所有標籤(symbol),建立「標籤→指令位置」的對照表。
  2. 生成執行過程(update-insts!):對每條指令,用 make-execution-procedure 根據指令類型分派,產生一個「無引數的 Scheme 過程」作為執行過程。

「分析一次、執行多次」——這與第 77 章後設循環求值器的「分析型求值器」(Section 4.1.7)思路完全相同:把靜態分析(查找標籤位置、解析指令格式)從執行時間中移出,大幅提升效率。

Python 對照:極簡暫存器機器模擬器

下面用 Python 展示「指令就是可呼叫的過程」的核心設計思想(簡化版,只支援基本指令):

"""
極簡暫存器機器模擬器(Python)
支援:assign (reg/const/op)、test、branch、goto
"""

class RegisterMachine:
    def __init__(self, reg_names, ops, controller):
        self.regs = {r: None for r in reg_names}
        self.regs['flag'] = False
        self.ops = dict(ops)
        # 第一步:掃描標籤(組譯器 extract-labels)
        self.labels = {}
        self.insts = []
        for item in controller:
            if isinstance(item, str):         # 標籤 symbol
                self.labels[item] = len(self.insts)
            else:
                self.insts.append(item)
        self.pc = 0

    def run(self):
        while 0 <= self.pc < len(self.insts):
            inst = self.insts[self.pc]
            self.pc += 1
            self._exec(inst)

    def _exec(self, inst):
        op = inst[0]
        if op == 'assign':
            _, reg, *src = inst
            self.regs[reg] = self._val(src)
        elif op == 'test':
            self.regs['flag'] = self._val(inst[1:])
        elif op == 'branch':
            if self.regs['flag']:
                self.pc = self.labels[inst[1]]
        elif op == 'goto':
            self.pc = self.labels[inst[1]]

    def _val(self, src):
        if src[0] == 'reg':   return self.regs[src[1]]
        if src[0] == 'const': return src[1]
        if src[0] == 'op':
            fn = self.ops[src[1]]
            args = [self._val(list(a)) for a in src[2:]]
            return fn(*args)

# 執行 GCD 機器
m = RegisterMachine(
    reg_names=['a', 'b', 't'],
    ops=[('rem', lambda a, b: a % b), ('=', lambda x, y: x == y)],
    controller=[
        'test-b',
        ('test', 'op', '=', ('reg', 'b'), ('const', 0)),
        ('branch', 'gcd-done'),
        ('assign', 't', 'op', 'rem', ('reg', 'a'), ('reg', 'b')),
        ('assign', 'a', 'reg', 'b'),
        ('assign', 'b', 'reg', 't'),
        ('goto', 'test-b'),
        'gcd-done'
    ]
)
m.regs['a'] = 206
m.regs['b'] = 40
m.run()
print(m.regs['a'])   # → 2

儲存配置與垃圾回收

SICP 第 5.3 節解決了一個現實問題:真實電腦的記憶體有限,但 Lisp 程式不斷用 cons 建立新的序對。當 free 指標超過記憶體邊界,怎麼辦？答案是垃圾回收(garbage collection, GC)——自動回收不再需要的記憶體。

記憶體作為向量:Lisp 序對的底層表示

SICP 把 Lisp 記憶體設計成兩個向量:the-cars 和 the-cdrs。每個序對用一個整數索引表示:the-cars[i] 是第 i 個序對的 car,the-cdrs[i] 是其 cdr。指標(pointer)是一個「型別標籤 + 索引」的組合——例如 p5 表示「pair 指標,索引 5」,n4 表示數字 4,e0 表示空列表。

cons 的暫存器機器實作——每次 (cons reg2 reg3) 等同於: 

; (cons reg2 reg3) → 結果存入 reg1
(perform (op vector-set!) (reg the-cars) (reg free) (reg reg2))
(perform (op vector-set!) (reg the-cdrs) (reg free) (reg reg3))
(assign reg1 (reg free))
(assign free (op +) (reg free) (const 1))   ; free 往前移一格

free 指標總是指向下一個可用位置。當 free 超過記憶體邊界,就觸發垃圾回收。

ℹ️
連結:OS 記憶體管理與 GC

第 24 章的作業系統介紹了虛擬記憶體(OS 層的記憶體管理)；本節的 GC 是語言層的記憶體管理。第 42 章的編譯器也需要生成與 GC 友好的程式碼(如精確式 GC 需要知道哪些值是指標)。三者共同維持了「程式設計師眼中無限記憶體」的抽象。

Stop-and-Copy 垃圾回收

SICP 詳細描述了停止並複製(stop-and-copy) GC 演算法。基本思路:

  1. 記憶體分成「工作記憶體」和「自由記憶體」兩半
  2. GC 觸發時,從所有機器暫存器出發,追蹤所有可到達的(reachable)序對
  3. 把有用的序對連續複製到自由記憶體；複製後的舊位置留下「斷心(broken heart)」標記和轉發地址
  4. 交換兩半的角色——原「自由記憶體」成為新工作記憶體,原工作記憶體整體作廢

這個追蹤過程的核心是一組雙指標(two-pointer) BFS:free 與 scan。兩者初始都指向新記憶體的開頭。free 指向「下一個可寫入位置」——每搬移一個序對,free 就往前一格；而 scan 落在 free 後面,負責「逐一檢查已複製到新記憶體、但內部 car/cdr 指標還指向舊記憶體的序對」,把那些內部指標也 relocate 並更新。對每個 scan 到的序對,演算法先 relocate 它的 car(update-car),再 relocate 它的 cdr(update-cdr),然後 scan 才前進一格。新發現的序對被 relocate 時會推進 free,於是 scan 不斷追趕 free；當 scan 終於追上 free(兩者相等),代表所有可到達序對都已複製且內部指標都已更新,GC 結束。這正是用兩個指標在連續記憶體上實現的廣度優先走訪。

Stop-and-copy 的優點:

  • 緊湊化(compaction):複製後,有用資料連續存放,消除碎片,對虛擬記憶體友好
  • 只掃描有用資料:不需要線性掃描全部記憶體(mark-sweep 需要)
  • 「斷心」機制:防止同一序對被複製兩次(若 car 位置是 broken-heart 標記,直接讀 cdr 位置的轉發地址)

SICP 也提到另一種常見演算法:標記清除(mark-sweep)。先從根指標出發標記所有可到達物件,再線性掃描記憶體,把未標記的位置回收。代價是要掃描全部記憶體,且不做緊湊化。兩種演算法各有使用場景,現代 GC(如分代 GC)往往是兩者思想的融合。

🔑
GC 維持「無限記憶體的假象」

程式設計師用 cons 毫不在意地建立序對,GC 在幕後默默回收不再使用的記憶體。這是「抽象屏障」的底層設施版本:GC 把「有限實體記憶體」與「語義上無限的 Lisp 記憶體空間」分隔開來。

顯式控制求值器:把 eval/apply 降到暫存器層

有了前面幾節的鋪墊,SICP 第 5.4 節做了這本書最震撼的事:把第 77 章的後設循環求值器翻譯成暫存器機器語言,得到顯式控制求值器(explicit-control evaluator, EC evaluator)。它不是另一個求值器——它就是同一個求值器,只是精確到每一條暫存器操作。

七個核心暫存器

暫存器用途
exp當前要求值的運算式
env當前求值使用的環境
val最近一次求值的結果
continue求值完成後的返回地址(遞迴的關鍵)
proc被應用的過程物件

unev尚未求值的運算元列表

eval-dispatch:求值的總入口

後設循環求值器的 eval 是一個大型 cond,在 EC 求值器裡變成一串 test-branch 序列,統稱 eval-dispatch: 

eval-dispatch
  (test (op self-evaluating?) (reg exp))
  (branch (label ev-self-eval))
  (test (op variable?) (reg exp))
  (branch (label ev-variable))
  (test (op quoted?) (reg exp))
  (branch (label ev-quoted))
  (test (op assignment?) (reg exp))
  (branch (label ev-assignment))
  (test (op definition?) (reg exp))
  (branch (label ev-definition))
  (test (op if?) (reg exp))
  (branch (label ev-if))
  (test (op lambda?) (reg exp))
  (branch (label ev-lambda))
  (test (op begin?) (reg exp))
  (branch (label ev-begin))
  (test (op application?) (reg exp))
  (branch (label ev-application))
  (goto (label unknown-expression-type))

自求值的運算式(數字、字串)最簡單——直接把 exp 搬到 val,跳到 continue: 

ev-self-eval
  (assign val (reg exp))
  (goto (reg continue))

ev-variable
  (assign val (op lookup-variable-value) (reg exp) (reg env))
  (goto (reg continue))

ev-lambda
  (assign unev (op lambda-parameters) (reg exp))
  (assign exp  (op lambda-body) (reg exp))
  (assign val  (op make-procedure) (reg unev) (reg exp) (reg env))
  (goto (reg continue))

ev-application:過程應用的堆疊舞步

過程應用是最複雜的部分,對應後設循環 eval 的 (application? exp) 分支。需要先求值運算子,再逐一求值運算元,最後呼叫 apply-dispatch。每次遞迴進入 eval-dispatch 之前,都要 save 必要的暫存器: 

ev-application
  (save continue)               ; 保存最終返回地址
  (save env)                    ; 保存環境(求值運算元時需要)
  (assign unev (op operands) (reg exp))
  (save unev)                   ; 保存運算元列表
  (assign exp (op operator) (reg exp))
  (assign continue (label ev-appl-did-operator))
  (goto (label eval-dispatch))  ; 先求值運算子

ev-appl-did-operator
  (restore unev)                ; 恢復運算元列表
  (restore env)                 ; 恢復環境
  (assign argl (op empty-arglist))
  (assign proc (reg val))       ; proc ← 求值得到的過程物件
  (test (op no-operands?) (reg unev))
  (branch (label apply-dispatch))
  (save proc)
  ; ... 進入 ev-appl-operand-loop 逐一求值各運算元 ...

apply-dispatch:過程應用的執行

apply-dispatch
  (test (op primitive-procedure?) (reg proc))
  (branch (label primitive-apply))
  (test (op compound-procedure?) (reg proc))
  (branch (label compound-apply))
  (goto (label unknown-procedure-type))

primitive-apply
  (assign val (op apply-primitive-procedure) (reg proc) (reg argl))
  (restore continue)
  (goto (reg continue))

compound-apply
  (assign unev (op procedure-parameters) (reg proc))
  (assign env  (op procedure-environment) (reg proc))
  (assign env  (op extend-environment) (reg unev) (reg argl) (reg env))
  (assign unev (op procedure-body) (reg proc))
  (goto (label ev-sequence))

對照第 77 章的 Scheme 版 apply:邏輯完全相同——基本過程直接套用,複合過程在新環境中執行過程體。差別只是:現在每一步都精確對應一至幾條暫存器機器指令,save/restore 的位置清晰可見。

ev-sequence 與尾遞迴的底層機制

ev-sequence 處理運算式序列(過程體或 begin)。關鍵在最後一個運算式的特殊處理: 

ev-sequence
  (assign exp (op first-exp) (reg unev))
  (test (op last-exp?) (reg unev))
  (branch (label ev-sequence-last-exp))  ; 最後一個 → 特別路徑
  (save unev)
  (save env)
  (assign continue (label ev-sequence-continue))
  (goto (label eval-dispatch))           ; 求值非最後運算式

ev-sequence-continue
  (restore env)
  (restore unev)
  (assign unev (op rest-exps) (reg unev))
  (goto (label ev-sequence))

; ★ 尾遞迴消除的核心:最後一個運算式「不 save,直接 restore continue」
ev-sequence-last-exp
  (restore continue)           ; 從堆疊恢復外層的返回地址
  (goto (label eval-dispatch)) ; 直接跳去——不留任何堆疊痕跡
🔑
尾遞迴的底層真相

ev-sequence-last-exp 在執行序列最後一個運算式之前,先從堆疊 restore continue(外層的返回地址),再直接跳到 eval-dispatch——不做任何 save。這意味著:如果最後一個運算式是過程呼叫(尾呼叫),ev-application 看到的 continue 已是外層的返回地址,整個呼叫不增加堆疊深度。這就是「尾遞迴消除」在暫存器機器層的精確實現。

以 sqrt-iter 為例: 

(define (sqrt-iter guess x)
  (if (good-enough? guess x)
      guess
      (sqrt-iter (improve guess x) x)))  ; 尾呼叫,走 ev-sequence-last-exp 路徑

無論迭代多少次,堆疊深度恆為常數。對比:若把 ev-sequence-last-exp 改成和前面一樣也 save,sqrt-iter 就會線性累積堆疊,最終 stack overflow。

編譯:把 Scheme 編成暫存器指令

直譯器(不論是後設循環版還是 EC 版)每次執行程式都要重新分析語法、查找標籤、分派指令。編譯器(compiler)把這些靜態工作提前做好,直接生成可以「一跑就是結果」的暫存器機器指令序列。

SICP 第 5.5 節設計了一個 Scheme-to-register-machine 編譯器。基本原理:對每種運算式形式,生成對應的指令模板。例如自求值只需一條指令: 

; 編譯「自求值」數字 5 → 直接生成
(assign val (const 5))

; 編譯「變數查找」x → 直接生成
(assign val (op lookup-variable-value) (const x) (reg env))

; 編譯「lambda」→ 直接生成
(assign val (op make-compiled-procedure) (label entry) (reg env))

最關鍵的最佳化:編譯型尾遞迴(compiled tail recursion)。在直譯器中,尾遞迴消除靠的是 ev-sequence-last-exp 的特殊邏輯；在編譯器中,編譯器「靜態地知道」某個呼叫是不是尾呼叫,可以直接生成跳轉指令,完全省去 save/restore 的開銷: 

; 直譯器對尾呼叫的處理(隱式):
;   ev-sequence-last-exp → restore continue → goto eval-dispatch → ...

; 編譯器對尾呼叫直接生成(顯式):
;   (求值引數序列後)
;   (goto (reg proc))   ; 一條跳轉,無 save/restore 開銷
ℹ️
連結:編譯器原理與機器語言

第 42 章(編譯器原理)介紹了從高階語言到機器碼的完整流程(詞法分析、語法分析、語意分析、代碼生成、最佳化)。第 21 章(機器語言與 CPU)從 Nand2Tetris 視角描述了真實暫存器機器的指令格式與 CPU 架構。SICP 第 5.5 節的編譯器是兩者的橋樑:它把 Scheme 直接編成暫存器機器指令,揭示「高階語言如何最終落地為機器碼」。

直譯 vs 編譯 vs 分析型直譯

SICP 在第 5.5.7 節也討論了三種執行方式的對比:

  • 直譯(interpretation):靈活、互動快；但每次執行都重複做語法分析
  • 編譯(compilation):執行快；但需要預先的編譯步驟,部分靈活性損失
  • 分析型直譯(analyzing evaluation)(第 4.1.7 節):把語法分析與執行分離,只分析一次,多次執行,效率介於前兩者之間

現代語言往往混用:Python CPython 先編譯成位元組碼再直譯,Java JVM 再加上 JIT 把熱點代碼編成機器碼。這正是 SICP 第 5 章所預示的「漸進精細化」路線。

大圖:從 NAND 到直譯器

站在這裡回望,你所看到的是整本書的大圖——一條從最基礎的邏輯閘,到能執行任意程式的直譯器的完整鏈條:

  1. 第 19 章・布林邏輯:一切始於 NAND 閘。AND、OR、NOT、XOR 都是 NAND 的組合；半加器、全加器、ALU 都是邏輯閘的組合。這是計算的物理起點。
  2. 第 21 章・機器語言與 CPU:在邏輯閘上建 ALU、暫存器、程式計數器,得到一台可以執行機器語言的 CPU。機器語言是人類能寫給機器的最低抽象。
  3. 第 23 章・虛擬機與編譯器:在 CPU 上建虛擬機(VM)；高階語言編譯成 VM 位元組碼,再由 VM 解釋執行或 JIT 編譯。這一層讓「平台無關」成為可能。
  4. 本章・暫存器機器(SICP 第 5.1–5.2 節):SICP 的暫存器機器是另一種視角的「CPU」——不關心電路細節,只精確描述「哪個暫存器搬到哪裡、測試什麼、跳到哪裡」。
  5. 本章・垃圾回收(SICP 第 5.3 節):在有限實體記憶體上,用 stop-and-copy 維持「無限 Lisp 序對空間」的假象。這是語言基礎設施的一部分。
  6. 本章・EC 求值器(SICP 第 5.4 節):把後設循環求值器的 eval/apply 降到暫存器機器層——現在可以清楚地看見:eval/apply 就是一台在按規則搬暫存器、跳指令的機器。
  7. 本章・編譯(SICP 第 5.5 節):編譯器把靜態可知的工作預先做好,生成更精煉的指令序列,消除執行時分析的開銷。
🔑
「高階」與「低階」只是視角的差異

第 77 章的後設循環求值器用三百行 Scheme 描述 Scheme 的語意——那個層次的讀者看到的是「eval/apply 的結構」。本章的 EC 求值器用暫存器機器語言描述同樣的計算——那個層次的讀者看到的是「哪個暫存器被 save、哪裡 goto」。兩者描述的是同一件事,只是精確程度不同。「抽象」的本質正是如此:在不同的層次,同一件事有不同的面貌,各自為對應的問題提供最清晰的視角。

SICP 這本書的弧線:第 1 章「過程即計算的模型」→ 第 2 章「資料抽象」→ 第 3 章「狀態與變異」→ 第 4 章「語言即工具」→ 第 5 章「機器就是語言的真面目」。每一章都不是孤立的技術,而是「計算的本質」這個大問題的一個切面。讀完第 5 章,你手中握著的已不只是一個直譯器,而是一個關於「計算是什麼」的完整視角。

練習題

✏️ 練習 78.1 思考

設計一台暫存器機器,用以下迭代演算法計算階乘: 

(define (factorial n)
  (define (iter product counter)
    (if (> counter n)
        product
        (iter (* counter product)
              (+ counter 1))))
  (iter 1 1))

說明:需要哪些暫存器？哪些運算？並寫出完整的控制器序列。這台機器需要堆疊嗎？

看解答

需要的暫存器:n(輸入)、product(累積乘積)、counter(計數器)、val(輸出)。需要的運算:*、+、>(比較)。

; 迭代階乘暫存器機器(不需要堆疊！)
(controller
  (assign product (const 1))
  (assign counter (const 1))
  test-counter
    (test (op >) (reg counter) (reg n))    ; counter > n？
    (branch (label fact-done))
    (assign product (op *) (reg counter) (reg product))
    (assign counter (op +) (reg counter) (const 1))
    (goto (label test-counter))
  fact-done
    (assign val (reg product)))

這台機器不需要堆疊:迭代過程的全部狀態在每一步都完全存在 product 和 counter 這兩個暫存器裡,不需要「記住過去的狀態」再回來使用。這正是迭代過程與遞迴過程在機器層面的根本差別。

✏️ 練習 78.2 實作

用 EC 求值器觀察遞迴階乘與迭代階乘的堆疊深度差異(SICP 練習 5.26–5.27)。用裝有堆疊計數器的模擬器分別執行: 

; 遞迴版
(define (factorial-rec n)
  (if (= n 1) 1 (* (factorial-rec (- n 1)) n)))

; 迭代版
(define (factorial-iter n)
  (define (iter p c)
    (if (> c n) p (iter (* c p) (+ c 1))))
  (iter 1 1))

對 n = 1, 2, 3, 4, 5 分別記錄最大堆疊深度,說明兩者的增長規律。

看解答

遞迴版:每次遞迴呼叫,ev-application 都會 save continue、env、unev,加上乘法的運算元求值也要 save。最大堆疊深度大致與 n 成線性關係(SICP 實測約為 5n+3)。

迭代版:過程體最後一個運算式是尾呼叫 (iter ...),走 ev-sequence-last-exp 路徑,不做額外 save。每次迭代在常數深度的堆疊上進行,深度與 n 無關(約為固定常數 10)。

這是尾遞迴消除的直接量化體現:兩種語義上「等價」的程式,在 EC 求值器下表現出截然不同的堆疊行為。

✏️ 練習 78.3 思考

Stop-and-copy GC 的手動追蹤。假設記憶體有 6 個位置(索引 0–5),以 -1 代表 nil、nK(如 n1、n2)代表數字 K: 

索引:     0    1    2    3    4    5
the-cars: [p3, n1, n2, p5, n3, p0]
the-cdrs: [p1, -1, -1, p4, -1, p2]

機器根指標 root = p0(索引 0)。問:哪些序對是可到達的？GC 後,新工作記憶體中各索引存放的是什麼？(按 BFS 追蹤順序複製)

看解答

關鍵:SICP 的 gc-loop 在每個 scan 位置先 relocate car(update-car),再 relocate cdr(update-cdr),然後 scan 才前進。複製到新記憶體的順序就是這個「car 先於 cdr」的走訪順序。

先 relocate root(p0)放到 free=0,scan 從 0 起與 free 並進,逐格 car 先、cdr 後:

  • relocate root:p0 → 新位址 0(free 變 1)
  • scan=0(p0):car=p3 → 新位址 1；接著 cdr=p1 → 新位址 2
  • scan=1(p3):car=p5 → 新位址 3；接著 cdr=p4 → 新位址 4
  • scan=2(p1):car=n1(數字,原樣返回)；cdr=-1(nil,原樣返回)—— 無新增
  • scan=3(p5):car=p0(已是斷心,取轉發地址 → 0)；接著 cdr=p2 → 新位址 5
  • scan=4(p4):car=n3、cdr=-1 —— 無新增
  • scan=5(p2):car=n2、cdr=-1 —— 無新增
  • scan=6 時 scan = free,迴圈結束。

結論:所有 6 個序對(p0–p5)都可到達,沒有垃圾。對應表(舊指標 → 新索引):

p0 → 0   p3 → 1   p1 → 2   p5 → 3   p4 → 4   p2 → 5

GC 後的新工作記憶體(陣列中的 pX 代表「指向 pX 之搬移後版本」的指標):

新索引:   0    1    2    3    4    5
new-cars: [p3,  p5,  n1,  p0,  n3,  n2]
new-cdrs: [p1,  p4,  -1,  p2,  -1,  -1]

驗算:新位址 0(原 p0)的 car 是 p3,而 p3 搬到了新位址 1；cdr 是 p1,搬到了新位址 2——與對應表一致。注意 p3 排在 p1 之前(car 先於 cdr),這正是 update-car 先於 update-cdr 的結果。

✏️ 練習 78.4 挑戰

在 EC 求值器的 ev-sequence 中,如果我們把最後一個運算式也用和前幾個「完全一樣」的方式處理(save unev、save env、設 continue、跳 eval-dispatch),而不走 ev-sequence-last-exp 的特殊路徑——這會造成什麼問題？

具體說明:對以下程式,在「壞的 ev-sequence」下,堆疊深度如何隨呼叫次數變化？

(define (count n)
  (display n)
  (count (+ n 1)))
看解答

如果最後一個運算式也做 save/restore,那每次呼叫 (count ...) 都會向堆疊推入若干值(continue、env、unev)但永不彈出。堆疊深度線性增長。

結果:(count 0) 語意上是「無限迴圈(尾遞迴)」,但在「壞的 ev-sequence」下,它是一個不斷增長的遞迴堆疊——最終耗盡記憶體(stack overflow)。

這正是為什麼 Scheme 規格書(R5RS, R7RS)要求直譯器/編譯器必須支援尾呼叫消除(tail-call elimination):它不是「最佳化」,而是語言語意的一部分。沒有 TCE,Scheme 就無法用遞迴表達真正的迭代。

✏️ 練習 78.5 挑戰

用 Python 實作一個極簡的 stop-and-copy GC 模擬器。規格如下:

  • 記憶體為兩個列表 cars 和 cdrs,各長 N
  • 指標用非負整數表示序對索引；-1 = nil；負整數 ≤ -2 表示數字(-2 = 0,-3 = 1,依此類推)
  • 實作 gc(root, cars, cdrs),回傳 (new_root, new_cars, new_cdrs)
看解答 
BROKEN = -999   # 斷心標記(broken heart)

def gc(root, cars, cdrs):
    N = len(cars)
    new_cars = [None] * N
    new_cdrs = [None] * N
    free_ptr = [0]   # 用列表讓巢狀函數可修改

    def relocate(old):
        """把 old 指向的序對搬到新記憶體,回傳新指標"""
        if old < 0:                    # 數字、nil:直接回傳
            return old
        if cars[old] == BROKEN:         # 已複製 → 讀轉發地址
            return cdrs[old]
        # 複製到新記憶體
        addr = free_ptr[0]
        free_ptr[0] += 1
        new_cars[addr] = cars[old]
        new_cdrs[addr] = cdrs[old]
        # 設斷心 + 轉發地址
        cars[old] = BROKEN
        cdrs[old] = addr
        return addr

    new_root = relocate(root)
    scan = 0
    while scan < free_ptr[0]:          # 掃描並更新新記憶體內的指標
        new_cars[scan] = relocate(new_cars[scan])
        new_cdrs[scan] = relocate(new_cdrs[scan])
        scan += 1

    return new_root, new_cars[:free_ptr[0]], new_cdrs[:free_ptr[0]]

# 測試:列表 (1 2),即 cons(1, cons(2, nil))
# 索引0: car=-3(=1), cdr=1   → p0=(1 . p1)
# 索引1: car=-4(=2), cdr=-1  → p1=(2 . nil)
# 索引2: 垃圾(不可到達)
orig_cars = [-3, -4, -3]   # -3=數字1,-4=數字2
orig_cdrs = [ 1, -1, -1]
new_root, nc, nd = gc(0, orig_cars, orig_cdrs)
print(new_root, nc, nd)
# → 0  [-3, -4]  [1, -1]
# 索引2的垃圾序對被回收,new_cars/new_cdrs 只有長度2

把這一章串起來

這是 SICP 部的最後一章,也是本書「從 NAND 到直譯器」旅程的終點站。讓我們做最後一次回顧:

  • 暫存器機器模型:任何計算都可以用「暫存器 + 運算 + 測試 + 堆疊 + 控制器」精確描述。GCD 是最簡單的例子；EC 求值器是最複雜的例子。兩者使用完全相同的機制。
  • 堆疊與遞迴:遞迴不是魔法,是「save 舊狀態 → 遞迴 → restore 舊狀態」的精確機制。堆疊讓一台有限機器模擬任意深度的遞迴；迭代過程則根本不需要堆疊。
  • 暫存器機器模擬器:用 Scheme 寫一個能執行暫存器機器語言的模擬器——這本身是後設循環求值器思想的另一次體現:用語言的直譯器去執行另一個語言。組譯器的「分析一次、執行多次」與第 77 章的分析型求值器一脈相承。
  • 垃圾回收:stop-and-copy 通過追蹤可到達物件、緊湊複製,在有限實體記憶體上維持「無限 Lisp 記憶體」的假象。斷心機制防止重複複製；scan/free 兩指標驅動整個 GC 過程。
  • 顯式控制求值器:把後設循環的 eval/apply 降到暫存器層。eval-dispatch 是 eval；apply-dispatch 是 apply；七個暫存器精確對應求值過程的七個關注面向。
  • 尾遞迴的底層真相:ev-sequence-last-exp 的 restore-before-jump 是尾遞迴消除的實現。這不是「最佳化」,而是 Scheme 的語言承諾。
  • 編譯:編譯器把靜態可知的工作預先做好,生成更精煉的指令序列。尾呼叫在編譯器中直接化為跳轉,不留任何 save/restore。

SICP 選擇以第 5 章收尾,不是偶然的。整本書的主軸是「計算是什麼、怎麼描述它」。到了第 5 章,答案完整了:計算就是一台暫存器機器在按照規則搬動資料、跳轉控制流——而那台機器可以用任何夠精確的語言描述,包括 Scheme 本身。高階語言是對底層機器的抽象；求值器是把那個抽象「翻譯回」機器的工具；這整個過程可以在機器上跑——無限的層次,相同的本質。Kepler 說:那不是神聖的活物,而是鐘錶機構。SICP 說:那不是魔法,而是暫存器與指令。懂得了這一點,你就真正「進入了機器」。
