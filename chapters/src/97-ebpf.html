eBPF:讓核心可程式化

不改核心一行程式碼、不載入任何模組,你的程式就在核心裡跑——這是魔法?不,這是 eBPF。

你想知道「系統現在到底在幹嘛」——傳統做法有多痛

想像你的生產環境突然變慢了。CPU 用量正常,記憶體也沒問題,但 latency 就是高了兩倍。 你只有一個問題:「哪一個系統呼叫花最多時間?哪一個行程在搶 I/O?」

傳統的方法有幾種,但每一種都有代價:

  • 加 printk 進核心原始碼:要重新編譯核心、重開機。生產環境不可能。
  • 載入核心模組(Loadable Kernel Module, LKM):寫一個 .ko 模組、insmod 載入。一旦模組有 bug——例如存取了無效指標——整個核心就 panic,機器當場死機。更嚴重的是,載入模組需要 root,惡意模組可以做任何事:rootkit、後門、繞過所有安全機制。
  • 用 strace 追蹤:基於 ptrace(),對每個系統呼叫都造成兩次 context switch,開銷高達 10–100 倍,不適合 production。
  • perf + ftrace:功能強大,但設定複雜、輸出格式難解析、動態改行為的能力有限。

有沒有一種方法,讓你把「自己寫的程式」放進核心裡執行,但又不怕它讓核心當機? 這就是 eBPF(extended Berkeley Packet Filter) 解決的問題。

🔑
eBPF 的核心價值主張

eBPF 讓你在 Linux 核心裡安全地執行沙箱程式——不修改核心原始碼、不載入核心模組。 核心在載入 eBPF 程式時,會先用 verifier(驗證器)做靜態安全分析,確保程式不會讓核心當機; 通過後再用 JIT 編譯成機器碼,掛在你指定的核心事件上執行。效能接近原生核心程式碼。

eBPF 是什麼:核心裡的虛擬機 + JIT——從 cBPF 到 eBPF 的演進

要理解 eBPF,先從它的名字說起。BPF 是 Berkeley Packet Filter 的縮寫, 1992 年由 Steven McCanne 與 Van Jacobson 在一篇論文中提出, 最初的用途只有一個:在核心裡過濾網路封包。 當你執行 tcpdump -i eth0 port 80,核心裡跑的就是 BPF(現在稱為 cBPF)。

cBPF(classic BPF)的設計非常簡單:一個只有 2 個暫存器(A 與 X)的微型 VM, 指令集非常受限。但它的沙箱特性——程式在進核心前被驗證——奠定了重要先例。

2014 年,Alexei Starovoitov 與 Daniel Borkmann 把 BPF 大幅擴展, 正式合入 Linux 3.18 的 eBPF(extended BPF):

面向 cBPF(舊) eBPF(現代)
暫存器數量 2(A, X) 11(r0–r10,每個 64 位元)
指令長度 32 位元 64 位元(固定長度)
程式大小上限 4096 指令 100 萬指令(Linux 5.2+)
用途 封包過濾 觀測、網路、安全、效能分析等
maps(共享資料) 無 有(hash/array/ring buffer 等)
掛載點 socket filter kprobe/tracepoint/XDP/LSM 等數十種
JIT 編譯 部分架構支援 x86-64/ARM64/s390x 等全支援

eBPF 程式以受限的 C 語言寫成(或直接寫 eBPF 位元組碼), 用 Clang/LLVM 編譯成 eBPF 位元組碼(.o 檔), 再透過 bpf() 系統呼叫載入核心。 這個過程與「載入核心模組」本質上不同:

⚠️
eBPF ≠ 核心模組(Kernel Module)

核心模組(.ko)是直接在核心位址空間執行的原生程式碼—— 它能呼叫任何核心函式、存取任何記憶體位址、掛載任何 hook。 一旦有 bug(空指標解引用、越界寫入)就會立即引發核心 panic。 eBPF 程式則是在核心的沙箱 VM 裡執行: 載入前 verifier 必須靜態證明程式安全;記憶體存取受限在已知範圍; 不能呼叫任意核心函式,只能呼叫預先定義的 eBPF helper。 eBPF 程式無法讓核心 panic——最壞情況是 verifier 拒絕載入。

安全的關鍵:verifier(驗證器)——載入前的靜態守門人

eBPF 之所以安全,關鍵在於 verifier(驗證器)—— 一個在 eBPF 程式被載入核心之前就執行的靜態分析程式。 verifier 是核心程式碼裡的 kernel/bpf/verifier.c, 數萬行,是整個 eBPF 安全性的核心。

verifier 做什麼

verifier 對 eBPF 位元組碼程式進行以下分析:

  • 控制流圖(CFG)有界性:遍歷所有可能的執行路徑,確認程式一定會結束。 Linux 5.3 之前完全不允許迴圈;5.3+ 允許有界迴圈(bounded loops), 但 verifier 必須能靜態證明迴圈的最大迭代次數是有限的。 無界迴圈(verifier 無法確定終止)→ 直接拒絕載入。
  • 記憶體安全:追蹤每個暫存器的「型別」與「值域」(value range)。 例如 r1 是一個指向 map value 的指標,r2 是一個大小為 64 的整數偏移—— verifier 會驗證所有基於這些指標的存取是否在合法範圍內。 越界存取 → 拒絕。
  • 未初始化暫存器:讀取未初始化的暫存器 → 拒絕。
  • helper 函式呼叫正確性:確認呼叫 eBPF helper 時傳入的參數型別與數量正確。
  • 返回值:程式必須以 r0 存放返回值然後結束;不能有「跳到程式外」的分支。
  • 指標運算限制:對 map 指標的算術運算(pointer arithmetic)受到嚴格限制,防止構造任意記憶體存取。

verifier 的限制——它不是萬能的

verifier 只做靜態分析,不能捕捉「邏輯錯誤」(例如計數器算法寫錯了)。 此外,verifier 本身也是核心程式碼,歷史上曾有 verifier bypass 漏洞—— 攻擊者精心構造位元組碼繞過驗證,讓惡意程式進入核心。這也是為什麼 eBPF 仍然需要特權:verifier 不是萬能的護盾。

eBPF Maps:核心程式與使用者空間共享資料的橋

eBPF 程式在核心裡執行,但它收集到的資料要怎麼傳給使用者空間的分析工具? 答案是 eBPF maps——一種核心管理的 key-value 儲存結構, 核心端的 eBPF 程式和使用者空間程式都能透過 file descriptor 讀寫。

透過 bpf(BPF_MAP_CREATE, ...) 系統呼叫建立 map 後, 回傳一個 fd(file descriptor);使用者空間程式用 bpf(BPF_MAP_LOOKUP_ELEM, ...) 讀取 map 的值;eBPF 程式(核心端)用 bpf_map_lookup_elem()、 bpf_map_update_elem() 等 helper 函式存取 map。

常見 map 型別

Map 型別 說明 典型用途
BPF_MAP_TYPE_HASH 雜湊表,任意 key/value,O(1) 查詢 統計每個 PID 的系統呼叫次數
BPF_MAP_TYPE_ARRAY 固定大小陣列,key 為 uint32 索引 系統呼叫計數器(以 syscall_nr 為 key)
BPF_MAP_TYPE_PERCPU_HASH 每個 CPU 核心有獨立副本的雜湊表,避免鎖競爭 高頻率事件的無鎖統計
BPF_MAP_TYPE_PERCPU_ARRAY 每個 CPU 核心有獨立副本的陣列 高效能 per-CPU 計數器
BPF_MAP_TYPE_RINGBUF 環形緩衝區(Linux 5.8+),核心→使用者空間的高效事件串流 即時事件追蹤,取代 perf_event output
BPF_MAP_TYPE_LRU_HASH LRU 淘汰策略的雜湊表 追蹤最近活躍的 IP 連線
BPF_MAP_TYPE_LPM_TRIE 最長前綴匹配樹(Longest Prefix Match) IP 路由表查詢(Cilium 的 eBPF 路由)
BPF_MAP_TYPE_PROG_ARRAY 儲存 eBPF 程式 fd,支援 tail call(程式鏈) 模組化 eBPF 程式組合
🔑
Maps 是核心與使用者空間的資料共享橋

eBPF 程式本身在核心裡執行且無法直接「回傳」資料給使用者空間—— Maps 就是這個橋。核心端用 helper(bpf_map_update_elem)寫; 使用者空間用 bpf() 系統呼叫或 libbpf API 讀。 BPF_MAP_TYPE_RINGBUF 是最新也最高效的串流機制: 核心可以「預留空間、填資料、提交」,使用者空間用 poll/epoll 等待即可,幾乎零複製。

掛載點(Hooks):eBPF 能插在核心的哪些地方

eBPF 程式本身不是常駐後台——它掛在一個「核心事件」上,每當事件發生就執行一次。 你選擇哪個 hook(掛載點),決定了你的程式能看到什麼、能攔截什麼。

Hook 類型 觸發時機 典型用途 代表 SEC 名稱
kprobe 任意核心函式入口(動態插樁) 追蹤核心函式呼叫、參數 SEC("kprobe/tcp_connect")
kretprobe 核心函式返回時 追蹤返回值、計算函式執行時間 SEC("kretprobe/tcp_connect")
uprobe 使用者空間函式入口(user-space dynamic probe) 追蹤 OpenSSL、libc 等函式呼叫 SEC("uprobe//lib/x86_64-linux-gnu/libssl.so:SSL_write")
tracepoint 核心靜態插樁點(穩定 ABI) 追蹤系統呼叫進入/退出、排程等 SEC("tracepoint/syscalls/sys_enter_execve")
raw_tracepoint 原始 tracepoint(效能更高,ABI 較不穩定) 高頻事件的低開銷追蹤 SEC("raw_tracepoint/sys_enter")
XDP (eXpress Data Path) 封包剛進網卡驅動,未進協議棧(最早期) DDoS 防禦、封包過濾、負載均衡(L4 LB) SEC("xdp")
tc (traffic control) 封包進入/離開網路協議棧的 tc 層 封包改寫、策略路由、容器網路(Cilium) SEC("tc")
LSM (Linux Security Module) Linux 安全 hook 點(如 file_open、bprm_check) 強制存取控制、執行期安全策略 SEC("lsm/file_open")
cgroup/sock cgroup 裡的 socket 操作 容器網路策略、流量計費 SEC("cgroup/connect4")
perf_event CPU 效能計數器取樣 效能剖析、On-CPU 火焰圖 SEC("perf_event")
ℹ️
XDP:網路封包最快的攔截點

XDP hook 在封包剛離開網卡驅動就介入,還沒有分配 sk_buff 結構體、 還沒進入 IP 協議棧——這讓 XDP 的封包處理速度可達每秒數千萬個封包(Mpps), 遠勝 iptables。Cloudflare 使用 XDP eBPF 做 DDoS 防禦; Cilium 使用 XDP 做 Kubernetes Service 的 L4 負載均衡。 XDP 程式的返回值決定封包命運:XDP_PASS(繼續)、XDP_DROP(丟棄)、 XDP_TX(從同一張網卡轉發)、XDP_REDIRECT(轉發到其他介面)。

動手:寫一支最小 eBPF 觀測程式

理論說夠了,來動手。我們用三種方式從簡單到完整地示範 eBPF 觀測: bpftrace 一行版、bcc Python 版、libbpf C 版。

方法一:bpftrace 一行版(最簡單)

bpftrace 是一個高階 eBPF 前端,語法類似 awk/DTrace, 讓你用一行指令完成原本需要數百行程式碼的事: 

# 追蹤所有 execve 系統呼叫(執行新程式),印出 PID、程式名稱與第一個參數
bpftrace -e 'tracepoint:syscalls:sys_enter_execve { printf("PID=%d comm=%s arg=%s\n", pid, comm, str(args->filename)); }'

# 統計每個系統呼叫的次數(Ctrl+C 後輸出)
bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'

# 追蹤 openat() 呼叫,印出行程名稱與開啟的檔案路徑
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s opened: %s\n", comm, str(args->filename)); }'

# 統計每個函式的核心 CPU 時間(On-CPU Profiling),用 99Hz 取樣
bpftrace -e 'profile:hz:99 { @[kstack] = count(); }' -c sleep 10

bpftrace 在背後自動做了所有事:把你的腳本編譯成 eBPF 位元組碼、載入核心、 掛載 hook、從 maps 讀取資料、格式化輸出。你只需要描述「你想觀察什麼」。

方法二:bcc Python 版(可程式化的觀測)

bcc(BPF Compiler Collection) 讓你用 Python 寫使用者空間邏輯, 嵌入 C 字串作為 eBPF 核心程式。以下範例統計每個 PID 呼叫 execve 的次數: 

#!/usr/bin/env python3
# execve_count.py — 用 bcc 統計各 PID 的 execve 呼叫次數

from bcc import BPF
import time

# eBPF 核心程式(C 語言,以字串嵌入)
# 注意:此處 C 程式中的 < 和 > 是真實原始碼,bcc 會自行處理跳脫
bpf_program = """
#include <uapi/linux/ptrace.h>

BPF_HASH(counts, u32, u64);   // key: PID, value: 呼叫次數

int trace_execve(struct pt_regs *ctx) {
    u32 pid = bpf_get_current_pid_tgid() >> 32;  // 取得 PID
    u64 zero = 0;
    u64 *count = counts.lookup_or_try_init(&pid, &zero);
    if (count) {
        (*count)++;
    }
    return 0;
}
"""

# 載入 eBPF 程式
b = BPF(text=bpf_program)

# 掛載到 execve 系統呼叫的 kprobe
b.attach_kprobe(event=b.get_syscall_fnname("execve"), fn_name="trace_execve")

print("追蹤 execve 呼叫中... 10 秒後輸出結果")
time.sleep(10)

# 從 map 讀取並輸出結果
print("\nPID\t呼叫次數")
for k, v in b["counts"].items():
    print(f"{k.value}\t{v.value}")

方法三:libbpf C 版(核心向 CO-RE 可移植)

最現代的做法是用 libbpf 搭配 BTF(BPF Type Format) 實現 CO-RE(Compile Once – Run Everywhere)—— 程式在一台機器上編譯,可在不同核心版本的機器上執行,因為型別資訊在執行時從核心 BTF 取得。

eBPF 核心程式(execve_count.bpf.c):

// execve_count.bpf.c — eBPF 核心程式 (CO-RE 風格)

#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>   /* SEC macro 與 helper 函式定義 */
#include <linux/types.h>

/* 定義 BPF map:hash table,key=PID(u32),value=計數(u64) */
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __uint(max_entries, 1024);
    __type(key, __u32);
    __type(value, __u64);
} counts SEC(".maps");

/* 掛載到 tracepoint:syscalls/sys_enter_execve */
SEC("tracepoint/syscalls/sys_enter_execve")
int trace_execve(void *ctx)
{
    __u32 pid = bpf_get_current_pid_tgid() >> 32;
    __u64 zero = 0;
    __u64 *count;

    count = bpf_map_lookup_elem(&counts, &pid);
    if (count) {
        __sync_fetch_and_add(count, 1);   /* 原子遞增 */
    } else {
        bpf_map_update_elem(&counts, &pid, &zero, BPF_ANY);
    }

    /* 可選:用 bpf_printk 輸出除錯訊息到 /sys/kernel/debug/tracing/trace_pipe */
    bpf_printk("execve called by PID %u\n", pid);

    return 0;
}

/* 所有 eBPF 程式必須宣告 GPL 授權 */
char LICENSE[] SEC("license") = "GPL";

使用者空間載入程式(execve_count.c,核心部分):

// execve_count.c — 使用者空間載入器(簡化版)

#include <bpf/libbpf.h>
#include <stdio.h>
#include <unistd.h>
#include "execve_count.skel.h"   /* 由 bpftool gen skeleton 自動產生 */

int main(void)
{
    struct execve_count_bpf *skel;
    int err;

    /* 開啟並載入 eBPF 物件(會觸發 verifier 驗證) */
    skel = execve_count_bpf__open_and_load();
    if (!skel) { fprintf(stderr, "載入失敗\n"); return 1; }

    /* 掛載到核心 hook 點 */
    err = execve_count_bpf__attach(skel);
    if (err) { fprintf(stderr, "掛載失敗: %d\n", err); goto cleanup; }

    printf("追蹤 execve 中... Ctrl+C 結束\n");
    sleep(10);

    /* 讀取 map 資料(示意) */
    /* 實際讀取需遍歷 bpf_map_get_next_key + bpf_map_lookup_elem */

cleanup:
    execve_count_bpf__destroy(skel);
    return err;
}

快速上手建議

初學 eBPF 建議順序:先玩 bpftrace 的一行指令,感受 hook 的威力; 再看 bcc tools(如 execsnoop、opensnoop、tcptop)的原始碼學 Python/C 結合; 最後轉向 libbpf + CO-RE 寫生產環境程式。 Ubuntu 22.04+ 直接 apt install bpftrace bpfcc-tools linux-tools-common 即可開始。

eBPF 在雲原生:Cilium 與 Falco

eBPF 不只是除錯工具——它正在重新定義雲原生基礎設施的網路與安全層。 最具代表性的兩個專案:Cilium 和 Falco。

Cilium:用 eBPF 取代 iptables,成為 Kubernetes 的神經系統

傳統 Kubernetes 的網路依賴 kube-proxy 與 iptables—— iptables 是 1998 年設計的，它把 Service 規則存在 iptables 規則鏈裡。 當 Service 數量增長到幾千個時，iptables 的規則鏈可以有幾萬條， 每個封包都要線性掃描——這在大規模叢集裡成了嚴重瓶頸。

Cilium 用 eBPF 完整取代了這個架構:

  • Service 負載均衡:用 BPF_MAP_TYPE_LPM_TRIE 和 BPF_MAP_TYPE_HASH 實作 Service-to-Endpoint 映射;XDP hook 在封包最早期就完成 DNAT—— O(1) 查詢替代 iptables 的 O(n) 線性掃描。
  • 網路策略(NetworkPolicy):在 tc hook 點執行 eBPF 程式, 根據 Pod label(透過 map 查詢)做 L3/L4/L7 層的允許/拒絕。
  • 可觀測性 Hubble:eBPF 程式在所有網路事件上收集 flow 資訊, 存入 ring buffer map;Hubble 讀取後提供 Prometheus 指標與 UI 介面—— 不需要任何 sidecar proxy。
  • mTLS 透明加密:在 socket 層用 eBPF 為 Pod 間流量自動加密。
🔑
Cilium 的核心優勢:eBPF 讓網路策略和觀測「零開銷」

傳統做法需要在每個 Pod 裡注入一個 Envoy sidecar(佔用 CPU/記憶體)才能做 L7 觀測。 Cilium 把這些邏輯移進核心的 eBPF 程式——不需要 sidecar、不需要改應用程式、 效能開銷接近零。這也是為什麼 Google GKE、AWS EKS、Azure AKS 都支援 Cilium 作為 CNI。

Falco:用 eBPF 做 Kubernetes 執行期安全

Falco(CNCF 畢業專案)是一個執行期安全工具, 用 eBPF 程式(或傳統核心模組,但現代部署偏好 eBPF)監聽系統呼叫, 根據預定義的規則(YAML 語法)偵測異常行為: 

# Falco 規則範例:偵測容器內的 shell 啟動
- rule: Terminal shell in container
  desc: A shell was spawned in a container
  condition: >
    evt.type = execve and container and
    (proc.name in (shell_binaries)) and
    proc.tty != 0
  output: >
    Shell spawned in container (user=%user.name container=%container.name
    shell=%proc.name parent=%proc.pname)
  priority: WARNING

Falco 在 tracepoint/sys_enter hook 上執行 eBPF 程式,把事件寫入 ring buffer map; 使用者空間的 Falco daemon 從 map 讀取、比對規則、觸發告警—— 可輸出到 stdout、syslog、Slack、Webhook、甚至 Kubernetes Audit log。 用途包括:偵測容器逃逸嘗試、意外的網路連線、敏感檔案讀取等。

ℹ️
Cilium vs Falco 的定位

Cilium 關注網路——封包如何在 Pod 間傳遞、策略允許/拒絕哪些流量、 Service 如何做負載均衡。它是 CNI(Container Network Interface)的替代品。 Falco 關注行為——哪個行程執行了什麼系統呼叫、 有沒有符合「惡意特徵」的事件序列。它是執行期安全(runtime security)的偵測層, 不做封包轉發。兩者互補,很多生產叢集同時部署兩者。

限制與風險:eBPF 的黑暗面

eBPF 被稱為「Linux 的超能力」,但任何超能力都有代價。在部署 eBPF 之前,你必須誠實地面對它的限制與風險。

需要特權:CAP_BPF 與 CAP_SYS_ADMIN

eBPF 程式的載入需要特權。歷史上一直需要 CAP_SYS_ADMIN(幾乎等同 root); Linux 5.8(2020 年)引入了更精細的 CAP_BPF capability—— 分離了「載入 eBPF 程式」所需的最小特權。 但大多數有用的 eBPF 程式(如掛 kprobe 追蹤核心符號)仍然需要 CAP_PERFMON 或 CAP_SYS_ADMIN。 在容器環境中,這意味著只有特權容器或有 CAP_BPF/CAP_PERFMON 的容器才能使用 eBPF。

核心版本限制

eBPF 功能隨核心版本快速演進:

  • 有界迴圈:Linux 5.3+
  • BTF(BPF Type Format,CO-RE 基礎):Linux 5.2+
  • LSM hook:Linux 5.7+
  • ring buffer map:Linux 5.8+
  • CAP_BPF:Linux 5.8+

在 CentOS 7(Linux 3.10)或舊版 Ubuntu 上,大多數現代 eBPF 功能根本無法使用。 這是 eBPF 生態系的一大挑戰——CO-RE 的目標就是讓程式跨版本可移植, 但仍然需要目標核心版本夠新(通常要求 5.4+)。

verifier 的限制

verifier 本身帶來了一些程式設計上的不便:

  • 程式複雜度上限:verifier 的分析有指令數上限(目前約 100 萬)與執行路徑數上限。 過於複雜的程式——例如大量的 if-else 分支或深度循環——可能超過 verifier 的分析預算而被拒絕。
  • 有界迴圈的限制:即使是 Linux 5.3+ 允許的有界迴圈,verifier 仍需要能靜態確定最大迭代次數。 動態大小的迴圈(如 for (int i = 0; i < map.size; i++))可能無法通過 verifier。
  • 指標運算受限:對 map value 指標的算術運算(pointer arithmetic)有嚴格限制, 讓某些「在 C 裡天經地義」的操作在 eBPF 裡變得繁瑣。

eBPF rootkit:超能力也可以是武器

eBPF 的能力——在核心任意事件上執行程式、攔截系統呼叫、修改封包—— 同樣可以被惡意程式利用。eBPF rootkit 是真實存在的威脅:

  • 隱藏行程:掛 kprobe 在 /proc 相關的核心函式上, 過濾掉特定 PID 的回應——讓 ps、top 看不到惡意行程。
  • 網路後門:用 XDP 或 tc hook 攔截特定封包(例如包含特殊 magic byte 的 UDP 封包), 觸發反向 shell——連 netstat 都看不到的後門監聽。
  • 憑證竊取:用 uprobe 掛在 OpenSSL 的 SSL_read/SSL_write 上, 在 TLS 解密後、應用程式讀取前攔截明文資料——繞過加密。

真實案例:2021 年的 Pamspy、2022 年的 TripleCross 等 eBPF rootkit 概念驗證, 展示了僅憑 CAP_BPF 就能建立幾乎無法被傳統工具偵測的後門。 這也正是 Falco 這類執行期安全工具的價值——用 eBPF 對抗 eBPF。

⛔
eBPF 特權必須嚴格管控

在第 34 章我們談過最小權限原則(principle of least privilege)。 eBPF 是這個原則的試煉場: 絕對不要給一般容器 CAP_SYS_ADMIN 或不必要的 eBPF 特權。 只有特定的觀測/安全工具(Cilium、Falco、DataDog agent 等)在受信任的 DaemonSet 裡才應該有這些特權, 且應搭配 AppArmor / Seccomp profile 進一步限制。 eBPF 程式的來源也需要嚴格審查——就像你不會隨便 insmod 一個來路不明的核心模組。

動手練習:驗證你的理解

✏️ 練習 91.1 實作

在 Linux 機器(Ubuntu 22.04+、或 WSL2)上安裝 bpftrace: 

sudo apt install bpftrace

然後執行以下一行指令來追蹤 execve 系統呼叫: 

sudo bpftrace -e 'tracepoint:syscalls:sys_enter_execve { printf("PID=%d COMM=%s FILE=%s\n", pid, comm, str(args->filename)); }'

在另一個終端開啟幾個新 shell、執行幾個指令(如 ls、date、uname)。 觀察並回答:(1) 每次執行指令都會觸發幾次 execve?(2) comm 欄位顯示的是什麼?(3) bpftrace 背後使用了哪種 eBPF hook 類型?為什麼選 tracepoint 而不是 kprobe?

看解答

(1) 幾次 execve: 通常每個外部指令觸發一次 execve(Shell 的 fork+exec 模型)。 但如果你執行的是 pipeline(如 ls | grep foo), 每個管線元素各 fork+exec 一次——會看到兩筆 execve 記錄。

(2) comm 欄位: comm(bpf_get_current_comm())顯示觸發 execve 的父行程的名稱—— 即執行 exec 的 shell(如 bash)。 args->filename 才是新執行的程式路徑(如 /bin/ls)。

(3) Tracepoint vs kprobe: tracepoint:syscalls:sys_enter_execve 是核心的靜態插樁點—— 核心開發者在特定位置明確放置 tracepoint,並維護穩定的 ABI(參數格式在核心版本間不輕易改變)。 kprobe 是動態插樁——掛在任意核心函式入口,但函式介面在不同核心版本可能改變,移植性較差。 追蹤系統呼叫時,優先用 tracepoint 而非 kprobe,穩定性更好。

✏️ 練習 91.2 思考

下面這段 eBPF C 程式碼片段會被 verifier 拒絕,原因是什麼? 應該如何修正? 

SEC("tracepoint/syscalls/sys_enter_read")
int trace_read(void *ctx)
{
    int i = 0;
    /* 問題迴圈:verifier 能確定它一定終止嗎? */
    while (some_map_value > 0) {
        i++;
        some_map_value--;
    }
    return 0;
}

請解釋:(1) verifier 為什麼無法接受這段程式?(2) 如果把迴圈改成 for (int i = 0; i < 100; i++) { ... } 是否能通過 verifier?為什麼? (3) verifier 拒絕無界迴圈的目的是什麼?

看解答

(1) 為何拒絕: some_map_value 的值是在執行時從 map 讀取的—— verifier 在靜態分析階段無法確定它的初始值, 因此無法證明 while (some_map_value > 0) 迴圈一定會終止。 這是一個無界迴圈(unbounded loop)——verifier 拒絕載入。

(2) 改成固定上限的 for 迴圈: for (int i = 0; i < 100; i++)——verifier 能靜態確定迴圈最多執行 100 次, 是一個有界迴圈(bounded loop)。Linux 5.3+ 允許這類迴圈通過 verifier。 但注意:如果迴圈體很複雜、分支很多,展開後的指令數可能超過 verifier 的複雜度預算。

(3) 目的: 核心是所有行程共用的執行環境。一個無限迴圈的 eBPF 程式掛在高頻事件(如每個系統呼叫入口)上, 會讓 CPU 卡死在核心模式——所有行程都無法被排程。 verifier 強制要求程式必須有界(bounded),確保 eBPF 程式在有限時間內完成、 將 CPU 還給排程器,這是 eBPF 能安全在核心執行的根本保證。

✏️ 練習 91.3 思考

解釋 eBPF map 在核心程式與使用者空間之間如何共享資料。 具體地說:假設你在 kprobe hook 上統計每個 PID 的 open() 系統呼叫次數, 並希望每秒在終端印出排名前 10 的 PID。 描述完整的資料流:(1) 核心端 eBPF 程式如何寫入 map?(2) 使用者空間程式如何讀取 map?(3) 為什麼 BPF_MAP_TYPE_PERCPU_HASH 比 BPF_MAP_TYPE_HASH 更適合高頻事件的計數?

看解答

(1) 核心端寫入 map: eBPF 程式用 bpf_map_lookup_elem(&counts, &pid) 查詢 PID 是否已有計數;若有則用 __sync_fetch_and_add(count, 1) 原子遞增;若無則用 bpf_map_update_elem(&counts, &pid, &zero, BPF_ANY) 插入初始值 0。整個過程在核心的 kprobe handler 裡完成, 每次 open() 系統呼叫進入時觸發一次。

(2) 使用者空間讀取: 使用者空間持有 map 的 fd(file descriptor)。 每秒呼叫 bpf(BPF_MAP_GET_NEXT_KEY, ...) 遍歷所有 key(PID), 再用 bpf(BPF_MAP_LOOKUP_ELEM, ...) 取得每個 PID 的計數值。 libbpf 提供了更方便的 API(bpf_map__lookup_elem)。 注意:讀取期間核心端程式仍在繼續更新 map——這是「並發讀寫」, 但 map 的原子更新保證每次讀到的是完整的值。

(3) PERCPU_HASH vs HASH: BPF_MAP_TYPE_HASH 是一個所有 CPU 核心共用的雜湊表—— 高頻事件(如每個 open() 系統呼叫)在多核心下並發更新同一個計數, 需要用自旋鎖保護,會造成鎖競爭與效能瓶頸。 BPF_MAP_TYPE_PERCPU_HASH 為每個 CPU 核心維護一份獨立的 map 副本—— 核心端更新時只更新當前 CPU的副本,完全無鎖、無競爭。 使用者空間讀取時需要把所有 CPU 的副本加總(sum)才得到真實計數。 代價:記憶體用量乘以 CPU 核心數。適合高頻場景。

把這一章串起來

從一個「系統在幹嘛」的問題出發,我們拆解了 eBPF 的完整技術棧。 幾個值得帶走的核心觀念:

  • eBPF ≠ 核心模組:核心模組是「完全信任、無沙箱」的原生程式碼; eBPF 是「verifier 靜態驗證後在 VM 裡執行、JIT 優化的沙箱程式」。 eBPF 不會讓核心 panic,核心模組可以。這個差異決定了 eBPF 能在生產環境安全部署。
  • verifier 是核心安全的守門人:載入前靜態檢查有界迴圈、記憶體安全、 未初始化暫存器——不是執行時檢查,而是載入時就拒絕危險程式。 verifier 不是萬能的,但它把攻擊面縮到可接受的程度。
  • maps 是橋:核心端 eBPF 程式靠 helper 函式讀寫 maps; 使用者空間靠 bpf() 系統呼叫讀寫同一份 maps。 Ring buffer 是最現代的非同步事件串流機制;per-CPU map 是高頻場景的無鎖計數方案。
  • hook 種類決定能力邊界:kprobe 動態、tracepoint 穩定、 XDP 最早期最快、LSM 安全策略、cgroup 容器網路——選對 hook 才能以最低開銷達到目標。
  • Cilium 重新定義 Kubernetes 網路:eBPF 替代 iptables, O(1) 查詢、無 sidecar 可觀測性、透明 mTLS——這是雲原生的下一代基礎設施。
  • 誠實面對風險:eBPF 需要特權、verifier 可被繞過、eBPF rootkit 真實存在。 最小權限原則在這裡比任何地方都重要——見第 34 章。

eBPF 是現代 Linux 最強大的可程式化工具,也是容器(見第 87 章) 與雲原生平台(見第 90 章)的底層超能力基礎設施。 理解 eBPF,就是理解下一個十年的 Linux 系統程式設計。
