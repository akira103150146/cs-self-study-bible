手刻最小 RAG

LLM 不知道你的私有資料、也不知道昨天發生的事——而且它還可能用充滿自信的語氣告訴你假答案。RAG(Retrieval-Augmented Generation,檢索增強生成)是讓 AI 先「查書」再「開口」的工程解法。這一章,我們從零手刻它。

LLM 的盲區:私有資料與「一本正經的幻覺」

假設你正在寫一個幫同事查公司內部文件的 agent。你心想:「直接問 LLM 就好了吧?」 然後你測了一下——模型給了一個聽起來完全合理的答案,卻和你的內部規定完全不符。 它沒有說「我不知道」,它說的是「根據業界標準做法……」。

這就是 LLM 的兩個根本限制在同一句話裡同時發生:

  • 知識截止(knowledge cutoff):模型只知道訓練資料截止日前的資訊。 你的公司內部規範、昨天的新聞、上週才更新的 API 文件——它統統不知道。
  • 幻覺(hallucination):在不確定時,模型不會說「我不知道」, 而是「預測最像樣的下一個 token」——這往往是一個聽起來自信但其實是虛構的答案。 (這個機制在第 93 章《從零打造 GPT》裡有完整說明。)

RAG(Retrieval-Augmented Generation,檢索增強生成)是目前業界最廣泛使用的補救方案。 它的核心點子很簡單:在你向 LLM 提問之前,先從你的文件庫裡找出最相關的幾段文字, 然後把這些文字塞進提示裡,讓 LLM「依據這些資料回答」——而不是憑空猜測。

🔑
RAG 的根本邏輯

RAG 不是讓 LLM 「記住更多東西」——而是在每次呼叫前,動態地把相關知識放進它的 context window, 讓它有「依據」可以回答。這是一種工程補丁,不是讓模型變聰明的方法。

RAG 的核心點子:先檢索,再增強,最後生成

RAG 的完整流程只有三個步驟,縮寫就是它的名字本身:

  1. Retrieval(檢索):拿使用者的問題去向量資料庫搜尋,找出語意最相近的 k 個文件片段。
  2. Augmentation(增強):把這些片段拼接成「參考資料」,連同原本的問題一起放進提示。
  3. Generation(生成):把增強後的提示送給 LLM,讓它「依據資料」生成答案。

但在能夠「檢索」之前,你需要先把文件庫「索引化」——也就是把所有文件切成片段、算出嵌入向量、存進向量資料庫。 下面的圖把完整流程分成「離線索引」與「線上查詢」兩個階段:

嵌入(Embedding):把文字變成可搜尋的向量

要做語意搜尋,你需要把文字轉成數字——而且是一種「語意相近的文字,向量也相近」的數字。 這就是嵌入向量(embedding vector):把一段文字壓縮成一個高維實數向量(通常 768 到 4096 維)。 語意相近的文字,嵌入向量的方向也相近;語意無關的文字,向量方向大相徑庭。

第 94 章《手刻你的 LLM client》裡提到 embedding 是 LLM 的另一個能力—— 這一章我們就正式用上它。取得嵌入最簡單的本地方式,是讓 Ollama 跑一個專門的嵌入模型: 

# 下載嵌入模型(nomic-embed-text,384 維,輕量快速)
ollama pull nomic-embed-text

Ollama 的嵌入 API 端點是 /api/embed: 

import requests
import numpy as np

def get_embedding(text: str,
                  model: str = "nomic-embed-text",
                  base_url: str = "http://localhost:11434") -> list[float]:
    """呼叫 Ollama /api/embed 取得文字的嵌入向量。
    前提:ollama serve 執行中,且已 ollama pull nomic-embed-text。
    回傳:長度 384 的 float 串列(nomic-embed-text 的向量維度)。
    """
    resp = requests.post(
        f"{base_url}/api/embed",
        json={"model": model, "input": text},
        timeout=30,
    )
    resp.raise_for_status()
    # Ollama /api/embed 回傳 {"embeddings": [[...]]},取第一個
    return resp.json()["embeddings"][0]


# 快速測試
if __name__ == "__main__":
    v = get_embedding("台灣的首都")
    print(f"向量維度:{len(v)}")   # 384

嵌入模型 vs 生成模型

嵌入模型(如 nomic-embed-text)和生成模型(如 llama3.2)是不同的模型。 嵌入模型只做「文字 → 向量」,速度快、耗資源少;生成模型做「提示 → 文字」,能力強但較重。 RAG 系統通常兩者都需要:嵌入模型負責索引與搜尋,生成模型負責最後的回答。

餘弦相似度:衡量語意接近度

有了嵌入向量,我們需要一個「兩個向量有多像」的衡量標準。 常見的選擇是餘弦相似度(cosine similarity)——它衡量的是兩個向量之間的角度, 而不是距離。向量方向完全一致時,餘弦相似度為 1;正交(無關)時為 0;方向相反時為 -1。

ℹ️
餘弦相似度在第 54 章已教

點積、向量範數、餘弦相似度的數學定義與幾何直覺在 第 54 章《線性代數》有完整推導。 這裡我們直接使用公式,只給最小程式碼實作。

餘弦相似度公式:

$$\text{cosine\_similarity}(\mathbf{a}, \mathbf{b}) = \frac{\mathbf{a} \cdot \mathbf{b}}{\|\mathbf{a}\|\|\mathbf{b}\|}$$

用 numpy 實作只需幾行: 

import numpy as np

def cosine_similarity(a: list[float], b: list[float]) -> float:
    """計算兩個向量的餘弦相似度,回傳 -1.0 到 1.0 之間的浮點數。"""
    va = np.array(a, dtype=np.float32)
    vb = np.array(b, dtype=np.float32)
    norm_a = np.linalg.norm(va)
    norm_b = np.linalg.norm(vb)
    if norm_a == 0.0 or norm_b == 0.0:
        return 0.0                      # 零向量無法計算相似度
    return float(va @ vb / (norm_a * norm_b))   # @ 是矩陣/向量乘法(點積)


# 直覺驗證:語意相同的句子,相似度應接近 1
if __name__ == "__main__":
    emb_fn = get_embedding
    v1 = emb_fn("台灣的首都在哪裡")
    v2 = emb_fn("台北是台灣的首都嗎")
    v3 = emb_fn("如何煮出完美的義大利麵")
    print(f"相似問題:{cosine_similarity(v1, v2):.4f}")   # 預期 > 0.8
    print(f"不相關:{cosine_similarity(v1, v3):.4f}")      # 預期 < 0.4
🔑
為何用餘弦,不用歐氏距離?

嵌入向量的「長度」(norm)和語意無關——同一段文字加了幾個標點符號,向量長度可能不同, 但語意不變。餘弦相似度只看方向不看長度,因此對文字長短更穩健。 這也是為什麼向量資料庫幾乎都預設用餘弦相似度(或等效的內積搜尋)。

切塊(Chunking):讓長文件變得可搜尋

你不能把一整份 100 頁的 PDF 算成一個嵌入向量——這樣的向量是對所有內容的「平均」, 搜尋時幾乎找不到特定細節。正確的做法是先把長文件切塊(chunk): 把它分成一個個小片段,每個片段獨立算嵌入、獨立存進向量資料庫。

切塊的幾個關鍵參數:

  • chunk_size(塊大小):每個片段的目標長度。太短 → 上下文不足,LLM 看不懂; 太長 → 向量「平均掉」了細節,搜尋準確度下降。實務上常用 200–500 字元(或 100–200 tokens)。
  • overlap(重疊):相鄰兩塊共享多少字元。沒有重疊,跨塊的概念可能被切斷; 有重疊(通常 10–20% 的 chunk_size),讓邊界附近的資訊仍能被找到。

最簡單的切塊方法是按固定字元數切、帶重疊: 

def chunk_text(text: str,
               chunk_size: int = 300,
               overlap: int = 50) -> list[str]:
    """把長文字切成帶重疊的固定大小塊。
    chunk_size: 每塊最大字元數
    overlap:    前後兩塊重疊的字元數(避免切斷邊界概念)
    """
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start += chunk_size - overlap   # 往前推 chunk_size - overlap
    return chunks


# 使用範例
sample = "Python 是一種直譯式、高階、通用的程式語言…(接下去很長的文章)" * 10
pieces = chunk_text(sample, chunk_size=200, overlap=40)
print(f"共切出 {len(pieces)} 塊,各塊長度:{[len(p) for p in pieces]}")
⚠️
按字元切不一定對齊語意邊界

固定字元切塊簡單好實作,但可能把一個段落或一句話切斷在中間。 更進階的做法是「按段落 / 句子切」或「遞迴分割」(先試大塊、太長再切小)。 本章先掌握最小可用版本;真實系統可考慮 LangChain 的 RecursiveCharacterTextSplitter 或 Llama-Index 的 SentenceSplitter。

手刻 VectorStore:in-memory 向量資料庫

現在我們有了嵌入函式和切塊函式,可以開始手刻這一章的核心產物: 一個最小的 in-memory 向量資料庫(VectorStore)。 它只需要兩個方法:

  • add(text, metadata):把一段文字加進資料庫——自動算嵌入、連同 metadata 一起存。
  • search(query, k) -> list:用查詢字串搜尋——自動算查詢的嵌入,再算所有文件的餘弦相似度,回傳 top-k 結果。
from __future__ import annotations
import numpy as np
import requests


# ── 嵌入函式(連接 Ollama) ─────────────────────────────────────────────────────

def get_embedding(text: str,
                  model: str = "nomic-embed-text",
                  base_url: str = "http://localhost:11434") -> list[float]:
    """呼叫 Ollama /api/embed 取得嵌入向量。"""
    resp = requests.post(
        f"{base_url}/api/embed",
        json={"model": model, "input": text},
        timeout=30,
    )
    resp.raise_for_status()
    return resp.json()["embeddings"][0]


# ── 餘弦相似度 ────────────────────────────────────────────────────────────────

def cosine_similarity(a: list[float], b: list[float]) -> float:
    """計算兩向量的餘弦相似度(值域 -1 到 1)。"""
    va = np.array(a, dtype=np.float32)
    vb = np.array(b, dtype=np.float32)
    norm_a = np.linalg.norm(va)
    norm_b = np.linalg.norm(vb)
    if norm_a == 0.0 or norm_b == 0.0:
        return 0.0
    return float(va @ vb / (norm_a * norm_b))


# ── VectorStore ───────────────────────────────────────────────────────────────

class VectorStore:
    """最小 in-memory 向量資料庫。
    介面契約(後續章節可依賴):
      add(text: str, metadata: dict | None = None) -> None
      search(query: str, k: int = 3) -> list[dict]
         回傳 list of {"text": str, "score": float, "metadata": dict}
         按 score 遞減排序,最多 k 個。
    """

    def __init__(self, embed_fn=get_embedding):
        self._docs: list[tuple[str, list[float], dict]] = []
        # _docs 每個元素是 (text, embedding, metadata)
        self._embed = embed_fn

    def add(self, text: str, metadata: dict | None = None) -> None:
        """新增一筆文字到向量資料庫。
        自動計算嵌入向量並存入記憶體。
        metadata 可存任意資訊(例如來源檔名、頁碼)。
        """
        emb = self._embed(text)
        self._docs.append((text, emb, metadata or {}))

    def search(self, query: str, k: int = 3) -> list[dict]:
        """語意搜尋:回傳與 query 最相似的 top-k 文件片段。
        回傳格式:list of {"text": str, "score": float, "metadata": dict}
        """
        if not self._docs:
            return []
        q_emb = self._embed(query)
        scored = []
        for text, emb, meta in self._docs:
            score = cosine_similarity(q_emb, emb)
            scored.append({"text": text, "score": score, "metadata": meta})
        # 按相似度遞減排序,取前 k 個
        scored.sort(key=lambda x: x["score"], reverse=True)
        return scored[:k]

    def __len__(self) -> int:
        return len(self._docs)


# ── 端對端使用範例 ────────────────────────────────────────────────────────────

if __name__ == "__main__":
    store = VectorStore()

    # 把幾段文字加進向量資料庫
    docs = [
        ("Python 的 GIL(全局直譯器鎖)限制了多執行緒的真正並行。", {"source": "python_faq.md"}),
        ("asyncio 是 Python 的非同步 I/O 框架,用於高並發 I/O 密集型任務。", {"source": "python_faq.md"}),
        ("機器學習模型訓練時需要大量 GPU 記憶體。", {"source": "ml_notes.md"}),
    ]
    for text, meta in docs:
        store.add(text, meta)

    print(f"已存入 {len(store)} 筆文件")

    # 查詢
    results = store.search("Python 並發程式設計", k=2)
    for r in results:
        print(f"  [score={r['score']:.4f}] {r['text'][:40]}…")
🔑
VectorStore 介面契約(後續章節依賴此定義)

VectorStore.add(text: str, metadata: dict | None = None) -> None:把文字加進向量庫,自動計算並存嵌入。
VectorStore.search(query: str, k: int = 3) -> list[dict]:語意搜尋,回傳按相似度排序的 top-k 結果,每筆含 text、score、metadata。

升級儲存:SQLite 持久化與 FAISS 加速

上面的 VectorStore 用 Python 串列存在記憶體裡——程式一關,所有資料就消失了。 而且 search 是線性掃描(每次都算所有文件的相似度),文件多了就很慢。 這一節介紹兩個升級方向:

SQLite 持久化向量庫

把嵌入向量序列化成 JSON 存進 SQLite,就能跨執行持久保存。 對幾千筆以下的文件,這個方法完全夠用: 

import sqlite3
import json

class SQLiteVectorStore(VectorStore):
    """基於 SQLite 的持久化向量資料庫(適合小到中等規模)。
    繼承 VectorStore,覆寫 add/search,在磁碟上保存嵌入向量。
    """

    def __init__(self, db_path: str = "vector_store.db", embed_fn=get_embedding):
        # 不呼叫父類別 __init__,因為儲存後端完全不同
        self._embed = embed_fn
        self.conn = sqlite3.connect(db_path)
        self.conn.execute("""
            CREATE TABLE IF NOT EXISTS docs (
                id       INTEGER PRIMARY KEY AUTOINCREMENT,
                text     TEXT    NOT NULL,
                embedding TEXT   NOT NULL,
                metadata TEXT    NOT NULL DEFAULT '{}'
            )
        """)
        self.conn.commit()

    def add(self, text: str, metadata: dict | None = None) -> None:
        emb = self._embed(text)
        self.conn.execute(
            "INSERT INTO docs (text, embedding, metadata) VALUES (?, ?, ?)",
            (text, json.dumps(emb), json.dumps(metadata or {})),
        )
        self.conn.commit()

    def search(self, query: str, k: int = 3) -> list[dict]:
        q_emb = self._embed(query)
        rows = self.conn.execute(
            "SELECT text, embedding, metadata FROM docs"
        ).fetchall()
        scored = []
        for text, emb_json, meta_json in rows:
            emb = json.loads(emb_json)
            score = cosine_similarity(q_emb, emb)
            scored.append({
                "text": text,
                "score": score,
                "metadata": json.loads(meta_json),
            })
        scored.sort(key=lambda x: x["score"], reverse=True)
        return scored[:k]

    def __len__(self) -> int:
        return self.conn.execute("SELECT COUNT(*) FROM docs").fetchone()[0]
ℹ️
向量檢索 vs 結構化 SQL 查詢

第 37 章《資料庫系統》介紹的 SQL 是「精確匹配與結構化篩選」—— 你問的是「找出所有 price < 100 的商品」,回答是確定性的。 向量搜尋問的是「找出語意最接近『便宜商品』的文件」——回答是統計性的、有誤差的。 兩者互補:向量搜尋找「語意相近」,SQL 過濾「精確條件」。 真實 RAG 系統常用「混合搜尋」:先用向量搜尋召回候選,再用 SQL / 元資料條件過濾。

FAISS:近似最近鄰(ANN)加速

當文件數量達到幾十萬、幾百萬時,線性掃描就太慢了。 FAISS(Facebook AI Similarity Search)是一個高效能的 近似最近鄰(Approximate Nearest Neighbor,ANN)搜尋函式庫, 能在亞線性時間內找到「幾乎最近」的向量。 

# 安裝 FAISS(CPU 版)
pip install faiss-cpu
import faiss
import numpy as np

class FAISSVectorStore:
    """用 FAISS 加速的向量資料庫骨架(概觀示意,非完整實作)。"""

    def __init__(self, dim: int = 384, embed_fn=get_embedding):
        self._embed = embed_fn
        self._texts: list[str] = []
        self._metas: list[dict] = []
        # IndexFlatIP:內積索引(對 L2 正規化後的向量,內積 == 餘弦相似度)
        self._index = faiss.IndexFlatIP(dim)

    def add(self, text: str, metadata: dict | None = None) -> None:
        emb = self._embed(text)
        vec = np.array([emb], dtype=np.float32)
        faiss.normalize_L2(vec)         # 正規化 → 內積等同餘弦相似度
        self._index.add(vec)
        self._texts.append(text)
        self._metas.append(metadata or {})

    def search(self, query: str, k: int = 3) -> list[dict]:
        q_emb = np.array([self._embed(query)], dtype=np.float32)
        faiss.normalize_L2(q_emb)
        scores, indices = self._index.search(q_emb, k)  # 回傳 shape (1, k)
        results = []
        for score, idx in zip(scores[0], indices[0]):
            if idx < 0:              # FAISS 找不到時回傳 -1
                continue
            results.append({
                "text":     self._texts[idx],
                "score":    float(score),
                "metadata": self._metas[idx],
            })
        return results

FAISS 的 IndexFlatIP 是精確搜尋;更進階的索引(如 IndexIVFFlat)才是真正的 ANN, 能用少量精度損失換來大幅加速。本章不深入 FAISS 內部原理——重點是掌握「向量搜尋的介面是什麼」, 底層索引可以換插。

手刻 rag_answer:三步走的完整 RAG 函式

現在所有積木都齊了。最後一步:把「第 94 章的 LLMClient」和「這一章的 VectorStore」 拼在一起,實作 rag_answer——這一章最重要的對外介面。

完整 rag_answer 實作

from llm_client import LLMClient, get_client   # 第 94 章的介面

def rag_answer(client: LLMClient,
               store: VectorStore,
               query: str,
               k: int = 3) -> str:
    """RAG 主函式:retrieve → augment → generate。
    介面契約(後續章節可依賴):
      client : LLMClient(第 94 章定義)
      store  : VectorStore(本章定義)
      query  : 使用者的問題字串
      k      : 要檢索的文件片段數量
      回傳   : 帶引用來源標記的回答字串
    """
    # Step 1: Retrieve — 語意搜尋,取 top-k 相關片段
    docs = store.search(query, k=k)

    if not docs:
        # 向量庫是空的,降級為純 LLM 回答(並加警告)
        return client.complete(
            f"{query}\n\n(注意:知識庫為空,以下為模型自身知識的回答,可能不準確。)"
        )

    # Step 2: Augment — 把檢索到的片段拼成「參考資料」塊
    context_parts = []
    for i, doc in enumerate(docs, 1):
        source = doc["metadata"].get("source", f"文件{i}")
        context_parts.append(f"[來源 {i} — {source}]\n{doc['text']}")
    context = "\n\n".join(context_parts)

    augmented_prompt = f"""請根據以下參考資料回答問題。
如果參考資料中沒有足夠資訊,請如實說明「資料中未提及」,不要憑空推測。
在回答中請標明你引用的來源編號(例如「根據來源 1」)。

=== 參考資料 ===
{context}

=== 問題 ===
{query}"""

    # Step 3: Generate — 呼叫 LLMClient 生成帶引用的回答
    return client.chat([{"role": "user", "content": augmented_prompt}])

短期記憶 vs 長期記憶

RAG 的 VectorStore 可以扮演 agent 的長期記憶(long-term memory): 把知識文件、歷史對話、工具執行結果都 add 進去,下次問問題時就能「想起來」。 相對地,LLM 的 context window 是短期記憶——只在單次呼叫中有效。 把「有意義的長期記憶寫進 VectorStore」,是讓 agent 具備「記憶感」的核心技術。 

def log_to_memory(store: VectorStore,
                  user_query: str,
                  assistant_reply: str) -> None:
    """把這一輪對話存進 VectorStore 作為長期記憶。"""
    summary = f"用戶問:「{user_query}」,助理回答:「{assistant_reply[:200]}…」"
    store.add(summary, metadata={"type": "conversation_log"})

進階概念:混合檢索、Rerank 與 GraphRAG

最小 RAG 跑起來了。但真實系統常常需要更多:

混合檢索(Hybrid Search):關鍵字 + 向量

純向量搜尋有時會漏掉明確的關鍵字(例如「找所有包含『條款 7.2』的段落」)。 混合檢索結合傳統關鍵字搜尋(BM25)與向量語意搜尋,再用加權融合算最終分數。 Elasticsearch、OpenSearch、Weaviate 等都支援這個模式。

Rerank(重排):讓精準度更高

向量搜尋召回的 top-k 結果有時「看起來相關」但「其實不準」。 Rerank(重排)在 vector search 之後加一個更精準但較慢的模型, 對候選結果重新評分排序。常用工具:Cohere Rerank API、FlashRank(本地)。 典型的 RAG pipeline 變成:vector search(top 20) → rerank → top 5 → LLM。

GraphRAG:用知識圖譜加強關聯推理

標準 RAG 把文件當作獨立的「片段」——但如果你的問題需要跨文件推理 (「A 與 B 有什麼關係?」「為什麼 X 導致了 Y?」),純向量搜尋就力有未逮。 GraphRAG(微軟提出)先用 LLM 從文件中抽取「實體 - 關係 - 實體」三元組, 建成知識圖譜(knowledge graph),然後圍繞相關節點做圖遍歷再送 LLM。 適合需要多跳推理的複雜問答場景,但建置成本也顯著更高。

💡
什麼時候需要進階技術?

對多數的私有文件問答場景,最小 RAG(本章)就夠用了。 只有當你發現「明明文件裡有答案,但 RAG 找不到」或「需要多文件推理」時,才考慮混合檢索或 GraphRAG。 優先把基礎做好:選對切塊大小、確認嵌入模型語意對得上查詢、過濾無關文件。

RAG 的誠實邊界:能做什麼,不能做什麼

RAG 是非常有用的技術,但業界對它有許多常見的誤解,值得在這裡誠實說清楚。

RAG 能做的

  • 讓 LLM 依據你的文件回答問題,而不是憑空猜測。
  • 注入最新資訊:截止日後的新聞、API 更新都能即時加進向量庫。
  • 提供引用來源:每個答案都能附上「這段話來自哪裡」的可查證資訊。
  • 顯著降低幻覺率——在有相關文件的問題上。

RAG 做不到的

  • RAG 無法完全消除幻覺。如果相關文件沒有被檢索到(切塊太大?語意不匹配?), LLM 仍然可能幻覺。即使文件被找到,LLM 還是可能曲解、斷章取義。 「提供了參考資料」≠「答案一定正確」。
  • RAG 依賴嵌入品質。如果嵌入模型對你的領域語言(法律、醫療、台灣在地用語) 語意捕捉不夠好,搜尋結果就會不準確。
  • 切塊不當會讓搜尋失效。塊太大(語意被稀釋)或太小(上下文不足)都會讓 retrieval 效果大打折扣。
  • RAG 不是向量資料庫的萬靈丹。結構化查詢(「找出所有 2025 年的訂單」)還是用 SQL 更精確。
⚠️
常見的 RAG 錯誤期待

「加了 RAG 就不會幻覺了」——這是錯的。RAG 降低了特定類型的幻覺,但沒有消滅它。 你的系統仍然需要對答案做驗證(在關鍵決策場景尤其重要)。 誠實地告訴使用者「以下回答基於這幾段文件」,並讓他們能點開查原文,比「相信 AI 說的」更安全。

練習

✏️ 練習 96.1 實作

修改 chunk_text 函式,讓它接受一個額外的參數 by_sentence: bool = False。 當 by_sentence=True 時,改用句子邊界(中文句號 。 或英文 .)切塊, 而不是固定字元數。切出來的塊不要超過 chunk_size 個字元;如果單句就超過,則單獨成一塊。 然後把同樣一段文字分別用「固定字元切」和「按句子切」兩種方式各切一次,比較哪種方式的切塊邊界更乾淨。

看解答 
import re

def chunk_text(text: str,
               chunk_size: int = 300,
               overlap: int = 50,
               by_sentence: bool = False) -> list[str]:
    """切塊函式,支援固定字元與按句子兩種模式。"""
    if not by_sentence:
        # 原本的固定字元切法
        chunks = []
        start = 0
        while start < len(text):
            end = start + chunk_size
            chunks.append(text[start:end])
            start += chunk_size - overlap
        return chunks

    # 按句子切:先拆成句子,再貪婪合併直到超過 chunk_size
    sentence_endings = re.compile(r"(?<=[。！？.!?])\s*")
    sentences = sentence_endings.split(text)
    sentences = [s.strip() for s in sentences if s.strip()]

    chunks = []
    current = ""
    for sent in sentences:
        if len(current) + len(sent) <= chunk_size:
            current += sent
        else:
            if current:
                chunks.append(current)
            # 單句超過 chunk_size 時單獨成塊
            current = sent
    if current:
        chunks.append(current)
    return chunks


# 比較兩種切法
sample = ("Python 的 asyncio 讓你寫出非同步程式碼。"
          "它基於事件迴圈(event loop)運作。"
          "當你 await 一個 coroutine,控制權會回到事件迴圈,讓其他任務執行。"
          "這對 I/O 密集型任務非常有效,例如爬蟲或 API 呼叫。")

fixed  = chunk_text(sample, chunk_size=50, overlap=10, by_sentence=False)
by_sent = chunk_text(sample, chunk_size=50, overlap=0, by_sentence=True)
print("固定字元切:", fixed)
print("按句子切:", by_sent)

按句子切的好處:每個塊都是完整的句子,語意不會在句中截斷,嵌入向量更能代表這個句子的意思。 代價:塊大小不均勻,有時一塊很短(單句很短)、有時接近 chunk_size(單句很長)。 實務上,大多數成熟的框架用「遞迴切塊」:先試按段落切,太長再試按句子切,再太長才按字元切。

✏️ 練習 96.2 實作

為 rag_answer 加上「來源引用標註」的後處理: 在函式回傳的字串後面,自動附加一個「--- 參考來源 ---」區塊, 列出這次 retrieve 到的所有文件的來源(從 metadata["source"] 取)與相似度分數(保留 4 位小數)。 不要改動 LLM 生成的部分,只在結尾附加這個區塊。

def rag_answer_with_citations(client: LLMClient,
                               store: VectorStore,
                               query: str,
                               k: int = 3) -> str:
    """rag_answer 的加強版:在答案結尾附帶引用來源清單。"""
    docs = store.search(query, k=k)

    if not docs:
        answer = client.complete(

        )
        return answer + "\n\n--- 參考來源 ---\n(無:知識庫為空)"

    context_parts = []
    for i, doc in enumerate(docs, 1):
        source = doc["metadata"].get("source", f"未知來源{i}")
        context_parts.append(f"[來源 {i} — {source}]\n{doc['text']}")
    context = "\n\n".join(context_parts)

    augmented_prompt = f"""請根據以下參考資料回答問題。
如果資料中沒有足夠資訊,請如實說明,不要憑空推測。
請在回答中標明引用的來源編號(例如「根據來源 1」)。

=== 參考資料 ===
{context}

=== 問題 ===
{query}"""

    answer = client.chat([{"role": "user", "content": augmented_prompt}])

    # 後處理:附加引用區塊
    citation_lines = ["", "--- 參考來源 ---"]
    for i, doc in enumerate(docs, 1):
        source = doc["metadata"].get("source", f"未知來源{i}")
        score  = doc["score"]
        citation_lines.append(f"  [{i}] {source}  (相似度: {score:.4f})")
    citation_block = "\n".join(citation_lines)

    return answer + citation_block

這個模式在真實 RAG 系統中非常重要——使用者能看到「這個答案是根據哪些文件得出的」, 就能自行驗證正確性,而不是盲目相信 AI。 相似度分數也提示了「這次找到的文件有多相關」——如果 top-1 的分數很低(例如 0.3 以下), 通常代表向量庫裡沒有真正相關的文件,LLM 可能在胡說。

✏️ 練習 96.3 挑戰

實作一個簡單的關鍵字 + 向量混合搜尋。 為 VectorStore 加一個方法 hybrid_search(query, k=3, alpha=0.5), 其中 alpha 控制向量相似度的權重(1-alpha 給關鍵字分數)。 關鍵字分數的簡單定義:查詢中的詞在文件中出現幾個就得幾分,再除以文件長度正規化。 最後把 alpha * cosine_score + (1-alpha) * keyword_score 作為混合分數排序。 用一個例子說明什麼情況下混合搜尋的結果比純向量搜尋更準確。

看解答 
class HybridVectorStore(VectorStore):
    """支援關鍵字 + 向量混合搜尋的 VectorStore。"""

    def _keyword_score(self, query: str, text: str) -> float:
        """簡單關鍵字分數:查詢詞在文件中出現的頻率。"""
        query_terms = set(query.lower().split())
        text_lower  = text.lower()
        hit_count   = sum(1 for t in query_terms if t in text_lower)
        # 正規化:避免長文件因有更多詞而佔便宜
        return hit_count / (len(query_terms) + 1e-9)

    def hybrid_search(self,
                      query: str,
                      k: int = 3,
                      alpha: float = 0.5) -> list[dict]:
        """alpha=1.0 → 純向量; alpha=0.0 → 純關鍵字; 0.5 → 各半。"""
        if not self._docs:
            return []
        q_emb = self._embed(query)
        results = []
        for text, emb, meta in self._docs:
            vec_score = cosine_similarity(q_emb, emb)
            kw_score  = self._keyword_score(query, text)
            combined  = alpha * vec_score + (1 - alpha) * kw_score
            results.append({
                "text": text,
                "score": combined,
                "vec_score": vec_score,
                "kw_score": kw_score,
                "metadata": meta,
            })
        results.sort(key=lambda x: x["score"], reverse=True)
        return results[:k]


# 混合搜尋更準確的場景示範
store = HybridVectorStore()
store.add("Python GIL 限制多執行緒並行", {"source": "a"})
store.add("條款 7.2:合約終止須提前 30 天書面通知", {"source": "b"})
store.add("條款 3.1:服務費用每月自動扣款", {"source": "c"})

# 純向量可能找到語意相近但不含「7.2」的段落
# 混合搜尋能保證「條款 7.2」的精確詞出現優先
results = store.hybrid_search("條款 7.2 是什麼", k=2, alpha=0.3)
for r in results:
    print(f"[{r['score']:.3f}] {r['text'][:50]}")

這個例子說明混合搜尋的典型使用場景:當查詢包含專有名詞、合約編號、版本號等精確標識符時, 純向量搜尋可能因語意向量無法區分「條款 7.2」和「條款 3.1」而搜到錯的段落; 但加入關鍵字分數,含有精確字串「7.2」的段落就能得到更高的總分。 alpha 值可依業務場景調整:法律/技術文件用較低 alpha(重關鍵字); 一般問答用較高 alpha(重語意)。

把這一章串起來

這一章我們從零手刻了一個完整的最小 RAG 系統。回顧核心產物:

  • 嵌入函式:get_embedding(text) -> list[float]——呼叫 Ollama /api/embed 取得語意向量。
  • 餘弦相似度:cosine_similarity(a, b) -> float——用 numpy 的 @(點積)與 np.linalg.norm 計算,只看向量角度不看長度(連回第 54 章)。
  • 切塊:chunk_text(text, chunk_size, overlap)——把長文件切成帶重疊的小片段,讓每段都能被語意搜尋到。
  • VectorStore(本章核心產物):
    • add(text, metadata) -> None:自動算嵌入、存進記憶體(或 SQLite)。
    • search(query, k) -> list[dict]:語意搜尋,回傳按餘弦相似度排序的 top-k 結果。
  • rag_answer(本章核心產物): rag_answer(client, store, query) -> str——把第 94 章的 LLMClient 和 VectorStore 接起來,固定走「retrieve → augment → generate」三步,回傳帶引用的答案。
  • 誠實認知:RAG 顯著降低幻覺率,但不能完全消除。切塊品質、嵌入模型選擇、k 值設定都影響準確率。對 SQL 精確查詢需求(如第 37 章所述),向量搜尋不能取代結構化查詢。

有了 VectorStore 和 rag_answer,你的 agent 現在有了「長期記憶與知識檢索」的能力。 第 95 章《工具呼叫與 ReAct》讓 agent 能執行工具;這一章讓它能查閱知識。 下一章(第 97 章)我們要把這些工具的定義與資料源存取標準化——用 MCP(Model Context Protocol)讓 agent 與工具的接口變成可插拔、可組合的生態系。
