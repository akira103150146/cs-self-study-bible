少數強核 vs 海量弱核：CPU 與 GPU 的根本哲學差異

想像你要把一億個浮點數兩兩相加。用 CPU 做，你有 16 個高頻核心， 每個核心有亂序執行(out-of-order)、分支預測、大快取——是個全能的「廚師長」， 什麼工作都能高效完成，但同時只能讓 16 個廚師長上工。

GPU 的思路完全不同。一塊現代 GPU 可能有 6,000–16,000 個「迷你核心」， 每個核心的單執行緒效能遠不如 CPU，沒有複雜的亂序引擎，快取也小； 但它們同時執行同一段程式——只是資料不同。把那一億個加法分給一億個 （虛擬的）執行緒，每個執行緒只算一對，全部同時跑完， 這就是 GPU 計算的核心思想。

🔑
CPU vs GPU 設計哲學

CPU 把大部分晶片面積給了控制邏輯與快取，追求單執行緒延遲(latency)最小化。 GPU 把面積給了算術單元(ALU)，追求聚合吞吐(throughput)最大化， 用執行緒切換隱藏記憶體存取延遲。

為什麼深度學習天生適合 GPU？因為訓練一個神經網路的核心操作是矩陣乘法(matrix multiplication)—— 你在第 54 章學過它的數學，在 第 93 章看到它撐起了 GPT 的 attention 計算。 矩陣乘法有個完美的特性：每一個輸出元素的計算之間完全獨立， 可以無限並行。幾千個 CUDA 核心同時計算矩陣裡的幾千個格子——這就是為什麼 一張 GPU 能讓訓練速度比 CPU 快 100 倍。

CUDA(Compute Unified Device Architecture)是 NVIDIA 在 2006 年發布的 GPU 通用計算平台，讓開發者能用類 C 的語言直接撰寫在 GPU 上執行的程式。 本章以 CUDA C 為主，你在這裡學到的概念——SIMT、warp、共享記憶體、 合併存取——在 OpenCL、Metal Compute 與 WebGPU Compute Shader 裡同樣適用。

📜
GPU 通用計算的誕生

2006 年之前，研究者只能把科學計算「偽裝」成圖形問題，才能用 GPU 跑。 CUDA 的發布讓 GPU 真正成為通用計算平台。2012 年 AlexNet 在 ImageNet 競賽上以 GPU 訓練奪冠， 把 GPU 訓練推進主流——從此 GPU 不再只是遊戲顯示卡， 而是 AI 時代最珍貴的算力資源。

GPU 硬體模型：SM、CUDA Core、Warp 與執行緒三層階層

打開一塊 NVIDIA GPU，你會看到幾個層次的組織：

  • GPU 晶片：整塊裝置，有幾十到上百個 SM。
  • SM(Streaming Multiprocessor，串流多處理器)：GPU 的基本運算單元， 類似 CPU 的「一個核心」，但比 CPU 核心簡單得多。 每個 SM 包含幾十到上百個 CUDA core、共享記憶體(shared memory)、 暫存器檔案(register file)、warp scheduler。
  • CUDA Core：SM 內部最小的算術執行單元，能做浮點加法或乘法。
  • Warp(線束)：32 個執行緒的群組，是 GPU 排程的最小單位。 一個 warp 內所有執行緒同步執行同一條指令，只是各自處理不同的資料。

從程式設計師的視角，你把工作組織成三層：

對照到硬體：當你啟動一個 kernel 時，CUDA 執行期(runtime)會把你的 block 分配到 GPU 上各個 SM； 每個 SM 負責執行分配給它的所有 block。一個 SM 同時可以駐留(resident)多個 warp—— 當某個 warp 在等待記憶體讀取時，SM 立刻切換執行另一個 warp，完全不需要儲存上下文(context switch)的開銷， 因為每個 warp 都有自己獨立的暫存器。

ℹ️
Block 大小的慣例

Block 的執行緒數必須是 warp size(32)的倍數，常用 128、256、512、1024。 每個 block 最大 1024 個執行緒(現代 GPU 皆同)； 每個 SM 可同時駐留多個 block，合計最多約 2048 個執行緒(架構而異)。 選 256 是個安全的起點，因為它讓每個 block 有 8 個 warp，SM 的 warp scheduler 有足夠的 warp 可以切換。

SIMT 執行模型：鎖步、分支發散與 Warp 效率

GPU 採用 SIMT(Single Instruction, Multiple Threads，單一指令多執行緒) 模型—— 在你從第 48 章學到的 SIMD 之上再加一層抽象。 在同一個 warp 裡的 32 個執行緒，在任意一個時鐘週期，執行的是同一條指令； 差別只在它們處理的資料(寄存器值)不同。

鎖步執行(Lockstep Execution)

把 warp 想像成一列 32 個士兵，他們被命令「一起舉右手、一起放下、一起邁左腳」。 每一個時鐘週期，指揮官(warp scheduler)廣播一條指令，所有士兵同時執行， 用各自持有的「資料」(registers)做運算。這樣的設計讓硬體非常簡單—— 你不需要為 32 個核心分別維護 32 個 instruction fetch / decode 單元，一套就夠了。

分支發散(Branch Divergence)的代價

問題來了：如果那 32 個士兵要做「如果你是第一組，舉右手；否則舉左手」這種判斷呢？ 在 CPU 執行緒裡，每個執行緒獨立決定跳不跳轉，沒有任何問題。 在 CUDA warp 裡，因為必須鎖步，GPU 的做法是：

  1. 先讓「條件為真」的執行緒執行 then-branch，「條件為假」的執行緒此時被遮罩(mask off)，空轉。
  2. 再讓「條件為假」的執行緒執行 else-branch，「條件為真」的執行緒空轉。

如果 warp 裡有一半執行緒走 if、另一半走 else，那麼有效利用率只剩 50%。 極端情況(每個執行緒走不同路徑)會讓效能掉成 1/32。

⚠️
避免 warp 內的分支發散

最佳實務是讓同一個 warp(連續 32 個執行緒)在遇到分支時都走同一條路。 常見技法：把邏輯上不同的「工作類型」安排到不同的 block， 或用資料重排(data rearrangement)把同類資料聚在一起。 若分支發散不可避免(如只在邊界執行緒做邊界檢查)，代價往往可接受， 因為邊界執行緒只佔少數 warp。

記憶體階層：Global、Shared、Register 與合併存取

GPU 的記憶體階層是理解效能的核心。不懂這個，你寫的 CUDA 程式可能比 CPU 還慢。

四種記憶體空間

記憶體類型位置大小延遲頻寬可見範圍
Register(暫存器) SM 片上 每執行緒 ~255 個 ~1 cycle 極高 單一執行緒
Shared Memory(共享記憶體) SM 片上 每 SM 48–228 KB ~5 cycle 極高 同一 block 內所有執行緒
L1 / L2 Cache SM / 晶片 幾 MB ~30–100 cycle 高 自動管理
Global Memory(全域記憶體/VRAM) 裝置 DRAM(HBM) 8–80 GB ~200–600 cycle 高(但需合併) 所有執行緒
Constant Memory(常數記憶體) 裝置(有快取) 64 KB ~5 cycle(命中) 中 唯讀，所有執行緒

合併存取(Coalescing)：為何它是第一要義

GPU 的全域記憶體控制器每次讀取是一個 128 bytes 的交易(transaction)。 如果一個 warp 的 32 個執行緒讀取的是連續的、對齊的 128 bytes（每個執行緒讀 4 bytes 的 float）， 控制器只需發出 1 次記憶體交易就能滿足所有 32 個執行緒的需求——這叫「合併存取」。

反之，如果 32 個執行緒讀取的是隨機散落的位址，控制器最多需要發出 32 次交易， 頻寬利用率只有 1/32（~3%）。兩者效能差距可達 10–30 倍。

💡
確保合併存取的鐵律

讓第 i 個執行緒存取 arr[i] 而非 arr[i * stride]。 若你的演算法必須走 column-major，考慮先轉置矩陣(一次性代價)， 再以 row-major 方式存取。共享記憶體的 bank conflict 是另一個需要注意的地方， 見後面 §平行歸約 的討論。

你的第一個 CUDA Kernel：向量加法

理論夠了，動手寫。CUDA 程式設計的最小工作單元叫做 kernel， 以 __global__ 修飾詞宣告，在 host(CPU)端啟動，在 device(GPU)端執行。

以下是完整的向量加法範例：C[i] = A[i] + B[i]。 請特別注意 host 端的記憶體管理流程與 kernel 啟動語法。 

/* vec_add.cu — 在 GPU 上平行計算 C[i] = A[i] + B[i]
 * 編譯：nvcc vec_add.cu -o vec_add
 * 執行：./vec_add
 */
#include <stdio.h>
#include <cuda_runtime.h>

/* ① Kernel：__global__ 表示在 GPU 上執行，由 CPU 呼叫 */
__global__ void vecAdd(float *A, float *B, float *C, int N) {
    /* 每個執行緒計算自己負責的索引 */
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N)          /* 邊界防護：最後一個 block 可能不滿 */
        C[i] = A[i] + B[i];
}

int main(void) {
    int N = 1 << 20;            /* 2^20 = 1,048,576 個元素 */
    size_t bytes = N * sizeof(float);

    /* ② Host 端配置記憶體 */
    float *h_A = (float *)malloc(bytes);
    float *h_B = (float *)malloc(bytes);
    float *h_C = (float *)malloc(bytes);
    for (int i = 0; i < N; i++) { h_A[i] = 1.0f; h_B[i] = 2.0f; }

    /* ③ Device 端配置記憶體 */
    float *d_A, *d_B, *d_C;
    cudaMalloc(&d_A, bytes);   /* &d_A：傳指標的指標 */
    cudaMalloc(&d_B, bytes);
    cudaMalloc(&d_C, bytes);

    /* ④ Host → Device 資料搬移 */
    cudaMemcpy(d_A, h_A, bytes, cudaMemcpyHostToDevice);
    cudaMemcpy(d_B, h_B, bytes, cudaMemcpyHostToDevice);

    /* ⑤ 啟動 Kernel：<<<gridDim, blockDim>>> */
    int BLOCK = 256;
    int GRID  = (N + BLOCK - 1) / BLOCK;   /* 向上取整 */
    vecAdd<<<GRID, BLOCK>>>(d_A, d_B, d_C, N);

    /* ⑥ Device → Host 取回結果 */
    cudaMemcpy(h_C, d_C, bytes, cudaMemcpyDeviceToHost);

    /* ⑦ 驗證 */
    printf("h_C[0] = %.1f (期待 3.0)\n", h_C[0]);
    printf("h_C[%d] = %.1f (期待 3.0)\n", N - 1, h_C[N - 1]);

    /* ⑧ 釋放記憶體 */
    cudaFree(d_A); cudaFree(d_B); cudaFree(d_C);
    free(h_A); free(h_B); free(h_C);
    return 0;
}

讓我們逐步拆解關鍵點：

  • __global__：告訴 nvcc 這個函式要在 GPU 上執行，但只能由 CPU 呼叫。 相對地，__device__ 函式由 GPU 呼叫、在 GPU 上執行； __host__ 是預設，只在 CPU 上執行。
  • 三層括號 <<<GRID, BLOCK>>>：CUDA 的 kernel 啟動語法， 指定格子大小(grid)與 block 大小。例如 <<<4096, 256>>> 表示 啟動 4096 個 block、每個 block 256 個執行緒，總計 4096 × 256 = 1,048,576 個執行緒。
  • blockIdx.x * blockDim.x + threadIdx.x：這個公式計算出每個執行緒的 全域索引，是幾乎所有 CUDA kernel 的第一行。blockIdx 告訴你「我在第幾個 block」， blockDim 是每個 block 的執行緒數，threadIdx 是在 block 內的位置。
  • if (i < N)：當 N 不是 BLOCK 的整數倍時，最後一個 block 的部分執行緒索引會超界，需要這道防護牆。
  • cudaMalloc(&d_A, bytes)：注意傳的是指標的指標(float **)， 因為函式需要修改指標本身的值。
⚠️
CUDA 錯誤檢查

生產環境中，每個 CUDA API 呼叫都應檢查回傳值。 慣用做法是包一個 CUDA_CHECK 巨集： cudaMalloc(&ptr, size) 成功時回傳 cudaSuccess(0)，失敗時回傳錯誤碼。 核心啟動後用 cudaGetLastError() 取得 async 錯誤。 錯誤若不處理，程式會靜默崩潰，極難偵錯。

手刻矩陣乘法：Naive 版 → Tiled Shared Memory 版

矩陣乘法 $C = A \times B$，其中 $A, B, C$ 均為 $N \times N$ 的方陣， 在第 54 章你用 Python 算過。 現在我們用 CUDA 把它從 $O(N^3)$ 的計算量分散到數千個執行緒上平行完成。

Naive 版本

最直觀的想法：每個執行緒計算輸出矩陣的一個元素 C[row][col]。 

/* Naive matmul：每個執行緒獨立算 C[row][col]，所有資料從 global memory 讀取 */
__global__ void matMulNaive(float *A, float *B, float *C, int N) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < N && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < N; k++)
            sum += A[row * N + k] * B[k * N + col];
        C[row * N + col] = sum;
    }
}
/* 啟動：dim3 block(16,16); dim3 grid((N+15)/16, (N+15)/16);
 *       matMulNaive<<<grid, block>>>(d_A, d_B, d_C, N);
 */

問題在哪裡？以 block(16,16) 分析：A[row*N + k] 中 row 取決於 threadIdx.y，同一 warp 的不同執行緒 row 相差 1，位址間距 N×4 bytes—— 造成 A 在 warp y 維度的 stride-N 非合併存取。此外，每個輸出 block 都各自重複從 global memory 載入 A、B(無 block 內共享)，記憶體交易量龐大。 tiled 版本把 A-tile、B-tile 載進 shared memory 供整個 block 重用，大幅減少 global memory 存取。

Tiled 版本：用共享記憶體切 Tile

改進的核心思路：把矩陣切成 TILE × TILE 的小塊(tile)， 每個 block 負責計算輸出的一個 tile；計算前先把對應的 A-tile 和 B-tile 搬進 共享記憶體，再從共享記憶體讀取做乘積。 共享記憶體只需~5個 cycles，而 global memory 需要 200–600 個 cycles—— tiling 把 global memory 存取次數從 $O(N^3)$ 降到 $O(N^3 / \text{TILE})$。 

#define TILE 16

/* Tiled matmul：用共享記憶體大幅降低 global memory 流量 */
__global__ void matMulTiled(float *A, float *B, float *C, int N) {
    /* 每個 block 在共享記憶體裡各放一個 A-tile 與 B-tile */
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    int row = blockIdx.y * TILE + threadIdx.y;
    int col = blockIdx.x * TILE + threadIdx.x;
    float sum = 0.0f;

    /* 沿 K 維度分段走，每段載入一個 tile */
    for (int t = 0; t < (N + TILE - 1) / TILE; t++) {
        /* 協作式載入：這個 block 的每個執行緒各搬一個元素進 shared memory */
        int aCol = t * TILE + threadIdx.x;
        int bRow = t * TILE + threadIdx.y;
        As[threadIdx.y][threadIdx.x] = (row < N && aCol < N) ? A[row * N + aCol] : 0.0f;
        Bs[threadIdx.y][threadIdx.x] = (bRow < N && col < N) ? B[bRow * N + col] : 0.0f;

        __syncthreads();   /* 確保 tile 完全載入後再計算 */

        /* 從共享記憶體讀取做點積 */
        for (int k = 0; k < TILE; k++)
            sum += As[threadIdx.y][k] * Bs[k][threadIdx.x];

        __syncthreads();   /* 確保計算完成後再載入下一個 tile */
    }

    if (row < N && col < N)
        C[row * N + col] = sum;
}
/* 啟動：dim3 block(TILE, TILE);
 *       dim3 grid((N+TILE-1)/TILE, (N+TILE-1)/TILE);
 *       matMulTiled<<<grid, block>>>(d_A, d_B, d_C, N);
 */

關鍵：__syncthreads() 出現了兩次：

  1. 第一次：在載入 tile 後，確保 block 內所有執行緒都已把資料寫入共享記憶體， 才能安全開始讀取。
  2. 第二次：在計算完這個 tile 後，確保所有執行緒都用完了共享記憶體裡的資料， 才能讓其他執行緒覆蓋它(準備下一個 tile)。
🔑
Tiling 加速的來源

TILE=16 的 tiled matmul，每個 block 只需讀取 global memory $2N/\text{TILE}$ 次 (每個 tile 一次)，而 naive 版需讀 $2N$ 次。加速比 ≈ TILE。 TILE=32 帶來 32 倍的記憶體流量降低。這正是 cuBLAS 與 PyTorch 底層 gemm kernel 的核心技術。

平行歸約：Tree Reduction 與 Bank Conflict

歸約(reduction)——把一個陣列的所有元素合併成單一值(如求和、求最大值)—— 是 GPU 程式設計的另一個基礎模式，也是最容易踩雷的地方。

樹狀歸約(Tree Reduction)

直覺做法：每一輪讓一半的執行緒把相鄰的兩個值相加，如此經過 $\log_2(\text{blockDim})$ 輪， block 的 smem[0] 就是區段的和。 

/* reduction.cu：每個 block 把自己負責的段落求和，寫入 out[] */
__global__ void reduceSum(float *in, float *out, int N) {
    __shared__ float smem[256];           /* 每個 block 256 個執行緒 */
    int tid = threadIdx.x;
    int i   = blockIdx.x * blockDim.x + threadIdx.x;

    /* ① 載入：每個執行緒把自己的元素放進 smem；超界補 0 */
    smem[tid] = (i < N) ? in[i] : 0.0f;
    __syncthreads();

    /* ② 樹狀歸約：stride 從 blockDim/2 開始，每輪減半 */
    for (int stride = blockDim.x >> 1; stride > 0; stride >>= 1) {
        if (tid < stride)
            smem[tid] += smem[tid + stride];
        __syncthreads();
    }

    /* ③ 只有 thread 0 把 block 的和寫到全域記憶體 */
    if (tid == 0)
        out[blockIdx.x] = smem[0];
}
/* 啟動：reduceSum<<<GRID, 256>>>(d_in, d_partial, N);
 * 若 GRID > 1，還需要再對 d_partial 做一次 reduction
 */

為何不用連續 stride 的舊版寫法？

一個常見的錯誤版本是讓執行緒 0 跟執行緒 stride 配對，然後讓 tid 0 到 stride-1 工作—— 這會讓只有 warp 0 工作，其他 warp 空轉，並且在 stride 變小後造成 warp 內發散。 上面的版本讓 index 最小的 tid 繼續工作，確保每一輪工作的執行緒都在連續的 warp 裡， 避免 warp 間的浪費。

Bank Conflict

共享記憶體被組織成 32 個「記憶體銀行(bank)」，每個銀行寬 4 bytes。 如果同一個 warp 的多個執行緒存取同一個 bank（但不是同一個位址，那是 broadcast）， 就會發生 bank conflict，存取被序列化。 tiled matmul 中的 Bs[k][threadIdx.x] 若 TILE 恰好等於 32， 每輪 k 固定，所有執行緒存取 Bs[k][0..31]，它們散落在不同 bank，沒有 conflict——這是精心設計的。 本例 TILE=16 時同理(無 bank conflict)。

同步原語：__syncthreads()、競態與原子操作

__syncthreads() 的語意

__syncthreads() 是一個 block 層級的屏障(barrier)： block 內所有執行緒都必須到達這個呼叫點，才能繼續往下執行。 它只對同一個 block 內有效——不同 block 的執行緒之間沒有直接同步機制 （因為它們可能在不同 SM 上，甚至不同時被調度）。

⛔
__syncthreads() 不能在分支內呼叫

若一個 block 內只有部分執行緒執行到 __syncthreads() (例如它在 if (tid < 16) 的分支裡)，行為是未定義的， 通常導致死鎖或資料損毀。請確保 __syncthreads() 在 block 內所有執行緒都會走到的路徑上。

競態條件(Race Condition)

在第 43 章，你見過多執行緒在 CPU 上操作共享變數導致競態。 GPU 裡同樣有這個問題。若多個執行緒同時寫入同一個 global memory 位址而沒有同步， 結果是不確定的——取決於哪個 warp 最後寫入。

原子操作(Atomic Operations)

CUDA 提供原子操作函式，保證讀-改-寫的不可分割性： 

/* atomicAdd：以原子方式把 val 加到 *address，回傳原值 */
__global__ void countPositive(float *data, int *count, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N && data[i] > 0.0f)
        atomicAdd(count, 1);   /* 多個執行緒安全地更新同一個計數器 */
}

常用原子操作：atomicAdd、atomicMax、atomicMin、 atomicExch(exchange)、atomicCAS(compare-and-swap)。 原子操作對 global memory 或 shared memory 都有效；對 shared memory 的原子操作延遲更低。

⚠️
原子操作的代價

原子操作會序列化競爭的存取，高競爭(hot spot)時吞吐大幅下降。 最佳實踐是先讓每個 block 用 shared memory 歸約出局部結果， 再以 atomicAdd 把局部結果合併到 global 計數器， 把原子競爭從「所有執行緒」降低到「每個 block 只發一次」。

生態系：cuBLAS、cuDNN、Thrust 與 Tensor Core

手刻 CUDA kernel 是理解底層的必修課，但生產環境中你幾乎不需要自己寫 matmul—— 因為 NVIDIA 已經有一整套高度優化的函式庫。

cuBLAS：GPU 版 BLAS

cuBLAS(CUDA Basic Linear Algebra Subroutines) 提供 GPU 加速的矩陣乘法、 向量操作等，相當於 CPU 上的 OpenBLAS / MKL。 單一個 cublasSgemm(single-precision general matrix multiply)呼叫， 底層可能用了幾十種針對不同矩陣尺寸優化的 kernel， 並利用 Tensor Core 達到接近理論峰值吞吐。

cuDNN：深度學習運算元函式庫

cuDNN(CUDA Deep Neural Network library) 提供卷積、池化、 批次正規化(batch normalization)、注意力(attention)等深度學習特有的運算—— 並且針對不同輸入形狀自動選擇最快的 kernel。PyTorch 與 TensorFlow 的卷積與 transformer 層底層都呼叫 cuDNN。

Thrust：GPU 的 C++ STL

Thrust 提供 GPU 版的 sort、reduce、transform、scan 等演算法， API 設計與 C++ STL 相同，讓 GPU 程式設計更像寫普通 C++ 程式： 

#include <thrust/device_vector.h>
#include <thrust/reduce.h>

thrust::device_vector<float> d_vec(N, 1.0f);   /* 在 GPU 上分配並初始化 */
float total = thrust::reduce(d_vec.begin(), d_vec.end(), 0.0f);
/* total == N，完全不需要手寫 kernel */

Tensor Core：混合精度矩陣乘法的硬體加速器

從 Volta 架構(2017)開始，NVIDIA GPU 加入了 Tensor Core—— 專門做 $D = A \times B + C$ 矩陣乘加的硬體單元，且在更低的精度下(FP16/BF16/INT8) 運算速度是傳統 CUDA core 的 8–16 倍。 深度學習的訓練和推論大量使用 FP16 或 BF16（brain float，犧牲精度換速度）， 配合 Tensor Core 可以讓一塊 H100 達到 3,958 TFLOPS 的峰值算力。

你在第 38 章學到的神經網路， 在第 93 章自己打造的 GPT—— 它們能在合理時間內訓練，全仰賴 cuDNN + Tensor Core 這一套硬體軟體協同設計的奇蹟。

ℹ️
從 CUDA kernel 到 PyTorch 的距離

呼叫 torch.matmul(A, B) 時，PyTorch 會判斷張量是否在 GPU 上， 若是則分派到 cuBLAS 的 cublasSgemm（或 Tensor Core 版本）， 後者再呼叫對應的高度優化 CUDA kernel。 從你的 Python 程式碼，到最終在幾千個 CUDA core 上爆發出的計算， 中間就是這幾層分派。

練習

✏️ 練習 112.1 實作

撰寫一個 CUDA kernel saxpy，執行 SAXPY(Single-precision A·X Plus Y)運算： y[i] = alpha * x[i] + y[i]，其中 alpha 是純量。 並撰寫對應的 host 端程式碼(cudaMalloc、Memcpy、kernel 啟動、結果驗證)。

看解答 
/* saxpy.cu */
#include <stdio.h>
#include <cuda_runtime.h>

__global__ void saxpy(float alpha, float *x, float *y, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N)
        y[i] = alpha * x[i] + y[i];
}

int main(void) {
    int N = 1 << 20;
    size_t bytes = N * sizeof(float);
    float alpha = 2.5f;

    float *h_x = (float *)malloc(bytes);
    float *h_y = (float *)malloc(bytes);
    for (int i = 0; i < N; i++) { h_x[i] = 1.0f; h_y[i] = 3.0f; }

    float *d_x, *d_y;
    cudaMalloc(&d_x, bytes);
    cudaMalloc(&d_y, bytes);
    cudaMemcpy(d_x, h_x, bytes, cudaMemcpyHostToDevice);
    cudaMemcpy(d_y, h_y, bytes, cudaMemcpyHostToDevice);

    int BLOCK = 256;
    int GRID  = (N + BLOCK - 1) / BLOCK;
    saxpy<<<GRID, BLOCK>>>(alpha, d_x, d_y, N);

    cudaMemcpy(h_y, d_y, bytes, cudaMemcpyDeviceToHost);
    /* 期待：2.5 * 1.0 + 3.0 = 5.5 */
    printf("h_y[0] = %.1f (期待 5.5)\n", h_y[0]);

    cudaFree(d_x); cudaFree(d_y);
    free(h_x); free(h_y);
    return 0;
}

SAXPY 是 cuBLAS 中 cublasSaxpy 的手刻版本， 也是 BLAS Level-1 中最經典的向量操作之一， 常被用作 GPU 記憶體頻寬的基準測試(benchmark)。

✏️ 練習 112.2 思考

假設你有一個 N×N 的 float 矩陣，以 row-major(C 語言預設)儲存在 GPU 的全域記憶體中。 考慮以下兩種存取模式（每個執行緒的索引公式）：

  • 模式 A（按列走）：val = mat[row * N + threadIdx.x]，其中所有執行緒的 row 相同。
  • 模式 B（按行走）：val = mat[threadIdx.x * N + col]，其中所有執行緒的 col 相同。

哪個模式的記憶體存取更有效率？為什麼？

看解答

模式 A 更有效率，因為它產生合併存取(coalesced access)。

分析：在一個 warp 的 32 個執行緒中，threadIdx.x 從 0 到 31 連續變化。

  • 模式 A：32 個執行緒存取 mat[row*N + 0]、 mat[row*N + 1]、…、mat[row*N + 31]—— 這是連續的記憶體位址，落在同一個(或少數幾個)128-byte 交易中，完美合併。
  • 模式 B：32 個執行緒存取 mat[0*N + col]、 mat[1*N + col]、…、mat[31*N + col]—— 相鄰位址間距 N×4 bytes(可能是 4096 bytes)，觸發 32 次獨立的記憶體交易， 頻寬利用率只有 4/(N×4) = 1/N。

這正是 naive matmul 讀取矩陣 B 時的問題：B 以 row-major 儲存， 但 kernel 要讀 B 的一整行(column)，每個執行緒的存取 stride = N， 造成嚴重的非合併存取。tiled 版本把 B-tile 先搬進共享記憶體， 共享記憶體存取不受 DRAM 合併限制，才解決了這個問題。

✏️ 練習 112.3 挑戰

分析本章 reduceSum kernel 的以下版本，找出其中的分支發散問題， 並說明上面給出的版本如何避免它： 

/* 有問題的舊版 reduction（連續執行緒版） */
__global__ void reduceBad(float *in, float *out, int N) {
    __shared__ float smem[256];
    int tid = threadIdx.x;
    int i   = blockIdx.x * blockDim.x + threadIdx.x;
    smem[tid] = (i < N) ? in[i] : 0.0f;
    __syncthreads();

    for (int stride = 1; stride < blockDim.x; stride *= 2) {
        if (tid % (2 * stride) == 0)          /* ← 問題在這裡 */
            smem[tid] += smem[tid + stride];
        __syncthreads();
    }
    if (tid == 0) out[blockIdx.x] = smem[0];
}
看解答

問題分析：

舊版以 if (tid % (2 * stride) == 0) 決定哪些執行緒工作。 第一輪(stride=1)只有偶數 tid(0,2,4,…)工作； 第二輪(stride=2)只有 0,4,8,… 工作； 每一輪都讓同一個 warp(warp 0)內有一半的執行緒「不做事」，但仍然佔用 lane， 這就是 warp 內的分支發散——warp 需要先讓工作的執行緒跑， 讓不工作的執行緒遮罩等待，再讓兩組都繼續。 越到後期，warp 0 裡工作的執行緒越來越少(1/4、1/8…)，效能持續下降。

改進版本（本章的寫法）的關鍵：

改進版以 if (tid < stride) 決定哪些執行緒工作：

  • 第一輪(stride = 128)：tid 0–127 工作，128–255 閒置。 前 4 個 warp 全部工作，後 4 個 warp 完全閒置——warp 內沒有發散！
  • 第二輪(stride = 64)：tid 0–63 工作，64–255 閒置。 前 2 個 warp 全部工作，後 6 個 warp 完全閒置——仍無 warp 內發散！
  • 最後幾輪 stride < 32 時才有 warp 內發散，但此時只剩一個 warp 在工作，影響已很小。

這個改進把分支發散從「每一輪都發生在多個 warp 裡」縮減到「只有最後幾輪的最後一個 warp 裡發生」， 大幅提升了 SM 的利用率。
