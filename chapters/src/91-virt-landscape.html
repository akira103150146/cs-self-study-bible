為什麼一個程式需要「以為自己獨佔整台電腦」?

想像你在一間共用辦公室裡工作。桌子是共用的、印表機是共用的、網路也是共用的。 這本來沒問題——直到某天隔壁的人把你的文件蓋掉、用光了所有印紙、又把網路塞滿了。 你開始懷念擁有自己辦公室的日子:有了私人空間,你才能不受干擾地工作, 也不必擔心把隔壁的文件搞砸。

電腦世界裡的「行程(process)」面臨同樣的處境。一台伺服器同時跑著資料庫、 Web 應用程式、背景任務……它們共用 CPU、記憶體和磁碟。若沒有任何隔離機制, 任一程式的 bug 就可能破壞其他程式的記憶體、讀到機密資料,甚至讓整台機器崩潰。

「隔離(isolation)」正是對抗這種混亂的答案。而「虛擬化(virtualization)」 則是實現隔離的技術手段——讓每個工作負載都活在自己的「幻境」裡,以為自己是唯一的主人。 這個幻境可以很薄(行程隔離),可以很厚(完整的虛擬機),也可以只做到剛好夠用(容器)。 這一章,我們就來把這條光譜從頭走到尾。

🔑
隔離的兩個維度

隔離通常在兩個維度上討論:故障隔離(fault isolation)——一個元件崩潰不拖累其他元件; 以及安全隔離(security isolation)——一個元件無法讀寫、干擾其他元件的資源。 不同的虛擬化技術在這兩個維度上提供的保證強度各不相同。

從作業系統的行程隔離說起

在深入容器和虛擬機之前,先回到我們已經熟悉的地基。 在第 24 章裡,你看到作業系統(OS) 如何用兩個關鍵抽象來隔離每個程式:

  • 行程(process):每個執行中的程式都活在自己的行程裡, 有獨立的執行緒、開啟的檔案描述符,以及——最關鍵的——獨立的位址空間(address space)。
  • 虛擬記憶體(virtual memory):每個行程看到的記憶體位址都是虛擬的, 作業系統與 CPU 的 MMU(Memory Management Unit)負責在背後把虛擬位址翻譯成實體位址。 行程 A 的 0x1000 和行程 B 的 0x1000 指向完全不同的實體位置—— 它們根本不可能互相干擾。
🔑
行程:最基本的虛擬化

行程隔離本身就是一種虛擬化——每個行程都有「自己的 CPU」(輪流排程的幻象) 和「自己的記憶體」(虛擬位址空間)。從這個角度看,作業系統早在容器和 VM 出現之前, 就已經是一個虛擬化引擎了。

那為什麼還需要容器和 VM?因為行程隔離有它的邊界:

  • 多個行程共用同一個 OS 核心(kernel)。若核心有漏洞,所有行程都暴露。
  • 它們共用相同的系統程式庫版本、相同的網路設定、相同的主機名稱。 「這個程式需要 Python 3.9,那個需要 Python 3.12」——用純行程隔離很難乾淨地解決。
  • 行程隔離的安全邊界依賴核心的正確性。若攻擊者能利用系統呼叫漏洞逃逸, 就能影響同主機的所有行程。

容器和 VM 都是為了突破這些邊界而誕生的——只是它們選擇了不同的突破路徑。

虛擬化光譜:從行程到 unikernel

把各種隔離技術放在同一條軸線上,你會看到一個清晰的光譜: 隔離強度越強,開銷通常也越大;越輕量,隔離邊界就越薄。

這條光譜並不是線性的「越強越好」——每個位置都有它最適合的場景。 接下來,我們依序把光譜上的幾個關鍵節點說清楚。

虛擬機(VM):在硬體之上再跑一整個 OS

虛擬機(Virtual Machine,VM)的想法很直接:與其讓多個應用程式共用同一個作業系統, 何不讓每個工作負載都有自己的完整作業系統?

這件事靠虛擬機監控器(Hypervisor,也稱 VMM, Virtual Machine Monitor)實現。 Hypervisor 坐在硬體之上,把實體 CPU、記憶體、磁碟、網路卡等硬體資源「切割」成一份份 虛擬硬體,分給每個 VM。每個 VM 裡跑的作業系統稱為客端作業系統(Guest OS), 它完全不知道自己在一台虛擬機上——它以為自己有獨享的 CPU 和記憶體。

📜
VM 的誕生:IBM 的 1960 年代

虛擬機的概念可以追溯到 1960 年代的 IBM System/360,當時是為了讓大型主機能同時服務多個「互不干擾」的用戶。 第一個廣泛使用的現代 Hypervisor 是 VMware(1998 年創立)帶進 x86 世界的。 2003 年,英國劍橋大學發表開源的 Xen Hypervisor,拉開了雲端虛擬化的序幕。 Amazon EC2(2006 年)一開始就是建立在 Xen 之上的。

Hypervisor 有兩種主要類型:

  • Type 1(裸機型,Bare-metal):直接跑在硬體上,沒有底層 OS。 例子:VMware ESXi、Microsoft Hyper-V、開源的 KVM(Linux 核心內建)、Xen。 大多數雲端提供商的底層都是 Type 1。
  • Type 2(宿主型,Hosted):跑在一個現有 OS 之上,是一般應用程式。 例子:VirtualBox、VMware Workstation。適合開發者在自己筆電上測試。
ℹ️
KVM 的特殊身份

KVM(Kernel-based Virtual Machine)嚴格說來是 Type 1 和 Type 2 的混血:它是 Linux 核心的一個模組, 把 Linux 本身變成 Hypervisor。因此 KVM 直接利用 Linux 的排程器與記憶體管理,效能接近裸機型, 但管理上像個宿主型。它是目前 Linux 伺服器虛擬化的主流選擇,也是 AWS、GCP 等雲端平台的核心技術之一。

VM 的最大優點是完全的 OS 層隔離:Guest OS 可以是 Windows、Linux、FreeBSD 任意組合, 且 Guest OS 的崩潰不影響 Host 或其他 VM。這讓 VM 成為「多租戶雲端」的首選技術。 後續的第 86 章(虛擬機與 Hypervisor 底層)將深入 Hypervisor 的實作細節——包括 Intel VT-x / AMD-V 硬體輔助、 記憶體影子頁表與 EPT,以及 I/O 虛擬化。

容器(Container):共享核心、只隔離視圖

VM 的隔離很強,但代價是整個 Guest OS 都要跑起來。有時候你只是想讓兩個應用程式 「看起來」住在不同的世界——它們可以共用同一個 Linux 核心,只要各自看到不同的 檔案系統、不同的行程樹、不同的網路介面就夠了。

容器就是這樣的東西。它利用 Linux 核心的兩個關鍵特性實現隔離:

  • 命名空間(namespace):讓每個容器擁有獨立的「視圖」—— 自己的行程 ID 命名空間(PID namespace)、網路介面(net namespace)、 掛載點(mnt namespace)、主機名稱(UTS namespace)等。 容器裡的行程看到的 PID 1 就是容器自己的 init 行程,而非 Host 的真正 init。
  • 控制群組(cgroup, control group):限制每個容器能使用的 CPU 時間、記憶體上限、磁碟 I/O 速率等資源,防止某個容器把 Host 的資源耗光。

在這之上,容器映像(image)通常使用聯合掛載(Union Mount)技術 (如 OverlayFS)分層疊加檔案系統,讓多個容器共用相同的基底層而不互相汙染。

🔑
容器 ≠ 虛擬機

容器不是「輕量的 VM」。容器沒有自己的 OS 核心——它只是 Host 核心上 用 namespace + cgroup 圍起來的一組行程。這意味著容器裡跑的程式仍然在直接呼叫 Host 的 Linux 核心系統呼叫。 VM 則有完整獨立的 Guest OS 核心,與 Host 核心完全分離。

Docker(2013 年發布)讓容器技術從 Linux 專家的工具變成每個開發者都能用的東西: 透過 Dockerfile 描述映像、透過映像倉庫(registry)分發、透過統一的 CLI 管理。 現在雲原生生態的底層容器執行時主要是 containerd(由 Docker 貢獻給 CNCF), 以及 CRI-O 等符合 OCI(Open Container Initiative)標準的執行環境。 後續的第 87 章將深入 namespace、cgroup、OverlayFS 的實作,第 88 章則會帶你親手寫一個迷你 Docker。

⚠️
「容器比 VM 快」的正確理解

容器啟動速度快,是因為它不需要啟動 Guest OS,只是在現有核心上建立新的 namespace。 但這不代表容器裡的應用程式執行速度比 VM 裡的快——兩者的應用層效能差異通常可以忽略不計。 關鍵差異在於資源開銷與啟動延遲,不是執行時的計算速度。 實際的啟動時間差異取決於具體環境、映像大小、系統負載等因素,難以給出精確的通用數字。

✏️ 練習 85.1 思考

你是一家金融公司的架構師,需要在同一台伺服器上同時跑: (A) 一個高合規需求的核心交易系統,需要強安全隔離且使用 Windows Server; (B) 幾十個輕量的 Python 微服務 API,每個都很小,需要能快速橫向擴展。 你會如何搭配使用 VM 和容器?說明你的理由。

看解答

交易系統(A)適合放在 VM 裡。理由:需要 Windows Server(容器在 Linux Host 上無法直接跑 Windows 核心應用);高合規需求需要強隔離(Hypervisor 邊界比 namespace 邊界更難突破);崩潰或安全事件不應影響同主機其他服務。

Python 微服務(B)適合用容器部署,並透過 Kubernetes 等編排系統管理。理由:需要快速啟動與橫向擴展(容器啟動快、資源開銷低,同一台機器可以跑更多副本);OCI 映像格式讓開發/測試/生產環境一致;透過 cgroup 限制每個服務的資源用量,防止某個服務拖垮整台機器。

這種「VM 跑 Host OS + 容器在 Host OS 上」的組合在現實中很常見:雲端 VM 本身就是跑在 Hypervisor 之上的,而 VM 裡再用容器部署應用——兩層隔離各司其職。

✏️ 練習 85.2 思考

為什麼容器的啟動速度比 VM 快?請從技術原理的角度解釋,而不只是說「因為容器比較輕量」。

看解答

容器啟動快的根本原因是它不需要啟動 OS 核心。VM 啟動時需要:BIOS/UEFI 初始化、Hypervisor 建立虛擬硬體、Guest OS bootloader 執行、Guest OS 核心載入與初始化(驅動程式、子系統、服務)——這些步驟合計需要數秒到數十秒。

容器啟動時,Host OS 核心已經在執行中。Container Runtime 只需要:建立新的 namespace(幾個系統呼叫)、設定 cgroup 限制、掛載 rootfs(OverlayFS 分層)、啟動容器內的第一個行程(PID 1)。這些操作在核心層面極為輕量,通常在毫秒至秒的量級內完成。

總結:容器快是因為「省掉了 Guest OS 的整個啟動流程」,而非應用程式本身執行更快。

現代生態一覽:各技術的定位

光有 VM 和容器的概念還不夠——現代生態裡還有幾個值得認識的角色, 填補了光譜上的各種空隙:

虛擬機層

  • KVM(Kernel-based Virtual Machine):Linux 核心內建的 Type 1 Hypervisor。 是 OpenStack、AWS(早期)等主流雲端平台的基礎。
  • VMware ESXi / vSphere:企業市場的 Type 1 Hypervisor,管理介面成熟, 廣泛用於私有雲與企業資料中心。
  • QEMU:開源的完整機器模擬器,常與 KVM 搭配(QEMU-KVM): QEMU 提供設備模擬,KVM 提供硬體加速的 CPU/記憶體虛擬化。

容器層

  • Docker:讓容器技術普及的先驅,提供完整的開發工作流程(build/ship/run)。 底層執行時已換為 containerd。
  • containerd:業界標準的容器執行時(container runtime), 符合 OCI 標準,是 Kubernetes 的預設 CRI 實作。
  • Podman:Red Hat 主導的無守護行程(daemonless)容器工具, 設計上相容 Docker CLI,適合需要無 root 執行的場景。

輕量虛擬化:兩全其美的嘗試

容器的隔離不夠強?VM 的開銷又太高?有幾個專案試圖在中間找到平衡:

  • Firecracker(AWS 開源):一個極簡的 microVM VMM, 使用 KVM 提供硬體層隔離,但刻意省去傳統 VM 的大量設備模擬, 因此能在極短時間內啟動一個有獨立核心的微型 VM。 AWS Lambda 和 Fargate 背後就是 Firecracker。它試圖同時達到 VM 的安全隔離和容器的輕量啟動。
  • gVisor(Google 開源):在用戶空間實作了一個 Linux 系統呼叫的沙箱層(Sentry), 攔截容器的 syscall,讓它們不直接落到 Host 核心。 犧牲一些效能換取更強的安全隔離。Google Cloud Run 背後使用了 gVisor。
  • kata-containers:把 OCI 容器標準和輕量 VM 結合, 讓每個「容器」實際上跑在一個輕量 VM 裡,兼顧容器的使用者體驗與 VM 的隔離邊界。

Unikernel:把 OS 縮進應用程式

Unikernel 走的是一條更激進的路:把應用程式與它所需的 OS 功能 (網路、儲存、記憶體管理等)編譯成單一可執行映像, 直接跑在 Hypervisor 之上(或裸機)。沒有多餘的 OS 程式庫、沒有 shell、 沒有你用不到的核心子系統——攻擊面極小。

代表專案有 MirageOS(OCaml)、IncludeOS(C++)、Nanos 等。 Unikernel 的缺點是開發與除錯比傳統 OS 困難得多,生態系也相對小眾。 它目前主要應用在網路功能虛擬化(NFV)、嵌入式系統,以及對安全性有極端要求的場景。

WebAssembly(WASM):沙箱的另一個維度

WebAssembly(WASM) 原本是為瀏覽器設計的沙箱執行環境, 但近年來 WASM Runtime(如 Wasmtime、WasmEdge)讓它在伺服器端也能作為輕量隔離單元。 WASM 在語言無關、啟動極快、細粒度安全控制上有獨特優勢, 是 Serverless 和邊緣運算場景的新興選項。Cloudflare Workers 便是基於 V8 Isolate(概念上類似 WASM 沙箱)。

💡
想親眼看 Linux 在瀏覽器裡跑?

WebVM.io 用 WebAssembly 在瀏覽器裡執行了一個完整的 Linux 環境(x86 虛擬化)。 打開它,你可以在瀏覽器的 Terminal 裡跑 Bash、Python、gcc——完全在你的瀏覽器沙箱內,不需要後端伺服器。 這是虛擬化技術的一個很酷的現場示範。

✏️ 練習 85.3 思考

Unikernel 宣稱同時達到「輕量」與「高安全隔離」。但在光譜圖(圖 85-1)中,它被放在「隔離強」的右端。這兩個說法矛盾嗎?Unikernel 是用什麼方法在不增加傳統開銷的情況下達到高隔離的?它最適合什麼樣的場景?

看解答

不矛盾,但需要釐清「輕量」與「隔離」的含義。

Unikernel 的「輕量」:映像體積小(只包含用到的 OS 功能)、啟動快(沒有龐大的 OS 初始化)、記憶體用量少。這些與「傳統 VM 跑完整 Guest OS」相比確實輕量。

Unikernel 的「高隔離」:它不是靠 namespace 或 cgroup(那是容器的方法),而是靠縮小攻擊面——每個 Unikernel 只有一個應用程式,沒有 shell、沒有多餘的系統工具、沒有動態連結的通用程式庫。攻擊者即使找到漏洞,能利用的東西極少。此外,Unikernel 通常跑在 Hypervisor 之上,仍有硬體層隔離。

最適場景:功能單一、定義明確的服務——例如 DNS 伺服器、TLS 終端點、NFV(網路功能虛擬化)中的防火牆或路由器、以及對安全性與啟動速度要求都極高的 Serverless 函式。不適合需要豐富 OS 生態系(開發工具、偵錯器)的通用應用。

把這一章串起來

我們從一個核心問題出發——「為什麼程式需要以為自己獨佔整台電腦?」——走過了整條虛擬化光譜。 幾個值得帶走的關鍵觀念:

  • 行程隔離是最基本的虛擬化:虛擬 CPU(排程)+ 虛擬記憶體(位址空間)是作業系統送給每個程式的「獨佔幻象」。但它共用核心,安全邊界有限。
  • 容器 = 共用核心 + 隔離視圖:namespace 切割資源視圖,cgroup 限制資源用量。輕量、啟動快、部署密度高,是雲原生應用的首選。但安全隔離邊界就是 Host 核心——核心漏洞是共同風險。
  • VM = 獨立 Guest OS + Hypervisor 虛擬硬體:提供最強的 OS 層隔離,可跑不同 OS。代價是每個 VM 都要跑一整個 OS,資源開銷較高、啟動較慢。
  • 光譜沒有唯一答案:Firecracker 試圖在 VM 安全與容器速度之間找到折衷;gVisor 用用戶空間 syscall 攔截加固容器;Unikernel 以極致縮小系統表面同時達到輕量與高隔離;WASM 則從語言虛擬機角度提供沙箱。
  • 現實中兩者常常同時使用:雲端 VM 跑在 Hypervisor 之上,VM 裡再用容器部署應用——兩層隔離各司其職。

延伸閱讀

動手體驗:WebVM.io 可以在瀏覽器裡現場體驗 Linux VM, 感受「瀏覽器沙箱裡的 Linux」這件事本身就是虛擬化的精彩演示。

理論深度:《Operating Systems: Three Easy Pieces(OSTEP)》 第一部「虛擬化」章節對行程與記憶體虛擬化有深入且平易近人的說明,免費在線閱讀。

容器技術:Ivan Velichko 的 Container Learning Path 以圖文並茂的方式從 namespace、cgroup 到 OCI 逐步拆解容器原理,是少數能把底層講清楚的資源。

雲原生全景:CNCF Landscape 提供了現代雲原生生態的全景地圖,看完本部各章後回來看這張圖,很多名詞都會豁然開朗。
