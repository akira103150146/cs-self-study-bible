trait 是什麼:Rust 的抽象基石

在 Java 或 C++ 裡,你用繼承(inheritance)來共享行為: 讓 Dog 繼承 Animal,自動擁有 eat()、sleep()。 但繼承有個臭名昭彰的問題——它把型別的是誰(identity)和型別能做什麼(capability)混在一起, 產生深層耦合、菱形繼承、脆弱基底類別等難題。 Rust 選擇了另一條路:trait(特徵)。

trait 是能力的聲明,不是身份的繼承。 它只說「任何型別,只要你能做這些事,就算實作了這個 trait」。 這和 Haskell 的 type class(第 44 章)在精神上一脈相承—— 但 Rust 多了一層:trait 的方法會透過借用規則約束 &self 或 &mut self 的使用, 讓多型與所有權系統自然融合。 

// 定義一個 trait:能描述自己的事物
trait Describe {
    fn describe(&self) -> String;           // 必須實作的方法(無預設實作)

    fn label(&self) -> String {             // 預設方法(default method):有實作體
        format!("[{}]", self.describe())    // 呼叫方可選擇覆寫或沿用
    }
}

// 為 String 實作 Describe
impl Describe for String {
    fn describe(&self) -> String {
        format!("字串 {:?},長度 {}", self, self.len())
    }
}

// 為自訂型別 Point 實作 Describe
struct Point { x: f64, y: f64 }

impl Describe for Point {
    fn describe(&self) -> String {
        format!("座標 ({}, {})", self.x, self.y)
    }
}

fn main() {
    let s = String::from("hello");
    let p = Point { x: 3.0, y: 4.0 };

    println!("{}", s.describe());    // 字串 "hello",長度 5
    println!("{}", p.label());       // [座標 (3, 4)],使用預設 label 實作
}
🔑
trait 與 OOP interface 的關鍵差異

Java 的 interface 要在定義型別時宣告它實作什麼介面。 Rust 的 trait 可以在任何地方為任何型別補上實作——包括你沒有原始碼的標準庫型別 (只要 trait 或型別其中一個是你自己定義的,即孤兒規則 orphan rule)。 這讓第三方擴充更靈活,不需要繼承或包裝器(wrapper)。

trait bound:泛型函式的能力限制

單獨的 trait 宣告只是「能力契約」;真正的力量在trait bound—— 讓泛型函式能「接受任何實作了某 trait 的型別」: 

// 接受任何實作了 Describe trait 的型別 T
fn print_label<T: Describe>(item: &T) {
    println!("{}", item.label());
}

// 等價寫法:where 子句(多個 trait bound 時更清晰)
fn print_label_v2<T>(item: &T)
where
    T: Describe + std::fmt::Debug,   // T 必須同時實作 Describe 和 Debug
{
    println!("{:?} -> {}", item, item.label());
}

fn main() {
    let s = String::from("world");
    let p = Point { x: 1.0, y: 2.0 };
    print_label(&s);   // 傳 &String
    print_label(&p);   // 傳 &Point —— 同一個函式,不同型別
}

T: Describe 不是在說「T 繼承自 Describe」,而是「T 必須有 Describe 所要求的能力」。 這個約束在編譯期確認——違反時程式直接編不過,且錯誤訊息會精確指出缺少哪個方法實作。

✏️ 練習 80.1 實作

定義一個 trait Area,包含一個方法 fn area(&self) -> f64。 分別為 struct Circle { radius: f64 } 和 struct Rectangle { w: f64, h: f64 } 實作這個 trait。 再寫一個泛型函式 print_area<T: Area>(shape: &T) 印出面積。 在 main() 裡各建一個實例並呼叫 print_area。

看解答 
trait Area {
    fn area(&self) -> f64;
}

struct Circle    { radius: f64 }
struct Rectangle { w: f64, h: f64 }

impl Area for Circle {
    fn area(&self) -> f64 {
        std::f64::consts::PI * self.radius * self.radius
    }
}

impl Area for Rectangle {
    fn area(&self) -> f64 { self.w * self.h }
}

fn print_area<T: Area>(shape: &T) {
    println!("面積: {:.4}", shape.area());
}

fn main() {
    let c = Circle    { radius: 3.0 };
    let r = Rectangle { w: 4.0, h: 5.0 };
    print_area(&c);   // 面積: 28.2743
    print_area(&r);   // 面積: 20.0000
}

重點:兩個完全不同的型別共享同一個 print_area 函式—— 靠的是 trait bound,而非繼承層次結構。

泛型與單型化:零成本的由來

Rust 的泛型讓你寫一次、適用多種型別。 但它和 Java 的泛型有一個根本差異:Java 靠型別抹除(type erasure)在執行時把泛型參數擦掉, 統一用 Object 存放,每次使用都需要轉型; Rust 靠單型化(monomorphization)—— 在編譯期為每個具體型別生成獨立的機器碼。 

fn largest<T: PartialOrd>(a: T, b: T) -> T {
    if a > b { a } else { b }   // PartialOrd 提供了 > 運算子
}

fn main() {
    println!("{}", largest(3_i32, 7_i32));     // 編譯器為 i32 生成一份 largest
    println!("{}", largest(3.0_f64, 7.0_f64)); // 另生成一份 largest for f64
}

上面的程式在編譯後等同於你手寫了兩個函式: largest_i32 和 largest_f64—— 呼叫時沒有任何執行時的虛擬分派開銷,甚至可能被 inline 展開。 這就是「零成本抽象(zero-cost abstraction)」的由來: 你用高層次的泛型語法撰寫,執行時的效率和手寫特化版本完全相同。

💡
單型化的代價:編譯時間與二進位大小

天下沒有白吃的午餐。單型化讓執行時零成本,但代價是: 每個具體型別都生成一份機器碼,導致編譯時間增加和二進位檔變大。 這正是 Rust 大型專案編譯時間較長的主要原因之一。 若需要節省二進位大小、或型別在編譯時無法確定,可改用 dyn Trait(見第七節)。

用 Result<T, E> 表達錯誤:錯誤即值

為什麼 Rust 不用例外(exception)? 讓我們從所有權的視角來思考:exception 是跨越作用域邊界的隱式跳躍—— 函式可以在任何一行悄悄拋出例外、退出執行,把清理責任丟給 stack unwinding 機制。 這和 Rust 的精神相違背:Rust 希望每個資源的釋放都是確定的、可見的。

Rust 的解法是讓錯誤成為回傳值。 Result<T, E> 是標準庫定義的 enum—— 它正是第 9 章所說的「和型別(sum type)」的直接應用: 

// Result<T, E> 的定義(標準庫):
// enum Result<T, E> {
//     Ok(T),    // 成功時裝著結果值 T
//     Err(E),   // 失敗時裝著錯誤值 E
// }

use std::fs;
use std::io;

// 回傳型別明確告訴呼叫者:這個函式可能失敗,失敗時給你 io::Error
fn read_file(path: &str) -> Result<String, io::Error> {
    let content = fs::read_to_string(path)?;   // ? 運算子,下一節詳述
    Ok(content)
}

fn main() {
    match read_file("data.txt") {
        Ok(content) => println!("讀到 {} 個字元", content.len()),
        Err(e)      => eprintln!("讀取失敗: {}", e),
    }
}
🔑
為什麼「錯誤即值」更好

用 exception 時,函式簽名看不出它可能拋出什麼錯誤(除非語言有 checked exceptions,但那又帶來另一種樣板地獄)。 用 Result<T, E>,錯誤的可能性刻在型別裡: 呼叫者被迫處理(或明確說「我接受 panic」),不可能無聲無息地忽略。 編譯器會因為「未使用的 Result」發出警告——這是一道安全網。

從所有權的角度看錯誤傳播:當函式回傳 Err(e),e 的所有權移交給呼叫者—— 呼叫者決定如何處理、何時釋放。沒有隱式的 stack unwinding,沒有神秘的 destructor 呼叫順序, 一切都在型別系統的掌控之中。

? 運算子:優雅傳播錯誤

如果沒有語法糖,逐一 match Result 傳播錯誤會很囉嗦: 

use std::fs;
use std::io;

// ✗ 沒有 ? 的版本:充滿重複的樣板程式碼
fn process_v1(path: &str) -> Result<usize, io::Error> {
    let content = match fs::read_to_string(path) {
        Ok(s)  => s,
        Err(e) => return Err(e),
    };
    Ok(content.len())
}
// ✓ 用 ? 的版本:清晰如同「不會出錯的程式碼」
fn process_v2(path: &str) -> Result<usize, io::Error> {
    let content = fs::read_to_string(path)?;   // 失敗 → 立即 return Err
    Ok(content.len())
}

? 做了三件事:

  1. 若值是 Ok(v),解包取出 v。
  2. 若值是 Err(e),呼叫 From::from(e) 轉換錯誤型別(如需要),然後 return Err(converted_e)。
  3. 只能在回傳型別為 Result(或 Option)的函式裡使用。

步驟 2 的「自動型別轉換」特別重要:當你的函式回傳 Result<T, AppError>, 而你呼叫的函式回傳 Result<T, io::Error>, 只要你為 AppError 實作了 From<io::Error>, ? 就會自動幫你做轉換。這是下一節的主角。

⚠️
? 只能在 Result 或 Option 函式裡用

在 main() 使用 ?,需把簽名改為 fn main() -> Result<(), Box<dyn std::error::Error>>。 在回傳 Option 的函式裡,? 遇到 None 時直接回傳 None。 兩種情境不能混用。

✏️ 練習 80.2 實作

下面這段程式用 unwrap() 處理錯誤,當輸入不是有效整數時會 panic。 請改寫 parse_and_double,讓它回傳 Result<i32, std::num::ParseIntError>, 並在 main() 裡用 match 優雅處理兩種情況:

fn parse_and_double(s: &str) -> i32 {
    let n: i32 = s.trim().parse().unwrap();   // ← 把這行改掉
    n * 2
}

fn main() {
    println!("{}", parse_and_double("21"));   // 42
    println!("{}", parse_and_double("abc"));  // panic!
}
看解答 
fn parse_and_double(s: &str) -> Result<i32, std::num::ParseIntError> {
    let n: i32 = s.trim().parse()?;   // 失敗 → 回傳 ParseIntError
    Ok(n * 2)
}

fn main() {
    match parse_and_double("21") {
        Ok(v)  => println!("{}", v),           // 42
        Err(e) => eprintln!("錯誤: {}", e),
    }
    match parse_and_double("abc") {
        Ok(v)  => println!("{}", v),
        Err(e) => eprintln!("錯誤: {}", e),   // 錯誤: invalid digit found in string
    }
}

這個改動很小,但意義重大:現在呼叫者被型別系統強制考慮失敗的情況, 而不是任由程式在執行時崩潰。

自訂錯誤型別與型別轉換

當程式可能遭遇多種不同來源的錯誤時,自訂錯誤型別是整理它們的好方法。 Rust 慣例是定義一個 enum 列舉所有可能的失敗情境,並實作幾個關鍵 trait: 

use std::fmt;
use std::num::ParseIntError;
use std::io;

// 自訂錯誤型別:用 enum 列舉所有可能的失敗原因
#[derive(Debug)]                      // 自動實作 Debug,方便印出除錯資訊
enum AppError {
    Io(io::Error),                    // 包裝 IO 錯誤
    Parse(ParseIntError),             // 包裝解析錯誤
    InvalidRange(i64),                // 純語意錯誤:數值超出有效範圍
}

// 實作 Display:給終端使用者看的友善訊息
impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            AppError::Io(e)           => write!(f, "IO 錯誤: {}", e),
            AppError::Parse(e)        => write!(f, "解析錯誤: {}", e),
            AppError::InvalidRange(n) => write!(f, "數值 {} 超出有效範圍 [0, 100]", n),
        }
    }
}

// 實作 std::error::Error trait(幾乎所有錯誤型別都需要)
impl std::error::Error for AppError {}

// 實作 From:讓 ? 自動把 io::Error 轉換成 AppError
impl From<io::Error> for AppError {
    fn from(e: io::Error) -> Self { AppError::Io(e) }
}

// 實作 From:讓 ? 自動把 ParseIntError 轉換成 AppError
impl From<ParseIntError> for AppError {
    fn from(e: ParseIntError) -> Self { AppError::Parse(e) }
}

fn load_score(path: &str) -> Result<i64, AppError> {
    let content = std::fs::read_to_string(path)?;   // io::Error -> AppError::Io(e)
    let n: i64  = content.trim().parse()?;           // ParseIntError -> AppError::Parse(e)
    if !(0..=100).contains(&n) {
        return Err(AppError::InvalidRange(n));        // 自訂語意錯誤
    }
    Ok(n)
}

fn main() {
    match load_score("score.txt") {
        Ok(n)  => println!("分數: {}", n),
        Err(e) => eprintln!("載入失敗: {}", e),
    }
}

Box<dyn Error>:快速原型的捷徑

設計完整的自訂錯誤型別需要些樣板程式碼。在原型開發或小型工具裡, Box<dyn std::error::Error> 是更快速的選擇—— 它利用 trait object 接受任何實作了 Error trait 的型別: 

fn quick_parse(s: &str) -> Result<i32, Box<dyn std::error::Error>> {
    let n: i32 = s.trim().parse()?;    // 任何錯誤都被 Box 裝起來回傳
    Ok(n * 2)
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    println!("{}", quick_parse("21")?);    // 42
    Ok(())
}
💡
何時用自訂錯誤型別,何時用 Box<dyn Error>

函式庫(library crate):優先用自訂錯誤型別。 呼叫者需要能夠 match 你的錯誤做出不同回應——Box<dyn Error> 把型別資訊藏起來了,呼叫者只能印出訊息,無法精確處理。
應用程式(binary crate / 快速原型):Box<dyn Error> 或社群的 anyhow 套件是更省力的選擇。

✏️ 練習 80.3 挑戰

定義一個自訂錯誤型別 MathError,包含兩個變體: DivisionByZero 和 NegativeSqrt(f64)。 實作 fmt::Display 和 std::error::Error。 再寫一個函式 safe_sqrt_div(a: f64, b: f64) -> Result<f64, MathError>, 計算 sqrt(a) / b,若 a < 0.0 回傳 NegativeSqrt, 若 b == 0.0 回傳 DivisionByZero。

看解答 
use std::fmt;

#[derive(Debug)]
enum MathError {
    DivisionByZero,
    NegativeSqrt(f64),
}

impl fmt::Display for MathError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            MathError::DivisionByZero   => write!(f, "除以零"),
            MathError::NegativeSqrt(n)  => write!(f, "不能對負數 {} 取平方根", n),
        }
    }
}

impl std::error::Error for MathError {}

fn safe_sqrt_div(a: f64, b: f64) -> Result<f64, MathError> {
    if a < 0.0 { return Err(MathError::NegativeSqrt(a)); }
    if b == 0.0 { return Err(MathError::DivisionByZero); }
    Ok(a.sqrt() / b)
}

fn main() {
    println!("{:?}", safe_sqrt_div(9.0, 3.0));   // Ok(1.0)
    println!("{:?}", safe_sqrt_div(-1.0, 3.0));  // Err(NegativeSqrt(-1.0))
    println!("{:?}", safe_sqrt_div(9.0, 0.0));   // Err(DivisionByZero)
}

trait objects 與動態分派

泛型用靜態分派(static dispatch)——編譯時決定呼叫哪個具體實作。 但有時你需要在執行時決定: 例如一個 Vec 裡要放多種不同型別的物件,只要它們都實作了同一個 trait。 這就是 trait object 的用途:dyn Trait。 

trait Shape {
    fn area(&self) -> f64;
    fn name(&self) -> &str;
}

struct Circle { radius: f64 }
struct Square { side: f64   }

impl Shape for Circle {
    fn area(&self) -> f64 { std::f64::consts::PI * self.radius * self.radius }
    fn name(&self) -> &str { "圓形" }
}

impl Shape for Square {
    fn area(&self) -> f64 { self.side * self.side }
    fn name(&self) -> &str { "正方形" }
}

fn main() {
    // Box<dyn Shape>:在 heap 上放一個「實作了 Shape 的某個型別」
    let shapes: Vec<Box<dyn Shape>> = vec![
        Box::new(Circle { radius: 3.0 }),
        Box::new(Square { side: 4.0   }),
    ];

    for shape in &shapes {
        // 執行時才決定呼叫 Circle::area 還是 Square::area
        println!("{} 面積: {:.2}", shape.name(), shape.area());
    }
}

dyn Shape 是胖指標(fat pointer)——包含兩個指標: 一個指向實際資料,一個指向虛擬函式表(vtable),記錄這個型別各個 trait 方法的位址。 這就是「動態分派(dynamic dispatch)」——執行時查表,有少量額外開銷。

🔑
object safety:並非所有 trait 都能做成 dyn Trait

trait object 有一個限制:該 trait 必須是object-safe的。 簡單說,trait 的方法不能有泛型型別參數、不能回傳 Self—— 因為 vtable 無法表示這些「執行時才確定的型別」。 Clone(fn clone(&self) -> Self)就不是 object-safe 的,所以你不能用 dyn Clone。

慣用錯誤處理模式

學了 Result、?、自訂錯誤,接下來面對的是實際判斷: 在這個位置,我到底應該怎麼處理這個錯誤?

unwrap 和 expect:何時可以用

// unwrap():若 Err,直接 panic
let val = some_result.unwrap();

// expect("訊息"):若 Err,panic 並附上說明(比 unwrap 好,因為有 context)
let val = some_result.expect("讀取設定檔失敗,請確認檔案存在於當前目錄");

unwrap 和 expect 是合法選擇的情境:

  • 你邏輯上確定不可能失敗(例如解析一個編譯期硬寫的字串常數)。
  • 原型開發/測試期間,不想在架構未定時先費心處理每個錯誤路徑。
  • 失敗代表不可恢復的程式邏輯錯誤(而非使用者輸入問題),此時 panic 是正確的選擇。
⚠️
函式庫裡永遠不要在使用者輸入路徑上呼叫 unwrap

若你的函式庫呼叫了 unwrap() 而使用者的輸入觸發了 Err, 整個呼叫端程式會 panic 崩潰。函式庫應該把錯誤傳回給呼叫者,由呼叫者決定怎麼處理。

Option 與 Result 的互轉

// Option -> Result:提供「沒有值時的錯誤說明」
let opt: Option<i32> = Some(42);
let res: Result<i32, &str> = opt.ok_or("值不存在");    // Some(42) -> Ok(42)

// Result -> Option:丟棄錯誤資訊,只在乎有沒有值
let res: Result<i32, &str> = Ok(42);
let opt: Option<i32> = res.ok();    // Ok(42) -> Some(42);  Err(..) -> None

anyhow 與 thiserror:社群標準解

在真實應用程式中,多數 Rust 社群使用兩個輕量套件簡化錯誤處理:

  • anyhow:為應用程式設計。anyhow::Result<T> 包裝任何錯誤,支援 .context("做什麼時失敗") 附加說明,比 Box<dyn Error> API 更人性化。
  • thiserror:為函式庫設計。#[derive(thiserror::Error)] 自動生成 Display、Error、From 的樣板程式碼,省去手寫之苦。
ℹ️
本章只介紹這兩個套件的定位

理解了本章的原理(Result、?、From、dyn Error),翻一翻官方 README 就能上手這兩個套件。 真正重要的是底層機制,而非背誦套件 API。

手刻:帶錯誤處理的迷你表示式求值器

把本章所有工具組合起來,實作一個小型表示式求值器。 它用 enum 表示 AST(抽象語法樹),用 Result 傳播求值錯誤, 用 ? 保持程式碼整潔。

ℹ️
連結:編譯器與直譯器

這個範例是第 42 章介紹的直譯器/求值器的 Rust 實作版本—— 但這次我們把重點放在:用 enum + Box 表示遞迴 AST、用 Result 傳播求值錯誤、用 ? 讓程式碼如「快樂路徑」一樣清晰。

use std::fmt;

// 表示式 AST(抽象語法樹):用 enum 表達遞迴結構
#[derive(Debug)]
enum Expr {
    Num(f64),                         // 數值字面量
    Add(Box<Expr>, Box<Expr>),       // 加法
    Mul(Box<Expr>, Box<Expr>),       // 乘法
    Div(Box<Expr>, Box<Expr>),       // 除法(可能除以零)
}

// 求值錯誤
#[derive(Debug)]
enum EvalError {
    DivisionByZero,
}

impl fmt::Display for EvalError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            EvalError::DivisionByZero => write!(f, "除以零"),
        }
    }
}

impl std::error::Error for EvalError {}

// 遞迴求值:遇到錯誤用 ? 立即傳播
fn eval(expr: &Expr) -> Result<f64, EvalError> {
    match expr {
        Expr::Num(n) => Ok(*n),
        Expr::Add(l, r) => Ok(eval(l)? + eval(r)?),   // ? 傳播 EvalError
        Expr::Mul(l, r) => Ok(eval(l)? * eval(r)?),
        Expr::Div(l, r) => {
            let divisor = eval(r)?;
            if divisor == 0.0 {
                Err(EvalError::DivisionByZero)          // 回傳語意錯誤
            } else {
                Ok(eval(l)? / divisor)
            }
        }
    }
}

fn main() {
    // 建構 (3.0 + 4.0) * 2.0
    let expr = Expr::Mul(
        Box::new(Expr::Add(
            Box::new(Expr::Num(3.0)),
            Box::new(Expr::Num(4.0)),
        )),
        Box::new(Expr::Num(2.0)),
    );
    match eval(&expr) {
        Ok(v)  => println!("結果: {}", v),    // 結果: 14
        Err(e) => eprintln!("錯誤: {}", e),
    }

    // 10.0 / 0.0:觸發 DivisionByZero
    let bad = Expr::Div(
        Box::new(Expr::Num(10.0)),
        Box::new(Expr::Num(0.0)),
    );
    println!("{:?}", eval(&bad));   // Err(DivisionByZero)
}

注意這個設計的優雅之處:eval(l)? 一旦遇到 Err, 整個呼叫鏈立即中止,錯誤「冒泡」到最頂層—— 行為和 exception 類似,但完全顯式:所有可能失敗的點都有 ? 標記, 讀者一眼就知道哪裡可能出錯、哪裡保證安全。

✏️ 練習 80.4 挑戰

擴充上面的求值器,新增兩個功能:

  1. 新增 Neg(Box<Expr>) 變體,對子表示式取負號。
  2. 新增 EvalError::Overflow 變體:當結果的絕對值超過 1e15 時回傳此錯誤。

確保 eval 在每次計算後都檢查溢位條件,並讓 Display 印出有意義的訊息。

看解答 
use std::fmt;

#[derive(Debug)]
enum Expr {
    Num(f64),
    Neg(Box<Expr>),
    Add(Box<Expr>, Box<Expr>),
    Mul(Box<Expr>, Box<Expr>),
    Div(Box<Expr>, Box<Expr>),
}

#[derive(Debug)]
enum EvalError {
    DivisionByZero,
    Overflow(f64),
}

impl fmt::Display for EvalError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            EvalError::DivisionByZero => write!(f, "除以零"),
            EvalError::Overflow(v)    => write!(f, "溢位:結果 {} 超出範圍", v),
        }
    }
}

impl std::error::Error for EvalError {}

const LIMIT: f64 = 1e15;

fn check(v: f64) -> Result<f64, EvalError> {
    if v.abs() > LIMIT { Err(EvalError::Overflow(v)) } else { Ok(v) }
}

fn eval(expr: &Expr) -> Result<f64, EvalError> {
    match expr {
        Expr::Num(n)    => check(*n),
        Expr::Neg(e)    => check(-eval(e)?),
        Expr::Add(l, r) => check(eval(l)? + eval(r)?),
        Expr::Mul(l, r) => check(eval(l)? * eval(r)?),
        Expr::Div(l, r) => {
            let d = eval(r)?;
            if d == 0.0 { return Err(EvalError::DivisionByZero); }
            check(eval(l)? / d)
        }
    }
}

fn main() {
    let e = Expr::Neg(Box::new(Expr::Num(5.0)));
    println!("{:?}", eval(&e));   // Ok(-5.0)

    let big = Expr::Mul(
        Box::new(Expr::Num(1e10)),
        Box::new(Expr::Num(1e10)),
    );
    println!("{:?}", eval(&big)); // Err(Overflow(1e20))
}

關鍵技巧:把「檢查溢位」抽成 check() 輔助函式, 再用 ? 在每個計算後呼叫——讓錯誤傳播保持簡潔。

把這一章串起來

從 trait 的能力宣告出發,走過泛型的零成本展開,最後抵達 Rust 最具特色的錯誤哲學。 幾個值得帶走的核心觀念:

  • trait 是能力,不是身份:任何型別在任何時候都能實作任何 trait(孤兒規則除外),比 OOP 繼承更靈活、更組合。預設方法讓 trait 能提供合理的實作,使用者只需覆寫有意義的部分。
  • 泛型 + 單型化 = 零成本抽象:寫一次泛型程式碼,編譯器為每個具體型別生成手寫特化版本效率相同的機器碼。代價是編譯時間與二進位大小。
  • 錯誤即值(Result<T, E>):把失敗的可能性刻在回傳型別裡,讓呼叫者無法遺忘。所有權確保錯誤值被明確處理後才釋放。
  • ? 運算子:自動傳播錯誤、透過 From 自動型別轉換,讓錯誤處理的程式碼和「快樂路徑」一樣清晰。
  • 靜態 vs 動態分派:泛型給你零成本的靜態分派;dyn Trait 給你執行時的彈性。根據場景選擇,而非教條地偏好其中一種。
