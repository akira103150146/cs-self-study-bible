Kubernetes 編排與雲原生

Compose 管好了單台機器——但跨十台伺服器、自動重啟、零停機更新，你需要一個叢集的「大腦」。

Compose 到了頭：跨機器、自動重啟、零停機更新

在第 89 章，你用 Docker Compose 把 web、db、cache 三個容器 宣告在一份 docker-compose.yml 裡，一個指令全部跑起來。這對單台機器的開發環境或小型部署非常夠用。 但當服務成長之後，問題一個一個冒出來：

  • 高可用(high availability)：只有一台機器，一台機器掛掉，服務就全斷。
  • 水平擴展(horizontal scaling)：流量突然翻倍，你要手動 SSH 到每台機器跑 docker run？
  • 滾動更新(rolling update)：Compose 沒有原生的「零停機更新 + 失敗自動回滾」機制。
  • 自我修復(self-healing)：容器崩潰後，Compose 的 restart: always 只能在同一台機器重啟；跨節點的自動重新調度做不到。
  • 跨節點網路：多台機器上的容器要互相通訊，需要 overlay 網路——Compose 管不了。

這些問題正是「容器編排器(container orchestrator)」要解決的。市場上曾出現過 Mesos、Docker Swarm 等競爭者，但今天 Kubernetes(K8s) 已經是事實上的業界標準—— 從 Google 的生產系統(Borg 的開源版本)演化而來，2014 年開源，2016 年捐給 CNCF (Cloud Native Computing Foundation)，目前是規模最大的開源專案之一。

📜
K8s 名字的由來

Kubernetes 是希臘文「舵手(helmsman)」——這也是 logo 是船舵的原因。 「K8s」是縮寫:K + 8 個字母 + s。 Google 工程師將其稱為 Borg 的繼任者；2014 年在 DockerCon 首次公開展示， 不到兩年便在容器編排市場中確立主導地位。

Kubernetes 是什麼：控制平面與工作節點

一個 Kubernetes 叢集(cluster)由兩類機器組成：負責「思考決策」的 控制平面(control plane)，和負責「實際跑容器」的 工作節點(worker node)。

控制平面元件詳解

元件職責類比
kube-apiserver 叢集唯一的 HTTP REST 入口；驗證請求、授權、然後寫入 etcd 公司前台——所有進出都過這裡
etcd 分散式 key-value 儲存，保存叢集全部狀態（Pod、Deployment、Service…） 公司的資料庫——唯一的事實來源
kube-scheduler 監聽未調度的 Pod，根據資源需求、親和性規則選出節點 HR 排班——決定誰去哪個工作站
kube-controller-manager 運行多個控制器（Deployment / ReplicaSet / Node / Job…），每個控制器跑一個調和迴路 巡查主管——不斷確認現況是否符合計畫
kubelet（節點） 每個工作節點上的代理人；向 api-server 回報節點狀態，並確保 Pod 依規格執行 現場領班——在機台旁執行指令
kube-proxy（節點） 維護節點的網路規則（iptables / eBPF），讓 Service IP 能路由到正確 Pod 廠內電話總機——把打進來的電話轉給對的人
🔑
etcd 是叢集大腦的記憶體

整個 Kubernetes 的「狀態」——有哪些 Pod、哪些 Deployment、哪些 Service——全部存在 etcd 裡。 其他元件（api-server 之外）不直接讀 etcd；它們透過 api-server 的 watch 機制 訂閱感興趣的資源，一旦資源有變化就收到通知並作出反應。 etcd 備份 = 叢集快照。

宣告式設定與調和迴路：你描述期望，K8s 持續收斂

Kubernetes 最核心的哲學差異在於「宣告式(declarative)」而非「命令式(imperative)」。

命令式的思維是你下指令、系統執行：「啟動 3 個 nginx 容器」「把第 2 個停掉」「把第 3 個的映像換成 1.27」。 你要對系統當前狀態心中有數，每一步都要自己算。

宣告式的思維是你描述目標：「我要 3 個執行 nginx:1.27 的副本，帶有 label app=nginx。」 你把這份描述交給 Kubernetes，Kubernetes 負責讓現實收斂到這個目標——不管現在是 0 個還是 5 個副本。

這個「讓現實收斂到目標」的過程叫做調和(reconciliation)。Kubernetes 內部每個控制器都跑一個無限迴路： 

loop forever:
    desired_state  = read from etcd (你宣告的期望)
    current_state  = observe actual cluster
    if current_state != desired_state:
        take_action_to_converge()   # 啟動 Pod / 刪除 Pod / 更新映像…
🔑
宣告式帶來自我修復

假設你宣告 replicas: 3，某個 Pod 崩潰了，現況變成 2 個—— 調和迴路立刻發現 current(2) != desired(3)，自動補起一個新 Pod。 你不需要監控腳本，也不需要手動重啟——K8s 持續幫你把現況拉回到宣告的目標。 這就是「自我修復(self-healing)」的根源：不是有人在盯著看，而是 §40 軟體工程中提到的「使系統行為可預測」的宣告式哲學。

這與§11 軟體架構中「讓系統能夠推理(reasoning about systems)」 的原則相呼應：宣告式 YAML 是一份可版本控制、可審查、可重現的系統描述—— 這比「一串 CLI 指令的執行歷史」要可靠得多。

Pod：K8s 最小調度單位

在 Docker 的世界，最小單位是容器(container)。 在 Kubernetes，最小的調度單位是 Pod——一個 Pod 包含一個或多個容器， 這些容器共享：

  • 網路 namespace：同一個 Pod 內的容器共用同一個 IP；它們用 localhost 互通， 就像同一台機器上的兩個行程。
  • 儲存 volume：掛載到 Pod 的 volume 所有容器都可以讀寫。
  • 生命週期：同生同滅——Pod 被刪除，裡面所有容器都終止。

一個最簡單的 Pod 宣告如下：

# pod.yaml — 用來理解結構，實際部署請用 Deployment(見下節)
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx          # 標籤：供 Service selector 使用
spec:
  containers:
  - name: nginx
    image: nginx:1.27   # 映像名稱與 tag
    ports:
    - containerPort: 80 # 宣告容器監聽的埠(僅文件性，不自動開放)
    resources:
      requests:
        cpu: "100m"       # 100 milliCPU = 0.1 個 CPU core
        memory: "128Mi"
      limits:
        cpu: "500m"
        memory: "256Mi"
⚠️
直接建立 Pod 的陷阱

你可以 kubectl apply -f pod.yaml 直接建立一個 Pod——但這樣的 Pod 如果崩潰了，不會自動重建（沒有 ReplicaSet 看著它）。 節點故障的話，Pod 也就消失了。 實際部署請永遠用 Deployment（下一節）——Pod 只是理解結構的入口。

sidecar 模式

多容器 Pod 最常見的用法是 sidecar 模式：主容器跑應用程式， sidecar 容器承擔橫切面關注點（cross-cutting concern）——例如日誌收集、服務網格代理（Envoy / Istio）、 或設定熱載入。兩個容器共享 network 和 volume，但各自有獨立的行程空間。

Deployment：管理副本群、滾動更新與回滾

Deployment 是最常用的 k8s 工作負載物件。它管理一個 ReplicaSet， ReplicaSet 再管理一組 Pod，確保副本數量符合宣告。 Deployment 還支援：滾動更新(rolling update)、回滾(rollback)、暫停/繼續更新。 

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3                   # 期望副本數
  selector:
    matchLabels:
      app: nginx                # 必須與 template.metadata.labels 一致
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1               # 更新時最多多出幾個 Pod
      maxUnavailable: 0         # 更新時允許最多幾個 Pod 不可用(0 = 零停機)
  template:                     # Pod 模板：這裡的設定等同 Pod 的 spec
    metadata:
      labels:
        app: nginx              # Deployment selector 用這個找到它的 Pod
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "256Mi"
🔑
Deployment → ReplicaSet → Pod 的三層關係

Deployment 控制器在更新時不修改舊 ReplicaSet，而是建立一個新 ReplicaSet， 然後逐漸把新 RS 的副本數調高、把舊 RS 的副本數調低——這就是「滾動更新」。 回滾也只是把舊 ReplicaSet 的副本數調回來，速度極快。 kubectl rollout history deployment/nginx-deployment 可查看更新歷史。

Deployment 常用 kubectl 指令

# 套用 YAML 宣告(建立或更新)
kubectl apply -f deployment.yaml

# 查看 Deployment 狀態
kubectl get deployment nginx-deployment
kubectl describe deployment nginx-deployment

# 查看 Pod 列表(帶標籤篩選)
kubectl get pods -l app=nginx

# 手動調整副本數
kubectl scale deployment nginx-deployment --replicas=5

# 觸發滾動更新(更新映像版本)
kubectl set image deployment/nginx-deployment nginx=nginx:1.27.1

# 查看更新進度
kubectl rollout status deployment/nginx-deployment

# 查看更新歷史
kubectl rollout history deployment/nginx-deployment

# 回滾到上一個版本
kubectl rollout undo deployment/nginx-deployment

# 回滾到指定版本
kubectl rollout undo deployment/nginx-deployment --to-revision=2

# 查看 ReplicaSet(看到新舊 RS 的副本數變化過程)
kubectl get replicaset -l app=nginx
💡
--record 已棄用，改用 annotations

舊版文件常見 kubectl apply --record 把指令記錄進 rollout history。 這個旗標已在 k8s 1.22 標記為棄用，1.25 移除。 現代做法是在 Deployment 的 metadata.annotations 加入 kubernetes.io/change-cause: "upgrade to nginx 1.27.1" 作為變更說明，rollout history 就能顯示原因。

Service 與 Ingress：穩定的存取入口

Pod 的 IP 是臨時的——Pod 重啟、滾動更新後，IP 就換了。 如果讓別人直接連 Pod IP，系統就會在每次更新後斷線。 Service 解決了這個問題：它提供一個穩定的虛擬 IP（ClusterIP）， 並用標籤選擇器(label selector) 動態追蹤後端 Pod 的集合， kube-proxy 把流量分流到任一健康的 Pod。 

# service.yaml — ClusterIP Service(只在叢集內可存取)
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:
    app: nginx          # 選取帶有 app=nginx 的所有 Pod
  ports:
  - protocol: TCP
    port: 80            # Service 對外暴露的埠
    targetPort: 80      # Pod 容器監聽的埠
  type: ClusterIP       # 預設值：只在叢集內可存取

除了 ClusterIP，Service 還有兩種常用類型：

  • NodePort：在每個節點上開一個固定埠（預設 30000–32767）， 讓叢集外部可以透過 NodeIP:NodePort 存取——適合開發環境或沒有 LoadBalancer 的場景。
  • LoadBalancer：在雲端環境（AWS/GCP/Azure）上自動建立一個外部負載均衡器， 分配一個外部 IP——生產環境最常用。

Ingress：HTTP 路由與 TLS 終止

Ingress 比 Service 高一層：它基於 HTTP Host 和 path 做路由， 並可以集中處理 TLS 憑證終止(TLS termination)——讓多個 Service 共用一個對外 IP。 

# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /v1
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
  - host: www.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
  tls:
  - hosts:
    - api.example.com
    - www.example.com
    secretName: tls-secret     # 存放 TLS 憑證的 Secret
ℹ️
Ingress Controller 才是實際做事的

Ingress 資源本身只是宣告（routes 的規則描述）。 要讓它生效，叢集裡必須有一個 Ingress Controller—— 最常見的是 ingress-nginx（由社群維護），也有 Traefik、Kong、AWS ALB Ingress Controller 等。 Ingress Controller 監聽 Ingress 物件，動態更新自己的 nginx / Envoy 設定來實現路由。 minikube 可用 minikube addons enable ingress 快速安裝。

設定與儲存：ConfigMap、Secret 與 PersistentVolumeClaim

ConfigMap：非敏感設定

把設定從映像中分離出來，讓同一個映像能在開發/測試/生產環境用不同的設定跑起來—— 這是 ConfigMap 的核心用途。 

# configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DATABASE_HOST: "postgres-service"
  LOG_LEVEL: "info"
  MAX_CONNECTIONS: "100"

ConfigMap 可以以環境變數或檔案的方式注入到 Pod：

spec:
  containers:
  - name: app
    image: myapp:1.0
    envFrom:
    - configMapRef:
        name: app-config    # 把 ConfigMap 的所有 key 注入為環境變數

Secret：敏感設定

密碼、API 金鑰、TLS 憑證要用 Secret 存放。 Secret 的值是 Base64 編碼（不是加密）——主要目的是隔離敏感資料， 讓 RBAC 可以單獨控管 Secret 的存取權限；生產環境務必結合 etcd 加密或 HashiCorp Vault / Sealed Secrets 等外部密鑰管理。 

# 用 kubectl 建立 Secret(值自動 Base64)
# kubectl create secret generic app-secret \
#   --from-literal=DB_PASSWORD=supersecret \
#   --from-literal=API_KEY=abc123

# 等效的 YAML(值須手動 Base64 編碼)
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
data:
  DB_PASSWORD: c3VwZXJzZWNyZXQ=   # echo -n 'supersecret' | base64
  API_KEY: YWJjMTIz               # echo -n 'abc123' | base64
spec:
  containers:
  - name: app
    image: myapp:1.0
    env:
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: app-secret
          key: DB_PASSWORD

PersistentVolumeClaim：有狀態應用的儲存

Pod 預設是無狀態的——Pod 刪除，儲存就消失。 資料庫等有狀態應用需要 PersistentVolume(PV) 與 PersistentVolumeClaim(PVC)： PV 是管理員預置的儲存資源，PVC 是 Pod 對儲存的「申請書」。 動態供應(dynamic provisioning)讓雲端叢集自動根據 PVC 建立 PV（如 AWS EBS、GCP PD）。 

# pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-pvc
spec:
  accessModes:
  - ReadWriteOnce          # 一次只有一個 Pod 可讀寫(適合資料庫)
  resources:
    requests:
      storage: 10Gi
  storageClassName: standard   # 由 StorageClass 定義供應方式
spec:
  volumes:
  - name: postgres-data
    persistentVolumeClaim:
      claimName: postgres-pvc   # 引用上面的 PVC
  containers:
  - name: postgres
    image: postgres:16-alpine
    volumeMounts:
    - name: postgres-data
      mountPath: /var/lib/postgresql/data
⚠️
Secret 的 Base64 不是加密

echo 'supersecret' | base64 任何人都能解碼。 Secret 存在 etcd 預設是明文的（只有 Base64）。 生產叢集應啟用 etcd 的靜態加密(encryption at rest)， 或使用 Sealed Secrets 讓 Secret 能安全提交到 Git 倉庫。

自我修復與水平擴展：Probe 與 HPA

liveness probe：應用還活著嗎？

容器在跑不代表應用正常——有時行程還在，但已經死鎖(deadlock)或陷入無限迴圈。 liveness probe 讓 kubelet 定期探測應用是否「還活著」； 如果探測連續失敗達到 failureThreshold，kubelet 就重啟容器。

readiness probe：應用準備好接受流量了嗎？

應用剛啟動時可能還在暖機（連資料庫、載入快取）——這時候雖然行程在跑， 但還沒準備好服務請求。 readiness probe 探測通過後，Pod 才會被 Service 加入後端， 開始接收流量；失敗時從後端移除（但不重啟容器）。 

# 在 Deployment 的 container spec 裡加 probe
spec:
  containers:
  - name: app
    image: myapp:1.0
    ports:
    - containerPort: 8080
    livenessProbe:
      httpGet:
        path: /healthz       # 應用需要提供這個 endpoint
        port: 8080
      initialDelaySeconds: 15  # 容器啟動後等 15 秒再開始探測
      periodSeconds: 10        # 每 10 秒探測一次
      failureThreshold: 3      # 連續失敗 3 次才重啟
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 5
      failureThreshold: 2      # 連續失敗 2 次就從 Service 後端移除
🔑
liveness vs readiness：容易混淆的差異

liveness：「我還活著嗎？」失敗 → 重啟容器。
readiness：「我準備好接流量了嗎？」失敗 → 從 Service 後端移除（不重啟）。

典型場景：資料庫連線初始化中，readiness 失敗（Service 不分流量給我）， 但 liveness 還通過（行程健康不需要重啟）。 一旦資料庫連上，readiness 通過，Service 開始把流量導過來。

HPA：水平自動擴展(Horizontal Pod Autoscaler)

HPA 根據 CPU / 記憶體使用率（或自訂指標）自動調整 Deployment 的副本數， 讓叢集在流量高峰自動橫向擴展、尖峰過後自動縮減、節省資源費用。 

# hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-deployment
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70   # CPU 超過 70% 就擴展

HPA 需要叢集安裝 Metrics Server（minikube 用 minikube addons enable metrics-server）才能取得 Pod 的 CPU/記憶體用量。 Pod 的 resources.requests 也必須設定，HPA 才有基準值可算百分比。

ℹ️
startup probe：保護啟動緩慢的應用

如果應用啟動需要 60 秒（如 JVM 預熱），把 initialDelaySeconds 設很大很粗糙。 startup probe（k8s 1.18+）可在容器成功啟動之前保護它： startup probe 通過之前，liveness/readiness 暫停探測， 不會因為啟動慢而被誤殺。Startup 通過後，才接棒給 liveness/readiness。

動手：用 minikube 跑起第一個 Deployment + Service

minikube 是本機單節點 k8s 環境，適合入門學習； kind(Kubernetes IN Docker) 則把整個叢集跑在 Docker 容器裡，適合測試多節點場景。 以下用 minikube 示範完整流程。

✏️ 練習 90.1 實作

寫一份完整的 postgres-app.yaml，包含：

(b) 一個 Deployment，跑 postgres:16-alpine，副本數 1， 掛上 PVC 到 /var/lib/postgresql/data， 並用 Secret（自行建立）注入 POSTGRES_PASSWORD；
(c) 一個 Service（ClusterIP），把 5432 埠暴露到叢集內部；
在 minikube 上用 kubectl apply 套用，確認 Pod 進入 Running 狀態， 並用 kubectl exec 進入容器執行 psql -U postgres 驗證。

看解答 
# 先建立 Secret
kubectl create secret generic postgres-secret \
  --from-literal=POSTGRES_PASSWORD=mysecretpassword

apiVersion: v1

      storage: 2Gi

    matchLabels:
      app: postgres

    metadata:

        app: postgres
    spec:

        image: postgres:16-alpine

        env:

              name: postgres-secret
              key: POSTGRES_PASSWORD

✏️ 練習 90.2 思考

解釋 liveness probe 與 readiness probe 的差異， 並說明以下情境下應用哪種（或兩者都用）：
(a) 一個 Java 應用，JVM 啟動需要 30 秒，啟動期間不應接受流量，但啟動後若陷入死鎖應自動重啟；
(b) 一個連資料庫的 API 服務，若資料庫暫時斷線，API 不應接流量，但不需要重啟；
(c) 一個批次處理 worker，沒有 HTTP 服務，若行程卡死超過 5 分鐘應重啟。

看解答

(a) JVM 應用——應用 startup probe + liveness + readiness

  • startup probe：保護啟動期，讓 liveness/readiness 在 JVM 暖機完成前不介入。 failureThreshold: 30, periodSeconds: 2（最多等 60 秒）。
  • liveness：startup 通過後，持續偵測應用是否死鎖，失敗則重啟。
  • readiness：確保暖機完成後才接流量（可與 liveness 使用同一 endpoint 或更嚴格的 endpoint）。

(b) 資料庫斷線——只用 readiness probe

  • readiness：probe 連資料庫，斷線時失敗 → 從 Service 後端移除，不接流量； 資料庫恢復後 probe 通過 → 自動重新加入。
  • 不應用 liveness：資料庫斷線是外部問題，重啟自身 Pod 沒有意義。

(c) 批次 worker——只用 liveness probe（exec 類型）

livenessProbe:
  exec:
    command:
    - sh
    - -c
    - test $(find /tmp/heartbeat -mmin -5 | wc -l) -gt 0
  periodSeconds: 60
  failureThreshold: 5

Worker 每分鐘 touch /tmp/heartbeat；若超過 5 分鐘沒更新（卡死），liveness 失敗，kubelet 重啟容器。 沒有 HTTP 服務，所以用 exec 類型 probe。

✏️ 練習 90.3 思考

一個 Deployment 目前跑著 nginx:1.26，你需要零停機地更新到 nginx:1.27。 說明 Kubernetes 的滾動更新機制如何確保零停機，並回答：
(a) maxSurge: 1, maxUnavailable: 0 的含義是什麼？更新 5 個副本時，副本數的變化過程是？
(b) 什麼情況下應該選 strategy: Recreate（刪除全部舊 Pod 再建立新 Pod）？有什麼缺點？
(c) 若更新途中發現新版本有 bug，如何最快速回復到舊版本？

看解答

(a) maxSurge: 1, maxUnavailable: 0

maxSurge: 1 = 更新過程中，Pod 總數最多比期望值多 1 個。
maxUnavailable: 0 = 任何時候，可用的 Pod 數不得少於期望值（5 個）。

更新 5 個副本的過程（replicas: 5, maxSurge: 1, maxUnavailable: 0）：

  1. 建立 1 個新 Pod（v1.27），總數 6（5+1）
  2. 新 Pod readiness 通過後，刪除 1 個舊 Pod（v1.26），總數 5
  3. 重複直到所有 5 個 Pod 都是 v1.27

整個過程可用 Pod 一直 ≥ 5，不中斷服務。

(b) strategy: Recreate 的適用場景與缺點

適用：應用不支援多版本同時執行（如持有共享資料庫 schema lock），或有狀態應用只能單副本。

缺點：有停機期——所有舊 Pod 刪除後，到新 Pod 就緒之前，服務完全中斷。

(c) 快速回滾

# 立即回滾到上一個版本(就是把舊 ReplicaSet 的副本數調回來)
kubectl rollout undo deployment/nginx-deployment

# 驗證回滾後的映像版本
kubectl get deployment nginx-deployment -o jsonpath='{.spec.template.spec.containers[0].image}'

回滾速度很快，因為 k8s 保留了舊的 ReplicaSet（只是副本數調為 0）—— 無需重新拉取映像，只是把舊 RS 的副本數調回 5， 同時把更新後的 RS 縮為 0。 這也是宣告式模型帶來的優雅之處：回滾只是「重新宣告一次舊狀態」。

Namespace 與 RBAC：多租戶與存取控制概觀

當多個團隊共用同一個 k8s 叢集，需要資源隔離與權限管控—— 這是 Namespace 和 RBAC(Role-Based Access Control) 的用武之地。

Namespace

Namespace 是叢集內的邏輯隔離單位——不同 namespace 的資源名稱可以重複（如 dev 和 prod 各自有一個叫 nginx-deployment 的 Deployment，互不干擾）。 Network Policy 和 ResourceQuota 也以 namespace 為邊界。 

# 建立 namespace
kubectl create namespace production

# 在指定 namespace 操作
kubectl apply -f nginx-app.yaml -n production
kubectl get pods -n production

# 查看所有 namespace
kubectl get namespaces

RBAC 基本概念

k8s RBAC 由 Role（定義可以對哪些資源做什麼操作） 和 RoleBinding（把 Role 綁定到 User / ServiceAccount）組成。 跨 Namespace 的版本是 ClusterRole 和 ClusterRoleBinding。 

# role.yaml — 只能讀取 pods
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: production
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: production
  name: read-pods-binding
subjects:
- kind: User
  name: alice
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
ℹ️
Namespace 不是安全邊界

Namespace 提供邏輯隔離與 RBAC 邊界，但不是強安全隔離—— 不同 Namespace 的 Pod 在預設情況下可以互相通訊（透過 ClusterIP Service）。 要實現網路隔離，需搭配 NetworkPolicy（如 Calico、Cilium CNI 支援）。 多租戶強安全隔離應考慮不同叢集，或用更嚴格的機制（如 vCluster）。

把這一章串起來

這一章從「第 89 章 Compose 只管得了一台機器」出發， 踏進了叢集編排的世界。讓我們總結核心物件與概念的對應關係：

概念 / 物件核心職責關鍵 YAML 欄位
Pod 最小調度單位；共享網路 + volume 的容器群 spec.containers[].image、spec.containers[].resources
Deployment 管理 Pod 副本群、滾動更新、回滾 spec.replicas、spec.selector、spec.template、spec.strategy
ReplicaSet Deployment 自動建立；維護固定副本數 由 Deployment 管理，通常不直接操作
Service 穩定 ClusterIP；標籤選擇器追蹤後端 Pod spec.selector、spec.ports、spec.type
Ingress HTTP/HTTPS 路由；TLS 終止；對外暴露多服務 spec.rules[].host、spec.rules[].http.paths、spec.tls
ConfigMap 非敏感設定與環境變數 data 鍵值對；envFrom.configMapRef
Secret 敏感設定（Base64 存放，搭配 etcd 加密） data（Base64 值）；env.valueFrom.secretKeyRef
PVC 有狀態應用的持久儲存申請書 spec.accessModes、spec.resources.requests.storage
liveness / readiness probe 應用健康偵測；自我修復與流量管控 livenessProbe / readinessProbe（httpGet / exec / tcpSocket）
HPA 依 CPU / 記憶體自動調整副本數 spec.scaleTargetRef、spec.metrics[].resource.target.averageUtilization

Kubernetes 的設計哲學——宣告式設定、調和迴路、標籤選擇器——貫穿了所有物件。 你描述「期望狀態」，K8s 不停地讓「現況」收斂過去： Pod 崩潰了，自動重建；節點故障了，Pod 調度到其他節點； 流量暴增，HPA 自動擴展副本；版本更新失敗，一條指令回滾。 這就是「雲原生(cloud native)」的核心承諾： 把運維複雜度從工程師的腦袋裡卸載到系統本身。

本章只觸及了 K8s 的入門層面——還有 StatefulSet（有狀態服務）、 DaemonSet（每個節點跑一個 Pod）、Job / CronJob（批次/定時任務）、 NetworkPolicy（網路隔離）、Helm（套件管理）、 以及 Service Mesh（Istio / Linkerd）等進階主題等著你探索。 在接下來的章節，這些容器化技術也將應用到 AI agent 的工具執行隔離—— 讓每次工具呼叫都在全新容器沙箱裡安全執行。 而關於多個服務如何在叢集中協調通訊、實現高可用的分散式系統， 則是第 92 章分散式系統會深入探討的主題。
