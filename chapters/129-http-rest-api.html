一個請求的一生

你寫了一個待辦清單 App。在手機上按一下「完成」,畫面就打勾了。背後發生的事是:手機送出一段文字給伺服器, 大意是「把第 1 筆待辦的 done 改成 true」;伺服器改好資料庫,再回一段文字:「好了,這是改完的樣子」。

接著問題就來了。網路剛好斷了,App 沒收到回應,可以再送一次嗎?會不會改兩次? 使用者在標題欄位什麼都沒填,伺服器該回什麼,App 才知道要顯示「標題不能空白」? 另一個人剛好在同一秒刪掉了這筆待辦,又該怎麼回?這一章就是在回答這種問題。

你已經有兩塊拼圖:在第 33 章,你用 socket 寫了一個最小的 HTTP/1.1 伺服器,它回傳一頁 HTML; 在第 37 章,你用 sqlite3 存取資料庫。 這一章把兩塊接起來:伺服器不再回 HTML 給人看,而是回 JSON(JavaScript Object Notation) 給程式讀。 這種「給程式用的介面」叫 API(Application Programming Interface,應用程式介面); 照著 HTTP 原本的設計來用它,就是本章要學的 REST 風格。

  2. ThreadingHTTPServer 在 accept() 收到連線,替這條連線開一條執行緒。
  3. Handler(轉接層)把請求拆成五樣東西:方法、路徑、query、標頭(鍵改小寫)、本體位元組,交給 app。

核心觀念

一個 HTTP 服務,說穿了就是一個函式:(方法, 路徑, 標頭, 本體) → (狀態碼, 標頭, 本體)。 連線、執行緒、資料庫都是為了讓這個函式跑起來。先把這個函式設計清楚、寫成可以單獨測試的樣子,伺服器之後隨時可以換。

資源建模:先想名詞,再想動詞

第 40 章已經提過 REST 的核心想法: 把系統裡的東西看成資源(resource),用 URL 指出它,再用 HTTP 方法說要對它做什麼。 資源是名詞;方法是動詞。伺服器送回來的 JSON 是資源的一種表示法(representation): 同一筆待辦,可以用 JSON 表示,也可以用 HTML 表示。

📜
REST 這個名字從哪裡來

REST 是 Representational State Transfer(表示法狀態轉移)的縮寫,出自 Roy Fielding 2000 年在加州大學爾灣分校的博士論文。 Fielding 也是 HTTP/1.1 規格的主要作者之一。他描述的是「Web 為什麼能長到這麼大」的架構限制; 今天大家說的「REST API」,通常只用到其中一部分:資源、統一的方法、無狀態的請求。

設計 URL 時,照這幾條規則走,大部分情況都不會錯:

  • 集合用複數名詞:/todos 是所有待辦;單筆在後面接 id:/todos/42。
  • 篩選、排序、分頁放在 query string:/todos?done=false&limit=20&offset=40。它們不是新的資源,只是「看集合的方式」。
  • URL 裡不放動詞:不要 /createTodo、/deleteTodo?id=42。動作交給方法。
  • 不是增刪改查的動作,把它變成名詞。「借書」不是 /borrow,而是「建立一筆借閱紀錄」:POST /loans。 「還書」改變的是那筆借閱的狀態,可以寫成它的子資源:POST /loans/7/return。
  • 常用的查詢可以是一個「檢視」:「所有逾期的借閱」寫成 GET /loans/overdue,它是 /loans 集合篩選後的樣子。

小技巧:把動詞改寫成「建立一筆紀錄」

遇到「付款」「報名」「借書」這種動詞,先問:「這個動作做完,世界上多了什麼紀錄?」多了一筆付款、一筆報名、一筆借閱。 那筆紀錄就是資源,動作就是 POST 到它的集合。這樣做還有一個好處:紀錄有自己的 id,之後可以查、可以還、可以列出逾期的。

方法的語意:安全與冪等

💡
為什麼要學

網路一定會斷線、逾時、被使用者連點兩下。這時客戶端只能猜:「剛剛那個請求,伺服器到底做了沒?」 方法的「安全」與「冪等」就是 HTTP 給的答案:冪等的請求可以放心重送。 本章 Lab bookapi/api 的隱藏檢定「資料一致」會重複呼叫刪除與還書; 第 93 章的重試與至少一次送達,也是建立在同一個觀念上。

HTTP 規格(RFC 9110)替每個方法定了兩個性質:

  • 安全(safe):客戶端沒有要求、也不預期伺服器的狀態改變。也就是「只讀」。
  • 冪等(idempotent):同一個請求做一次和連做 N 次,伺服器狀態的預期效果一樣。

安全的方法一定冪等(什麼都不改,做幾次都一樣);反過來不成立。

方法用途安全冪等待辦服務的例子成功時常見的狀態碼
GET讀取是是GET /todos/1200(或 304)
HEAD和 GET 一樣,但只要標頭是是HEAD /todos/1200
OPTIONS問這個 URL 支援什麼是是OPTIONS /todos200 或 204
POST建立新資源,或請伺服器「處理」否否POST /todos201(建立)、200
PUT用請求的內容整筆取代否是PUT /todos/1200、204
PATCH部分修改否不一定PATCH /todos/1200
DELETE刪除否是DELETE /todos/1204、200

PUT 和 PATCH 最容易搞混。PUT /todos/1 的本體要是「這筆待辦完整的新樣子」: {"title": "買豆漿", "done": false},少給一個欄位就是錯(本章的服務回 422)。 PATCH /todos/1 只給要改的欄位:{"done": true},其他欄位不動。 PATCH 是不是冪等,要看本體寫的是什麼:「把 done 設成 true」做幾次都一樣; 「把計數器加 1」做兩次就加了 2。所以表格寫「不一定」。

🔑
核心觀念

冪等說的是伺服器的狀態,不是回應。第一次 DELETE /todos/2 回 204,第二次回 404; 兩次之後,伺服器裡一樣「沒有第 2 筆」。狀態一樣,所以 DELETE 是冪等的,回應不同也沒關係。

看起來對但其實錯:關於方法的四個誤會

下面四句話,每一句都能舉出「看起來支持它」的例子,但每一句都是錯的。例子都對 ≠ 敘述為真:一個反例就夠推翻它。

看起來對的說法為什麼看起來對反例
「PUT 和 POST 可以互換,反正都會寫入資料。」第一次送的時候,兩個都會寫入,也都成功。 網路逾時,客戶端重送。POST /todos {"title": "讀 RFC"} 送兩次,伺服器多了兩筆(id 1 和 2,見下面手算的第 2、3 列); PUT /todos/1 送兩次,第 1 筆還是同一個樣子。能不能安全重送,差在這裡。
「DELETE 是冪等的,所以第二次 DELETE 也必須回 200(或 204)。」「冪等」聽起來像「每次結果都一樣」。 本章的服務第一次 DELETE /todos/2 回 204,第二次回 404,而它完全符合冪等:狀態都是「沒有第 2 筆」。 第二次回 204 或 404 都可以,重點是寫進規格、每個端點都一樣。本章和借書 Lab 都選 404。
「GET 是安全的,所以處理 GET 時伺服器什麼都不能寫。」安全就是「只讀」。 寫存取日誌、累加瀏覽次數都可以;「安全」說的是客戶端沒有要求改變。真正的錯誤是反過來: 用 GET /todos/1/delete 這種連結刪資料。搜尋引擎的爬蟲、瀏覽器的預先載入都會自動跟著 GET 連結走,資料就被刪光了。
「PATCH 一定不冪等。」(或「一定冪等」)表格寫 PATCH 的冪等是「不一定」。 PATCH /todos/1 {"done": true} 連做兩次,狀態一樣,是冪等的; PATCH /counters/1 {"op": "add", "value": 1} 連做兩次加了 2,不是冪等的。要看本體的內容,不能只看方法。

ℹ️
422 的名字

422 原本是 WebDAV 擴充(RFC 4918)定的,叫 Unprocessable Entity;RFC 9110 把它收進 HTTP 本體,改叫 Unprocessable Content。 Python 3.12 的 http.server 送出的狀態列還是舊名字 422 Unprocessable Entity。沒關係:客戶端只看數字,不看後面的文字。

判斷順序:由外往內

一個請求可能同時有好幾個毛病(例如路徑不存在、而且 JSON 也壞了)。規格要說清楚先檢查哪一個,否則兩個人寫出來的服務會回不同的狀態碼。本書的順序是由外往內:

  1. 路徑存在嗎?不存在 → 404。
  2. 這個路徑支援這個方法嗎?不支援 → 405,加 Allow。
  3. 要讀本體的請求(POST、PUT、PATCH),Content-Type 是 application/json 嗎?不是 → 415。
  4. 本體是合法的 JSON 嗎?不是 → 400。
  5. 內容合規則嗎?(是物件、欄位齊、型別對、範圍對、沒有多的欄位)不合 → 422。
  6. 要動的那一筆存在嗎?不存在 → 404。
  7. 和目前的狀態衝突嗎?衝突 → 409。
  8. 都沒問題 → 200、201 或 204。過程中丟出沒預料到的例外 → 500。

所以 PATCH /todos/99 帶著壞掉的 JSON,本章的服務回 400,不是 404:本體在第 4 步就被擋下,還輪不到第 6 步去找第 99 筆。 別的 API 可以有別的順序;重點是寫清楚,而且每個端點都一樣。

驗證:400 還是 422

這兩個最常被混用。本書用一句話分:400 是「我讀不懂」,422 是「我讀懂了,但內容不對」。

有些 API 把所有輸入錯誤都回 400,這也說得通。真正的錯誤是同一個 API 裡有時回 400、有時回 422, 客戶端就沒辦法寫判斷。本書的範例和借書 Lab 一律用上面這張表的分法。

409 和 422 怎麼分

問自己:「同一個請求,換一個時間送,會不會成功?」 {"days": 0}(借 0 天)什麼時候送都不對,是 422。 「借第 1 本書」本身沒錯,只是現在最後一本剛被借走;等別人還了再送,就會成功,所以是 409。 409 是「和目前的狀態衝突」,422 是「這個請求本身就不合規則」。

標頭:回應的說明書

本體是內容,標頭是「關於內容的說明」。JSON API 最常用的是這幾個:

標頭出現在意思本章怎麼用
Content-Type請求、回應本體是什麼格式回應一律 application/json; charset=utf-8;請求不是 JSON 就回 415
Content-Length請求、回應本體有幾個位元組(不是幾個字)「寫」是 1 個字、3 個位元組(UTF-8);204 和 304 不送
Location201 回應新資源的 URLLocation: /todos/1
Allow405 回應這個路徑支援哪些方法Allow: GET, POST
Cache-Control回應可以怎麼快取no-cache:可以存,但每次用之前要先問伺服器
ETag回應這個版本的「指紋」本體的 SHA-256 取前 16 個十六進位數字,加上雙引號
If-None-Match請求「我手上是這個 ETag,有變才給我」一樣 → 304,沒有本體;不一樣 → 200 和新的本體

ETag 與 If-None-Match:沒變就不用再傳一次

App 每次打開都要 GET /todos/1。如果那筆待辦根本沒變,伺服器每次都送一樣的 52 個位元組,很浪費。 解法是條件式請求:第一次的回應帶 ETag: "3160ff4792ad8839",App 把本體和 ETag 一起存起來; 下一次請求帶 If-None-Match: "3160ff4792ad8839"。伺服器算一下現在的 ETag,一樣就回 304 Not Modified,沒有本體, App 直接用手上那份。下一節的 curl -v 會讓你親眼看到這段對話。

⚠️
看起來對但其實錯:no-cache 就是「不要快取」

名字很像,意思不是。Cache-Control: no-cache 是「可以存起來,但每次用之前都要先問伺服器(重新驗證)」,正好配合 ETag 用。 真正的「不准存」是 no-store,用在密碼、個資這種不該留在任何快取裡的回應。快取的完整故事留給後面的快取主題(bookapi 任務線的第 3 個檢查點)。

出錯時把 Python 的 traceback 原封不動送給客戶端,等於把檔案路徑、SQL、函式庫版本告訴攻擊者。 細節寫進伺服器自己的日誌;回應只說 {"error": {"code": "internal", "message": "伺服器內部錯誤"}}。 為什麼這很重要,見第 36 章與第 53 章。

分頁:limit 與 offset

待辦只有 5 筆時,GET /todos 全部送回去沒問題;有 10 萬筆時,一次送完會拖垮伺服器、網路和客戶端。 所以列表一律分頁(pagination):GET /todos?limit=10&offset=20 是「跳過前 20 筆,給我接下來的 10 筆」, 對應 SQL 的 ORDER BY id LIMIT 10 OFFSET 20。本書 API 的規則:

  • limit:1 到 100 的整數,沒給就是 20。offset:0 以上的整數,沒給就是 0。不是整數或超出範圍 → 422。
  • offset 超過結尾不是錯誤:回 200,items 是空陣列。
  • 一定要 ORDER BY。SQL 沒有寫排序時,不保證每次的順序一樣,分頁就沒有意義。本書的列表一律照 id 由小到大。
  • 回應的形狀:{"items": [...], "limit": 10, "offset": 20}。

總共 $N$ 筆、每頁 $L$ 筆(頁和筆都從 1 開始算)時:

  • 頁數 $= \lceil N / L \rceil$;第 $p$ 頁的 offset $= (p-1) \times L$。
  • 第 $k$ 筆在第 $\lfloor (k-1)/L \rfloor + 1$ 頁,那一頁的 offset 是 $\lfloor (k-1)/L \rfloor \times L$。
  • 最後一頁有 $N - (\lceil N/L \rceil - 1) \times L$ 筆。
  • 任何 offset $= o$ 的請求,拿到的是第 $o+1$ 到第 $\min(o+L, N)$ 筆;$o \ge N$ 時是空的。

offset 的陷阱:翻頁翻到一半,有人新增或刪除

上面的公式有一個隱藏的假設:翻頁的過程中,資料沒有變。真實的服務一直有人在寫入。下面的程式在兩頁之間插入或刪除一筆,看看會發生什麼事:

# offset_drift.py — 翻頁翻到一半,有人新增或刪除資料
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE posts (id INTEGER PRIMARY KEY)")
conn.executemany("INSERT INTO posts VALUES (?)", [(i,) for i in range(1, 8)])  # 1..7


def page(offset, limit=3, order="DESC"):
    sql = f"SELECT id FROM posts ORDER BY id {order} LIMIT ? OFFSET ?"
    return [r[0] for r in conn.execute(sql, (limit, offset))]


# 情況一:最新的排前面(DESC),翻頁途中有人新增一篇
print("第 1 頁:", page(0))
conn.execute("INSERT INTO posts VALUES (8)")
print("第 2 頁:", page(3), "← 5 又出現一次")

# 情況二:舊的排前面(ASC),翻頁途中有人刪掉一篇
conn.execute("DELETE FROM posts WHERE id = 8")
print("第 1 頁:", page(0, order="ASC"))
conn.execute("DELETE FROM posts WHERE id = 2")
print("第 2 頁:", page(3, order="ASC"), "← 4 被跳過了")

# 修法:keyset(游標)分頁——記住「上一頁最後一個 id」,從它之後接著拿
conn.execute("INSERT INTO posts VALUES (2)")       # 還原成 1..7
first = page(0, order="ASC")
conn.execute("DELETE FROM posts WHERE id = 2")
after = first[-1]
rest = [r[0] for r in conn.execute(
    "SELECT id FROM posts WHERE id > ? ORDER BY id LIMIT 3", (after,))]
print("keyset:", first, "→", rest, "← 沒有重複也沒有跳過")

輸出:

第 1 頁: [7, 6, 5]
第 2 頁: [5, 4, 3] ← 5 又出現一次
第 1 頁: [1, 2, 3]
第 2 頁: [5, 6, 7] ← 4 被跳過了
keyset: [1, 2, 3] → [4, 5, 6] ← 沒有重複也沒有跳過

情況一:最新的排前面時,新增的第 8 篇把所有東西往後推一格,原本在第 1 頁最後的 5 被推到第 2 頁的開頭,看到兩次。 情況二:刪掉第 2 篇,後面的往前補一格,原本該在第 2 頁開頭的 4 被擠到第 1 頁(而第 1 頁早就讀過了),從來沒看到。 offset 數的是「第幾個位置」,位置會跟著資料移動。

修法是 keyset 分頁(也叫游標分頁):不說「跳過幾筆」,而說「給我 id 大於 3 的接下來 3 筆」(WHERE id > ? ORDER BY id LIMIT ?)。 id 不會因為別人新增或刪除而移動。代價是不能直接跳到「第 37 頁」。本書的 API 用 offset(簡單、Lab 的規格就是它);練習 129.6 會讓你寫 keyset 版本。

⚠️
看起來對但其實錯:「offset 分頁不會漏資料,也不會重複」

沒有人同時寫入時,上面的手算表每一頁都剛好接起來,看起來永遠對。但只要翻頁途中有一次新增或刪除,就會重複或漏掉。 例子都對 ≠ 敘述為真;測試分頁時,要故意在兩頁之間改資料。

版本:API 改了,舊的客戶端怎麼辦

網頁改版,使用者重新整理就拿到新版。API 不一樣:已經裝在幾萬支手機上的舊 App,不會馬上更新。 所以改 API 之前,先分清楚這個改動相容還是不相容:

改動舊客戶端會不會壞
回應多一個欄位(例如待辦多了 created_at)不會,只要客戶端忽略不認得的欄位
請求多一個可選的欄位不會,舊客戶端不送,伺服器用預設值
欄位改名(title → name)、改型別、刪掉會
可選欄位改成必填會,舊客戶端沒送,突然收到 422
同一種情況改用別的狀態碼(404 改成 410)會,客戶端的 if 判斷失效

不相容的改動要開新版本。常見做法有三種:

  • 放在路徑:/v1/todos、/v2/todos。最直觀,用 curl 一眼看得出版本;最常見。
  • 放在標頭:例如 Accept: application/vnd.example.v2+json。URL 不變,但除錯時要記得看標頭。
  • 放在 query:/todos?version=2。簡單,但容易和篩選參數混在一起。

不管哪一種,原則都一樣:能用相容的方式改,就不要開新版本(加欄位,不要改欄位);真的要改,新舊版並存一段時間,先公告舊版什麼時候停用。 本章的待辦服務和借書 Lab 都只有一個版本,所以路徑沒有 /v1。

嚴格驗證的代價

本書的服務遇到不認得的請求欄位就回 422。好處是客戶端打錯字(titel)時馬上知道; 代價是新版客戶端多送一個欄位給舊版伺服器,會被拒絕。這是設計上的取捨,沒有標準答案,但一定要寫進規格。

資料層:todo_store.py

# todo_store.py — 待辦事項的資料層(sqlite3)
import sqlite3
import threading


class NotFound(Exception):
    """找不到這筆待辦。"""


# 能改的欄位只有這兩個;每個欄位一條固定的 SQL(不用字串拼接組 SQL)
UPDATE_SQL = {
    "title": "UPDATE todos SET title = ? WHERE id = ?",
    "done": "UPDATE todos SET done = ? WHERE id = ?",
}


class TodoStore:
    def __init__(self, db_path=":memory:"):
        # 多個執行緒共用一個連線:關掉 sqlite3 的執行緒檢查,改用自己的鎖保護
        self.conn = sqlite3.connect(db_path, check_same_thread=False)
        self.conn.row_factory = sqlite3.Row
        self.lock = threading.Lock()
        with self.lock, self.conn:
            self.conn.execute(
                "CREATE TABLE IF NOT EXISTS todos ("
                " id INTEGER PRIMARY KEY,"
                " title TEXT NOT NULL,"
                " done INTEGER NOT NULL DEFAULT 0)"
            )

    @staticmethod
    def _to_dict(row):
        return {"id": row["id"], "title": row["title"], "done": bool(row["done"])}

    def _get(self, todo_id):
        row = self.conn.execute(
            "SELECT * FROM todos WHERE id = ?", (todo_id,)).fetchone()
        if row is None:
            raise NotFound(todo_id)
        return self._to_dict(row)

    def add(self, title, done=False):
        with self.lock, self.conn:        # with conn:成功就 commit,出錯就 rollback
            cur = self.conn.execute(
                "INSERT INTO todos (title, done) VALUES (?, ?)", (title, int(done)))
            return self._get(cur.lastrowid)

    def get(self, todo_id):
        with self.lock:
            return self._get(todo_id)

    def list(self, limit=20, offset=0, done=None):
        sql, args = "SELECT * FROM todos", []
        if done is not None:
            sql += " WHERE done = ?"
            args.append(int(done))
        sql += " ORDER BY id LIMIT ? OFFSET ?"   # 一定要排序,分頁才有意義
        args += [limit, offset]
        with self.lock:
            return [self._to_dict(r) for r in self.conn.execute(sql, args)]

    def update(self, todo_id, **fields):
        with self.lock, self.conn:
            self._get(todo_id)                   # 不存在就丟 NotFound
            for name, value in fields.items():
                self.conn.execute(UPDATE_SQL[name], (value, todo_id))
            return self._get(todo_id)

    def delete(self, todo_id):
        with self.lock, self.conn:
            cur = self.conn.execute("DELETE FROM todos WHERE id = ?", (todo_id,))
            if cur.rowcount == 0:
                raise NotFound(todo_id)
  • with self.lock, self.conn::先拿鎖,再進交易。sqlite3 連線的 with 區塊正常結束就 commit,丟例外就 rollback(第 37 章的交易與 ACID)。
  • 為什麼要鎖:伺服器會用好幾條執行緒同時處理請求,它們共用這一個連線。check_same_thread=False 只是關掉 sqlite3 的檢查,保護要靠自己的鎖。
  • UPDATE_SQL:要改哪個欄位,從固定的兩條 SQL 裡挑一條,值一律用 ? 傳。不要用字串拼出 SET {name} = ...,那是 SQL injection 的入口。
  • ORDER BY id:分頁的前提。

核心:路由表、驗證與錯誤

# todo_app.py — 待辦事項 JSON API 的核心(不綁任何伺服器)
import hashlib
import json
import re
import traceback

from todo_store import NotFound

# 一個狀態碼對一個固定的錯誤代碼:客戶端用 code 判斷,message 給人看
ERROR_CODES = {
    400: "bad_request",
    404: "not_found",
    405: "method_not_allowed",
    409: "conflict",
    415: "unsupported_media_type",
    422: "validation_error",
    500: "internal",
}


class ApiError(Exception):
    def __init__(self, status, message, headers=None):
        super().__init__(message)
        self.status = status
        self.message = message
        self.headers = headers or {}


def json_response(status, data, headers=None):
    body = json.dumps(data, ensure_ascii=False).encode("utf-8")
    h = {"Content-Type": "application/json; charset=utf-8"}
    h.update(headers or {})
    return status, h, body


def error_response(err):
    data = {"error": {"code": ERROR_CODES[err.status], "message": err.message}}
    return json_response(err.status, data, err.headers)


def read_json(headers, body):
    """讀請求本體:先看 Content-Type(415),再解析(400),最後要求是物件(422)。"""
    ctype = headers.get("content-type", "").split(";")[0].strip().lower()
    if ctype != "application/json":
        raise ApiError(415, "Content-Type 必須是 application/json")
    try:
        data = json.loads(body.decode("utf-8"))
    except (UnicodeDecodeError, json.JSONDecodeError):
        raise ApiError(400, "本體不是合法的 JSON")
    if not isinstance(data, dict):
        raise ApiError(422, "本體必須是 JSON 物件")
    return data


def validate(data, required):
    """欄位檢查:讀得懂、但內容不合規則 → 422。"""
    unknown = sorted(set(data) - {"title", "done"})
    if unknown:
        raise ApiError(422, "不認得的欄位:" + ", ".join(unknown))
    for name in required:
        if name not in data:
            raise ApiError(422, "缺少欄位:" + name)
    if "title" in data:
        t = data["title"]
        if not isinstance(t, str) or not t.strip() or len(t.strip()) > 100:
            raise ApiError(422, "title 必須是 1 到 100 個字的字串")
        data["title"] = t.strip()
    if "done" in data and not isinstance(data["done"], bool):
        raise ApiError(422, "done 必須是 true 或 false")
    return data


def int_param(query, name, default, lo, hi):
    raw = query.get(name)
    if raw is None:
        return default
    if not re.fullmatch(r"-?[0-9]+", raw):
        raise ApiError(422, f"{name} 必須是整數")
    value = int(raw)
    if not lo <= value <= hi:
        raise ApiError(422, f"{name} 必須在 {lo} 到 {hi} 之間")
    return value


def etag_of(payload):
    return '"' + hashlib.sha256(payload).hexdigest()[:16] + '"'


def make_app(store):
    # ── 處理函式:每個都收 (query, headers, body, 路徑裡的 id...) ──
    def list_todos(query, headers, body):
        limit = int_param(query, "limit", 20, 1, 100)
        offset = int_param(query, "offset", 0, 0, 10**9)
        done = query.get("done")
        if done not in (None, "true", "false"):
            raise ApiError(422, "done 只能是 true 或 false")
        items = store.list(limit, offset, None if done is None else done == "true")
        return json_response(200, {"items": items, "limit": limit, "offset": offset})

    def create_todo(query, headers, body):
        data = validate(read_json(headers, body), required=["title"])
        todo = store.add(data["title"], data.get("done", False))
        return json_response(201, todo, {"Location": f"/todos/{todo['id']}"})

    def get_todo(query, headers, body, todo_id):
        status, h, payload = json_response(200, store.get(todo_id))
        tag = etag_of(payload)
        cache = {"ETag": tag, "Cache-Control": "no-cache"}
        if headers.get("if-none-match") == tag:
            return 304, cache, b""             # 你手上那份還是新的
        h.update(cache)
        return status, h, payload

    def replace_todo(query, headers, body, todo_id):      # PUT:整筆取代
        data = validate(read_json(headers, body), required=["title", "done"])
        return json_response(200, store.update(todo_id, **data))

    def patch_todo(query, headers, body, todo_id):        # PATCH:只改給的欄位
        data = validate(read_json(headers, body), required=[])
        return json_response(200, store.update(todo_id, **data))

    def delete_todo(query, headers, body, todo_id):
        store.delete(todo_id)
        return 204, {}, b""                    # 204:成功,而且沒有本體

    # ── 路由表:(方法, 路徑樣式, 處理函式) ──
    routes = [
        ("GET",    r"/todos",          list_todos),
        ("POST",   r"/todos",          create_todo),
        ("GET",    r"/todos/([0-9]+)", get_todo),
        ("PUT",    r"/todos/([0-9]+)", replace_todo),
        ("PATCH",  r"/todos/([0-9]+)", patch_todo),
        ("DELETE", r"/todos/([0-9]+)", delete_todo),
    ]
    compiled = [(m, re.compile(p), f) for m, p, f in routes]

    def app(method, path, query, headers, body):
        """回傳 (狀態碼, 標頭 dict, 本體 bytes)。headers 的鍵是小寫。"""
        try:
            allowed = []
            for m, pattern, func in compiled:
                match = pattern.fullmatch(path)
                if match is None:
                    continue
                if m == method:
                    ids = [int(g) for g in match.groups()]
                    return func(query, headers, body, *ids)
                allowed.append(m)
            if allowed:                        # 路徑對、方法錯 → 405 + Allow
                raise ApiError(405, f"{path} 不支援 {method}",
                               {"Allow": ", ".join(allowed)})
            raise ApiError(404, "沒有這個路徑:" + path)
        except ApiError as e:
            return error_response(e)
        except NotFound as e:
            return error_response(ApiError(404, f"待辦 {e.args[0]} 不存在"))
        except Exception:
            traceback.print_exc()              # 細節寫進伺服器日誌,不送給客戶端
            return error_response(ApiError(500, "伺服器內部錯誤"))

    return app

幾個值得停下來看的地方:

  • 路由表是一張 (方法, 路徑樣式, 處理函式) 的表。app 由上往下比對;路徑對、方法也對,就呼叫那個函式,路徑裡括號抓到的 id 轉成 int 當參數。 路徑對、方法不對,就把方法收集進 allowed,最後回 405 和 Allow。新增一個端點,只要在表裡加一列。
  • fullmatch:整條路徑都要符合。用 match 的話,/todos/1/whatever 也會被當成 /todos/1。
  • [0-9]+ 而不是 \d+:Python 的 \d 也會比對阿拉伯-印度數字「٣」這類 Unicode 數字。路徑裡的 id 只接受 ASCII 數字。
  • read_json 的順序就是「判斷順序」的第 3、4、5 步:先看 Content-Type(415),再解析(400),最後要求是物件(422)。
  • validate 先全部檢查完,才交給資料層。手算 129.1 第 7 列的「全部不改」就是這樣來的。
  • 例外變成回應:ApiError 帶著自己的狀態碼;資料層的 NotFound 變成 404;其他沒預料到的例外變成 500,細節用 traceback.print_exc() 印到伺服器的 stderr。
  • 304 的時候,只回 ETag 與 Cache-Control,本體是空的。
  • If-None-Match 只做字串相等:這是簡化版。RFC 9110 的規則還包括弱比較(W/"…")、用逗號分開的多個 ETag、以及 *;這個範例都不處理。

掛上 http.server:BaseHTTPRequestHandler 與 ThreadingHTTPServer

# todo_server.py — 把 app 掛到標準函式庫的 http.server 上
import re
import sys
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import parse_qsl, urlsplit

from todo_app import ApiError, error_response, make_app
from todo_store import TodoStore


def make_handler_class(app):
    class Handler(BaseHTTPRequestHandler):
        protocol_version = "HTTP/1.1"   # 持續連線:每個有本體的回應都要有 Content-Length

        def _send(self, status, headers, body):
            self.send_response(status)          # 會自動加 Server 與 Date
            for name, value in headers.items():
                self.send_header(name, value)
            if status not in (204, 304):        # 204/304 不能有本體,也不送 Content-Length
                self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)

        def _dispatch(self):
            parts = urlsplit(self.path)
            query = dict(parse_qsl(parts.query))     # 同名參數取最後一個
            headers = {k.lower(): v for k, v in self.headers.items()}
            raw_len = headers.get("content-length", "0")
            if not re.fullmatch(r"[0-9]+", raw_len):   # 不是非負整數 → 400
                status, h, body = error_response(ApiError(400, "Content-Length 不合法"))
                h["Connection"] = "close"            # 本體有多長不知道,只好斷線
                self.close_connection = True
                return self._send(status, h, body)
            body = self.rfile.read(int(raw_len))
            self._send(*app(self.command, parts.path, query, headers, body))

        do_GET = do_POST = do_PUT = do_PATCH = do_DELETE = _dispatch

        def log_message(self, fmt, *args):           # 存取日誌寫到 stderr
            sys.stderr.write("[log] " + fmt % args + "\n")

    return Handler


def make_server(port=8000, db=":memory:"):
    app = make_app(TodoStore(db))
    return ThreadingHTTPServer(("127.0.0.1", port), make_handler_class(app))


if __name__ == "__main__":
    port = int(sys.argv[1]) if len(sys.argv) > 1 else 8000
    server = make_server(port)
    print(f"serving on http://127.0.0.1:{server.server_address[1]}", flush=True)
    server.serve_forever()
  • BaseHTTPRequestHandler 已經幫你讀好請求列和標頭:self.command 是方法,self.path 是路徑加 query,self.headers 是標頭,self.rfile 是還沒讀的本體。 收到 PATCH 時它會呼叫 do_PATCH;這裡讓五個方法都指向同一個 _dispatch。沒定義的方法(例如 OPTIONS)它會自己回 501。HEAD 也沒定義,所以這個範例對 HEAD 回 501;一般的伺服器應該支援 HEAD(回 GET 的標頭、不送本體),這裡是為了簡單而省略。
  • self.rfile.read(n) 剛好讀 Content-Length 個位元組。不能「讀到沒有為止」:連線是保留著的,沒有「結尾」。
  • protocol_version = "HTTP/1.1":預設是 HTTP/1.0(每個回應後就斷線)。改成 1.1 之後連線會保留,客戶端完全靠 Content-Length 知道本體在哪裡結束,所以每個有本體的回應都要送它。 Content-Length 不合法時不知道本體有多長,只好回 400 並斷線。
  • 204 與 304 不送 Content-Length:RFC 9110 規定 204 回應不能帶這個標頭,這兩種回應也一定沒有本體。
  • ThreadingHTTPServer(Python 3.7 起)替每條連線開一條執行緒,所以一個慢的客戶端不會擋住別人。這也是資料層要上鎖的原因。
  • make_server(port=0):埠號給 0,作業系統會挑一個空的埠,測試時很好用;實際的埠在 server.server_address[1]。
⚠️
http.server 適合學習與測試,不適合直接上線

Python 官方文件明白寫著:http.server 只做了基本的安全檢查,不建議用在正式環境。 它沒有逾時(一個只連線不送資料的客戶端會一直佔著一條執行緒)、沒有請求大小上限、沒有 HTTPS。本章的 Handler 也只看 Content-Length,不支援 Transfer-Encoding: chunked 的請求本體。 學習 HTTP、寫測試、在本機跑小工具都很好;正式上線時,前面要有反向代理和正式的應用伺服器。 逾時和執行緒池正好是 srv/pool 那一站要你自己做的事。

# client_demo.py — 用 urllib 當客戶端,走一遍待辦 API
import json
import sys
import urllib.error
import urllib.request

BASE = "http://127.0.0.1:" + sys.argv[1]


def call(method, path, data=None, headers=None):
    body = None if data is None else json.dumps(data).encode("utf-8")
    req = urllib.request.Request(BASE + path, data=body, method=method,
                                 headers=headers or {})
    if data is not None:
        req.add_header("Content-Type", "application/json")
    try:
        with urllib.request.urlopen(req) as resp:
            status, h, raw = resp.status, resp.headers, resp.read()
    except urllib.error.HTTPError as e:      # 4xx/5xx 會變成例外,一樣讀出來
        status, h, raw = e.code, e.headers, e.read()
    text = raw.decode("utf-8")
    print(method, path, "→", status, text if text else "(沒有本體)")
    return status, h, text

小技巧:urllib 遇到 4xx/5xx 會丟例外

urllib.request.urlopen 收到 4xx 或 5xx 會丟 HTTPError。對 API 來說,錯誤回應也是正常的回應, 所以 call 把例外接住,照樣讀出狀態碼、標頭與本體。e.read() 就是錯誤格式的 JSON。

兩個人借最後一本:併發與 409

圖書館的《小王子》只剩一本。小明和小華在同一秒按下「借」。兩個 POST /loans 分別在兩條執行緒裡處理 (ThreadingHTTPServer 或你的 srv/pool 都會這樣)。如果借書的程式寫成「先查還有幾本,有的話再扣一本」,就可能發生這件事:

時間小明的執行緒小華的執行緒資料庫裡的剩餘本數
1查:剩 1 本1
2查:剩 1 本1
3有剩,扣一本,回 2010
4(它在時間 2 看到的是 1)有剩,扣一本,回 201−1

兩個人都拿到 201,書卻只有一本:超借。這種「先查再做」(check-then-act)的錯誤叫競態條件(race condition), 第 24 章和第 44 章談過它的一般形式。 下面的程式讓 10 條執行緒同時搶最後 1 個名額,比較三種寫法。每條執行緒用自己的連線,就像每個請求在不同的執行緒,甚至不同的伺服器上: 

# last_seat.py — 10 個人同時搶「最後 1 個名額」
import os
import sqlite3
import tempfile
import threading
import time

DB = os.path.join(tempfile.mkdtemp(), "seats.db")


def setup():
    conn = sqlite3.connect(DB)
    conn.execute("DROP TABLE IF EXISTS seats")
    conn.execute("CREATE TABLE seats (id INTEGER PRIMARY KEY, remaining INTEGER NOT NULL)")
    conn.execute("INSERT INTO seats VALUES (1, 1)")        # 只剩 1 個名額
    conn.commit()
    conn.close()


def take_naive(conn):
    """先查再扣(check-then-act):查和扣之間別人可以插隊。"""
    (left,) = conn.execute("SELECT remaining FROM seats WHERE id = 1").fetchone()
    if left <= 0:
        return False
    time.sleep(0.05)                     # 模擬「查完」到「扣掉」之間的空檔
    conn.execute("UPDATE seats SET remaining = remaining - 1 WHERE id = 1")
    conn.commit()
    return True


def take_atomic(conn):
    """把「檢查」寫進 UPDATE 的 WHERE:檢查和扣掉是同一個動作。"""
    cur = conn.execute(
        "UPDATE seats SET remaining = remaining - 1 WHERE id = 1 AND remaining > 0")
    conn.commit()
    return cur.rowcount == 1             # 真的扣到了才算成功


def take_tx(conn):
    """BEGIN IMMEDIATE:一開始就拿寫入鎖,查和扣之間沒人能寫。"""
    conn.execute("BEGIN IMMEDIATE")
    (left,) = conn.execute("SELECT remaining FROM seats WHERE id = 1").fetchone()
    if left <= 0:
        conn.execute("ROLLBACK")
        return False
    time.sleep(0.05)
    conn.execute("UPDATE seats SET remaining = remaining - 1 WHERE id = 1")
    conn.execute("COMMIT")
    return True


def race(take, n=10):
    setup()
    wins = []
    start = threading.Barrier(n)          # 讓 n 個執行緒同時起跑

    def worker():
        # 每個執行緒自己的連線,就像每個請求在不同的執行緒(或不同的伺服器)
        if take is take_tx:
            conn = sqlite3.connect(DB, timeout=10, isolation_level=None)
        else:
            conn = sqlite3.connect(DB, timeout=10)
        start.wait()
        if take(conn):
            wins.append(1)                # list.append 在 CPython 是執行緒安全的
        conn.close()

    threads = [threading.Thread(target=worker) for _ in range(n)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    conn = sqlite3.connect(DB)
    (left,) = conn.execute("SELECT remaining FROM seats WHERE id = 1").fetchone()
    conn.close()
    return len(wins), left


if __name__ == "__main__":
    for take in (take_naive, take_atomic, take_tx):
        wins, left = race(take)
        print(f"{take.__name__:12} 成功 {wins:2} 人,剩下 {left:3} 個名額", end="  ")
        # 兩個不變式:名額不能是負的;成功人數 + 剩下名額 = 原本的 1 個
        print("remaining >= 0:", left >= 0, " wins + remaining == 1:", wins + left == 1)

take_naive   成功 10 人,剩下  -9 個名額  remaining >= 0: False  wins + remaining == 1: True
take_atomic  成功  1 人,剩下   0 個名額  remaining >= 0: True  wins + remaining == 1: True
take_tx      成功  1 人,剩下   0 個名額  remaining >= 0: True  wins + remaining == 1: True
  • take_naive:10 個人都成功,剩下 −9。time.sleep(0.05) 只是把「查完到扣掉」的空檔放大,讓問題每次都出現;真實的伺服器沒有 sleep,問題一樣在,只是比較少見,更難抓。
  • take_atomic:把檢查寫進 UPDATE 的 WHERE remaining > 0。檢查和扣掉是同一個敘述,資料庫保證它不會被別人插隊。rowcount 是 1 就是借到了,是 0 就是沒得借,API 回 409。
  • take_tx:BEGIN IMMEDIATE 讓 SQLite 在交易一開始就拿寫入鎖,別的連線要寫入就得等(timeout=10 是最多等幾秒)。查和扣都在鎖裡,中間沒有人能改。查和扣之間有好幾步(查書、查會員、算可借本數、新增借閱)時,用這種寫法。

程式最後印的兩個檢查,是這個問題的不變式(invariant):任何時候都必須成立的性質。 注意 take_naive 只打破了第一個:「成功人數 + 剩下名額 = 1」還是成立(10 + (−9) = 1),但名額變成負的。 只檢查一個不變式,可能看不出錯。

借書 API 的不變式,寫成每一本書都要一直成立的兩句話:

0 <= available <= copies
available == copies - (這本書還沒還的借閱筆數)

隱藏檢定「資料一致」與「借還負載」會讓很多客戶端同時借還,再檢查這兩句話。 在 Lab 的資料表裡,available 不是一個欄位,而是算出來的(copies 減掉未還的借閱數),所以沒辦法只靠一句 UPDATE books ...; 你要用 BEGIN IMMEDIATE 把「算可借本數」和「新增借閱」包在同一個交易裡,或者把檢查寫進新增借閱的那一句 SQL。

⚠️
常見陷阱:Python 的鎖只管得到同一個行程

本章的 TodoStore 用一把 threading.Lock 保護共用的連線,在一個行程裡確實不會出事。 但同一個資料庫只要被兩個行程(例如開了兩台伺服器)使用,Python 的鎖就管不到了。 把正確性放在資料庫這一層(原子 UPDATE、交易、CHECK 約束),不管幾個行程、幾台伺服器都成立。

規則細節

  • 字串欄位(title、author、isbn、name、email):必須是字串,去掉頭尾空白後不能是空的,存的是去掉空白後的值;email 還要含 @。
  • 整數欄位(copies、book_id、member_id、days):必須是 JSON 整數,true 和 "1" 都不算;copies 小於 0 → 422(欄位驗證在資料層之前,所以走不到 LibraryRepo 的 Conflict)。
  • 不認得的欄位 → 422。PATCH 送 {} 是合法的:什麼都不改,回 200。
  • 分頁同本章:limit 1–100(預設 20),offset 0 以上(預設 0),否則 422;offset 超過結尾回空的 items。列表一律照 id 由小到大。
  • 時間:ISO 8601,到秒,不帶時區,例如 2026-10-01T09:00:00(和 bookapi/repo 的 now 同一種格式)。due_at = loaned_at + days 天。 逾期的意思是 returned_at 是 null,而且 due_at 早於 now;剛好等於 now 不算逾期。
  • 借書的檢查順序:欄位(422)→ 書存在嗎(404)→ 會員存在嗎(404)→ 還有可借的本數嗎(409)。檢查本數和新增借閱必須在同一個交易裡。
  • 回應:有本體的回應一律 Content-Type: application/json; charset=utf-8;204 沒有本體。
  • 錯誤:格式、代碼表、判斷順序都和本章的待辦服務一樣;路徑對、方法錯回 405 加 Allow;要讀本體的請求(POST /books、PATCH /books/{id}、POST /members、POST /loans),Content-Type 不對回 415;POST /loans/{id}/return 不讀本體,不檢查 Content-Type;沒預料到的例外回 500,不送程式細節。

借一本不存在的書:404 還是 422?

POST /loans 的路徑本身存在,不存在的是本體裡指到的那本書。有人主張這該回 422(「本體的內容不對」)。 本書的規格選 404,因為「找不到那一筆」對客戶端最好懂,而且你的 LibraryRepo.borrow 本來就丟 NotFound。兩種都有人用,規格寫清楚最重要。

# 練習:用 Idempotency-Key 讓 POST 可以安全重送
import json
import threading

from todo_app import make_app
from todo_store import TodoStore


def with_idempotency(app):
    seen = {}                       # 金鑰 → 第一次的回應
    lock = threading.Lock()

    def wrapped(method, path, query, headers, body):
        key = headers.get("idempotency-key")
        if method != "POST" or key is None:
            return app(method, path, query, headers, body)
        with lock:                  # 同一把金鑰同時進來兩次,也只做一次
            if key not in seen:
                seen[key] = app(method, path, query, headers, body)
            return seen[key]

    return wrapped

第 (3) 步不是 bug。本章的 ETag 是從本體算出來的,改了又改回去,本體和最初一模一樣,指紋也就一樣;客戶端手上那份確實是最新的。 如果 ETag 改用「版本號,每改一次加 1」,第 (3) 步就會回 200。兩種都正確,前者省流量,後者算起來比較便宜。

✏️ 練習 129.8 挑戰

給 seats 表加上 CHECK (remaining >= 0),再讓 10 條執行緒用 take_naive 搶。會發生什麼事?失敗的執行緒要怎麼處理,API 該回什麼?只靠 CHECK 夠嗎?

看解答 
# 練習:幫 seats 表加上 CHECK,再跑一次「先查再扣」
import sqlite3

import last_seat                      # 沿用 last_seat.py 的 race() 與 take_naive()


def setup_with_check():
    conn = sqlite3.connect(last_seat.DB)
    conn.execute("DROP TABLE IF EXISTS seats")
    conn.execute("CREATE TABLE seats (id INTEGER PRIMARY KEY,"
                 " remaining INTEGER NOT NULL CHECK (remaining >= 0))")
    conn.execute("INSERT INTO seats VALUES (1, 1)")
    conn.commit()
    conn.close()


def take_naive_checked(conn):
    try:
        return last_seat.take_naive(conn)
    except sqlite3.IntegrityError:    # 資料庫拒絕把名額扣成負的 → API 該回 409
        conn.rollback()
        return False


last_seat.setup = setup_with_check    # race() 一開始會呼叫 setup()
wins, left = last_seat.race(take_naive_checked)
print("成功", wins, "人,剩下", left, "個名額")
成功 1 人,剩下 0 個名額

第一個扣到 0 的成功;其他 9 個的 UPDATE 會讓 remaining 變負,資料庫丟 sqlite3.IntegrityError,交易被撤銷,API 回 409。 CHECK 是最後一道防線:就算程式的邏輯寫錯,資料也不會壞。但它不能取代原子 UPDATE 或交易: 借書時要檢查的「可借本數」是算出來的,不是一個欄位,CHECK 管不到;而且靠例外來判斷「沒得借」,很難區分是哪一種衝突。

✏️ 練習 129.10 挑戰

不看規格裡的表,只看「判斷順序」那一節,說明為什麼判斷順序必須寫進規格。舉一個請求,讓「先找資料、再驗證本體」和「先驗證本體、再找資料」的兩個服務回不同的狀態碼。這對隱藏檢定有什麼影響?

看解答

例子:PATCH /todos/99,本體 {oops,而第 99 筆不存在。先驗證本體的服務回 400(本章的服務就是這樣,練習 129.2 的第 2 題);先找資料的服務回 404。 兩個都「合理」,但一個請求只能有一個正確答案,否則測試沒辦法寫。所以規格要定下順序,而所有端點都要照同一個順序。 隱藏檢定的「錯誤處理」類會送這種同時有兩個毛病的請求;照本書的順序寫,就不會因為順序不同而失敗。

把這一章串起來

  • 資源與 URL:名詞當資源,方法當動作。不是增刪改查的動作,變成「建立一筆紀錄」(借書 = POST /loans)或子資源(還書 = POST /loans/{id}/return)。
  • 方法的語意:安全 = 只讀;冪等 = 做一次和做 N 次,伺服器狀態一樣。冪等看的是狀態,不是回應:第二次 DELETE 回 404 完全沒問題。POST 不冪等,要安全重送就用 Idempotency-Key。
  • 狀態碼:201 加 Location、204 沒有本體、400 讀不懂、422 讀懂了但不合規則、409 和目前的狀態衝突、405 加 Allow、415 不是 JSON、500 不洩漏細節。判斷順序由外往內,而且要寫進規格。
  • 標頭:Content-Length 數的是位元組;ETag 加 If-None-Match 讓沒變的資料回 304;no-cache 不是 no-store。
  • 錯誤格式:每一個錯誤都是 {"error": {"code", "message"}},程式看 code,人看 message。
  • 分頁與版本:limit/offset 一定要配 ORDER BY;翻頁途中有寫入會重複或漏掉,keyset 分頁可以解決。不相容的改動才開新版本。
  • 程式結構:資料層、核心 app、轉接層三層。app 是一個純函式,可以直接測試,也可以掛在 http.server 或你自己的 srv/http 上。
  • 併發:先查再做會超借。把檢查放進原子 UPDATE 或交易裡,沒得借就回 409;用不變式 0 <= available <= copies 檢查結果。
