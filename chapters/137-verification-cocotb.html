晶片沒有「下一版修正」

1994 年,一位數學教授 Thomas Nicely 發現他的 Pentium 電腦算某些除法時,答案在小數點後好幾位開始出錯。 原因是硬體除法器用的一張查表少了幾格。軟體的 bug 可以發一個更新檔;晶片的 bug 已經燒在矽裡了。 Intel 最後提供更換處理器,並為此認列了 4 億 7500 萬美元的費用。

這就是硬體和軟體最大的不同:晶片送去製造之後就改不了。所以晶片團隊把大量的人力花在「下線之前確定它是對的」。 業界常說,驗證占了一個晶片專案一半以上的工作量。這件事有一個專門的名字:驗證(verification)。

在第 50 章,你學會用 Verilog 描述電路。這一章學另一半:怎麼寫程式去檢查電路。 先認識幾個名詞:

  • DUT(design under test,被測電路):你要檢查的那個模組,例如一個加法器。
  • testbench(測試平台):包住 DUT 的程式。它餵輸入給 DUT、讀 DUT 的輸出、判斷對不對。testbench 本身不會變成晶片,它只在模擬器裡跑。
  • 測試向量(test vector):一組輸入,加上它應該得到的輸出。
  • 模擬器(simulator):在電腦上「假裝」電路在運作的程式。本章用開源的 Icarus Verilog(指令 iverilog 與 vvp)。
💡
為什麼要學

rtl 任務線(自己的 RV32I CPU)的 Boss 戰「ALU 與突變」不考你寫電路,考你寫測試:你的 cocotb 測試要在正確的 ALU 上全過,而且在 3 個藏起來的突變版上每個都至少失敗一項。 本章 Lab 的任務「cocotb 測試」就是為它準備的。之後的單週期 CPU 會用 rv32 任務線的指令集模擬器當參考模型,SoC 的驗收則要看 cocotb 的覆蓋率;本章教的 testbench 結構,在那些地方都會再用到。

🔑
核心觀念

測試能證明「有 bug」,很難證明「沒有 bug」。驗證的工作,是用有限的時間,讓剩下的 bug 盡量少、盡量不重要。本章每一種技巧,都在回答同一個問題:我的測試夠不夠強?

testbench 的四個角色

不管用什麼語言寫,一個好的 testbench 裡都有同樣幾個角色。先看圖,再一個一個說明。

角色做什麼本章的例子
產生輸入(stimulus)決定這一次要餵什麼給 DUT固定的 (5, 10);或用 random.Random(2026) 抽 200 組
DUT被檢查的電路adder.v、alu8.v、add_pipe2.v
監看器(monitor)在對的時間點讀 DUT 的輸出int(dut.X.value),有時脈的電路要在正緣之後讀
參考模型(reference model)用另一種寫法算出「應該是多少」adder_model(a, b):Python 的 a + b
scoreboard(計分板)把預期值排隊,等 DUT 的輸出來了再比對;記錄錯誤test_pipe.py 裡的 deque

組合電路(沒有時脈)很單純:輸入一給,等一下,輸出就出來了,監看器和 scoreboard 可以合成一行 assert。 有時脈、有延遲的電路才需要 scoreboard 把預期值「排隊」,本章後面會看到。

第一個自我檢查的 testbench

先用最熟悉的工具:純 Verilog。被測的是一個 8 位元加法器。輸出 X 比輸入多一個位元,用來裝最高位的進位。 這個加法器改寫自 cocotb 專案的範例 examples/adder(cocotb contributors,CC0 公有領域貢獻,github.com/cocotb/cocotb), 原版是 SystemVerilog、預設 4 位元,這裡改成純 Verilog、預設 8 位元。 

// adder.v:改寫自 cocotb examples/adder(CC0)
// X 比 A、B 多一個位元,用來裝進位
`timescale 1ns/1ps
module adder #(parameter DATA_WIDTH = 8) (
    input  [DATA_WIDTH-1:0] A,
    input  [DATA_WIDTH-1:0] B,
    output [DATA_WIDTH:0]   X
);
    assign X = A + B;
endmodule

初學者寫 testbench,常常只是「給輸入、跑模擬、打開波形用眼睛看」。這樣的 testbench 不會告訴你錯了,你要自己發現。 更好的做法是自我檢查的 testbench(self-checking testbench):每一組輸入都附上預期的輸出,testbench 自己比對,最後印 PASS 或 FAIL。 

// tb_adder.v:自我檢查的 testbench(純 Verilog)
`timescale 1ns/1ps
module tb_adder;
    reg  [7:0] A, B;
    wire [8:0] X;
    integer errors = 0;

    adder #(.DATA_WIDTH(8)) dut (.A(A), .B(B), .X(X));

    // 送一組輸入、等 1 ns、和預期值比
    task check(input [7:0] a, input [7:0] b, input [8:0] expected);
        begin
            A = a; B = b;
            #1;
            if (X !== expected) begin
                $display("FAIL: %0d + %0d = %0d,預期 %0d", a, b, X, expected);
                errors = errors + 1;
            end
        end
    endtask

    initial begin
        $dumpfile("wave.vcd");
        $dumpvars(0, A, B, X);    // 只記這三條訊號
        check(8'd5,   8'd10,  9'd15);    // 一般情況
        check(8'd0,   8'd0,   9'd0);     // 全 0
        check(8'd255, 8'd1,   9'd256);   // 進位一路傳到最高位
        check(8'd255, 8'd255, 9'd510);   // 最大值
        check(8'd15,  8'd1,   9'd16);    // 第 3 位元的進位傳到第 4 位元
        if (errors == 0) $display("PASS: 5 組全對");
        else             $display("共 %0d 組錯", errors);
        $finish;
    end
endmodule

幾個重點:

  • task check 把「給輸入、等 1 ns、比對」包成一個動作。#1 讓模擬時間前進 1 ns,組合電路的輸出才會更新。
  • 比對用 !==,不用 !=。如果 X 是未知值 x,X != expected 的結果也是 x,if 會當成「不成立」而漏報;!== 連 x、z 都逐位比,一定得到 0 或 1。
  • 5 組向量是挑過的:一般情況、全 0、進位一路傳到最高位、最大值、第 3 位元的進位傳到第 4 位元。這種「自己想、自己挑」的向量叫導向測試(directed test)。

用 Icarus Verilog 編譯、執行:

iverilog -g2012 -Wall -o tb.out tb_adder.v adder.v
vvp tb.out
VCD info: dumpfile wave.vcd opened for output.
PASS: 5 組全對

為了看 testbench 會不會抓錯,準備一個故意弄壞的版本 adder_bad.v:第 3 位元進到第 4 位元的進位,只算了「兩個位元都是 1」(產生), 忘了「低位的進位經過這一位傳上來」(傳遞)。這是手寫進位電路時很容易犯的錯。 

// adder_bad.v:故意弄壞的加法器(突變版)
// 第 3 位元進到第 4 位元的進位,只算了「產生」(a3 & b3),忘了「傳遞」
`timescale 1ns/1ps
module adder #(parameter DATA_WIDTH = 8) (
    input  [DATA_WIDTH-1:0] A,
    input  [DATA_WIDTH-1:0] B,
    output [DATA_WIDTH:0]   X
);
    wire [4:0] lo = A[3:0] + B[3:0];
    wire       c4 = A[3] & B[3];          // 應該是 lo[4]
    wire [4:0] hi = A[7:4] + B[7:4] + c4;
    assign X = {hi, lo[3:0]};
endmodule
iverilog -g2012 -Wall -o tb.out tb_adder.v adder_bad.v
vvp tb.out
VCD info: dumpfile wave.vcd opened for output.
FAIL: 255 + 1 = 240,預期 256
FAIL: 15 + 1 = 0,預期 16
共 2 組錯

第 1 組 5 + 10 沒有抓到它:5 是 0101,10 是 1010,低 4 位元相加是 15,根本沒有進位。 抓到它的是第 3 組和第 5 組,兩組都需要「低位的進位經過第 3 位元往上傳」。測試向量挑得好不好,決定了測試抓不抓得到 bug。

🔑
核心觀念

testbench 必須自己說 PASS 或 FAIL。需要人眼看波形才知道對錯的測試,不能重複跑、不能交給機器判,也不能抓突變版。看波形是除錯用的,不是判定用的。

cocotb:用 Python 寫 testbench

純 Verilog 的 testbench 寫起來很囉嗦:沒有方便的資料結構、沒有好用的亂數、參考模型要用 Verilog 再寫一次。 cocotb(coroutine cosimulation testbench)換一個做法:電路還是 Verilog,跑在原本的模擬器裡;testbench 改用 Python 寫。 Python 透過模擬器的 C 介面(VPI)讀寫電路裡的訊號,並且決定模擬時間什麼時候往前走。 

test_adder.py(Python 的 async 函式)
      │   dut.A.value = 5        ← 寫訊號
      │   await Timer(2, "ns")   ← 讓模擬時間前進
      │   int(dut.X.value)       ← 讀訊號
      ▼
cocotb(排程器:記住每個測試在等什麼)
      │   VPI(模擬器提供的 C 介面)
      ▼
Icarus Verilog(vvp)── adder.v

安裝:pip install cocotb,另外要有模擬器(Ubuntu/Debian:sudo apt install iverilog)。 cocotb 會把 Python 載進模擬器,所以還要有 Python 的共用函式庫 libpython(例 sudo apt install libpython3-dev);終端機要用 UTF-8(例 export LANG=C.UTF-8),否則印出中文的失敗訊息時會出現 UnicodeEncodeError。 本章的輸出都是在 Debian 12 的容器裡,用 Icarus Verilog 11 與 cocotb 1.9.2 實際執行的結果;cocotb 2.x 的差別在本節最後整理。

一個 cocotb 專案最少四個檔案:電路、參考模型、測試、Makefile。參考模型和測試同樣改寫自 cocotb 的 examples/adder(CC0):

# adder_model.py:加法器的參考模型(改寫自 cocotb examples/adder,CC0)
def adder_model(a, b, width=8):
    """回傳 a + b;結果有 width+1 個位元,不會溢位"""
    return (a + b) & ((1 << (width + 1)) - 1)
# test_adder.py:加法器的 cocotb 測試(改寫自 cocotb examples/adder,CC0)
import random

import cocotb
from cocotb.triggers import Timer

from adder_model import adder_model


@cocotb.test()
async def adder_basic_test(dut):
    """導向測試:5 + 10"""
    dut.A.value = 5
    dut.B.value = 10
    await Timer(2, "ns")                    # 等組合電路算完
    assert int(dut.X.value) == adder_model(5, 10), f"5 + 10 = {int(dut.X.value)}?"


@cocotb.test()
async def adder_randomised_test(dut):
    """隨機測試:200 組隨機的 A、B,和參考模型比"""
    rng = random.Random(2026)               # 固定種子,失敗才能重現
    for _ in range(200):
        a = rng.randrange(256)
        b = rng.randrange(256)
        dut.A.value = a
        dut.B.value = b
        await Timer(2, "ns")
        got = int(dut.X.value)
        assert got == adder_model(a, b), f"{a} + {b}:DUT={got},模型={adder_model(a, b)}"

dut 把手:讀寫訊號

每個測試函式的參數 dut 是頂層模組的把手(handle)。用點號往下找訊號:dut.A、dut.X; 子模組也可以:dut.u_alu.y。

  • 寫:dut.A.value = 5。這個寫入不會馬上生效,cocotb 會在這個時間點的稍後才交給模擬器。
  • 讀:dut.X.value 是一個「邏輯值陣列」,每個位元可能是 0、1、x(未知)、z(高阻抗)。要當整數比,寫 int(dut.X.value)。
  • 讀到 x 時,int() 會出錯。最常見的原因是忘了給某個輸入:
# test_undriven.py:忘了給 B 值
import cocotb
from cocotb.triggers import Timer


@cocotb.test()
async def forgot_b(dut):
    dut.A.value = 5                     # B 沒有設定
    await Timer(2, "ns")
    dut._log.info(f"X = {dut.X.value}")
    assert int(dut.X.value) == 5
     0.00ns INFO     cocotb.regression                  running forgot_b (1/1)
     2.00ns INFO     cocotb.adder                       X = xxxxxxxxx
     2.00ns INFO     cocotb.regression                  forgot_b failed
                                                        ValueError: Unresolvable bit in binary string: 'x'. Set the COCOTB_RESOLVE_X environment variable to configure how special values are resolved.
                                                        ** test_undriven.forgot_b         FAIL           2.00           0.00       6959.21  **

這其實是好事:電路裡出現 x,通常就是 testbench 或電路有地方沒接好,讓測試直接失敗比較安全。

await:讓模擬時間往前走

測試函式是 async def:它是一個協程(coroutine),可以在中間「暫停,等某件事發生再回來」。 await Timer(2, "ns") 的意思是「我先暫停,讓模擬器往前跑 2 ns,再叫醒我」。沒有 await,模擬時間就不會前進,電路也不會反應你剛寫的輸入。 

# test_noawait.py:忘了 await,時間就不會前進
import cocotb
from cocotb.triggers import Timer


@cocotb.test()
async def forgot_await(dut):
    dut.A.value = 1
    dut.B.value = 1
    await Timer(2, "ns")
    dut._log.info(f"第一組 1 + 1:X = {int(dut.X.value)}")
    dut.A.value = 5
    dut.B.value = 10
    Timer(2, "ns")                      # 少了 await:這一行什麼都沒做
    dut._log.info(f"第二組 5 + 10:X = {int(dut.X.value)}")
     2.00ns INFO     cocotb.adder                       第一組 1 + 1:X = 2
     2.00ns INFO     cocotb.adder                       第二組 5 + 10:X = 2
                                                        ** TESTS=1 PASS=1 FAIL=0 SKIP=0                  2.00           0.02        122.72  **

第二組讀到的還是第一組的答案 2,而且這個測試通過了,因為裡面根本沒有 assert。

⚠️
看起來對但其實錯:「我設定了輸入,馬上讀輸出就是新的答案」

少寫 await 的 Timer(2, "ns") 只是建立一個物件,什麼都沒做;Python 不會報錯。結果是你讀到舊的輸出。 如果舊的輸出剛好等於預期值,測試還會「通過」。寫完測試,一定要拿一個壞掉的電路跑一次,確定它真的會失敗。

測試怎麼被找到:MODULE、TOPLEVEL 與 TESTCASE

  • MODULE = test_adder:cocotb 匯入這個 Python 模組(可以用逗號列好幾個),把裡面所有加了 @cocotb.test() 的 async 函式收集起來,照定義的順序一個一個跑(輸出裡的 Found test …)。
  • TOPLEVEL = adder:頂層模組的名字,也就是 dut 指的那一個。
  • VERILOG_SOURCES:要編譯的 Verilog 檔,用絕對路徑最保險(上面用 $(PWD))。
  • 只想跑其中一個測試:make TESTCASE=adder_basic_test。

參考模型:另外寫一份「答案」

導向測試的預期值是你自己算好寫死的;隨機測試抽到哪一組事先不知道,預期值就要有人「當場算」。那個人就是參考模型:用另一種寫法描述同一個規格的程式。

好的參考模型有三個特點:

  • 簡單到一眼看得出對不對。加法器的模型就是 a + b。它不在乎進位怎麼一級一級傳,只在乎答案。
  • 和 DUT 用不同的方法寫。如果模型和 DUT 是同一份邏輯的兩份拷貝,它們會一起錯。Python 的整數、if/else 和 Verilog 的位元向量,本來就是不同的思考方式。
  • 位元寬度要自己處理。Python 的整數沒有上限,也有負數;硬體只有固定的位元數。模型最後一定要遮罩(mask):& 0xFF 留下 8 位元,負數就自動變成二補數。

接下來的例子用第 50 章的範例 ALU:8 位元、4 種運算(add、sub、and、or),加減法直接用 + 和 -。 埠名與運算碼都和那一章一樣,這裡只多了 `timescale 和幾行註解: 

// alu8.v:8 位元、4 種運算的小 ALU(本章的被測電路)
`timescale 1ns/1ps
module alu8 (
    input      [7:0] a,
    input      [7:0] b,
    input      [1:0] op,     // 00 add、01 sub、10 and、11 or
    output reg [7:0] y,
    output           zero    // y == 0 時為 1
);
    always @* begin
        case (op)
            2'b00:   y = a + b;
            2'b01:   y = a - b;
            2'b10:   y = a & b;
            2'b11:   y = a | b;
            default: y = 8'h00;     // op 有 x 或 z 時也有值
        endcase
    end
    assign zero = (y == 8'd0);
endmodule

它的參考模型和 cocotb 測試放在同一個檔案 test_alu8.py(完整檔案在「突變測試」那一節):

ADD, SUB, AND, OR = 0, 1, 2, 3


def alu8_model(op, a, b):
    """參考模型:回傳 (y, zero)"""
    if op == ADD:
        y = a + b
    elif op == SUB:
        y = a - b
    elif op == AND:
        y = a & b
    else:
        y = a | b
    y &= 0xFF                       # 只留 8 位元:負數變成二補數
    return y, int(y == 0)

手算:隨機測試抓不到 bug 的機率

步驟:(1)數出這個突變版在多少種輸入上會答錯;(2)除以全部的輸入數,得到「一組隨機向量抓到它」的機率 $p$; (3)$n$ 組獨立的隨機向量全部沒抓到的機率是 $(1-p)^n$。

換成 32 位元的 ALU,同樣的錯(zero 只看低 31 位元)只在 $y = $ 0x80000000 時出現,$p$ 大約是 $2^{-32}$。 就算跑 $10^6$ 組隨機向量,漏掉的機率還是 $(1-2^{-32})^{10^6} \approx 0.99977$。隨機測試幾乎不可能抓到它,一條「最小負數」的導向測試卻一定抓得到。 這就是為什麼 ALU 的測試總是「邊界值的兩兩組合」加上「隨機向量」。

ℹ️
證明(參考):$(1-p)^n \le e^{-np}$

對所有實數 $x$,$1 + x \le e^x$(曲線 $e^x$ 在 $x=0$ 的切線就是 $1+x$,而 $e^x$ 是凸函數,永遠在切線上方)。取 $x = -p$ 再兩邊 $n$ 次方,得到 $(1-p)^n \le e^{-np}$。 所以「漏掉的機率」至多 $e^{-np}$:要讓它小於 $\varepsilon$,只要 $n \ge \ln(1/\varepsilon)/p$。$p$ 小一半,向量數就要多一倍。 zero7 的例子:$e^{-200 \times 0.0103} \approx 0.127$,和精確值 0.126 很接近。

# vcd_table.py:把 VCD 檔印成「時間 × 訊號」的表格(只處理本章用到的簡單 VCD)
import sys


def read_vcd(path):
    names = {}            # 代號 → 訊號名稱
    unit = "?"
    rows = []             # [(時間, {名稱: 值})]
    now = None
    values = {}
    in_defs = True
    want_unit = False
    for line in open(path):
        tok = line.split()
        if not tok:
            continue
        if in_defs:
            if want_unit and tok[0] != "$end":
                unit = tok[0]                     # 例如 1ps、1us
                want_unit = False
            if tok[0] == "$timescale":
                want_unit = True
            elif tok[0] == "$var":                # $var wire 9 # X [8:0] $end
                names[tok[3]] = tok[4]
            elif tok[0] == "$enddefinitions":
                in_defs = False
            continue
        if tok[0].startswith("#"):                # 新的時間點
            if now is not None:
                rows.append((now, dict(values)))
            now = int(tok[0][1:])
        elif tok[0].startswith("b"):              # 向量:b1010 "
            bits = tok[0][1:]
            values[names[tok[1]]] = int(bits, 2) if set(bits) <= {"0", "1"} else bits
        elif tok[0][0] in "01xz":                 # 單一位元:1!
            values[names[tok[0][1:]]] = tok[0][0]
    if now is not None:
        rows.append((now, dict(values)))
    return unit, list(names.values()), rows

覆蓋率:測試到底碰到了哪裡

💡
為什麼要學

「我跑了 1000 組,應該夠了吧?」覆蓋率把這句話變成可以量的數字:哪些情況測過、哪些沒有。迷你 SoC 任務線的驗收會看 cocotb 的覆蓋率;本章 Lab 雖然不量覆蓋率,但你挑邊界值時,心裡想的就是 bin。

覆蓋率(coverage)分兩大類:

  • 程式碼覆蓋率(code coverage):工具自動量。行覆蓋率:每一行 Verilog 有沒有執行過;toggle 覆蓋率:每條訊號的每個位元有沒有 0→1、1→0 都翻過。
  • 功能覆蓋率(functional coverage):你自己定義「哪些情況重要」,每一種情況叫一個 bin(箱子),測試跑過時就在對應的箱子打勾。兩個項目的組合叫交叉覆蓋(cross coverage),例如「op × zero」。

程式碼覆蓋率回答「電路的每個部分有沒有被動到」,功能覆蓋率回答「規格裡的每種情況有沒有被測到」。專業的流程兩種都量(SystemVerilog 有 covergroup 語法,cocotb 有 cocotb-coverage 套件)。 本章自己用 Python 寫,看清楚 bin 是什麼。對 8 位元加法器定義 13 個 bin: 

# coverage.py:手工的功能覆蓋率(bins)與埠的 toggle 覆蓋率,對 8 位元加法器
def range_bin(v):
    if v == 0:
        return "0"
    if v == 255:
        return "255"
    return "1–127" if v < 128 else "128–254"


def carry4_bin(a, b):
    """第 3 位元進到第 4 位元的進位是怎麼來的"""
    if ((a & 0xF) + (b & 0xF)) < 16:
        return "沒有進位"
    if (a >> 3) & 1 and (b >> 3) & 1:
        return "產生"                  # a3、b3 都是 1,自己就產生進位
    return "傳遞"                      # 低位的進位經過第 3 位元傳上去


BINS = {
    "A": ["0", "1–127", "128–254", "255"],
    "B": ["0", "1–127", "128–254", "255"],
    "X[8]": ["0", "1"],
    "進位 3→4": ["沒有進位", "產生", "傳遞"],
}


def functional(vectors):
    hit = {k: set() for k in BINS}
    for a, b in vectors:
        hit["A"].add(range_bin(a))
        hit["B"].add(range_bin(b))
        hit["X[8]"].add(str((a + b) >> 8))
        hit["進位 3→4"].add(carry4_bin(a, b))
    return hit


def toggle(vectors):
    """每個埠的每個位元,是否 0→1 和 1→0 都發生過"""
    ports = [("A", 8, lambda a, b: a), ("B", 8, lambda a, b: b), ("X", 9, lambda a, b: a + b)]
    done = total = 0
    for name, width, f in ports:
        vals = [f(a, b) for a, b in vectors]
        for bit in range(width):
            seq = [(v >> bit) & 1 for v in vals]
            rise = any(p == 0 and q == 1 for p, q in zip(seq, seq[1:]))
            fall = any(p == 1 and q == 0 for p, q in zip(seq, seq[1:]))
            total += 1
            done += rise and fall
    return done, total


def report(vectors):
    hit = functional(vectors)
    n_hit = sum(len(hit[k]) for k in BINS)
    n_all = sum(len(v) for v in BINS.values())
    for k, names in BINS.items():
        marks = "  ".join(("■" if n in hit[k] else "□") + n for n in names)
        print(f"{k:8} {marks}")
    print(f"功能覆蓋率 {n_hit}/{n_all} = {n_hit / n_all:.0%}")
    d, t = toggle(vectors)
    print(f"toggle 覆蓋率 {d}/{t} = {d / t:.0%}")


if __name__ == "__main__":
    print("== 四組向量 ==")
    report([(0, 0), (255, 255), (1, 0), (0, 0)])
    print("== 練習的六組向量 ==")
    report([(5, 10), (0, 0), (255, 1), (255, 255), (15, 1), (200, 100)])

Boss 戰「ALU 與突變」的判法就是突變測試:你的測試跑在參考 ALU 上要全過,跑在每個隱藏突變版上要至少失敗一項。這一節的擊殺矩陣,就是判題程式在做的事。

覆蓋率量「碰到了沒」,突變測試(mutation testing)量「抓不抓得到」:把電路故意改壞一個小地方,得到一個突變版(mutant), 再拿你的測試去跑。測試失敗,就說這個突變版被殺死(killed)了;測試全過,它就存活(survived),表示你的測試有一個漏洞。 第 48 章用 Python 函式講過同樣的想法(那一章叫「變異測試」、「變異體」);硬體的突變通常長這樣:

突變的種類例子像哪一種真實的 bug
運算子換掉a & b ↔ a | b;a - b → b - a複製貼上之後忘了改
少一個常數a - b → a + ~b(二補數減法少加 1)用加法器做減法時忘了進位輸入 = 1
位元範圍錯y == 0 → y[3:0] == 0寬度改了,某一行沒跟著改
進位鏈斷掉第 6 位元進到第 7 位元的進位不見手接漣波加法器時少接一條線
有號/無號弄反$signed(a) < $signed(b) ↔ a < bslt 與 sltu 搞混
卡住的位元(stuck-at)某個輸出位元永遠是 0製造缺陷;測試晶片時也用這個模型

對 alu8.v 做 6 個突變版,每個只改一行(或一對 case):

突變版改了什麼
M1 m1_sub_off.vy = a - b → y = a + ~b(少加 1)
M2 m2_and_or.vand 與 or 的兩行對調
M3 m3_zero_lo.vzero = (y == 8'd0) → zero = (y[3:0] == 4'd0)
M4 m4_sub_swap.vy = a - b → y = b - a
M5 m5_carry7.vy = a + b → y = {a[7] ^ b[7], a[6:0] + b[6:0]}(第 6 位元的進位進不到第 7 位元)
M6 m6_or_equiv.vy = a | b → y = (a ^ b) | (a & b)

例如 M1 的完整檔案(其他突變版也一樣,模組名都還是 alu8,才能直接替換):

// m1_sub_off.v:alu8 的突變版
`timescale 1ns/1ps
module alu8 (
    input      [7:0] a,
    input      [7:0] b,
    input      [1:0] op,     // 00 add、01 sub、10 and、11 or
    output reg [7:0] y,
    output           zero    // y == 0 時為 1
);

        case (op)
            2'b00:   y = a + b;
            2'b01:   y = a + ~b;           // 突變:少加 1

            2'b11:   y = a | b;

import cocotb
from cocotb.triggers import Timer

ADD, SUB, AND, OR = 0, 1, 2, 3


def alu8_model(op, a, b):
    """參考模型:回傳 (y, zero)"""
    if op == ADD:
        y = a + b
    elif op == SUB:
        y = a - b
    elif op == AND:
        y = a & b
    else:
        y = a | b
    y &= 0xFF                       # 只留 8 位元:負數變成二補數
    return y, int(y == 0)

做法和第 48 章的擊殺矩陣一樣:每個突變版,把 5 條測試的輸入代進去,算出它的 y 和 zero,和「預期」那一列比。 y 或 zero 有一個不一樣,就標 ✗(這條測試殺死了它)。每一格寫「突變版的 y/zero」:

幾格算給你看:

  • M1、T2:~5 是 1111 1010 = 250,5 + 250 = 255 = FF;y 不是 0,zero 也跟著錯。T5:2 + ~7 = 2 + 248 = 250 = FA,比正確的 FB 少 1。這就是「少加 1」的指紋。
  • M3、T3:y = 0x30 = 0011 0000,低 4 位元剛好全是 0,M3 就說 zero = 1。其他 4 條的 y 低 4 位元都不是 0(或 y 本來就是 0),所以只有 T3 抓到。
  • M4、T2:5 - 5 和 5 - 5 對調還是 0,抓不到;要靠 T5 的 7 - 2 = 5。「相等」的輸入對「兩邊對調」的 bug 完全沒用。
  • M5:T1 的 3 + 4 低 7 位元沒有進位,根本沒用到被弄斷的那條線。

突變分數 = 被殺死的 / 全部 = 4 / 6 ≈ 67%。兩個存活者要分開看:M6 是等價突變版(equivalent mutant): (a ^ b) | (a & b) 對每個位元都等於 a | b(真值表 4 列逐一檢查就知道),沒有任何測試殺得死它,算分數時要從分母拿掉:4 / 5 = 80%。 本章最後一節會用窮舉證明它真的等價。M5 才是真的漏洞:5 條測試沒有一條讓進位進到第 7 位元。補一條 T6:add 0x40 + 0x40 = 0x80。 M5 算出低 7 位元 0x40 + 0x40 = 0x80,截成 7 位元變 0,第 7 位元 0 ^ 0 = 0,所以 y = 0、zero = 1,被殺死。

斷言:把不變式寫進測試

前面的檢查都是「拿 DUT 的輸出和參考模型比」。還有一種檢查不需要模型:不變式(invariant),也就是「不管輸入是什麼,都必須成立」的性質。 對 alu8 來說,zero == (y == 0) 永遠要成立。把不變式寫成程式,就是斷言(assertion)。

cocotb 測試裡的 assert 就是一種斷言。Verilog 這邊,SystemVerilog 有即時斷言(immediate assertion), 寫在程序區塊裡,執行到那一行就檢查一次。Icarus Verilog 11 在 -g2012 下支援這種寫法: 

// tb_assert.v:在 testbench 裡放即時斷言(immediate assertion)
`timescale 1ns/1ps
module tb_assert;
    reg  [7:0] a, b;
    reg  [1:0] op;
    wire [7:0] y;
    wire       zero;
    integer i;

    alu8 dut(.a(a), .b(b), .op(op), .y(y), .zero(zero));

    initial begin
        for (i = 0; i < 16; i = i + 1) begin
            op = 2'b10;                  // and
            a  = 8'hF0;
            b  = i * 16;                 // 0x00、0x10、…、0xF0
            #1;
            // 不變式:zero 一定等於 (y == 0),不管 op 是什麼
            assert (zero == (y == 8'd0))
                else $error("a=%h b=%h y=%h zero=%b", a, b, y, zero);
        end
        $display("跑完 16 組");
        $finish;
    end
endmodule

⚠️
常見陷阱:印了 ERROR,結束碼還是 0

上面最後一行 exit=0 是 vvp 的結束碼:$error 只印訊息,模擬照樣跑完、照樣回 0。用結束碼判斷成敗的腳本(例如持續整合)會以為測試通過。 要讓它失敗,用 $fatal(1, "…")(Icarus 11 會回 1),或像 tb_adder.v 那樣自己數錯誤、最後印出結論。cocotb 沒有這個問題:assert 失敗就記在 results.xml 裡。

斷言也是讓證明變成程式的方法。第 20 章講加法器時說「漣波加法器算出來的就是 $a + b$」; 寫成程式就是 assert int(dut.X.value) == a + b。第 49 章的有限狀態機「只會在合法的狀態之間移動」, 寫成斷言就是每個正緣檢查 state 是合法狀態之一。方法裡的斷言檢查「這一刻」的性質;整體的性質(例如 scoreboard 最後佇列是空的)放在測試結束時檢查。

ℹ️
★深入(選讀):SystemVerilog 的並行斷言(SVA)

即時斷言只看「這一刻」。SystemVerilog Assertions(SVA)還有並行斷言(concurrent assertion),描述跨越好幾個時脈週期的性質,例如「req 變成 1 之後,1 到 3 個週期內 ack 一定要變成 1」:

assert property (@(posedge clk) req |-> ##[1:3] ack);

Icarus Verilog 11 不支援這個語法(我們實際編譯,得到 syntax error)。商用模擬器支援完整的 SVA;開源的 Verilator 與 Yosys 支援一部分。 在 cocotb 裡,同樣的性質可以寫成一個背景協程:每個正緣看 req,看到 1 就數接下來 3 拍裡有沒有 ack。

★深入(選讀):形式驗證入門

💡
為什麼要學

Boss 戰「ALU 窮舉」對 8 位元版的 ALU 把所有輸入窮舉一遍,這就是最小的形式驗證:不是抽樣,而是全部。這一節說明窮舉為什麼等於證明、為什麼 32 位元就窮舉不完,以及形式驗證工具怎麼繞過去。它不擋關,是給想走 IC 驗證的人的路標。

Dijkstra 有一句名言:「程式測試可以用來證明 bug 存在,但永遠不能證明 bug 不存在。」測試是抽樣,前面的機率計算說明了抽樣會漏。 形式驗證(formal verification)換一個問法:不是「這些輸入對不對」,而是「有沒有任何輸入會讓性質不成立」。

對很小的電路,最直接的形式驗證就是窮舉。alu8 的輸入是 op(2 位元)、a、b(各 8 位元),一共 $2^{18} = 262144$ 種,模擬器一下子就跑完了。 下面的 testbench 把原版和突變版接上同樣的輸入,每一種輸入都比一次輸出。這種「兩個電路接同樣的輸入、比輸出」的結構叫 miter,是形式工具做等價檢查(equivalence checking)的基本形狀: 

// tb_miter.v:把原版和突變版接上同樣的輸入,窮舉 2^18 種輸入,數有幾種輸出不同
`timescale 1ns/1ps
module tb_miter;
    reg  [7:0] a, b;
    reg  [1:0] op;
    wire [7:0] y_ref, y_mut;
    wire       z_ref, z_mut;
    integer i, diff = 0;

    alu8     ref_(.a(a), .b(b), .op(op), .y(y_ref), .zero(z_ref));
    alu8_mut mut_(.a(a), .b(b), .op(op), .y(y_mut), .zero(z_mut));

    initial begin
        for (i = 0; i < (1 << 18); i = i + 1) begin
            {op, a, b} = i;
            #1;
            if ({y_ref, z_ref} !== {y_mut, z_mut}) begin
                if (diff == 0)
                    $display("第一個反例:op=%0d a=%0d b=%0d,原版 y=%0d zero=%0d,突變版 y=%0d zero=%0d", op, a, b, y_ref, z_ref, y_mut, z_mut);
                diff = diff + 1;
            end
        end
        $display("不同的輸入:%0d / %0d", diff, 1 << 18);
        $finish;
    end
endmodule

32 位元的 ALU 呢?a、b 各 32 位元,光是一種運算就有 $2^{64}$ 種輸入。就算每秒模擬一百萬組,16 個 op 要跑上將近一千萬年(練習 137.10)。 形式驗證工具不逐一列舉:它把電路和「性質不成立」一起翻譯成一個很大的邏輯式,交給 SAT 求解器去找「有沒有一組變數讓它為真」 (SAT 是第 32 章的第一個 NP 完全問題;最壞情況很難,但實際電路常常解得很快)。找到了,那組變數就是反例;證明找不到,性質就對所有輸入成立。 有時脈的電路則用有界模型檢查(bounded model checking):把電路展開 k 個週期,問「k 步之內有沒有走到壞狀態」。

開源的形式驗證流程是 Yosys 加 SymbiYosys(github.com/YosysHQ/sby):在 Verilog 裡寫 assert(要證明的性質)與 assume(輸入的限制),工具自動找反例或證明它成立。 本書不教它的用法,有興趣可以從它的文件開始。

⚠️
看起來對但其實錯:「8 位元版窮舉全對,32 位元版一定也對」

窮舉證明的是「這個寬度」。假設一個參數化的 ALU 在算 slt 時,把符號位元寫死成 y[7] 而不是 y[W-1]:W = 8 時它剛好是對的,窮舉全過;W = 32 時它看的是中間的一個位元,錯得一塌糊塗。 這就是 Boss 戰「ALU 窮舉」除了 8 位元窮舉,還要對 32 位元版跑隨機向量與邊界值的原因。證明只對它證明的那個東西成立。

✏️ 練習 137.4 計算

一個 16 位元的比較器有個 bug,只在 a == b 時答錯。a、b 各自平均隨機。(1)一組隨機向量抓到它的機率 $p$?(2)1000 組全部沒抓到的機率?(3)要讓漏掉的機率小於 1%,至少要幾組?(4)換成只有一條導向測試 a = b = 0x1234 呢?

看解答

(1)不管 a 是多少,b 剛好等於 a 的機率是 $p = 1/65536 = 2^{-16}$。(2)$(1 - 2^{-16})^{1000} \approx 0.985$:98.5% 的機率漏掉。 (3)$n > \ln 0.01 / \ln(1 - 2^{-16}) \approx 301802.1$,至少 301803 組(用 $e^{-np}$ 估:$n \ge 65536 \times \ln 100 \approx 301804$,幾乎一樣)。 (4)一條就抓到,機率 1。「相等」是很窄的情況,要用導向測試專門去打。

✏️ 練習 137.5 思考

替 alu8 定義交叉覆蓋「op × zero」:4 種 op、zero 是 0 或 1,一共 8 個 bin。「突變測試」那一節的 T1–T6 打到了哪幾個?覆蓋率多少?空著的 bin 各舉一組能打到的向量,並說明哪一個本章的突變版和這些空 bin 有關。

看解答

T1 add→0x07(zero 0);T2 sub→0(zero 1);T3 and→0x30(0);T4 or→0xFF(0);T5 sub→0xFB(0);T6 add→0x80(0)。 打到 add·0、sub·0、sub·1、and·0、or·0,共 5/8 = 62.5%。空著的是 add·1(例如 0x80 + 0x80)、and·1(例如 0x0F & 0xF0)、or·1(只有 0 | 0)。 M2(and、or 對調)就和它們有關:T3、T4 已經殺死它;or·1 只能用 0 | 0 打到,而 0 & 0 也是 0,所以這格殺不死 M2。空 bin 告訴你哪裡沒測,不保證補上就抓得到。

✏️ 練習 137.7 思考

(1)為什麼不管你寫多少條測試,M6 都殺不死?(2)判題用的隱藏突變版裡,會不會放等價突變版?如果放了,會發生什麼事?(3)你的測試殺不死某個突變版時,怎麼判斷它是「等價」還是「你的測試有漏洞」?

看解答

(1)對每個位元,(x ^ y) | (x & y) 和 x | y 的真值表一模一樣(00→0、01→1、10→1、11→1),所以對所有輸入,M6 的輸出都和原版相同;測試只看輸出,不可能分辨。窮舉也證明了這件事(262144 種輸入裡 0 種不同)。 (2)不會,也不應該:那樣沒有人能過關。出題者會先用窮舉或形式工具確認每個隱藏突變版都至少在一組輸入上和參考版不同。 (3)找一組讓兩者輸出不同的輸入。找得到,就是你的測試有漏洞,把那組加進去;小電路可以像本章一樣窮舉,大電路要用形式工具的等價檢查。

✏️ 練習 137.8 實作

只用不變式 zero == (y == 0)、不用參考模型,寫一個 200 組隨機向量的 cocotb 測試。先預測它殺得死 M1–M6 和 zero7 的哪幾個,再實際跑一次。

看解答 
# test_alu8_invariant.py:練習 137.8,只檢查不變式 zero == (y == 0),不用參考模型
import random

import cocotb
from cocotb.triggers import Timer


@cocotb.test()
async def zero_invariant(dut):
    rng = random.Random(1)
    for _ in range(200):
        dut.op.value = rng.randrange(4)
        dut.a.value = rng.randrange(256)
        dut.b.value = rng.randrange(256)
        await Timer(1, "ns")
        y = int(dut.y.value)
        assert int(dut.zero.value) == int(y == 0), f"y={y:#04x} zero={int(dut.zero.value)}"

預測:只有「zero 算錯」的突變版會違反不變式,也就是 M3 和 zero7;M1、M2、M4、M5 的 y 錯了,但 zero 仍然照著錯的 y 算,和 y 一致;M6 等價。 逐一跑完(make clean 之後 make DUT=… MODULE=test_alu8_invariant),數 results.xml 裡的 <failure>:

✏️ 練習 137.9 思考

把 add_pipe2 改成三級管線(多一級暫存器,valid 也多一級)。(1)test_pipe.py 的 scoreboard 要改哪裡?(2)如果有人把電路做錯,讓兩筆連續的結果順序對調輸出,scoreboard 會在什麼時候報錯?(3)如果電路把某一筆資料「吞掉」(那一筆的 out_valid 一直沒有變成 1),會怎樣?

看解答

(1)scoreboard 完全不用改,這正是它的好處:輸入端照樣放進去、輸出端看到 valid 照樣拿出來,延遲幾拍由佇列吸收。唯一要注意的是測試最後要留夠空拍,讓最後一筆資料流出來:本例最後一筆有效輸入在第 4 個正緣存進去,三級管線在第 6 個正緣輸出,而迴圈剛好跑到第 6 個正緣,所以 test_pipe.py 原封不動就能通過(我們實際做了一個三級版本跑過);空拍不夠的話,最後的 assert not expected 會失敗。 (2)第一筆對調的結果一出來就報錯:佇列前端是先進去的那筆的預期值,輸出卻是後面那筆。(3)那一拍不會報錯(沒有 valid 就不比);但之後的每一筆都會和「錯一個位置」的預期值比而失敗。如果被吞掉的是最後一筆,測試結束時佇列不是空的,assert not expected 會抓到。

✏️ 練習 137.10 計算

32 位元的 ALU 有 a、b(各 32 位元)與 op(4 位元,16 種)。如果每秒能模擬 $10^6$ 組向量,把所有輸入窮舉一遍要多久?8 位元版(a、b 各 8 位元、16 種 op)呢?

看解答

32 位元:$2^{32} \times 2^{32} \times 16 = 2^{68} \approx 2.95 \times 10^{20}$ 組;除以 $10^6$ 是 $2.95 \times 10^{14}$ 秒,約 $9.4 \times 10^{6}$ 年,將近一千萬年。 8 位元:$2^{8} \times 2^{8} \times 16 = 2^{20} = 1048576$ 組,大約 1 秒。所以 8 位元版窮舉、32 位元版只能抽樣(邊界值加隨機)或用形式工具。

把這一章串起來

  • testbench 的角色:產生輸入、DUT、監看器、參考模型、scoreboard。testbench 要自己說 PASS 或 FAIL;波形是除錯用的。
  • cocotb:電路照樣是 Verilog,測試改用 Python。dut.X.value 讀寫訊號、int() 轉整數;await Timer、RisingEdge、ReadOnly 讓時間前進;cocotb.start_soon(Clock(...).start()) 在背景產生時脈;Makefile 設 SIM、TOPLEVEL、MODULE、VERILOG_SOURCES;結果寫在 results.xml。
  • 參考模型:用另一種寫法、簡單到一眼看得出對錯,最後要遮罩成固定位元數。它和電路可能一起錯,所以要有從規格抄來的導向測試。
  • 導向與隨機:導向測試打你想得到的邊界,隨機測試打你沒想到的組合。只錯在 $p$ 比例輸入上的 bug,$n$ 組隨機向量漏掉的機率是 $(1-p)^n \le e^{-np}$;很窄的情況要用導向測試。
  • 時序:正緣剛發生時讀到的是舊值,ReadOnly 之後才是新值;有延遲的電路用 scoreboard 的佇列對齊,只在 valid 時比對。
  • 波形:VCD 是純文字,只記變化;讀成「時間 × 訊號」的表,從錯的值推回 bug。
  • 覆蓋率:程式碼覆蓋率量「碰到了沒」,功能覆蓋率的 bin 量「規格裡的情況測到了沒」。toggle 100% 不代表沒有 bug。
  • 突變測試:把電路改壞,看測試抓不抓得到;擊殺矩陣找出存活者,區分「等價」與「真的漏洞」。原版要全過,換 DUT 要 make clean。
  • 斷言與形式驗證:不變式寫成斷言,和參考模型互補。小電路窮舉就是證明;大電路靠 SAT 與模型檢查,證明也只對它證明的寬度與性質成立。
