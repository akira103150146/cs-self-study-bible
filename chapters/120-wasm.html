一份程式,一個承諾

想像三個場景。

場景一:你在瀏覽器裡開啟 Figma。幾百個向量物件即時拖拉、路徑計算、畫布縮放—— 完全在瀏覽器沙箱裡,速度媲美桌面原生應用。 秘密在於:Figma 的核心渲染引擎是用 C++ 寫的,然後編譯成了一種叫 WebAssembly(縮寫 WASM)的格式丟進瀏覽器執行。

場景二:你在瀏覽器裡打開 Pyodide, 在網頁上直接跑 Python 並執行 NumPy 矩陣運算——沒有後端伺服器。 同樣的答案:CPython 直譯器被 Emscripten 編譯成了 WASM。

場景三:Cloudflare Workers 在全球 300 個邊緣節點執行你的函式, 冷啟動時間不到一毫秒——比 Docker 容器快一千倍。 秘密是 V8 Isolate 技術:邊緣平台能微秒級冷啟動,靠的是隔離的 JS 執行環境;而 WASM 讓你也能在這類沙箱裡跑接近原生速度的非 JS 程式碼。

🔑
WASM 的三個承諾

(1) 可移植:一份 .wasm 二進位,在瀏覽器、伺服器、嵌入式、邊緣節點都能跑。
(2) 近原生速度:JIT/AOT 編譯到機器碼,數值計算只比 C 慢 5–20%。
(3) 安全沙箱:預設沒有任何 I/O 權限,只能做你明確授予的事。

這三個承諾是相互勾連的:可移植要求有一個統一的中間格式;近原生速度要求這個格式設計得夠簡單、讓編譯器好優化; 安全沙箱則要求格式本身有強邊界——而 WebAssembly 就是在這三個約束下取交集設計出來的。 這一章,我們從底層剖開它。

WASM 是什麼:可移植的堆疊式虛擬機

WebAssembly 的第一個直覺陷阱:它雖然叫「Assembly」,卻不是任何一款 CPU 的真正組合語言。 x86 組合語言只能跑在 x86 晶片上;ARM 組合語言只能跑在 ARM 晶片上。 WASM 是一種可移植的位元組碼(portable bytecode), 它的目標機器是一個「虛構的」虛擬機——就像我們在 第 23 章討論的 JVM、CLR 那樣的中間層思想。

這個虛構的機器採用堆疊式(stack-based)架構:沒有通用暫存器, 所有的中間值都放在一個操作堆疊(operand stack)上。 執行 i32.add 時,它從堆疊彈出(pop)兩個 32 位元整數,相加後把結果推回(push)堆疊—— 這和我們在第 23 章看到的 Hack VM 堆疊機概念完全一致。

ℹ️
WASM vs JVM

WASM 與 JVM 都是堆疊式 VM 位元組碼。主要差異在:JVM 有 GC、class 物件模型、執行緒模型, 為 Java 生態而生;WASM 刻意做得更小而正交——沒有 GC(預設)、沒有物件模型, 目的是讓任何語言都能把它當編譯目標,而不只服務某一個語言家族。

為何近原生速度

JavaScript 之所以快起來花了好幾年,是因為它需要動態型別推斷(JIT)才能優化。 WASM 的型別系統是靜態的:每個函式的參數與回傳型別都在二進位裡寫死, 瀏覽器的 JIT 引擎(V8、SpiderMonkey、JavaScriptCore)能直接為每個函式 預先編譯出機器碼,不需要先「熱身」。 加上 WASM 指令集刻意設計為容易映射到 x86 / ARM 原生指令, 實測數值密集(加解密、壓縮、影像處理)的 WASM 程式通常只比原生 C 慢 5–20%。

四種基本型別

WASM 的基本數值型別只有四種(加上後來的 SIMD 擴充):

型別說明常見用途
i3232 位元整數指標、布林、一般整數
i6464 位元整數大整數計算
f3232 位元 IEEE 754 浮點圖形運算
f6464 位元 IEEE 754 浮點科學計算

字串、陣列不是 WASM 的原生型別——它們住在線性記憶體裡,我們下一節就會看到。

模組解剖:函式、線性記憶體與 WAT

一個 WASM 模組(module)是 .wasm 二進位的基本單位。它由若干個「節(section)」組成; 最重要的四個概念是:

  • 函式(function):WASM 程式的最小執行單元,有靜態型別簽名。
  • 線性記憶體(linear memory):一塊連續的、可讀可寫的位元組陣列——WASM 的「RAM」。
  • 表(table):函式指標的陣列,用於間接呼叫(類似 C 的函式指標陣列)。
  • import / export:模組的公開介面——從外部(JS)匯入函式或記憶體、向外部匯出函式或記憶體。

WAT — 讓人讀得懂的文字格式

.wasm 是二進位,機器吃的,人看了頭痛。 WebAssembly 同時定義了一種對應的文字格式 WAT(WebAssembly Text Format), 語法是 S-expression(你在 第 74 章 Scheme 裡看過這種括號嵌套風格)。 WAT 和 .wasm 是一一對應的:工具 wat2wasm / wasm2wat 可以互相轉換。

下面是一個完整的小例子——一個 WASM 模組,宣告一個 add 函式並匯出它: 

;; add.wat — 一個最小的 WASM 模組(WAT 文字格式)
(module
  ;; 宣告函式:接收兩個 i32 參數,回傳一個 i32
  (func $add (export "add") (param $a i32) (param $b i32) (result i32)
    local.get $a   ;; 把 $a 推到操作堆疊
    local.get $b   ;; 把 $b 推到操作堆疊
    i32.add        ;; 彈出兩個值、相加、結果推回堆疊
  )               ;; 堆疊頂端的值就是回傳值
)

注意執行模型:每一條指令都從堆疊彈值(或推值),沒有「暫存器 R1 = R2 + R3」那樣的概念。 這種設計讓位元組碼非常緊湊——大多數指令只需要 1 個 opcode 位元組。

下面再看一個帶有線性記憶體的例子,示範如何從記憶體讀寫整數:

;; memory_rw.wat
(module
  (memory (export "mem") 1)         ;; 宣告 1 頁 (64 KB) 的線性記憶體並匯出

  ;; 把 val 寫到 offset 位置
  (func (export "store32") (param $offset i32) (param $val i32)
    local.get $offset
    local.get $val
    i32.store           ;; 從堆疊彈出 val 再彈出 offset,把 val 寫入 mem[offset]
  )

  ;; 從 offset 讀取 i32
  (func (export "load32") (param $offset i32) (result i32)
    local.get $offset
    i32.load            ;; 從堆疊彈出 offset,讀取 mem[offset],結果推回堆疊
  )
)
⚠️
線性記憶體與 JS 的共用邊界

WASM 的線性記憶體可以被 JS 以 TypedArray 的方式直接讀寫, 這是 JS 傳送字串、陣列給 WASM 的主要管道。但要注意:WASM 只能存取自己宣告的線性記憶體, 無法存取 JS 堆積(heap)或其他 WASM 模組的記憶體——這就是沙箱邊界。

從 C、Rust、Go 編譯到 WASM

沒有人真的用手寫 WAT(就像沒有人用手寫 JVM 位元組碼一樣)。 實際工作流程是:用你熟悉的語言寫程式,然後讓工具鏈幫你編出 .wasm。

C / C++ — Emscripten

Emscripten 是最老牌的 WASM 工具鏈,基於 Clang/LLVM。 它不只是個編譯器——它還提供一套 C 標準函式庫的 WASM 實作,以及讓 WASM 與瀏覽器互通的 JavaScript 膠水(glue code)。 

/* fib.c:計算第 n 個費波那契數 */
#include <emscripten/emscripten.h>

EMSCRIPTEN_KEEPALIVE
int fib(int n) {
    if (n <= 1) return n;
    return fib(n - 1) + fib(n - 2);
}
emcc fib.c -o fib.js \
  -s EXPORTED_FUNCTIONS='["_fib"]' \
  -s EXPORTED_RUNTIME_METHODS='["cwrap"]'
# 產生 fib.wasm + fib.js(膠水程式碼)

Rust — wasm-pack 與 wasm-bindgen

Rust 對 WASM 的支援是一流的(我們在 第 83 章與 第 84 章討論過 Rust 的系統程式設計能力)。 wasm-bindgen 讓 Rust 的 struct、method 能自動生成 JS 綁定; wasm-pack 則把整個「編譯 → 產生 JS 綁定 → 打包成 npm 套件」的流程一條命令搞定。 

// src/lib.rs
use wasm_bindgen::prelude::*;

/// 計算第 n 個費波那契數(匯出給 JS 呼叫)
#[wasm_bindgen]
pub fn fib(n: u32) -> u32 {
    match n {
        0 | 1 => n,
        _ => fib(n - 1) + fib(n - 2),
    }
}

/// 傳入字串、回傳字串(透過線性記憶體傳值)
#[wasm_bindgen]
pub fn greet(name: &str) -> String {
    format!("Hello, {}! (from WASM)", name)
}
# Cargo.toml 需加: [lib] crate-type = ["cdylib"]
# 以及 dependencies: wasm-bindgen = "0.2"
wasm-pack build --target web
# 在 pkg/ 目錄產生 .wasm + .js 綁定 + TypeScript 型別宣告
💡
純 Rust → WASM 不需要 wasm-bindgen

如果你只傳數值(i32/f64),不需要字串或 JS 物件,用 --target wasm32-unknown-unknown 直接編譯就好。wasm-bindgen 是為了讓複雜資料型別(字串、陣列、JS 物件) 能方便地跨越 JS↔WASM 邊界而存在的。

Go / TinyGo

標準 Go 支援 GOOS=js GOARCH=wasm(以及較新的 GOOS=wasip1 for WASI); TinyGo 是一個針對嵌入式與 WASM 的精簡 Go 編譯器,產生的 .wasm 比標準 Go 小很多, 適合在邊緣節點部署。

在瀏覽器執行:JS 載入與互通

有了 .wasm 檔,下一步是讓 JavaScript 載入並呼叫它。WebAssembly 的 JS API 設計得很乾淨: 

// 最簡單的 WASM 載入(await 語法)
const { instance } = await WebAssembly.instantiateStreaming(
  fetch('math.wasm')      // 網路串流直接餵給 WASM 引擎
);

// 呼叫匯出的函式
const result = instance.exports.add(3, 4);
console.log(result);  // 7

// 讀取匯出的線性記憶體(作為 Uint8Array 視圖)
const mem = new Uint8Array(instance.exports.mem.buffer);

WebAssembly.instantiateStreaming 是最推薦的載入方式—— 它邊下載 .wasm 邊讓引擎開始編譯(串流編譯,streaming compilation),不需要等到完整下載才開始。

JS ↔ WASM 的資料傳遞

數值(i32/i64/f32/f64)可以直接作為函式引數和回傳值傳遞,零成本。 但字串和陣列不是 WASM 的原生型別,傳遞時需要透過共享線性記憶體:

  1. JS 把字串的 UTF-8 編碼寫入 WASM 的線性記憶體(透過 TextEncoder)。
  2. JS 把記憶體中字串的起始偏移量與長度作為 i32 傳給 WASM 函式。
  3. WASM 函式在線性記憶體中讀取字串並處理。
  4. 若有回傳字串,WASM 把結果寫回記憶體,回傳指標與長度給 JS。
  5. JS 用 TextDecoder 從記憶體讀回字串。

這個過程繁瑣,wasm-bindgen 正是為了自動化這些步驟而生的。

🔑
WASM 為何適合計算密集任務

影像處理、加解密、音訊編解碼、遊戲物理——這些任務的共同特徵是: 大量的數值運算在一塊連續記憶體上進行。WASM 的靜態型別讓 JIT 省去推斷開銷; 線性記憶體的存取模式對 CPU 快取非常友善; 這兩點加在一起,讓 WASM 在這類任務上遠超 JS。

沙箱與能力安全模型

WASM 最常被忽視、卻最重要的特性是它的安全模型。 讓我們從一個對比開始:

當你在 Linux 上執行一支原生程式(ELF binary),它預設就擁有執行者的所有權限—— 可以讀任何你能讀的檔案、可以發動網路連線、可以 fork 子行程。
當你在 WASM 執行環境裡執行同一份程式的 .wasm 版本,它預設什麼都不能做—— 不能讀檔案、不能開網路、甚至不能取得系統時間。

這不是意外,而是刻意的設計哲學: 能力安全(capability-based security)。

能力安全是什麼

傳統的 UNIX 安全模型基於「身份(identity)」——你是誰,就擁有對應角色的全部權限。 能力安全基於「能力(capability)」——你手上有什麼「票」,才能做什麼事。 WASM 完整落實了能力安全:

  • WASM 模組只能呼叫它在 Import Section 裡明確宣告要從宿主匯入的函式。
  • 宿主(JS 或 WASI runtime)決定要不要提供那個函式——若不提供,實例化就會失敗。
  • WASM 只能存取自己宣告的線性記憶體;它無法讀取宿主的記憶體、其他模組的記憶體,或 JS 的 GC 堆積。
🔑
WASM 的安全保證來自格式本身

WASM 的沙箱不靠作業系統的 seccomp 或 Linux namespace(雖然 runtime 可能額外加這些), 而是靠位元組碼格式的設計:WASM 沒有可以跳出沙箱的指令。 沒有「讀任意記憶體位址」指令、沒有「呼叫任意函式指標」指令(table 呼叫有型別檢查)、 沒有「系統呼叫」指令。這讓 WASM 的安全邊界分析比容器更嚴格。

與容器隔離的比較

在第 85 章我們建立了虛擬化的光譜概念。 WASM 是這個光譜上一個特殊的點:

面向Linux 容器WASM 沙箱
隔離層次OS namespace/cgroup語言 VM 位元組碼邊界
信任基礎Linux 核心WASM spec + runtime 正確性
冷啟動時間數十~數百毫秒微秒~數毫秒
記憶體用量數十 MB(OS 映像)數 KB~數 MB(模組本身)
語言無關是(執行任意原生碼)是(任何能編譯到 WASM 的語言)
系統呼叫可見性共用宿主核心無系統呼叫;需透過 WASI API

從第 34 章學到的威脅模型角度看: 容器的攻擊面包括核心的所有系統呼叫;WASM 的攻擊面幾乎只有「runtime 實作的正確性」。 但容器可以跑任意現有的二進位(不需要重新編譯);WASM 需要重新編譯目標程式。 兩者各有適合的場景。

WASI:讓 WASM 跑出瀏覽器

WASM 最初是為瀏覽器設計的,JS 扮演宿主的角色。 但工程師很快發現:如果 WASM 能在瀏覽器外執行,它就是一個輕量的通用沙箱執行環境。 問題在於——瀏覽器外沒有 JS,那誰來扮演宿主?誰來提供「讀檔案」、「開網路」這些能力?

2019 年,Mozilla 工程師 Lin Clark 等人提出了 WASI(WebAssembly System Interface)——一套標準化的、模組化的「系統能力 API」, 讓 WASM 在任何 WASI 相容的 runtime 上都能以相同方式存取(被授權的)系統資源。

📜
那條著名的推文

2019 年,Docker 創辦人 Solomon Hykes 在推文寫道: 「如果 WASM + WASI 在 2008 年就存在,我們根本不需要創造 Docker。」 這句話簡潔地說明了 WASI 的野心:成為一個比容器更輕量、更安全的跨平台沙箱標準。

WASI 的設計哲學:能力即介面

WASI 的每一個「介面(interface)」都是一組函式,由 runtime 提供給 WASM 模組:

  • wasi:filesystem:讀寫特定(被授權的)目錄下的檔案。
  • wasi:sockets:開啟特定(被授權的)網路連線。
  • wasi:clocks:取得時間。
  • wasi:random:取得隨機數。

重點在「被授權的」:WASI runtime 在啟動模組時,明確地把「這個目錄的 handle」傳給模組。 模組拿到 handle 才能操作該目錄——它無法「猜測」或「暴力搜尋」出其他目錄的 handle。 這是能力安全哲學在系統呼叫層面的直接實現。 

# 用 Wasmtime 執行一個 WASI 模組
# --dir=. 明確授予「目前目錄」的讀寫能力;其他目錄無法存取
wasmtime run --dir=. my_app.wasm

# 若不給 --dir,模組執行期間讀檔就會拿到「權限拒絕」錯誤
wasmtime run my_app.wasm  # 無任何 filesystem 能力

邊緣運算與 Serverless

WASI 把 WASM 帶出了瀏覽器,讓它成為邊緣運算(edge computing)的核心技術:

  • Cloudflare Workers:每個 Worker 是一個 WASM 模組(或 JS 模組), 跑在全球 300+ 個 PoP(Point of Presence)節點上。 冷啟動用的是 V8 Isolate 技術(概念上類似 WASM 沙箱); Cloudflare 也直接支援用 Rust/C 編譯的 WASM。
  • Fastly Compute:直接用 Wasmtime 執行 WASM 模組, 冷啟動 ~50 微秒,遠快於任何容器技術。
  • Fermyon Spin:WASI 原生的 Serverless 框架, 讓你用 Rust/Go/Python 寫 HTTP handler,編成 WASM,部署在任何 WASI runtime 上。
ℹ️
WASI Preview 2 與元件模型

2024 年穩定的 WASI 0.2.0(Preview 2)帶來了元件模型(Component Model)的基礎支援, 讓 WASM 模組之間能用強型別介面相互組合——我們在下一節詳談。

進階:元件模型、SIMD、執行緒與 WebGPU

元件模型(Component Model)

傳統 WASM 模組之間的互動只能透過數值和線性記憶體——傳遞字串都很麻煩,更別說結構化資料。 元件模型(WebAssembly Component Model)是 W3C WebAssembly 工作組的下一個大賭注: 它定義了一套 IDL 叫 WIT(WebAssembly Interface Types), 讓你用強型別描述元件之間的介面:字串、列表、記錄、列舉……都是一等公民。 

// math.wit — WIT 介面定義
package example:math;

interface calculator {
  add: func(a: s32, b: s32) -> s32;
  greet: func(name: string) -> string;
}

world math-world {
  export calculator;
}

wit-bindgen 工具根據 WIT 定義自動生成 Rust/C/Go 的綁定程式碼。 這讓「用 Rust 寫的元件」能直接被「用 Python 寫的元件」呼叫, 中間不需要共享記憶體或手動序列化——元件模型的 runtime 負責翻譯。

WASM SIMD

WASM 的 SIMD 擴充(已標準化並在所有主流瀏覽器中可用)引入了 v128 型別—— 128 位元的 SIMD 暫存器,可以同時處理 4 個 f32、2 個 f64、16 個 i8 等等。 在影像處理、音訊編解碼、ML 推論這類任務上,SIMD 可以帶來 2–8x 的加速。 Rust 的 std::arch 模組和 C 的 SSE/NEON intrinsics 都能透過 LLVM 映射到 WASM SIMD。

執行緒

WASM 執行緒(Threads)擴充允許多個 WebWorker 共享同一塊 WASM 線性記憶體 (底層靠 SharedArrayBuffer),並用 i32.atomic.wait、 i32.atomic.notify 等原子操作同步——這本質上是 POSIX threads 的 WASM 版本。 對 Emscripten 編譯的多執行緒 C 程式而言,這讓原本需要改寫的 pthread 程式碼幾乎不動就能跑在瀏覽器裡。

WebGPU 與 WASM

在第 111 章我們討論了 GPU 著色器。 WebGPU 是下一代的瀏覽器 GPU API(取代 WebGL),它和 WASM 的組合正成為高效能 Web 計算的新標準:

  • Rust 的 wgpu crate 可以同時編譯到原生(Vulkan/Metal/DX12)和 WASM+WebGPU, 讓同一套 GPU 計算程式碼跨平台執行。
  • ML 框架(如 Google 的 MediaPipe Web)用 WASM 跑 CPU 邏輯、用 WebGPU 跑 GPU 加速—— 兩者透過共享 ArrayBuffer 傳遞資料。
  • 遊戲引擎 Bevy 已有 WASM 編譯目標,讓 Rust 寫的遊戲能直接跑在瀏覽器裡。

WASM 作為外掛沙箱

WASM 的沙箱特性讓它非常適合作為外掛(plugin)系統的執行環境—— 讓不受信任的第三方程式碼在宿主應用中安全執行:

  • Envoy Proxy(雲原生 L7 代理):外掛用任意語言寫、編成 WASM,在 Envoy 裡執行。
  • OPA(Open Policy Agent):政策規則可以編譯成 WASM 執行。
  • Shopify Functions:商家的自訂商業邏輯以 WASM 形式跑在 Shopify 的基礎設施上。
  • 各種資料庫(ClickHouse、ScyllaDB)也在探索讓使用者定義函式(UDF)以 WASM 形式執行。

動手練習:讀懂 WAT、分析安全模型、比較隔離技術

✏️ 練習 114.1 思考

閱讀下面這段 WAT,不查任何工具,純用紙筆追蹤堆疊狀態,回答: 函式 max 計算的是什麼?執行 max(5, 3) 時, 操作堆疊在每一條指令後的狀態是什麼?

(module
  (func (export "max") (param $a i32) (param $b i32) (result i32)
    local.get $a
    local.get $b
    i32.gt_s       ;; 有符號比較:若 $a > $b 則推入 1,否則 0
    if (result i32)
      local.get $a
    else
      local.get $b
    end
  )
)
看解答

這個函式計算兩個 i32 的最大值。

追蹤 max(5, 3) 時的堆疊狀態(初始堆疊為空,$a=5,$b=3):

  1. local.get $a → 堆疊:[5]
  2. local.get $b → 堆疊:[5, 3]
  3. i32.gt_s → 彈出 3 和 5,比較 5 > 3 為真,推入 1 → 堆疊:[1]
  4. if (result i32) → 彈出 1(條件為真),進入 if 分支
  5. local.get $a → 堆疊:[5]
  6. end → 結束 if/else,堆疊頂端的 5 就是回傳值

結果:max(5, 3) = 5。

注意 WASM 的 if/else/end 是結構化控制流(structured control flow)—— 不是任意 jump,而是像高階語言的 if-else 那樣有明確的開始和結束。 這讓 WASM 不可能有「跳到任意位址」的攻擊面,是安全設計的一部分。

✏️ 練習 114.2 思考

下面的說法哪些正確?哪些錯誤?請逐一說明理由:

  1. WASM 比 JavaScript 快,是因為 WASM 直接跑在 CPU 上,不需要任何中介。
  2. WASM 是安全的,因為它在沙箱裡,所以瀏覽器 WASM 程式完全無法讀取使用者的資料。
  3. 同一份 .wasm 檔案可以在 Chrome、Firefox 和 Wasmtime 上都能執行,不需要任何修改。
  4. WASM 沒有字串型別,所以 WASM 程式完全無法處理文字。
看解答
  1. 部分正確但說法不精確。WASM 並非直接跑在 CPU 上——它由 WASM runtime (V8、SpiderMonkey 等)JIT/AOT 編譯成原生機器碼後執行。 WASM 比 JS 快的真正原因是:靜態型別讓 JIT 省去動態型別推斷的開銷, 以及更緊湊的位元組碼讓解碼更快。
  2. 錯誤(有誤導性)。WASM 的沙箱保護的是宿主系統不被 WASM 侵犯, 而不是保護使用者的「瀏覽器資料」不被網頁讀取。 如果 JS 把使用者的 cookie 傳進 WASM 的線性記憶體,WASM 當然能讀到。 WASM 的安全性是「它不能做超出宿主授權範圍的事」,不是「它不能存取頁面上的資料」。
  3. 正確。這正是 WASM 的核心承諾——可移植性。 .wasm 二進位格式由 W3C 標準化,所有相容 runtime 的行為由規格決定。 這就是「一份程式,跑在任何地方」的意義。
  4. 錯誤。WASM 沒有內建的字串型別是事實, 但字串可以存放在線性記憶體裡(作為 UTF-8 位元組陣列), WASM 完全可以對它們進行各種處理。wasm-bindgen 等工具自動化了 JS 字串與 WASM 線性記憶體之間的轉換。
✏️ 練習 114.3 思考

你是一家公司的架構師。有一個場景:你的 SaaS 平台需要讓第三方開發者上傳「自訂處理邏輯」, 這些邏輯會在你的伺服器上針對每一筆使用者資料執行。 你有三個選擇:

  1. 讓開發者上傳 Python 腳本,用 subprocess 執行。
  2. 讓開發者上傳 Docker 映像,用容器執行。
  3. 讓開發者上傳 .wasm 模組,用 WASI runtime(如 Wasmtime)執行。

從安全性、效能、開發者體驗三個維度分析三個方案的取捨。

看解答

方案 1:Python + subprocess

  • 安全性:極差。subprocess 沒有資源隔離,腳本可以 import 任何 Python 套件, 輕易存取伺服器檔案、發動網路請求、消耗任意資源。即使加上 seccomp/cgroup 也很難做到足夠精細。
  • 效能:Python 本身有 GIL,多租戶並發差。
  • 開發者體驗:最佳,無需任何工具鏈。

方案 2:Docker 容器

  • 安全性:良好。namespace/cgroup 提供 OS 層隔離。但核心漏洞是共同風險; 容器鏡像若包含惡意程式可能在啟動時造成問題。
  • 效能:冷啟動數十~數百毫秒;每個租戶的容器佔用數十 MB 記憶體。
  • 開發者體驗:良好,但需要學習 Dockerfile。

方案 3:WASM + WASI

  • 安全性:優秀。能力安全確保模組只能存取你明確授予的資源 (例如只能讀特定輸入、不能開網路)。安全邊界由位元組碼格式保證。
  • 效能:冷啟動微秒級;記憶體用量極小;可以每請求啟動一個新模組實例。
  • 開發者體驗:需要編譯到 WASM 目標;Rust/C/Go 工具鏈完整,Python 透過 Pyodide 也可行但有一些限制。

結論:對於「不信任的第三方程式碼」這個使用場景,方案 3 是最佳選擇。 Shopify Functions、Cloudflare Workers 都採用這個模式。 若開發者體驗是首要考量且安全要求較低,方案 2 是實際的折衷。 方案 1 在生產環境裡不應使用。

✏️ 練習 114.4 實作

用 Rust 寫一個 WASM 函式,接受一個整數陣列(透過線性記憶體)和陣列長度, 回傳陣列中的最大值。不使用 wasm-bindgen,只用 wasm32-unknown-unknown target。 提示:需要在 Rust 裡直接操作原始指標讀取線性記憶體。

看解答 
// src/lib.rs
// 不使用 wasm-bindgen,直接操作原始記憶體

#[no_mangle]
pub unsafe extern "C" fn max_in_array(ptr: *const i32, len: usize) -> i32 {
    if len == 0 {
        return i32::MIN;
    }
    let slice = std::slice::from_raw_parts(ptr, len);
    *slice.iter().max().unwrap()
}

// 配置函式:讓 JS 可以分配 WASM 線性記憶體
#[no_mangle]
pub unsafe extern "C" fn alloc(size: usize) -> *mut u8 {
    let layout = std::alloc::Layout::from_size_align(size, 1).unwrap();
    std::alloc::alloc(layout)
}
cargo build --target wasm32-unknown-unknown --release
// 在 JS 中使用:
const { instance } = await WebAssembly.instantiateStreaming(fetch('max.wasm'));
const { max_in_array, alloc, memory } = instance.exports;

const arr = [3, 1, 4, 1, 5, 9, 2, 6];
const ptr = alloc(arr.length * 4);          // 配置 i32 陣列空間
const view = new Int32Array(memory.buffer, ptr, arr.length);
view.set(arr);                               // 把 JS 陣列寫入 WASM 線性記憶體
const result = max_in_array(ptr, arr.length);
console.log(result);  // 9

這個範例展示了 JS↔WASM 記憶體互動的完整流程: JS 請求 WASM 分配記憶體 → JS 把資料寫入 → WASM 在自己的線性記憶體中處理 → 回傳結果給 JS。

把這一章串起來

讓我們沿著這本書的脈絡,找出 WASM 在整個 CS 故事中的位置。

在第 23 章,我們看到「M×N 惡夢」—— M 種語言要編譯到 N 種 CPU,就需要 M×N 個編譯器。 解法是插入一個中間層:先編譯到虛擬機位元組碼(JVM、CLR),再由 runtime 翻到各種 CPU。 WebAssembly 是這個思想的現代實現,但目標更雄心勃勃: 不只讓語言可移植,還讓安全模型也可移植。

在第 85 章,我們走過了虛擬化的光譜—— 從行程隔離、容器到完整 VM。WASM 是這個光譜上一個全新的維度: 不依賴 OS namespace,不需要 hypervisor,安全邊界由位元組碼格式本身保證。 它讓「沙箱」這件事從基礎設施層下沉到了語言 VM 層。

🔑
WASM 是「從 NAND 到雲」故事的第三條主線

本書有一條主軸:從 NAND 閘組出 CPU,CPU 跑機器碼,機器碼被編譯器翻譯自高階語言, 高階語言跑在作業系統上,作業系統跑在容器/VM 裡,容器跑在雲上。 WebAssembly 是這條故事線上一個平行分支: 高階語言 → WASM 位元組碼 → 任何 runtime → 任何平台—— 可移植性和安全性在這裡以優雅的方式合而為一。

本章的核心要點:

  • 堆疊式 VM 位元組碼:WASM 是一種可移植的二進位格式,不是真正的組合語言, 靠 JIT/AOT 達到近原生速度。
  • 線性記憶體:WASM 的「RAM」是一塊平坦的位元組陣列,JS 與 WASM 可共享讀寫, 但 WASM 無法存取這塊記憶體之外的任何東西。
  • WAT:WASM 的人可讀文字格式,S-expression 語法,與 .wasm 一一對應。
  • 能力安全沙箱:預設無 I/O,只能呼叫宿主明確匯入的函式——這是設計上的安全,不是事後補丁。
  • WASI:讓 WASM 在瀏覽器外以能力安全的方式存取系統資源, 是邊緣運算與 serverless 的新引擎。
  • 前沿方向:元件模型讓 WASM 模組之間強型別互通;SIMD 與執行緒帶來並行計算能力; WebGPU 的整合讓 WASM 也能駕馭 GPU。
