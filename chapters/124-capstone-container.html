容器不是虛擬機——它只是被隔離的行程

你在第 85 章看過虛擬化光譜——從純行程隔離到全虛擬機， 中間有無數層次。容器坐落在最輕量的那一端：它沒有 Guest OS、沒有 Hypervisor、沒有模擬硬體， 只是一個普通的 Linux 行程，但被精心地放進一個「視圖受限、資源受管、根目錄替換過」的環境。

在第 87 章，你已經拆解了容器的四層機制理論： namespace 隔離、cgroup 資源限制、OverlayFS 聯合掛載、capabilities + seccomp 最小特權。 在第 88 章，你用約 200 行 C 語言把這些機制串起來， 寫出了能跑的 mydocker。

那這一章呢？這一章是整合性的 capstone：我們換用 Go 語言重打， 因為 Go 的型別系統讓錯誤處理更清晰，而且真實世界的容器工具（Docker Engine、containerd、runc 等） 大多用 Go 寫成。更重要的是，我們要往前走幾步：

  • 六個 namespace 全開，包含 user namespace（讓 rootless 容器成為可能）
  • 從 tarball 解出 rootfs，並用 OverlayFS 把映像層與可寫層組合
  • 完整的 veth pair + bridge 網路讓容器可以對外通訊
  • 認識 OCI Runtime Specification，理解 runc 遵循什麼規格

最終成品叫做 minioci，它的指令介面是：

ℹ️
為什麼要 re-exec？

Go runtime 是多執行緒的，直接在現有行程裡呼叫 clone() 後進行 fork 會有競態問題（執行緒鎖、goroutine 狀態未複製）。解法是： re-exec 技巧——父行程用 exec.Command("/proc/self/exe", "_child", ...) 重新啟動一個乾淨的子行程，並在 fork 時透過 SysProcAttr.Cloneflags 開新的 namespace。子行程（_child 路徑）在新 namespace 裡完成容器初始化後 再 exec 使用者的命令。

里程碑 1 — 行程與檔案系統隔離：clone() 與 pivot_root

第一個里程碑的目標：能夠執行 ./minioci run /path/to/rootfs /bin/sh， 進入一個有獨立 PID namespace 與獨立根目錄的 shell，而且 echo $$ 顯示 PID 為 1， ls / 看到的是 rootfs 的根目錄，而不是主機的根目錄。

main.go — 骨架與 run()

package main

import (
    "fmt"
    "os"
    "os/exec"
    "syscall"
)

func main() {
    if len(os.Args) < 2 {
        usage()
    }
    switch os.Args[1] {
    case "run":
        if len(os.Args) < 4 {
            usage()
        }
        run(os.Args[2], os.Args[3:])
    case "_child": // 內部子命令，由 run() 自動呼叫
        child()
    default:
        usage()
    }
}

func usage() {
    fmt.Fprintln(os.Stderr, "用法: minioci run <rootfs> <cmd> [args...]")
    os.Exit(1)
}

// run: 父行程 — 建立新 namespace，re-exec 自己為 _child
func run(rootfs string, args []string) {
    // 把所有參數轉給 _child
    cmdArgs := append([]string{"_child", rootfs}, args...)
    cmd := exec.Command("/proc/self/exe", cmdArgs...)
    cmd.Stdin  = os.Stdin
    cmd.Stdout = os.Stdout
    cmd.Stderr = os.Stderr

    cmd.SysProcAttr = &syscall.SysProcAttr{
        Cloneflags: syscall.CLONE_NEWUTS | // hostname 隔離
                    syscall.CLONE_NEWPID | // PID 空間隔離
                    syscall.CLONE_NEWNS  | // mount namespace
                    syscall.CLONE_NEWIPC,  // IPC/共享記憶體隔離
    }

    if err := cmd.Start(); err != nil {
        fatal("啟動容器失敗", err)
    }
    // 拿到子行程 PID，設定 cgroup（里程碑 3 加入）
    // setupCgroup(cmd.Process.Pid)

    must(cmd.Wait())
}

// child: 子行程 — 已在新 namespace，完成初始化後 exec 使用者命令
func child() {
    rootfs   := os.Args[2]
    userArgs := os.Args[3:]

    // 1. 設定容器 hostname
    must(syscall.Sethostname([]byte("minioci")))

    // 2. 換根目錄：pivot_root 比 chroot 更安全（見第 87 章）
    must(pivotRoot(rootfs))

    // 3. 掛載 /proc（讓 ps、top 等工具正常運作）
    must(syscall.Mount("proc", "/proc", "proc", 0, ""))

    // 4. 執行使用者指定的命令
    cmd := exec.Command(userArgs[0], userArgs[1:]...)
    cmd.Stdin  = os.Stdin
    cmd.Stdout = os.Stdout
    cmd.Stderr = os.Stderr
    must(cmd.Run())
}

func must(err error) {
    if err != nil { fatal("", err) }
}

func fatal(msg string, err error) {
    if msg != "" {
        fmt.Fprintf(os.Stderr, "minioci: %s: %v\n", msg, err)
    } else {
        fmt.Fprintf(os.Stderr, "minioci: %v\n", err)
    }
    os.Exit(1)
}

pivotRoot() — 安全換根

pivot_root(new_root, put_old) 是 第 87 章 講過的「安全換根」系統呼叫。它把容器的新根掛到 new_root， 舊根移到 put_old，然後我們把舊根 detach 卸除，讓容器看不到主機的任何路徑。 相比之下，chroot 仍能透過 /../ 跳出去，安全性不足。 

// main.go（接上）
import "path/filepath"

func pivotRoot(newroot string) error {
    putold := filepath.Join(newroot, ".pivot_old")
    if err := os.MkdirAll(putold, 0o700); err != nil {
        return fmt.Errorf("建立 put_old 目錄: %w", err)
    }

    // pivot_root 要求 new_root 必須是一個「獨立的掛載點」
    // 用 bind mount 把 newroot 掛到自己，讓核心認可它
    if err := syscall.Mount(newroot, newroot, "",
        syscall.MS_BIND|syscall.MS_REC, ""); err != nil {
        return fmt.Errorf("bind mount newroot: %w", err)
    }

    if err := syscall.PivotRoot(newroot, putold); err != nil {
        return fmt.Errorf("pivot_root: %w", err)
    }

    // 切換工作目錄到新的根
    if err := os.Chdir("/"); err != nil {
        return err
    }

    // 以 MNT_DETACH 懶卸除舊根（允許現有使用者存取完成），再刪目錄
    if err := syscall.Unmount("/.pivot_old",
        syscall.MNT_DETACH); err != nil {
        return fmt.Errorf("unmount 舊根: %w", err)
    }
    return os.Remove("/.pivot_old")
}

里程碑 2 — 六道命名空間門：namespace 全家桶

里程碑 1 只開了 UTS、PID、mount、IPC 四個 namespace。 完整的容器隔離需要全部六個，尤其是 NET namespace（讓容器有自己的網路介面）與 USER namespace（讓無 root 的 rootless 容器成為可能）。

ℹ️
六個 namespace 一覽（詳見第 87 章）

CLONE_NEWPID：獨立 PID 空間，容器初始行程為 PID 1。
CLONE_NEWNS：獨立 mount 表，容器看不到主機掛載。
CLONE_NEWUTS：獨立 hostname 與 domain name。
CLONE_NEWIPC：獨立 IPC/共享記憶體 key 空間。
CLONE_NEWNET：獨立網路介面、路由表、防火牆規則。
CLONE_NEWUSER：獨立 UID/GID 映射，容器內 root 可對應到主機的非 root。

加入 NET 與 USER namespace

更新 run() 的 SysProcAttr，加入 CLONE_NEWNET 與 CLONE_NEWUSER，並提供 UID/GID 映射讓容器內的 root（UID 0） 對應到主機上的一般使用者（避免真正的 root 洩漏）： 

func run(rootfs string, args []string) {
    cmdArgs := append([]string{"_child", rootfs}, args...)
    cmd := exec.Command("/proc/self/exe", cmdArgs...)
    cmd.Stdin  = os.Stdin
    cmd.Stdout = os.Stdout
    cmd.Stderr = os.Stderr

    uid := os.Getuid()
    gid := os.Getgid()

    cmd.SysProcAttr = &syscall.SysProcAttr{
        Cloneflags: syscall.CLONE_NEWUTS  |
                    syscall.CLONE_NEWPID  |
                    syscall.CLONE_NEWNS   |
                    syscall.CLONE_NEWIPC  |
                    syscall.CLONE_NEWNET  |  // ← 網路 namespace（里程碑 5 加入 veth）
                    syscall.CLONE_NEWUSER,   // ← user namespace
        // 把容器 UID 0（root）映射到主機目前使用者
        UidMappings: []syscall.SysProcIDMap{
            {ContainerID: 0, HostID: uid, Size: 1},
        },
        GidMappings: []syscall.SysProcIDMap{
            {ContainerID: 0, HostID: gid, Size: 1},
        },
    }

    if err := cmd.Start(); err != nil {
        fatal("啟動容器失敗", err)
    }
    setupCgroup(cmd.Process.Pid) // 里程碑 3
    must(cmd.Wait())
}

user namespace + OverlayFS 的注意事項

里程碑 3 — 資源限制：cgroup v2 的介面與 Go 實作

容器沒有資源限制，是一個裸行程。一個失控的容器可以把整台主機的 CPU 和記憶體耗盡。 cgroup v2（unified hierarchy）透過 /sys/fs/cgroup/ 下的 偽檔案系統提供一個統一介面：你往檔案裡寫值，核心就強制執行。

確認系統使用 cgroup v2： 

mount | grep cgroup2
# 應看到類似：cgroup2 on /sys/fs/cgroup type cgroup2 (rw,...)

cgroup.go

package main

import (
    "fmt"
    "os"
    "path/filepath"
    "strconv"
)

const cgroupBase = "/sys/fs/cgroup/minioci"

// setupCgroup: 建立 minioci cgroup，寫入資源限制，並把 pid 加入
func setupCgroup(pid int) error {
    if err := os.MkdirAll(cgroupBase, 0o755); err != nil {
        return fmt.Errorf("建立 cgroup 目錄: %w", err)
    }

    limits := map[string]string{
        // 記憶體上限：128 MiB（必須寫位元組數）
        "memory.max": "134217728",
        // 最多 64 個行程
        "pids.max":   "64",
        // CPU 配額：100000 微秒/100000 微秒週期 = 1 顆核心
        // 格式：<quota_us> <period_us>
        "cpu.max":    "100000 100000",
        // 啟用記憶體 swap 限制（等同 memory.max，不允許 swap）
        "memory.swap.max": "0",
    }

    for file, val := range limits {
        p := filepath.Join(cgroupBase, file)
        if err := os.WriteFile(p, []byte(val), 0o644); err != nil {
            return fmt.Errorf("寫 %s (%s): %w", file, val, err)
        }
    }

    // 把容器行程加入 cgroup
    procsFile := filepath.Join(cgroupBase, "cgroup.procs")
    return os.WriteFile(procsFile, []byte(strconv.Itoa(pid)), 0o644)
}

// teardownCgroup: 容器結束後刪除 cgroup（需先確認無行程）
func teardownCgroup() {
    os.Remove(cgroupBase) // 只有在沒有任何行程時才能刪成功
}
ℹ️
cpu.max 格式詳解

cpu.max 的格式是 <quota> <period>，單位都是微秒（µs）。 寫 100000 100000 表示每 100ms 週期裡，容器最多使用 100ms CPU，等同限制一顆完整核心。 若寫 50000 100000 則限制半顆核心。寫 max 100000 表示不限制。

在 run() 中呼叫 setupCgroup

注意時序：必須在子行程 Start() 之後、Wait() 之前 設定 cgroup，因為要先知道子行程的 PID： 

if err := cmd.Start(); err != nil {
    fatal("啟動容器失敗", err)
}
// cmd.Process.Pid 是剛 fork 出來的子行程 PID
if err := setupCgroup(cmd.Process.Pid); err != nil {
    fmt.Fprintln(os.Stderr, "警告: setupCgroup 失敗:", err)
}
defer teardownCgroup()
must(cmd.Wait())

里程碑 4 — 映像與根檔案系統：OverlayFS 疊層

里程碑 1 直接使用了一個預先解壓的 rootfs。真實的容器執行時會把 OCI 映像（一組 tar layer） 動態疊成一個根目錄——唯讀的映像層堆在下面，容器可寫層蓋在上面， 容器寫入的任何內容只存在可寫層，不會汙染映像層。 這就是 OverlayFS（聯合檔案系統，union filesystem）的工作。

overlay.go

package main

import (
    "fmt"
    "os"
    "strings"
    "syscall"
)

// MountOverlay: 把映像層（lowerDirs，可以多層用 : 分隔）與容器可寫層組合成 merged
// lowerDirs: 多個唯讀層，用冒號分隔，左邊優先（e.g. "layer2:layer1:layer0"）
// containerDir: 存放 upper + work 的目錄（與 lowerDirs 必須在同一檔案系統）
// mergedDir: 最終掛載點
func MountOverlay(lowerDirs []string, containerDir, mergedDir string) error {
    upperDir := containerDir + "/upper"
    workDir  := containerDir + "/work"

    for _, d := range []string{upperDir, workDir, mergedDir} {
        if err := os.MkdirAll(d, 0o755); err != nil {
            return err
        }
    }

    opts := fmt.Sprintf(
        "lowerdir=%s,upperdir=%s,workdir=%s",
        strings.Join(lowerDirs, ":"), upperDir, workDir,
    )
    return syscall.Mount("overlay", mergedDir, "overlay", 0, opts)
}

// UmountOverlay: 卸載 merged（容器退出後呼叫）
func UmountOverlay(mergedDir string) error {
    return syscall.Unmount(mergedDir, syscall.MNT_DETACH)
}

// ExtractTar: 把 OCI image layer tarball 解壓到 destDir
func ExtractTar(tarPath, destDir string) error {
    if err := os.MkdirAll(destDir, 0o755); err != nil {
        return err
    }
    // 使用系統的 tar，-C 指定目的地
    return runCmd("tar", "-xf", tarPath, "-C", destDir)
}
// 在 main.go 加入輔助函式
import "os/exec"

func runCmd(name string, args ...string) error {
    cmd := exec.Command(name, args...)
    cmd.Stdout = os.Stdout
    cmd.Stderr = os.Stderr
    return cmd.Run()
}

在 run() 裡整合 OverlayFS

func run(rootfs string, args []string) {
    // rootfs 現在是 lowerdir（映像解壓後的唯讀層）
    containerDir := "/tmp/minioci-container"
    mergedDir    := "/tmp/minioci-merged"

    // 疊 OverlayFS
    if err := MountOverlay([]string{rootfs}, containerDir, mergedDir); err != nil {
        fatal("MountOverlay 失敗", err)
    }
    defer UmountOverlay(mergedDir)

    // 後續把 mergedDir 當成 rootfs 傳給 _child
    cmdArgs := append([]string{"_child", mergedDir}, args...)
    cmd := exec.Command("/proc/self/exe", cmdArgs...)
    // ... 其餘同前
}

capabilities 降權

OverlayFS 一旦掛好，在執行使用者命令前，應收縮容器的 Linux capabilities。 真實的 runc 預設會保留約 14 個，並丟棄 CAP_SYS_ADMIN、 CAP_NET_ADMIN、CAP_SYS_BOOT 等危險能力。 在 Go 裡透過 syscall.Prctl 與 libcap 套件可以操作 capability bounding set。教學上最簡單的做法是把需要丟棄的能力 從 PR_CAPBSET_DROP 中移除，留給讀者作延伸練習。

里程碑 5 — 容器網路：veth pair 與 Linux bridge

在里程碑 2 裡，我們加入了 CLONE_NEWNET，容器有了自己的 NET namespace， 但裡面只有一個 lo（loopback）介面，完全無法對外通訊。 要讓容器「上網」，需要在主機與容器之間建立一條虛擬乙太網路通道， 這就是 veth pair（虛擬乙太對）的用途。

概念：veth pair + bridge

  1. 建立一對 veth：veth-host（在主機端）↔ eth0（在容器端）
  2. 把 eth0 移入容器的 NET namespace
  3. 把 veth-host 接到主機的 Linux bridge（br0）
  4. bridge 啟用 IP 轉發（ip_forward）與 NAT（iptables MASQUERADE）
  5. 容器設定 IP 與預設閘道即可對外通訊

network.go — 主機端設定

package main

import (
    "fmt"
    "os"
    "strconv"
)

const (
    bridgeName = "br0"
    bridgeIP   = "10.88.0.1/24"
    containerIP = "10.88.0.2/24"
    containerGW = "10.88.0.1"
    vethHost    = "veth-host"
    vethCont    = "eth0"
)

// SetupNetwork: 在主機建立 bridge 與 veth pair，把 veth 容器端移入 pid 的 NET namespace
func SetupNetwork(pid int) error {
    pidStr := strconv.Itoa(pid)

    steps := [][]string{
        // 若 bridge 不存在則建立
        {"ip", "link", "add", "name", bridgeName, "type", "bridge"},
        {"ip", "addr", "add", bridgeIP, "dev", bridgeName},
        {"ip", "link", "set", bridgeName, "up"},
        // 建立 veth pair
        {"ip", "link", "add", vethHost, "type", "veth", "peer", "name", vethCont},
        // 把容器端 veth 移入容器的 NET namespace
        {"ip", "link", "set", vethCont, "netns", pidStr},
        // 把主機端 veth 接到 bridge
        {"ip", "link", "set", vethHost, "master", bridgeName},
        {"ip", "link", "set", vethHost, "up"},
    }
    for _, s := range steps {
        if err := runCmd(s[0], s[1:]...); err != nil {
            // 部分步驟（如 bridge 已存在）允許失敗
            fmt.Printf("網路設定警告: %v: %v\n", s, err)
        }
    }
    return nil
}

// SetupContainerNetwork: 在容器的 NET namespace 裡設定 IP 與路由
// 必須在 child() 裡（已在新 NET namespace 後）呼叫
func SetupContainerNetwork() error {
    steps := [][]string{
        {"ip", "link", "set", "lo", "up"},
        {"ip", "addr", "add", containerIP, "dev", vethCont},
        {"ip", "link", "set", vethCont, "up"},
        {"ip", "route", "add", "default", "via", containerGW},
    }
    for _, s := range steps {
        if err := runCmd(s[0], s[1:]...); err != nil {
            return fmt.Errorf("容器網路設定: %v: %w", s, err)
        }
    }
    return nil
}

// EnableNAT: 主機端開啟 IP 轉發並設定 MASQUERADE，讓容器封包能出主機
func EnableNAT(iface string) error {
    // 開啟核心 IP 轉發
    if err := os.WriteFile(
        "/proc/sys/net/ipv4/ip_forward", []byte("1"), 0o644); err != nil {
        return err
    }
    // NAT：容器 10.88.0.0/24 的出口封包偽裝成主機 IP
    return runCmd("iptables", "-t", "nat", "-A", "POSTROUTING",
        "-s", "10.88.0.0/24", "-o", iface, "-j", "MASQUERADE")
}

在 run() 與 child() 整合網路

// run() 裡，Start() 之後：

里程碑 6 — 組裝完整執行時：認識 OCI Runtime Specification

把前五個里程碑組在一起，我們已經有了一個能隔離行程、限制資源、有獨立根目錄、 能對外通訊的容器執行時。但真實世界的 Docker、containerd、Podman 是如何協作的？ 答案是 OCI Runtime Specification（開放容器倡議執行時規範）。

OCI Runtime Spec 要求什麼

OCI Runtime Spec 定義了一個「符合規範的容器執行時」必須做的事：

  1. config.json：一個 JSON 設定檔，描述 namespace、mounts、process、 hooks、Linux 特定設定（capabilities、seccomp、cgroups）
  2. 生命週期操作：create（建立但不啟動）→ start（執行行程） → kill（送訊號）→ delete（清理）→ state（查詢狀態）
  3. bundle 格式：一個目錄，包含 config.json 與 rootfs/

最小 config.json 骨架

在 minioci 加入 config.json 解析

// config.go（示意，僅解析最小子集）
package main

import (
    "encoding/json"
    "os"
)

type Config struct {
    Process struct {
        Args []string `json:"args"`
        Cwd  string   `json:"cwd"`
    } `json:"process"`
    Root struct {
        Path string `json:"path"`
    } `json:"root"`
    Hostname string `json:"hostname"`
}

func LoadConfig(bundleDir string) (*Config, error) {
    data, err := os.ReadFile(bundleDir + "/config.json")
    if err != nil {
        return nil, err
    }
    var cfg Config
    if err := json.Unmarshal(data, &cfg); err != nil {
        return nil, err
    }
    return &cfg, nil
}

與 runc 的關係

runc 是 Docker/containerd 預設使用的 OCI 參考實作（大約 60,000 行 Go 程式碼）。 當你執行 docker run ubuntu bash，Docker Engine 呼叫 containerd， containerd 準備好 bundle（config.json + rootfs overlay）後呼叫 runc， runc 才是真正執行上述六個里程碑的那個程式。 我們的 minioci 走的是完全相同的路徑，只是功能更精簡。

在第 90 章（Kubernetes），kubelet 透過 CRI（容器執行時介面）呼叫 containerd 或 CRI-O，最後也是落到 runc/crun 層。 整個鏈路：kubectl → API Server → kubelet → CRI → containerd → runc（本章的 minioci 即扮演這一層）。

安全與隔離邊界：容器逃逸、能力降權與 seccomp

現在你懂了容器怎麼建，是時候問一個更重要的問題： 這堵牆究竟有多厚？

容器隔離 ≠ VM 等級安全

容器與 VM 的根本差距在第 85 章的虛擬化光譜裡講過： 容器共用主機的 Linux 核心。這意味著任何 Linux 核心漏洞都能讓容器「逃逸」， 直接操控主機。而 VM（如 KVM、Firecracker）在 Guest OS 與 Host 之間多了一層 Hypervisor， 攻擊者需要先在 Guest 裡找到 VM 層的漏洞，攻擊難度大得多。

隔離機制核心共用？逃逸難度啟動速度開銷
容器（namespace/cgroup）是低（核心漏洞可逃逸）毫秒幾乎為零
Firecracker microVM否高（需 VMM 漏洞）125ms低
gVisor部分（User-space kernel）中~100ms中
WASM（WASI）否高（能力安全沙箱）微秒低
KVM 全虛擬機否最高秒級高

第 114 章的 WebAssembly (WASM) 提供了一個完全不同的安全模型： 能力安全（capability-based security）沙箱，程式只能使用明確授予的能力， 不需要 namespace 或 cgroup。這是 Fastly、Cloudflare Workers 選擇 WASM 的原因之一。

真實世界的容器逃逸案例

  • CVE-2019-5736（runc container escape）： 攻擊者可以從容器內覆蓋 /proc/self/exe（即主機上的 runc 二進位）， 導致下次 docker exec 時以 root 執行任意程式。 根本原因：runc 在 exec 時以 root 在容器 mount namespace 裡打開了 /proc/self/exe， 而容器有權修改它。修復方法：runc 改用 /proc/self/fd/N 的 fd 而非路徑。
  • CAP_SYS_ADMIN 洩漏：許多「特權容器」（docker run --privileged） 擁有完整的 capabilities，幾乎等同 root 直接存取主機。 解法：第 34 章的最小特權原則 ——永遠只授予容器必要的能力。

capabilities 降權在 Go 中

在 child() 執行使用者命令前，丟棄危險 capability： 

import "golang.org/x/sys/unix"

func dropCaps() error {
    // 從 bounding set 丟棄幾個最危險的能力
    dangerous := []uintptr{
        unix.CAP_SYS_ADMIN,
        unix.CAP_SYS_MODULE,
        unix.CAP_SYS_BOOT,
        unix.CAP_NET_ADMIN,
        unix.CAP_SYS_RAWIO,
    }
    for _, cap := range dangerous {
        if err := unix.Prctl(unix.PR_CAPBSET_DROP, cap, 0, 0, 0); err != nil {
            return fmt.Errorf("丟棄 CAP %d: %w", cap, err)
        }
    }
    return nil
}

seccomp 過濾器

seccomp（secure computing mode）讓你限制行程能呼叫哪些系統呼叫。 Docker 預設的 seccomp profile 阻擋了約 44 個危險系統呼叫（如 mount、 reboot、ptrace、kexec_load）。 在 Go 裡，seccomp 過濾器必須在子行程初始化階段（re-exec 後的 child() 路徑內）自行載入—— 父行程無法透過 SysProcAttr 替子行程安裝過濾器。 注意：SysProcAttr.SeccompTsync（bool）並非「設定過濾器」的開關， 它的作用是讓子行程在呼叫 seccomp() 系統呼叫時附上 SECCOMP_FILTER_FLAG_TSYNC 旗標，把過濾器同步到行程內所有執行緒； 過濾器本體仍須由子行程自行建立並載入。 實際做法是在 child() 裡使用 libseccomp-golang 的 filter.Load()，或直接呼叫 unix.Prctl。 

// 正確做法：在 child()（re-exec 後）載入 seccomp 過濾器
// syscall.SysProcAttr 沒有 Seccomp 欄位；父行程無法替子行程設定過濾器。

// 方法一：libseccomp-golang（go get github.com/seccomp/libseccomp-golang）
// import seccomp "github.com/seccomp/libseccomp-golang"
func loadSeccomp() error {
    filter, err := seccomp.NewFilter(seccomp.ActErrno.SetReturnCode(int16(syscall.EPERM)))
    if err != nil { return err }
    for _, sc := range []seccomp.ScmpSyscall{
        seccomp.ScmpSyscall(unix.SYS_READ),  seccomp.ScmpSyscall(unix.SYS_WRITE),
        seccomp.ScmpSyscall(unix.SYS_OPEN),  seccomp.ScmpSyscall(unix.SYS_CLOSE),
        seccomp.ScmpSyscall(unix.SYS_EXIT_GROUP),
        // ... 完整白名單見 moby/moby profiles/seccomp/default.json
    } {
        filter.AddRule(sc, seccomp.ActAllow)
    }
    return filter.Load() // ← 必須在 child() 內、exec 前呼叫
}

// 方法二：直接呼叫 unix.Prctl（需自行組裝 BPF sock_filter）
// unix.Prctl(unix.PR_SET_SECCOMP, unix.SECCOMP_MODE_FILTER,

延伸方向

  • Rootless 容器：把所有 namespace（包含 user namespace） 在一般使用者身份下開啟，不需要 root。Podman、Buildah 走的就是這條路。 關鍵在 newuidmap/newgidmap 指令協助擴大 UID 映射範圍。
  • OCI 映像建置：實作一個簡單的 minioci build， 讀取 Dockerfile 並疊加 OverlayFS 層，最後打包成 OCI image manifest + tar layers。 可參考 OCI Image Spec。
  • Registry 整合：從 Docker Hub 或私有 registry 下載 OCI image， 需實作 Docker Registry HTTP API v2，驗證 layer sha256，然後逐層解壓。
  • 與 Kubernetes 整合：實作 CRI（Container Runtime Interface）gRPC 伺服器， 讓 kubelet 能呼叫你的 minioci 啟動容器。這就是 CRI-O、containerd 做的事。 詳見第 90 章的 Kubernetes 架構。
  • eBPF 觀測：用第 91 章學到的 eBPF 追蹤容器內的系統呼叫，實作細粒度的安全監控。

✏️ 練習 118.1 實作

在 child() 執行使用者命令前，加入 dropCaps() 並丟棄 CAP_SYS_ADMIN 與 CAP_NET_ADMIN。 驗證：在容器 shell 裡嘗試 mount -t tmpfs tmpfs /mnt， 應得到 Operation not permitted。

看解答

在 child() 裡 pivotRoot() 之後、cmd.Run() 之前加入：

if err := dropCaps(); err != nil {
    fmt.Fprintln(os.Stderr, "警告: dropCaps:", err)
}
// 或者更嚴格：must(dropCaps())

執行後，容器裡的 mount 命令會因缺少 CAP_SYS_ADMIN 而失敗。 注意：若使用 user namespace，部分 capability 的行為不同—— 在 user namespace 內部你「看起來」有 CAP_SYS_ADMIN，但實際上受到外部 namespace 的限制。

✏️ 練習 118.2 實作

修改 minioci，讓它從 OCI image tarball 解壓並疊 OverlayFS。 具體步驟：
1. 從命令列接受一個 .tar.gz 映像路徑（可用 docker save ubuntu:22.04 -o ubuntu.tar 匯出）
2. 解析 manifest.json 找出 layer 的 tar 路徑
3. 依序解壓每個 layer 到獨立目錄（layer0/、layer1/…）
4. 用 MountOverlay([]string{"layer2", "layer1", "layer0"}, ...) 疊成完整 rootfs

看解答 
// image.go（骨架）
func LoadImage(tarPath string) ([]string, error) {
    // 1. 解壓整個 image tar 到暫存目錄
    imgDir := "/tmp/minioci-img"
    os.MkdirAll(imgDir, 0o755)
    runCmd("tar", "-xf", tarPath, "-C", imgDir)

    // 2. 讀 manifest.json
    data, _ := os.ReadFile(imgDir + "/manifest.json")
    // 解析 JSON，取得 Layers 欄位（[]string，每個是 layer.tar 路徑）
    // ... （省略 JSON 解析細節）

    // 3. 解壓每個 layer
    var layerDirs []string
    for i, layerTar := range layers {
        dir := fmt.Sprintf("%s/layer%d", imgDir, i)
        os.MkdirAll(dir, 0o755)
        runCmd("tar", "-xf", imgDir+"/"+layerTar, "-C", dir)
        layerDirs = append([]string{dir}, layerDirs...) // 後層覆蓋前層
    }
    return layerDirs, nil
}

然後把回傳的 layerDirs 作為 MountOverlay 的 lowerDirs 參數。

✏️ 練習 118.3 挑戰

實作 rootless minioci：不需要 root 權限，完全在一般使用者身份下執行。 關鍵差異：
1. 必須加入 CLONE_NEWUSER 並設定 UID/GID 映射
2. OverlayFS 在 rootless 下需要 fuse-overlayfs（Kernel < 5.11）或 Kernel ≥ 5.11 的 rootless overlay 支援
3. 網路設定需要 slirp4netns 取代 veth + bridge（因為一般使用者無法建立 bridge）
驗證：以非 root 使用者執行 ./minioci run /path/to/rootfs /bin/sh，並在裡面 id 看到 uid=0。

看解答

rootless 的核心是 user namespace 讓一般使用者在容器內「假裝」是 root：

cmd.SysProcAttr = &syscall.SysProcAttr{
    Cloneflags: syscall.CLONE_NEWUSER | /* 其他 */ ,
    UidMappings: []syscall.SysProcIDMap{
        {ContainerID: 0, HostID: os.Getuid(), Size: 1},
    },
    GidMappings: []syscall.SysProcIDMap{
        {ContainerID: 0, HostID: os.Getgid(), Size: 1},
    },
    GidMappingsEnableSetgroups: false,
}

網路部分用 slirp4netns 替代：

slirp4netns --configure --mtu=65520 --disable-host-loopback $PID eth0 &

OverlayFS 若不支援 rootless，改用 fuse-overlayfs：

runCmd("fuse-overlayfs",
    "-o", fmt.Sprintf("lowerdir=%s,upperdir=%s,workdir=%s",
        lowerDirs, upperDir, workDir),
    mergedDir)

把這一章串起來

六個里程碑，六把鑰匙，開了同一扇門：

  1. 里程碑 1：clone() + pivot_root — 行程的視野被換掉了，它以為自己是 PID 1，根目錄是 /，但這一切都是主機核心製造的視圖。
  2. 里程碑 2：六個 namespace 全開 — hostname、PID 空間、mount 表、IPC key、網路介面、UID 空間全部隔離，容器變成一個高度封閉的環境。
  3. 里程碑 3：cgroup v2 — 把容器行程放進一個資源籠子裡，記憶體、CPU、PID 數量都受到核心強制執行。
  4. 里程碑 4：OverlayFS — 映像層是唯讀的底座，容器可寫層是透明的薄膜，合在一起就是容器看到的完整根目錄，而且容器退出後映像不受汙染。
  5. 里程碑 5：veth pair + bridge + NAT — 容器有了自己的 IP，封包出主機再轉回來，一條虛擬乙太網路通道把容器連接到外部世界。
  6. 里程碑 6：OCI Runtime Spec — 你的 minioci 與 runc 說著同一種語言：config.json 定義一切，生命週期操作是統一協定，上面可以接 containerd，再上面可以接 Kubernetes。

理論上，你已經「讀懂」了 docker run 背後所有步驟。 但這一章的目的不只是理解，而是讓你的手做過一遍，感受每一個系統呼叫的重量、 每一條錯誤訊息背後的核心語義、每一個 cgroup 介面的物理意義。 從今以後，當你看到一個容器化的生產系統，你不會只看到「黑盒子」， 而是看到六道被精心管理的 Linux 門。
