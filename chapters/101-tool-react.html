開場:LLM 只會吐字,怎麼讓它動手?

假設你剛完成了第 94 章的 LLMClient,現在你的 agent 能和 LLM 對話了。 你給它一個任務: 

from llm_client import get_client

client = get_client()
answer = client.complete(
    "請計算 (12 + 5) × 3 的結果,然後把答案寫進 result.txt。"
)
print(answer)

模型可能回答:「(12 + 5) = 17,17 × 3 = 51,我已把結果 51 寫進 result.txt。」 聽起來完美——但 result.txt 根本沒有被建立。 模型說「我已寫入」,是在「預測一個語氣上合理的 token 序列」,不是在「執行程式碼」。 LLM 的本質是語言預測機器:所有輸出都是文字。文字裡說「完成了」不代表真的完成了。

更麻煩的是數學。讓模型直接算 (123456789 × 987654321) mod 31? 它有可能給你一個「看起來合理」但實際上算錯的答案——這正是 「幻覺(hallucination)」在數值計算上的典型表現。

🔑
LLM 是語言機器,不是執行環境

LLM 只能輸出文字。要讓 agent 真正「動手」——計算、讀檔、搜尋、呼叫 API—— 你需要把工具(tool)交給它:讓模型決定「什麼時候用哪個工具、用什麼參數」, 然後由你的程式碼實際執行工具,再把結果回報給模型。 這個「決定 + 執行 + 回報」的循環,就是本章的主題。

這一章我們會手刻三個核心元件,它們會被後續所有 agent 章節直接 import 使用:

  • Tool:代表一個外部能力的抽象(name、description、parameters schema、run)
  • ToolRegistry:管理工具集合、生成給 LLM 的描述清單、依名稱分派執行
  • run_react(client, registry, task):ReAct 主迴圈——讓 LLM 在「推理」和「呼叫工具」之間交替,直到任務完成

Tool Calling 原理:你描述,LLM 決定,你執行

「Tool calling」(有時也叫「function calling」)是現代 LLM API 提供的一種能力: 你在請求裡附上一份「工具說明書」,模型在需要使用工具時, 會輸出一段結構化的「工具呼叫指令」而不是普通文字。 然後你解析這個指令、執行工具、把結果回填,模型再繼續推理。

原生 API tool calling vs. 手刻

Anthropic Claude、OpenAI GPT-4 等模型有「原生 function calling」——你可以在 API 請求裡傳 tools 欄位,模型會回傳格式化的 tool_use 物件。 本章我們選擇手刻:在系統提示裡描述工具、讓模型用文字輸出 Action JSON、 再用正則解析。這種方式不依賴特定 API 欄位,Ollama 本地模型也能跑, 而且讓你完全理解每一步在幹嘛。理解了手刻版,再看原生 API 就一目瞭然。

手刻工具抽象:Tool 與 ToolRegistry

我們要定義兩個類別。Tool 代表「一個工具」; ToolRegistry 是工具的「登記表」,負責管理工具集合並為 LLM 生成說明文件。 

"""tool_registry.py — Tool 與 ToolRegistry 的定義(後續章節直接 import)"""
import json
from typing import Callable, Any


class Tool:
    """代表 agent 可呼叫的一個外部工具。

    後續章節(第 96–100 章)假設 Tool 具備這四個屬性與 run() 方法。

    Attributes:
        name        — 唯一識別名稱,LLM 輸出 Action 時會寫這個名稱
        description — 一句話說明這個工具能做什麼,給 LLM 讀
        parameters  — JSON Schema 格式描述參數(dict);可為空 dict
        _run        — 實際執行函式,接受與 parameters 對應的 kwargs
    """

    def __init__(
        self,
        name: str,
        description: str,
        parameters: dict,
        run_fn: Callable[..., Any],
    ) -> None:
        self.name        = name
        self.description = description
        self.parameters  = parameters
        self._run        = run_fn

    def run(self, **kwargs: Any) -> str:
        """執行工具,回傳字串結果(供模型讀取)。
        任何例外都包成字串——由 ToolRegistry.dispatch() 捕捉。
        """
        return str(self._run(**kwargs))


class ToolRegistry:
    """工具登記表:管理、描述、分派。

    用法:
        registry = ToolRegistry()
        registry.register(my_tool)
        desc = registry.describe_all()          # 送給 LLM
        result = registry.dispatch("my_tool", {"x": 1})
    """

    def __init__(self) -> None:
        self._tools: dict[str, Tool] = {}

    def register(self, tool: Tool) -> None:
        """把工具加入登記表。重複名稱會覆蓋。"""
        self._tools[tool.name] = tool

    def describe_all(self) -> str:
        """產生給 LLM 看的工具說明清單。"""
        lines = []
        for tool in self._tools.values():
            params_json = json.dumps(tool.parameters, ensure_ascii=False)
            lines.append(
                f"- {tool.name}: {tool.description}\n"
                f"  參數 schema: {params_json}"
            )
        return "\n".join(lines) if lines else "(無可用工具)"

    def dispatch(self, name: str, args: dict) -> str:
        """依名稱找工具並執行;不存在或執行失敗時回傳錯誤訊息字串。"""
        if name not in self._tools:
            available = list(self._tools.keys())
            return f"[錯誤] 工具 '{name}' 不存在。可用工具:{available}"
        try:
            return self._tools[name].run(**args)
        except TypeError as e:
            return f"[參數錯誤] {e}"
        except Exception as e:
            return f"[工具執行錯誤] {type(e).__name__}: {e}"

✏️ 練習 95.1 實作

為 agent 加一個「查目前日期與時間」工具 get_current_time。 它不需要任何參數(parameters 為空 dict),呼叫後回傳格式化的目前時間字串,例如 "2026-07-01 14:32:00"。把它 register 進一個 ToolRegistry, 並呼叫 registry.describe_all() 確認輸出正確。

看解答 
from datetime import datetime
from tool_registry import Tool, ToolRegistry

time_tool = Tool(
    name="get_current_time",
    description="查詢目前的日期與時間。無需參數。",
    parameters={},
    run_fn=lambda: datetime.now().strftime("%Y-%m-%d %H:%M:%S"),
)

registry = ToolRegistry()
registry.register(time_tool)
print(registry.describe_all())
# - get_current_time: 查詢目前的日期與時間。無需參數。
#   參數 schema: {}

print(registry.dispatch("get_current_time", {}))
# 2026-07-01 14:32:00

觀察:run_fn 是 lambda: ...,不接收任何參數—— dispatch 呼叫 tool.run(**{}) 等於 tool.run(), 剛好符合無參數 lambda 的定義。 當 agent 需要知道「現在幾點」或「今天是幾號」時,這個工具就派上用場了。

ReAct 範式:先想再做,迴圈到完成

2022 年,Google 與 Princeton 的研究者發表了 ReAct: Synergizing Reasoning and Acting in Language Models (Yao et al., 2022),提出了一個優雅的想法:讓模型在每次「行動」之前先「推理」。

ReAct 的核心格式是三步迴圈:

  • Thought(推理):模型用自然語言說明它目前的推理過程與下一步計畫
  • Action(行動):模型決定要呼叫哪個工具、用什麼參數
  • Observation(觀察):你的程式碼執行工具後,把結果回填進對話

這個迴圈不斷重複,直到模型判斷「我已經能回答了」,輸出 Final Answer 結束。

為何「先想再做」比一步到位更可靠?

想像你問一個朋友:「幫我查台灣所有縣市的人口,算出前三名的平均。」 一步到位的方式是朋友直接給你一個數字——但你怎麼知道它對不對? ReAct 的方式是:朋友先說「我要先查各縣市人口」(Thought),再去查(Action), 拿到資料(Observation)後再說「我要排序取前三名並求平均」(Thought), 再計算(Action),最後回答你(Final Answer)。

這個「邊想邊做」的結構帶來幾個好處:

  • 可追蹤:你可以看到模型的推理步驟,方便除錯
  • 可自我修正:如果工具回傳錯誤或意外結果,Thought 可以反映並改變策略
  • 不容易幻覺:模型在 Thought 裡宣稱「我要去查」之後,它必須真的輸出 Action;如果它直接給 Final Answer 卻沒有查詢,邏輯上就說不通
📜
ReAct 論文與後繼影響

Yao et al. (2022)「ReAct: Synergizing Reasoning and Acting in Language Models」 (arXiv:2210.03629)在 HotpotQA、Fever、ALFWorld 等任務上展示 ReAct 顯著優於純 Chain-of-Thought 或純 Action 的基線。它影響了 LangChain Agent、AutoGPT、BabyAGI 等早期 agent 框架, 也是現在主流 agent loop 設計的直接前身。

手刻 run_react:ReAct 主迴圈程式碼

理解了原理,我們來把它寫成程式碼。 run_react 是本章最重要的產物,也是後續所有 agent 章節依賴的介面。 

"""react_loop.py — run_react:ReAct 主迴圈

後續章節統一 import:
    from react_loop import run_react
"""
import json
import re

from llm_client import LLMClient   # 第 94 章定義
from tool_registry import ToolRegistry  # 本章定義

MAX_STEPS = 10   # 最多幾輪 Thought/Action,防止無窮迴圈


def run_react(client: LLMClient, registry: ToolRegistry, task: str) -> str:
    """ReAct 主迴圈:Thought → Action → Observation → … → Final Answer。

    介面契約(後續第 96–100 章依賴此定義):
        client   — 符合 LLMClient 介面的物件(第 94 章定義)
        registry — ToolRegistry 物件(本章定義)
        task     — 自然語言任務描述字串
        回傳值   — agent 的最終答案字串

    迴圈最多執行 MAX_STEPS 輪。超過上限時回傳失敗訊息而非無限等待。
    """
    # ── 組系統提示 ──────────────────────────────────────────────────────────
    system_prompt = (
        "你是一個能使用工具的 AI agent。解決任務時,請嚴格遵循以下格式:\n\n"
        "Thought: 你的推理過程(繁體中文)\n"
        'Action: {"tool": "工具名稱", "args": {"參數名": "參數值"}}\n\n'
        "或,當你已能回答時:\n"
        "Final Answer: 最終答案\n\n"
        "規則:\n"
        "1. 每次只輸出一個 Thought/Action 或 Thought/Final Answer。\n"
        "2. Action 必須是合法 JSON 物件,tool 欄位為工具名稱,args 為參數 dict。\n"
        "3. 不要猜測工具的回傳值;等 Observation 回來再繼續。\n\n"
        f"可用工具:\n{registry.describe_all()}"
    )

    messages = [
        {"role": "system", "content": system_prompt},
        {"role": "user",   "content": f"任務:{task}"},
    ]

    # ── ReAct 主迴圈 ─────────────────────────────────────────────────────────
    for step in range(MAX_STEPS):
        reply = client.chat(messages)
        messages.append({"role": "assistant", "content": reply})

        # 1. 偵測重複(陷入迴圈保護)
        if _is_repeating(messages):
            return "[偵測到連續重複輸出,agent 可能陷入迴圈,已中止]"

        # 2. 偵測 Final Answer
        fa_match = re.search(r"Final Answer[:：]\s*(.+)", reply, re.DOTALL)
        if fa_match:
            return fa_match.group(1).strip()

        # 3. 解析 Action JSON
        act_match = re.search(r'Action[:：]\s*(\{[\s\S]*?\})', reply)
        if not act_match:
            # 模型沒有輸出 Action 也沒有 Final Answer → 提示它繼續
            messages.append({
                "role": "user",
                "content": "請繼續:輸出 Action(JSON)或 Final Answer。",
            })
            continue

        # 4. 解析工具名稱與參數
        try:
            action    = json.loads(act_match.group(1))
            tool_name = action["tool"]
            args      = action.get("args", {})
        except (json.JSONDecodeError, KeyError) as e:
            observation = f"[解析 Action 失敗:{e}。請確認 Action 是合法的 JSON 物件,且含 'tool' 欄位。]"
        else:
            # 5. 分派工具執行
            observation = registry.dispatch(tool_name, args)

        # 6. 把 Observation 回填進對話
        messages.append({
            "role": "user",
            "content": f"Observation: {observation}",
        })

    # 超過步數上限
    return f"[超過最大步數上限({MAX_STEPS}),agent 無法在限定步數內完成任務]"


def _is_repeating(messages: list, window: int = 4) -> bool:
    """偵測 messages 末尾 window 輪的 assistant 回應是否出現連續重複。"""
    assistant_msgs = [m["content"] for m in messages if m["role"] == "assistant"]
    if len(assistant_msgs) < window:
        return False
    recent = assistant_msgs[-window:]
    # 如果最新的兩條 assistant 回應完全相同,判定為重複
    return recent[-1] == recent[-2]

小模型的 Tool Calling 限制

本地小模型(如 Llama 3.2 3B)對「嚴格遵循 JSON 格式輸出 Action」的表現差異很大—— 有時輸出多餘文字包裹在 Action 前後,有時省略 tool 欄位,有時 JSON 有語法錯誤。 我們的解析已加入容錯(從包裹文字裡找第一個 {...}),但小模型的 ReAct 成功率仍然不如大模型穩定。 開發 agent 時,建議先用 Claude 或 GPT-4 級別的模型驗證邏輯; 確認流程正確後,再測試較小的本地模型。

工具一:安全計算機——告別裸 eval

第一個工具:計算機。最直覺的實作是 eval(expression)—— 但這是一個嚴重的安全漏洞。 如果 LLM(或惡意 prompt injection)讓模型輸出: 

action = {"tool": "calculator", "args": {"expression": "__import__('os').system('rm -rf /')}"}

eval 會乖乖執行。這叫程式碼注入(code injection)。 對於純算術,我們應該只允許數字和算術運算子——用 Python 的 ast 模組可以做到。 

"""safe_eval.py — 用 ast 模組安全求值純算術表達式"""
import ast
import operator as op

# 允許的運算子:純算術,不含位元運算或函式呼叫
_SAFE_OPS = {
    ast.Add:  op.add,    # +
    ast.Sub:  op.sub,    # -
    ast.Mult: op.mul,    # *
    ast.Div:  op.truediv, # /
    ast.Mod:  op.mod,    # %
    ast.Pow:  op.pow,    # **
    ast.USub: op.neg,    # 一元負號 -x
    ast.UAdd: op.pos,    # 一元正號 +x
}


def safe_eval(expr: str) -> float:
    """用 AST 安全求值純算術表達式。
    只允許數字常數與算術運算子——無函式呼叫、無屬性存取、無變數。
    """
    try:
        tree = ast.parse(expr.strip(), mode="eval")
    except SyntaxError as e:
        raise ValueError(f"無法解析算式: {e}") from e

    def _eval(node: ast.expr) -> float:
        # 數字常數
        if isinstance(node, ast.Constant):
            if isinstance(node.value, (int, float)):
                return float(node.value)
            raise ValueError(f"不支援非數字常數: {node.value!r}")
        # 二元運算(+、-、*、/ 等)
        if isinstance(node, ast.BinOp):
            fn = _SAFE_OPS.get(type(node.op))
            if fn is None:
                raise ValueError(f"不允許的運算子: {type(node.op).__name__}")
            return fn(_eval(node.left), _eval(node.right))
        # 一元運算(-x、+x)
        if isinstance(node, ast.UnaryOp):
            fn = _SAFE_OPS.get(type(node.op))
            if fn is None:
                raise ValueError(f"不允許的一元運算子: {type(node.op).__name__}")
            return fn(_eval(node.operand))
        # 括號表達式(AST 不單獨表示括號,它就是優先解析的子樹)
        raise ValueError(f"不支援的語法節點: {type(node).__name__}")

    return _eval(tree.body)


# ── 建立計算機工具 ────────────────────────────────────────────────────────────

from tool_registry import Tool

calculator_tool = Tool(
    name="calculator",
    description="安全地計算算術表達式,回傳數值結果。不能呼叫函式或存取變數。",
    parameters={
        "expression": {
            "type": "string",
            "description": "合法的算術表達式,例如 '(12+5)*3' 或 '100/7'",
        }
    },
    run_fn=lambda expression: safe_eval(expression),
)

    tests = [

⚠️
永遠不要用裸 eval 執行 LLM 輸出

Python 的 eval() 能執行任意程式碼。 如果 LLM 輸出的 expression 被惡意構造(例如透過 prompt injection 攻擊), 裸 eval 會執行惡意程式碼。 ast-based safe eval 只解析「算術語法樹」——任何函式呼叫、屬性存取、import 都無法通過 AST 節點型別檢查,會直接拋出 ValueError。

工具二/三:讀檔、寫檔與 Shell 執行器

計算機以外,agent 最常需要的就是讀寫檔案與執行系統指令。 這兩類工具功能強大,但也帶來安全風險——需要認真對待。

讀檔與寫檔工具

"""file_tools.py — 讀檔與寫檔工具"""
import pathlib
from tool_registry import Tool


def _read_file(path: str) -> str:
    """讀取文字檔案。只允許相對路徑,防止目錄穿越攻擊。"""
    p = pathlib.Path(path)
    if p.is_absolute():
        return "[錯誤] 只允許相對路徑,拒絕絕對路徑。"
    if ".." in p.parts:
        return "[錯誤] 路徑不可含 '..',防止目錄穿越(path traversal)攻擊。"
    try:
        content = p.read_text(encoding="utf-8")
        return content if content else "(空檔案)"
    except FileNotFoundError:
        return f"[錯誤] 找不到檔案: {path}"
    except PermissionError:
        return "[錯誤] 沒有讀取權限。"
    except Exception as e:
        return f"[錯誤] {e}"


def _write_file(path: str, content: str) -> str:
    """寫入文字檔案。只允許相對路徑。"""
    p = pathlib.Path(path)
    if p.is_absolute() or ".." in p.parts:
        return "[錯誤] 只允許相對路徑。"
    try:
        p.parent.mkdir(parents=True, exist_ok=True)
        p.write_text(content, encoding="utf-8")
        return f"已寫入 {path}({len(content)} 個字元)。"
    except PermissionError:
        return "[錯誤] 沒有寫入權限。"
    except Exception as e:
        return f"[錯誤] {e}"


read_file_tool = Tool(
    name="read_file",
    description="讀取文字檔案的內容。只允許相對路徑。",
    parameters={
        "path": {"type": "string", "description": "相對路徑,例如 'data.txt'"},
    },
    run_fn=_read_file,
)

write_file_tool = Tool(
    name="write_file",
    description="把指定內容寫入文字檔案(相對路徑)。若檔案不存在則建立。",
    parameters={
        "path":    {"type": "string", "description": "相對路徑,例如 'result.txt'"},
        "content": {"type": "string", "description": "要寫入的文字內容"},
    },
    run_fn=_write_file,
)

Shell 執行器工具(⚠️ 高風險——務必搭配沙箱)

Shell 工具讓 agent 能執行系統指令——功能強大,但也是最危險的工具之一。 如果 agent 能執行任意 shell 指令,惡意的 prompt injection 攻擊可能讓它刪除檔案、 竊取資料或安裝惡意程式。

⛔
Shell 工具需要容器沙箱隔離

在生產環境中,shell 工具絕對必須在隔離的容器環境中執行—— 透過 namespace、cgroups 與 seccomp profile 限制它能做的事。 第 87 章解釋了容器隔離的底層原理; 第 88 章示範了手寫 container runtime 的實作。 本章的白名單機制只是教學用最小防護,不足以替代真正的沙箱。

"""shell_tool.py — 白名單保護的 shell 執行工具(⚠️ 生產環境需加容器沙箱)"""
import shlex
import subprocess
from tool_registry import Tool

# 白名單:只允許無破壞性的唯讀/展示指令
_ALLOWED_PREFIXES = (
    "echo ",      # 顯示字串
    "ls",         # 列目錄(ls、ls -la 等)
    "pwd",        # 顯示工作目錄
    "date",       # 顯示日期時間
    "cat ",       # 讀檔(補充 read_file 工具)
    "python3 -c ", # 執行簡單 Python 片段
)


def _run_shell(command: str, timeout: int = 10) -> str:
    """在受限白名單中執行 shell 指令。
    ⚠️ 警告:這只是教學用白名單保護。生產環境請用容器沙箱(見第 88 章)。
    """
    cmd = command.strip()
    # 白名單檢查
    if not any(cmd == p.strip() or cmd.startswith(p) for p in _ALLOWED_PREFIXES):
        return (
            f"[拒絕] 指令 '{cmd}' 未在允許清單中。\n"
            "⚠️ 安全提示:shell 工具可執行任意系統指令。"
            "生產環境請用容器沙箱隔離(見第 88 章)。"
        )
    try:
        result = subprocess.run(
            shlex.split(cmd),
            capture_output=True,
            text=True,
            timeout=timeout,
        )
        output = (result.stdout + result.stderr).strip()
        return output if output else "(無輸出)"
    except subprocess.TimeoutExpired:
        return f"[超時] 指令超過 {timeout} 秒時限。"
    except FileNotFoundError as e:
        return f"[錯誤] 找不到指令: {e}"
    except Exception as e:
        return f"[錯誤] {e}"


shell_tool = Tool(
    name="shell",
    description=(
        "執行 shell 指令(白名單限制:echo/ls/pwd/date/cat/python3 -c)。"
        "⚠️ 生產環境務必搭配容器沙箱。"
    ),
    parameters={
        "command": {
            "type": "string",
            "description": "shell 指令字串,例如 'echo hello' 或 'ls -la'",
        }
    },
    run_fn=_run_shell,
)
💡
沙箱的進階做法

生產級 agent(如 GitHub Copilot Workspace、Devin)的 shell 執行通常有幾層防護: (1) 在容器內執行(第 88 章介紹的 namespace + cgroups 隔離); (2) seccomp 限制可呼叫的 syscall 集合; (3) 網路隔離(限制容器出口流量); (4) 執行時間與記憶體上限(cgroups)。 最小化攻擊面才是正確的 agent 安全工程。

失敗處理:格式亂、工具炸、圈圈轉

在真實使用中,agent 會遇到各種失敗情況。 好的設計不是「假裝不會失敗」,而是「優雅地處理每一種失敗」。

失敗一:模型輸出格式錯誤

模型沒有輸出 Action: 也沒有 Final Answer:—— 例如它只說了一段 Thought 就停下來,或者輸出了一段無關的文字。

我們的 run_react 已處理這個情況: 如果正則找不到 Action 或 Final Answer,就追加一條 user 訊息 "請繼續:輸出 Action(JSON)或 Final Answer。" 後繼續下一輪。 這個提示通常能喚醒模型回到正確格式。

失敗二:Action JSON 解析失敗

模型輸出了 Action:,但 JSON 有語法錯誤(多餘逗號、單引號等)。 我們的實作用 re.search 提取第一個 {...} 區塊再嘗試 json.loads; 失敗時把錯誤訊息作為 Observation 回填,讓模型有機會修正: 

# 解析失敗的 Observation 範例:
observation = "[解析 Action 失敗:Expecting ',' delimiter: line 1 column 25 (char 24)。請確認 Action 是合法的 JSON 物件,且含 'tool' 欄位。]"

# 模型下一輪的 Thought 通常會是:
# Thought: 剛才的 Action JSON 有語法錯誤,讓我重新格式化。
# Action: {"tool": "calculator", "args": {"expression": "(12+5)*3"}}

失敗三:工具執行拋出例外

工具本身丟出了例外(例如除以零、檔案不存在)。 ToolRegistry.dispatch() 已經用 try/except 包住 tool.run(), 把任何例外轉成字串 "[工具執行錯誤] ZeroDivisionError: division by zero" 作為 Observation。 模型讀到這個訊息,通常能自行修改參數重試。

失敗四:無窮迴圈

模型陷入重複——每輪都輸出相同的 Action,工具也每次回傳相同的 Observation。 這種情況下 MAX_STEPS 是最後的保險,確保迴圈一定結束。 此外,我們的 _is_repeating() 函式能提前偵測並中止: 

def _is_repeating(messages: list, window: int = 4) -> bool:
    """偵測連續重複的 assistant 輸出。"""
    assistant_msgs = [m["content"] for m in messages if m["role"] == "assistant"]
    if len(assistant_msgs) < window:
        return False
    recent = assistant_msgs[-window:]
    return recent[-1] == recent[-2]   # 最新兩條 assistant 回應完全相同
🔑
失敗處理設計原則

好的 agent 設計把「失敗」當成 Observation 的一部份回填給模型,讓模型有機會自我修正—— 而不是直接拋出例外讓整個程式崩潰。 但同時必須有最終的「出口」(MAX_STEPS + 重複偵測),否則 agent 可能無限耗費資源。 這個「給機會修正 + 設硬性出口」的雙層設計,是 agent 可靠性工程的基本模式。

✏️ 練習 95.2 思考

假設 agent 的 ReAct 迴圈陷入了一種「軟卡死」: 每輪模型都輸出合法的 Action(工具名稱和參數也正確), 但工具每次都回傳 "[錯誤] 找不到檔案: missing.txt"—— 模型沒有學到教訓,繼續用一樣的參數呼叫。

(a) 說明 _is_repeating() 是否能偵測到這種情況。 (b) 如果不能,你會如何改進偵測邏輯? (c) 有沒有辦法在系統提示層面就預防這種情況?

看解答

(a) 能偵測。因為 _is_repeating 比較的是 assistant 角色的訊息,而每輪模型都輸出同樣的 Thought + Action,所以 recent[-1] == recent[-2] 為 True,會在第 2 次重複後中止。

(b) 如果模型每輪的 Thought 稍有不同但 Action 相同(例如 Thought 說「再試一次」),那麼 assistant 訊息不完全一樣,就會偵測失敗。改進方式:只提取 Action JSON 部分來做比較:

def _is_action_repeating(messages: list, window: int = 3) -> bool:
    actions = []
    for m in messages:
        if m["role"] == "assistant":
            match = re.search(r'Action[:：]\s*(\{[\s\S]*?\})', m["content"])
            if match:
                actions.append(match.group(1).strip())
    if len(actions) < window:
        return False
    return len(set(actions[-window:])) == 1   # 最近 window 個 Action 全部相同

(c) 在系統提示加上規則:「如果工具兩次回傳相同錯誤,請改變策略或輸出 Final Answer 說明無法完成任務。」給模型明確的「放棄策略」,比用程式碼偵測更根本。

完整示範:讓 agent 計算並存檔

把所有元件組起來,看看 agent 跑一個多步任務的完整流程: 「計算 (12 + 5) × 3,然後把結果寫進 answer.txt」。 

#!/usr/bin/env python3

from llm_client import get_client          # 第 94 章

from safe_eval import calculator_tool      # 本章
from file_tools import write_file_tool     # 本章

registry.register(write_file_tool)

在使用 Claude 或強力本地模型的情況下,對話會大致像這樣流轉:

--- 步驟 1 ---
[assistant] Thought: 我需要先計算 (12 + 5) × 3。
            Action: {"tool": "calculator", "args": {"expression": "(12+5)*3"}}

[user]      Observation: 51.0

--- 步驟 2 ---
[assistant] Thought: 計算結果是 51。現在我要把答案寫進 answer.txt。
            Action: {"tool": "write_file", "args": {"path": "answer.txt", "content": "51"}}

[user]      Observation: 已寫入 answer.txt(2 個字元)。

--- 步驟 3 ---
[assistant] Thought: 計算完成且檔案已建立。
            Final Answer: (12 + 5) × 3 = 51,已寫入 answer.txt。

最終答案: (12 + 5) × 3 = 51,已寫入 answer.txt。

執行後你會發現工作目錄裡多了一個 answer.txt,內容是 51。 這一次,agent 真的「動手」了——不只是說「我已完成」。

✏️ 練習 95.3 實作

擴展上面的示範:讓 agent 解一個需要三個工具的任務—— 同時用到計算機、讀檔與寫檔:

任務字串:「讀取 numbers.txt 的內容(一行一個整數),把所有數字加總,再把結果寫進 sum.txt。」

步驟提示: (1) 先用 Python 建立一個 numbers.txt(例如內容為 "10\n20\n30")。 (2) 把 read_file_tool 也 register 進 registry。 (3) 執行 run_react,觀察 agent 如何分三步完成任務。 (4) 如果 agent 嘗試用 calculator 工具解析字串,說明為何會失敗,以及如何在系統提示或工具描述裡改善。

看解答 
import pathlib
from llm_client import get_client
from tool_registry import ToolRegistry
from safe_eval import calculator_tool
from file_tools import read_file_tool, write_file_tool
from react_loop import run_react

# 1. 建立測試檔案
pathlib.Path("numbers.txt").write_text("10\n20\n30", encoding="utf-8")

# 2. 組裝工具
registry = ToolRegistry()
registry.register(read_file_tool)
registry.register(calculator_tool)
registry.register(write_file_tool)

# 3. 執行
client = get_client()

關於失敗場景:calculator 工具的 safe_eval 無法解析字串 "10\n20\n30"——它只懂算術表達式。agent 可能需要先把讀到的內容整理成算式 "10+20+30" 再呼叫 calculator。改善方式:(a) 在任務描述裡說清楚 「請先把每行數字提取成算術表達式」;(b) 加一個「加總列表」工具,直接接受多行數字字串; (c) 換用能直接執行 Python 程式碼的 shell 工具。

這個練習說明了工具的粒度設計:工具太粗(shell 直接執行任意程式)有安全風險; 工具太細(只能算四則運算)讓 agent 需要更多步驟。好的工具集設計需要在能力和安全之間取得平衡。

把這一章串起來

這一章是整個 agent 宇宙的「心臟」——讓 LLM 能真正動手。回顧幾個關鍵決策:

  • Tool 抽象:四個屬性(name / description / parameters / run_fn)+ 一個方法(run(**kwargs) -> str)。 簡單、可組合、後續章節可自由擴充。
  • ToolRegistry:管理、描述、分派三個責任合一。describe_all() 生成 LLM 可讀的說明;dispatch() 永遠回傳字串(錯誤也是)——讓 agent 迴圈永不因工具失敗而崩潰。
  • run_react 介面契約:run_react(client, registry, task) -> str。 接收 LLMClient、ToolRegistry 和任務字串;回傳最終答案或失敗訊息。MAX_STEPS 與重複偵測是兩道保險。
  • 安全計算機:AST-based safe_eval 替代裸 eval——只允許數字與算術運算子。
  • Shell 工具需要沙箱:白名單只是最小防護。生產環境必須搭配第 88 章介紹的容器隔離機制。
  • 失敗是 Observation:工具錯誤、格式錯誤都回填為 Observation,讓模型有機會自我修正——而不是直接 raise。

接下來,第 96 章會給 agent 加上記憶與檢索(RAG)—— 讓它能從外部知識庫查詢資料,而不只是依賴 LLM 訓練時看過的知識。 第 97 章會把「工具」這個概念標準化成 MCP(Model Context Protocol)—— 讓工具可以跨 agent、跨平台複用。 這兩章的 agent 主迴圈都會直接使用我們今天定義的 Tool、ToolRegistry 與 run_react。
