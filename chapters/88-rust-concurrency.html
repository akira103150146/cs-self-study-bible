並行 bug 最難抓：從 §43 的 Python 視角到 Rust 的編譯期保證

在第 43 章，我們用 Python 親眼見識了「共享記憶體 + 多執行緒」的危險： counter += 1 不是原子操作，兩條執行緒同時跑會偷偷吃掉更新，印出比 2,000,000 小的怪數字。 修法是加 threading.Lock()——但鎖帶來新問題：死結、效能殺手、以及永遠不確定「這段程式碼有沒有加夠鎖」。

Python 的鎖是執行時工具——你忘了加，程式照樣編譯、照樣跑，只是答案偶爾錯。 這份「偶爾」是最危險的：它可能在 CI 測試時完全不出現，在生產環境高併發時突然炸出來。 並行 bug 比一般 bug 難抓，正因為它不確定、不可重現、依賴時序。

🔑
Rust 的承諾：編譯期消滅資料競爭

Rust 的型別系統加上 Send/Sync trait，讓編譯器能在程式跑起來之前， 就拒絕一切資料競爭(data race)——多個執行緒同時存取同一份資料、至少一方在寫入、 且沒有同步保護。這不是執行時的偵測，而是靜態保證。 犯了並行安全問題，程式根本無法通過編譯。

本章專注 Rust 特有的安全視角。Amdahl 定律、加速比、GIL 在 §43 已講透，不再重複； 這裡直接進入 Rust 的並行工具箱與背後的型別理論。

thread::spawn 與 move 閉包：把所有權搬進執行緒

Rust 建立執行緒的方式直截了當：std::thread::spawn 接受一個閉包，在新執行緒上執行它。 但有個關鍵限制：閉包捕獲的任何資料，都必須能安全地「搬進」新執行緒。 

use std::thread;

fn main() {
    let msg = String::from("hello from thread");

    // move 關鍵字：把 msg 的所有權完整移進閉包（進而移進新執行緒）
    let handle = thread::spawn(move || {
        println!("{}", msg);   // msg 現在屬於這個執行緒，安全
    });
    // println!("{}", msg);   // ✗ 編譯錯誤：msg 已被 move 進執行緒

    handle.join().unwrap();    // 等待子執行緒完成；子執行緒 panic 時 unwrap 向上傳播
}

為什麼要 move？主執行緒可能在子執行緒完成前就結束。 如果閉包只「借用」msg，子執行緒的生命週期可能超過 msg 的生命週期—— 懸空參考。move 強制閉包取得所有權，消除這個問題： 子執行緒擁有資料，資料的生命週期和執行緒綁在一起。

同時跑多條執行緒，收集 JoinHandle

use std::thread;

fn main() {
    let mut handles = Vec::new();   // Vec<JoinHandle<i32>>

    for i in 0..5_i32 {
        // i 是 i32（Copy），閉包直接複製一份；不需要 clone
        let h = thread::spawn(move || {
            println!("執行緒 {} 啟動", i);
            i * i   // 閉包回傳值，讓 join() 拿到
        });
        handles.push(h);
    }

    for h in handles {
        let result = h.join().unwrap();   // join() 回傳 Result<i32, Box<dyn Any>>
        println!("子執行緒回傳 {}", result);
    }
    // 印出五個 i² 值（0, 1, 4, 9, 16），但執行緒啟動順序不保證
}
ℹ️
JoinHandle::join() 的語意

thread::spawn 回傳 JoinHandle<T>，其中 T 是閉包的回傳型別。 呼叫 join() 會讓目前的執行緒阻塞，直到對應的子執行緒完成。 若子執行緒 panic，join() 回傳 Err；.unwrap() 會讓 panic 在目前執行緒重新拋出。 若不 join，主執行緒結束時子執行緒也會被強制終止。

Send 與 Sync：型別系統的並行護欄

Rust 怎麼「知道」某個型別能不能安全跨執行緒？答案是兩個 marker trait（標記 trait，不含任何方法，純粹標示能力）：

  • Send：若 T: Send，代表 T 的值（所有權） 可以安全地轉移到另一個執行緒。大多數型別自動是 Send。 thread::spawn 的閉包與它捕獲的所有變數都必須是 Send。
  • Sync：若 T: Sync，代表 &T（對 T 的不可變參考） 可以安全地跨執行緒共享。 換句話說，T: Sync 等價於 &T: Send。

哪些型別不是 Send 或 Sync？

最重要的非 Send 型別是 Rc<T>（引用計數指標）。 它的計數器是非原子的，多個執行緒同時增減計數會是資料競爭。 若你試著把 Rc<T> 傳進 thread::spawn，編譯器直接報錯： 

use std::rc::Rc;
use std::thread;

fn main() {
    let rc = Rc::new(42_i32);
    let rc2 = Rc::clone(&rc);

    thread::spawn(move || {
        println!("{}", rc2);
        // ✗ error[E0277]: `Rc<i32>` cannot be sent between threads safely
        //   the trait `Send` is not implemented for `Rc<i32>`
    });
}

同樣，Cell<T> 和 RefCell<T> 不是 Sync—— 它們的「內部可變性」是非原子的，多執行緒共享 &RefCell<T> 就是資料競爭。 編譯器阻止你把 &RefCell<T> 送進另一條執行緒。

🔑
Send/Sync 由編譯器自動推導，幾乎不用手寫

若一個 struct 的所有欄位都是 Send，這個 struct 自動是 Send； Sync 同理。你很少需要手動 impl Send for MyType （手動 impl 需要 unsafe，因為你在向編譯器保證某事）。 這套設計讓 Rust 能在零執行時開銷的情況下靜態消滅資料競爭—— 不需任何執行時掃描或偵測。

訊息傳遞：mpsc channel「以通訊共享記憶體」

共享記憶體的核心危險是「多人同時改」。有個完全不同的思路： 不讓執行緒直接共享資料——讓它們傳訊息。 Go 語言有句話說得很精準：「不要以共享記憶體來通訊，要以通訊來共享記憶體。」 Rust 標準庫內建了這個思路：std::sync::mpsc （多生產者單消費者，multiple producer single consumer）。 

use std::sync::mpsc;
use std::thread;

fn main() {
    // channel() 回傳一對 (Sender<T>, Receiver<T>)
    let (tx, rx) = mpsc::channel::<String>();

    // Sender 可以 clone，做到「多生產者」
    let tx2 = tx.clone();

    // 生產者執行緒 1
    thread::spawn(move || {
        for word in ["Rust", "is", "great"] {
            tx.send(String::from(word)).unwrap();
        }
    });

    // 生產者執行緒 2
    thread::spawn(move || {
        tx2.send(String::from("hello from thread 2")).unwrap();
    });

    // 主執行緒是唯一的消費者（Receiver 不能 clone）
    // for...in rx：阻塞直到所有 Sender 都 drop（channel 關閉）
    for msg in rx {
        println!("收到: {}", msg);
    }
    // 印出 4 條訊息（順序不確定）
}

注意一個初學者最常踩的坑： 我們在主執行緒上 clone 了 tx 產生 tx2， 原始的 tx 被 move 進第一條執行緒（已會自動 drop）。 tx2 被 move 進第二條執行緒（也會自動 drop）。 主執行緒不再持有任何 Sender，所以 for msg in rx 最終能正常結束。 若主執行緒還持有一個多餘的 Sender 沒有 drop，rx 的迴圈將永遠阻塞。

💡
channel 天然無競爭：所有權轉移即同步

send(T) 消耗 T 的所有權，把它移進 channel； recv() 取出時，所有權從 channel 移交給接收方。 任何時刻，資料只有一個擁有者——Rust 型別系統在語言層面保證了這一點。 你根本不可能「發出去又繼續讀」，不是靠紀律，是靠編譯器。

同步通道：有界緩衝

use std::sync::mpsc;

// sync_channel(n)：緩衝最多 n 個訊息
// 若緩衝滿了，send() 會阻塞（與 channel() 的「永不阻塞」不同）
let (tx, rx) = mpsc::sync_channel::<i32>(3);
// 適合限制生產者速度，防止記憶體無限成長

共享狀態：Arc<Mutex<T>>

有些問題天生需要多個執行緒共同修改同一份資料——計數器、共用快取、累積結果。 channel 在這裡顯得繁瑣；Rust 提供了另一條路：用型別系統保護共享狀態。

在第 81 章我們看到 Rc<RefCell<T>> 可在單執行緒裡做「共享 + 可變」。多執行緒場景需要兩個對應的執行緒安全版本：

  • Arc<T>（原子引用計數，Atomically Reference Counted）： 對應 Rc<T>，但用原子操作管理計數，可安全跨執行緒共享所有權（Arc: Send + Sync）。
  • Mutex<T>（互斥鎖，mutual exclusion）： 對應 RefCell<T>，但用作業系統鎖——同時只有一個執行緒能持有 MutexGuard 並存取內部資料。

手刻：多執行緒計數器（先看錯誤版，再修正）

先看一個無法編譯的版本——理解編譯器在說什麼：

use std::sync::Mutex;
use std::thread;

fn main() {
    let counter = Mutex::new(0_i32);
    let mut handles = Vec::new();

    for _ in 0..5 {
        let h = thread::spawn(move || {
            // ✗ error[E0382]: use of moved value: `counter`
            // 第一次迴圈把 counter move 進閉包，第二次就失效了
            // 根本問題：Mutex 只有一個擁有者，但五條執行緒都想擁有它
            let mut num = counter.lock().unwrap();
            *num += 1;
        });
        handles.push(h);
    }
}

用 Arc 讓多個執行緒共同擁有同一個 Mutex：

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // Arc 讓五條執行緒共同持有同一個 Mutex<i32>
    let counter = Arc::new(Mutex::new(0_i32));
    let mut handles = Vec::new();

    for _ in 0..5 {
        let c = Arc::clone(&counter);   // 原子遞增引用計數；不複製資料
        let h = thread::spawn(move || {
            let mut num = c.lock().unwrap();
            // lock() 若 Mutex 被佔用則阻塞，直到前一個持有者釋放
            // 回傳 MutexGuard<i32>，解參考後就是 &mut i32
            *num += 1;
            // MutexGuard 離開作用域 → 自動解鎖（RAII）
        });
        handles.push(h);
    }

    for h in handles {
        h.join().unwrap();
    }

    // 所有子執行緒結束後，主執行緒再取一次鎖讀出結果
    println!("最終計數: {}", *counter.lock().unwrap());   // 5
}
🔑
Arc 管「誰擁有它」，Mutex 管「誰能用它」

Arc<Mutex<T>> 是兩個正交問題的組合： Arc 解決「多個執行緒需要共同持有」（所有權問題）， Mutex 解決「同時只能一人讀寫」（存取同步問題）。 二者缺一不可：沒有 Arc，你沒辦法讓多個執行緒都持有 Mutex； 沒有 Mutex，多個執行緒同時修改資料就是資料競爭。

死結與 Mutex 毒化，以及 RwLock

鎖是強大的工具，但帶來兩個新危險：死結(deadlock)與毒化(poisoning)。

死結：循環等待

第 24 章（作業系統）和 §43 都講過死結的原理： 執行緒 A 持有鎖 1、等鎖 2；執行緒 B 持有鎖 2、等鎖 1——兩者永遠互等。 Rust 的型別系統無法在編譯期消滅死結（只能消滅資料競爭）； 死結依然需要靠設計來防範： 

use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

fn main() {
    let lock_a = Arc::new(Mutex::new("資源 A"));
    let lock_b = Arc::new(Mutex::new("資源 B"));

    let (a1, b1) = (Arc::clone(&lock_a), Arc::clone(&lock_b));
    let t1 = thread::spawn(move || {
        let _ga = a1.lock().unwrap();              // t1 先拿鎖 A
        thread::sleep(Duration::from_millis(10));  // 模擬做了一些事
        let _gb = b1.lock().unwrap();              // t1 再等鎖 B
        println!("t1 同時持有 A 和 B");
    });

    let (a2, b2) = (Arc::clone(&lock_a), Arc::clone(&lock_b));
    let t2 = thread::spawn(move || {
        let _gb = b2.lock().unwrap();              // t2 先拿鎖 B
        thread::sleep(Duration::from_millis(10));
        let _ga = a2.lock().unwrap();              // t2 再等鎖 A — t1 還拿著！
        println!("t2 同時持有 B 和 A");
    });

    // 以下兩行將永遠阻塞——這段程式會死結，請勿直接執行
    t1.join().unwrap();
    t2.join().unwrap();
}
⚠️
防死結守則：鎖的取得順序必須全域一致

最實用的防死結規則：替所有鎖編號，程式裡一律由編號小到大的順序取鎖。 上例的修法：兩條執行緒都先取鎖 A 再取鎖 B，循環就形不成了。 另一個選擇：用 try_lock()（非阻塞，若鎖忙就立刻回傳 Err） 並加上退讓策略，避免「傻等著形成循環」。

Mutex 毒化（Poisoning）

若一條執行緒在持有 Mutex 鎖的情況下 panic，Rust 會將該 Mutex 標記為 「毒化（poisoned）」。之後任何執行緒呼叫 lock() 都得到 Err(PoisonError)，.unwrap() 就會 panic。 這是一種防禦機制：被 panic 打斷的操作可能讓內部資料處於不一致狀態， Rust 選擇讓後續存取明確地面對這個可能性。 

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let m = Arc::new(Mutex::new(0_i32));
    let m2 = Arc::clone(&m);

    // 子執行緒拿鎖後 panic → Mutex 被毒化
    let _ = thread::spawn(move || {
        let _guard = m2.lock().unwrap();
        panic!("子執行緒在持鎖時 panic！");
    }).join();   // join() 回傳 Err，這裡用 let _ 忽略

    // 主執行緒嘗試取鎖
    match m.lock() {
        Ok(val) => println!("取鎖成功，值={}", *val),
        Err(e)  => {
            // into_inner() 強行取出資料（你自己承擔資料可能不一致的風險）
            let val = e.into_inner();
            println!("Mutex 已毒化，強行恢復，值={}", *val);
        }
    }
}

RwLock：讀多寫少場景

Mutex<T> 是悲觀的：就算只是讀，也要獨占，讓所有其他人等待。 若場景是「讀很多、寫很少」，RwLock<T>（讀寫鎖）更合適： 允許多個讀取者同時持鎖，但寫入者必須獨占。 

use std::sync::{Arc, RwLock};
use std::thread;

fn main() {
    let data = Arc::new(RwLock::new(vec![1_i32, 2, 3]));

    // 多個讀取者可同時持鎖
    let d1 = Arc::clone(&data);
    let d2 = Arc::clone(&data);
    let r1 = thread::spawn(move || println!("讀: {:?}", *d1.read().unwrap()));
    let r2 = thread::spawn(move || println!("讀: {:?}", *d2.read().unwrap()));
    r1.join().unwrap();
    r2.join().unwrap();

    // 寫入者獨占（等所有讀取者釋放後才能取得寫鎖）
    let dw = Arc::clone(&data);
    let w = thread::spawn(move || dw.write().unwrap().push(4));
    w.join().unwrap();

    println!("寫後: {:?}", *data.read().unwrap());   // [1, 2, 3, 4]
}
✏️ 練習 82.1 實作

下面這段程式試圖用 Rc<Cell<i32>> 在多個執行緒間共享計數器，但無法通過編譯。 請改寫為能正確執行的版本，讓五條執行緒各遞增計數器一次，最後印出 5。 

use std::rc::Rc;
use std::cell::Cell;
use std::thread;

fn main() {
    let counter = Rc::new(Cell::new(0_i32));
    let mut handles = Vec::new();
    for _ in 0..5 {
        let c = Rc::clone(&counter);
        handles.push(thread::spawn(move || {
            c.set(c.get() + 1);   // ✗ 編譯失敗
        }));
    }
    for h in handles { h.join().unwrap(); }
    println!("{}", counter.get());
}
看解答

Rc<T> 不是 Send（引用計數非原子），Cell<T> 不是 Sync（內部可變性非原子）。 改用執行緒安全版本：Arc<Mutex<i32>>。 

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0_i32));
    let mut handles = Vec::new();

    for _ in 0..5 {
        let c = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            *c.lock().unwrap() += 1;   // 取鎖、修改、MutexGuard 離開作用域自動解鎖
        }));
    }
    for h in handles { h.join().unwrap(); }

    println!("{}", *counter.lock().unwrap());   // 5
}

核心替換：Rc → Arc（原子計數，可跨執行緒）； Cell → Mutex（互斥保護，可變性安全）。

✏️ 練習 82.2 思考

你在設計一個多執行緒任務分配系統，有兩種選擇：

  1. mpsc channel：主執行緒把任務傳給工作者，工作者把結果傳回主執行緒。
  2. Arc<Mutex<VecDeque<Task>>>：共享任務佇列，工作者自己鎖定佇列、取出任務並放入結果佇列。

分析在以下兩個場景下，哪種設計更合適，並說明原因：
(a) 任務量固定，主執行緒依序生成所有任務後再分發；
(b) 任務量動態增長（工作者完成一個任務後，可能再生成新任務）。

看解答

(a) 固定任務量：mpsc channel 更合適。

主執行緒生成所有任務，用 Sender 逐一發送；工作者接收、完成後用另一個 channel 傳回結果。 這套模式乾淨：資料有明確的所有權轉移，不需要鎖，無死結風險。 控制流清楚——「生產→傳遞→消費→回報」的單向管道。

(b) 動態任務：共享佇列（Arc<Mutex<VecDeque>>）更合適。

當工作者完成任務後還能生成新任務，channel 的單向流就不夠用了 （你需要把新任務送回佇列，channel 變迴路，設計複雜）。 共享可變佇列在此更自然：任何執行緒都能 push（生成新任務）或 pop（取任務）。 代價是鎖競爭可能成為瓶頸；工作者數量多時，可考慮 crossbeam 的 work-stealing deque。

結論：channel 適合單向、結構化的資料流；共享佇列適合動態、雙向的任務調度。

async/await 心智模型：Future 是惰性的計算承諾

到目前為止，我們用的都是作業系統執行緒（OS thread）： 每條執行緒有自己的 stack（通常幾百 KB 到幾 MB）、由作業系統排程， 建立與切換的開銷相對較大。 如果你要同時處理數十萬條並發連線（HTTP 伺服器、資料庫代理）， 開數十萬條 OS 執行緒成本太高。

Rust 的 async/await 提供另一條路： 用少量 OS 執行緒驅動大量並發任務， 任務在等待 I/O 時不佔用執行緒，其他任務趁機推進—— 這就是非同步並發(asynchronous concurrency)。

Future 是什麼？

在 Rust 裡，每個 async fn 或 async { ... } 區塊都被編譯成一個 實作了 Future trait 的狀態機（state machine）： 

// Future trait（簡化版，非原始碼）
pub trait Future {
    type Output;
    // 執行器呼叫 poll 來推進這個 Future
    // cx: 含有「喚醒器（Waker）」，I/O 完成時用來通知執行器再次 poll
    fn poll(&mut self, cx: &mut Context<'_>) -> Poll<Self::Output>;
    //                                           ^^^^ Ready(val) 或 Pending
}

// 當你寫：
// async fn fetch_data() -> String { ... }
// 編譯器自動展開成：
// fn fetch_data() -> impl Future<Output = String> { ... 狀態機 ... }

完整版的 poll 第一參數是 Pin<&mut Self>，用以保證 Future 首次 poll 後不會被移動——詳見 async-book。

關鍵：Future 是惰性的。 建立一個 Future 本身什麼都不做——就像寫下一份待辦，但沒人去執行它。 要讓 Future 真正跑起來，你需要一個執行器（executor）不斷呼叫 poll： 若 Future 準備好（例如 I/O 回應了），回傳 Poll::Ready(value)； 若還在等（例如等網路），回傳 Poll::Pending， 執行器暫時讓出 CPU 去跑其他 Future，等 Waker 通知才再次 poll。

.await 的意義

在 async 函式裡，something.await 的意思是： 「poll 這個 Future，直到它 Ready；在它 Pending 時，暫停我自己、讓執行器去跑其他任務。」 這就是 async/await 的核心：不用手寫 callback，不用管執行緒切換， 用順序寫法表達並發邏輯。

⚠️
async ≠ 多執行緒，也 ≠ 真正平行（預設情況下）

單執行緒 async 執行器在一條執行緒上交錯執行多個 Future—— 這是並發(concurrency)，不是平行(parallelism)。 tokio 預設使用多執行緒執行器（和 CPU 核心數相同的執行緒池）， 讓 Future 能真正在多核上平行，但需要 Future 是 Send（可能在不同執行緒間轉移）。 CPU 密集任務在 async 裡應用 tokio::task::spawn_blocking 轉到執行緒池， 避免阻塞執行器的執行緒、餓死其他 Future。

tokio 入門：並發任務、計時與 join

Rust 標準庫只提供 Future trait 和 async/await 語法， 不包含執行器。tokio 是 Rust 生態最主流的非同步執行環境（async runtime）， 提供執行器、非同步 I/O、計時器、通道等完整工具。在 Cargo.toml 加入： 

[dependencies]
tokio = { version = "1", features = ["full"] }

Demo：三個並發計時任務

// Cargo.toml 需加: tokio = { version = "1", features = ["full"] }
use tokio::time::{sleep, Duration, Instant};

#[tokio::main]
// 展開為: fn main() { tokio::runtime::Builder::new_multi_thread()...block_on(async_main()) }
async fn main() {
    let start = Instant::now();

    // tokio::spawn 建立並發任務（立刻開始「排隊等執行」，不等 await）
    // 三個任務在 spawn 後即並發進行
    let t1 = tokio::spawn(async {
        sleep(Duration::from_millis(300)).await;
        "任務 A 完成（等了 300ms）"
    });
    let t2 = tokio::spawn(async {
        sleep(Duration::from_millis(200)).await;
        "任務 B 完成（等了 200ms）"
    });
    let t3 = tokio::spawn(async {
        sleep(Duration::from_millis(100)).await;
        "任務 C 完成（等了 100ms）"
    });

    // tokio::join! 同時等待多個 JoinHandle（並發等待，不是循序）
    let (r1, r2, r3) = tokio::join!(t1, t2, t3);
    println!("{}", r1.unwrap());   // 任務 A 完成（等了 300ms）
    println!("{}", r2.unwrap());   // 任務 B 完成（等了 200ms）
    println!("{}", r3.unwrap());   // 任務 C 完成（等了 100ms）

    // 三個任務並發等待，總耗時約 300ms（最慢那個），不是 600ms（循序加總）
    println!("總耗時: {:?}", start.elapsed());   // ~300ms
}

這個例子說明了 async 並發的核心紅利：三個任務同時在等待， 等待期間執行緒可以跑其他任務，總耗時只由最慢的那個決定。 對 I/O 密集的服務（同時處理數千個 HTTP 請求），這個模式讓吞吐量大幅提升。

async 函式：所有權與借用

use tokio::time::{sleep, Duration};

// async fn 回傳 impl Future<Output = String>
// 注意：&str 借用在 .await 跨點必須存活（tokio::spawn 需要 'static，不能借用外部變數）
async fn greet(name: String, delay_ms: u64) -> String {
    sleep(Duration::from_millis(delay_ms)).await;
    format!("Hello, {}!", name)   // name 的所有權在這個 Future 裡
}

#[tokio::main]
async fn main() {
    // tokio::join! 在目前任務內並發等待（可借用外部變數）
    let (a, b) = tokio::join!(
        greet(String::from("Alice"), 200),
        greet(String::from("Bob"),   100)
    );
    println!("{}", a);   // Hello, Alice!
    println!("{}", b);   // Hello, Bob!
    // 總耗時約 200ms，不是 300ms（兩個並發）
}
💡
tokio::spawn vs tokio::join!

tokio::spawn 建立一個獨立任務（即刻開始，分離執行）， 回傳 JoinHandle<T>。任務必須是 'static + Send（不能借用外部變數）。
tokio::join!(f1, f2, ...) 在目前任務內並發地等待多個 Future， 不建立新任務，可以借用外部變數。
簡單並發用 join!；需要「丟到背景跑、之後再等結果」用 spawn。

✏️ 練習 82.3 實作

把下面這段循序同步程式改寫成並發 async 版本。 原程式依序查詢 3 個使用者，每次耗時 100ms；改寫後三個查詢應並發進行，總耗時約 100ms 而非 300ms。 

use std::thread::sleep;
use std::time::Duration;

fn fetch_user(id: u32) -> String {
    sleep(Duration::from_millis(100));   // 模擬查詢耗時（阻塞！）
    format!("User #{}", id)
}

fn main() {
    // 循序：三次查詢共耗時 ~300ms
    let u1 = fetch_user(1);
    let u2 = fetch_user(2);
    let u3 = fetch_user(3);
    println!("{} {} {}", u1, u2, u3);
}
看解答

改用 tokio 的 sleep 模擬非同步查詢，用 tokio::join! 並發執行： 

// Cargo.toml: tokio = { version = "1", features = ["full"] }
use tokio::time::{sleep, Duration, Instant};

// async fn：呼叫後回傳 Future，不會立刻執行
async fn fetch_user(id: u32) -> String {
    sleep(Duration::from_millis(100)).await;   // 非阻塞等待（讓出執行緒給其他任務）
    format!("User #{}", id)
}

#[tokio::main]
async fn main() {
    let start = Instant::now();

    // 三個查詢並發進行：總耗時約 100ms（不是 300ms）
    let (u1, u2, u3) = tokio::join!(
        fetch_user(1),
        fetch_user(2),
        fetch_user(3)
    );
    println!("{} {} {}", u1, u2, u3);        // User #1 User #2 User #3
    println!("耗時: {:?}", start.elapsed()); // ~100ms
}

關鍵差異：std::thread::sleep 阻塞 OS 執行緒（期間執行緒完全停工）； tokio::time::sleep(...).await 讓執行器暫停這個 Future 並去跑其他任務。 三個 Future 同時在等，整體只花 ~100ms。

把這一章串起來

這一章從「並行 bug 為何難抓」出發，完整走過 Rust 的並行工具箱：

  • thread::spawn + move 閉包：建立 OS 執行緒，move 將所有權完整搬進執行緒，消除懸空參考。JoinHandle::join() 等待並取得結果。
  • Send/Sync：Rust 的並行護欄。 型別系統靜態保證「可以移入執行緒的型別」（Send）和「可以跨執行緒共享參考的型別」（Sync）。 Rc<T>、RefCell<T> 不過關；Arc<T>、Mutex<T> 過關。 這是 Rust 在零執行時開銷下消滅資料競爭的核心機制。
  • mpsc channel：以通訊代替共享記憶體。Sender<T> 可 clone（多生產者）， Receiver<T> 唯一（單消費者）。資料所有權從發送方移到接收方，天然無競爭。
  • Arc<Mutex<T>>：多執行緒共享可變狀態的標準組合。 Arc 管所有權（多個共同持有），Mutex 管存取（同時只能一人）。 MutexGuard 離開作用域自動解鎖（RAII）。
  • 死結與毒化：型別系統無法消滅死結——靠設計防範（固定鎖順序、try_lock）。 Mutex 毒化是防禦機制，panic 後的鎖讓後續呼叫顯式面對可能損壞的資料。 RwLock 在讀多寫少場景優於 Mutex。
  • async/await + Future：每個 async fn 是惰性狀態機。 執行器 poll 它；Pending 時讓出 CPU，Ready 時完成。 適合 I/O 密集並發（少量執行緒驅動大量任務）。
  • tokio：Rust 最主流的非同步 runtime。 #[tokio::main]、tokio::spawn、tokio::join! 是最常用的三個工具。 CPU 密集任務用 tokio::task::spawn_blocking 轉到執行緒池。
🔑
Rust 並行的選型指南

CPU 密集 + 真正平行：thread::spawn（OS 執行緒，多核並行）。
多方共享可變狀態：Arc<Mutex<T>> 或 Arc<RwLock<T>>。
結構化資料流（單向）：mpsc channel（天然無競爭，所有權清楚）。
I/O 密集 + 大量並發：async/await + tokio（高吞吐、低執行緒開銷）。
