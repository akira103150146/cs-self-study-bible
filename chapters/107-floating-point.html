開場:當電腦說 0.1 + 0.2 = 0.30000000000000004

打開 Python 直譯器,輸入這三行: 

>>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False

如果你是第一次看到這個結果,或許會覺得懷疑人生。電腦不是應該很精確嗎? 0.1 加 0.2,不就是 0.3 嗎?但它回答了 False。 這不是 Python 的 bug,不是哪個函式庫的問題, 而是幾乎所有主流程式語言——C、C++、Java、JavaScript、Rust、Go——共同遵守的一套標準所帶來的必然結果。 這套標準叫做 IEEE 754。

要理解這件事,我們得先問一個更根本的問題:電腦怎麼儲存小數? 在第 20 章中,我們看到整數可以用二補數(two's complement)精確地表示任何整數。 但浮點數是另一個故事——整數的世界是離散而精確的,實數的世界是連續而無窮的, 而記憶體是有限的。把無窮壓縮進有限,必然有所取捨。IEEE 754 就是那份取捨協議。

🔑
本章的主旋律

浮點數是一份妥協協議——它說清楚了:我們保留哪些資訊、丟掉哪些、什麼時候會產生奇怪的結果。 讀懂這份協議,你才能真正「駕馭」浮點數,而不是被它玩弄。

定點數的困境:範圍與精度不能兩全

要理解「為什麼需要浮點數」,先來看看不用浮點數的世界——定點數(fixed-point number)。

假設我們有 32 個位元,決定用前 16 位存整數部分、後 16 位存小數部分——小數點「固定」在第 16 位之後,這就是定點。 後 16 位的精度是 $\frac{1}{2^{16}} \approx 0.0000153$,最大可表示約 $32767$。 這聽起來不錯,但問題立刻浮現:

  • 想表示地球到月亮的距離 384,400,000 公尺?超出 32767——溢位。
  • 想表示一個氫原子的半徑 $5.29 \times 10^{-11}$ 公尺?精度遠遠不夠——下溢。
  • 如果把精度調細(更多位給小數部分),最大可表示的整數又更小。

定點數的致命弱點:動態範圍(dynamic range)太窄。 真實世界的數字跨度,從次原子尺度到宇宙尺度差了大約 $10^{60}$, 而定點數只能「顧好一個小區間」。

浮點數的靈感來自科學記號(scientific notation):與其固定小數點的位置, 不如讓它「浮動」。$6.674 \times 10^{-11}$ 牛頓力——先記住有效數字(6.674),再記住指數(−11)。 同樣的 32 個位元,換成浮點格式就可以同時覆蓋極大與極小的數, 代價是精度不再均勻分布在數線上(越靠近零越密,越遠離零越稀)。

ℹ️
定點數並未消失

在嵌入式系統、DSP(數位訊號處理器)、金融計算(用整數的「分」避免浮點誤差)、 遊戲引擎的確定性物理等場合,定點數至今仍然活躍——因為它快速、可預測、沒有浮點的奇怪邊界情況。 浮點數並不是唯一答案,選哪種取決於應用。

IEEE 754 格式:符號、指數、尾數

1985 年,IEEE(電機電子工程師學會)發布了 IEEE 754 標準,統一了業界的浮點數表示法。 在此之前,各家晶片廠商各有格式,程式在不同機器之間跑出不同結果是家常便飯。 IEEE 754 終結了這個混亂——它精確定義了位元佈局,讓浮點計算在任何符合標準的機器上都一致。

IEEE 754 定義了兩種最常用的格式:

  • 單精度(single-precision, float32):32 位元,精度約 7 位十進位有效數字,範圍約 $\pm 3.4 \times 10^{38}$。
  • 雙精度(double-precision, float64):64 位元,精度約 15–16 位十進位有效數字,範圍約 $\pm 1.8 \times 10^{308}$。Python 的 float 預設就是 float64。

兩者都由三個欄位組成:

  • 符號位(sign bit, S):1 位元。0 = 正,1 = 負。
  • 指數欄(exponent):儲存「2 的幾次方」,用偏移碼(biased exponent)表示。
  • 尾數欄(fraction / significand / mantissa):儲存有效數字的小數部分。

一個正規化浮點數的值公式為:

$$\text{值} = (-1)^{S} \times 1.f_{n-1}f_{n-2}\cdots f_0 \big|_2 \times 2^{E_{\text{stored}} - \text{bias}}$$

其中 $E_{\text{stored}}$ 是指數欄中存放的無符號整數,$\text{bias}$ 是偏移量(float32 為 127,float64 為 1023),$1.f\ldots$ 是以隱含前導 1 開頭的二進位小數。

正規化與隱含前導 1:免費多一位精度

二進位的科學記號與十進位類似:任何非零數都可以寫成 $1.xxx\ldots \times 2^n$ 的形式, 使得整數部分恰好是 1。這個過程叫做正規化(normalization)。

例如:$1101.011_2 = 1.101011 \times 2^3$。注意整數部分的「1」是固定的—— 在二進位裡,正規化數的整數部分一定是 1(非零)。 IEEE 754 聰明地利用了這一點:不儲存那個固定的 1,只儲存小數點後的部分(fraction)。 這叫做隱含前導 1(implicit leading 1)。 如此一來,float32 的 23 個 fraction 位元實際上提供了 24 位元的精度(因為那個 1 是免費的)。

🔑
隱含 1 = 免費多一位精度

float32 的 fraction 欄有 23 位元,但加上隱含的前導 1,實際有效位數是 24 位元; float64 的 fraction 欄有 52 位元,加上隱含 1 共 53 位元。 這就是為什麼 float64 能提供約 15–16 位十進位有效數字 ($2^{53} \approx 9 \times 10^{15}$,取 $\log_{10}$ ≈ 15.95)。

偏移碼(bias)的用意

指數欄存的不是帶正負號的整數,而是一個偏移碼:實際指數加上偏移量之後存入。 float32 的偏移量是 127,所以真正的指數 $e = E_{\text{stored}} - 127$。 例如指數欄存 130($= 10000010_2$),真正指數就是 $130 - 127 = 3$。

這樣設計的原因有兩個:

  • 比較方便:偏移碼讓整個 32 位元浮點數可以直接當作無號整數比較大小(除了符號位要特別處理),實作排序或最小/最大值時不需要先解析格式。
  • 統一化:避免分別設計正指數與負指數的儲存方式,一個無號整數欄位全部搞定。

float32 指數欄 8 位元,偏移 127:可表示真實指數範圍 $-126$ 到 $+127$(指數 0 和 255 保留給特殊值)。 float64 指數欄 11 位元,偏移 1023:真實指數範圍 $-1022$ 到 $+1023$。

手算編碼:把 13.375 存進 32 個位元

理論夠了——來親手把一個數字編碼成 IEEE 754 single precision,走一遍每一步:

用 Python 驗證,同時學會位元觀察的工具: 

import struct

def float32_bits(x):
    """把 float32 印出符號/指數/尾數三欄"""
    # '>f' = big-endian float; '>I' = big-endian unsigned int
    bits = struct.unpack('>I', struct.pack('>f', x))[0]
    b = f'{bits:032b}'
    sign = b[0]
    exp  = b[1:9]
    frac = b[9:]
    e_stored = int(exp, 2)
    print(f"符號   : {sign}  ({'正' if sign=='0' else '負'})")
    print(f"指數欄 : {exp} = {e_stored}  (真實指數 = {e_stored - 127})")
    print(f"尾數欄 : {frac}")
    print(f"Hex    : {bits:08X}")

float32_bits(13.375)
符號   : 0  (正)
指數欄 : 10000010 = 130  (真實指數 = 3)
尾數欄 : 10101100000000000000000
Hex    : 41560000

反向解碼:從位元回到數值

給你一串位元,同樣可以反推回數值。以 float32 的 0x3FC00000 為例: 

bits = 0x3FC00000
b = f'{bits:032b}'              # '00111111110000000000000000000000'
S    = int(b[0])                # 0 → 正
E    = int(b[1:9], 2)           # 01111111 = 127
frac = b[9:]                    # 10000000000000000000000

value = (-1)**S * (1 + int(frac, 2) / 2**23) * 2**(E - 127)
print(value)                    # 1.5

解析:$(-1)^0 \times 1.1_2 \times 2^{127-127} = 1.5 \times 1 = 1.5$。正確!

💡
Python 的 float.hex() 更直覺

(1.5).hex() 回傳 '0x1.8p+0', 意思是 $1.8_{16} \times 2^0 = 1.5_{10}$。 (0.1).hex() 回傳 '0x1.999999999999ap-4'——注意那個永遠跑不完的 9,正是 0.1 無法精確表示的直接體現。

特殊值:零、無窮大、NaN 與次正規數

IEEE 754 保留了一些特殊位元樣式來表示「超出正規化數範圍」的情況。 判斷方法:看指數欄是全 0 還是全 1。

名稱指數欄尾數欄符號位語意
+0全 0全 00正零
−0全 0全 01負零(計算上 = +0,但符號不同)
次正規數 (subnormal)全 0非全 0任意極小數,不帶隱含 1;漸進下溢
+∞全 1全 00正無窮大
−∞全 1全 01負無窮大
NaN全 1非全 0任意Not a Number;非數值結果

零與負零

IEEE 754 有兩個零:+0 和 −0。在大多數情況下 +0 == -0 為 True, 但它們在除法等運算中行為不同:1.0 / +0.0 得 +∞, 1.0 / -0.0 得 -∞。Python 因為會先丟出 ZeroDivisionError 而看不到這個, 在 C 中開啟 IEEE 模式就能觀察到。

無窮大(Infinity)

溢位或正數除以零的結果。Inf 可以參與運算: 

inf = float('inf')
print(inf + 1)        # inf
print(inf * 2)        # inf
print(inf - inf)      # nan  ← 無窮減無窮沒有意義
print(1.0 / inf)      # 0.0

NaN:不是數字

0.0 / 0.0、inf - inf、對負數開平方根——這些運算沒有有意義的實數結果,IEEE 754 用 NaN(Not a Number) 表示。 NaN 有一個非常反直覺的特性: 

nan = float('nan')
print(nan == nan)   # False  ← NaN 是唯一不等於自己的東西
print(nan != nan)   # True
print(nan > 0)      # False
print(nan < 0)      # False
import math
print(math.isnan(nan))   # True  ← 正確的 NaN 檢測方式

NaN != NaN 這個規則出自 IEEE 754 的刻意設計: 「無意義的結果」本來就無法比較——連「是不是同一個無意義」都說不清楚。 這個特性是很多 bug 的來源,我們在第八節會再提到。

次正規數(Subnormal / Denormal)

float32 最小的正規化數約為 $1.18 \times 10^{-38}$(指數 = 1,fraction = 0)。 如果計算結果比這還小怎麼辦?直接變成零會造成突然的「突然下溢」——兩個非零數相除突然得到零。 IEEE 754 用次正規數解決這個問題:當指數欄全為 0 且尾數欄非零時,去掉隱含的前導 1, 改成 $0.f\ldots \times 2^{-126}$。這讓浮點數能「漸進式地」接近零, 代價是有效位數減少。

⚠️
次正規數很慢

許多 CPU 處理次正規數時需要走軟體路徑(因為硬體浮點單元不直接支援), 速度可能比正規數慢 10–100 倍。效能敏感的程式(神經網路訓練、音訊處理)有時會設置 DAZ/FTZ 旗標(Denormals Are Zero / Flush To Zero)把次正規數強制歸零以換取速度。

為什麼 0.1 存不進去:機器精度與捨入

我們現在回頭看 $0.1$。把它轉成二進位:

$$0.1 \times 2 = 0.2 \Rightarrow 0$$ $$0.2 \times 2 = 0.4 \Rightarrow 0$$ $$0.4 \times 2 = 0.8 \Rightarrow 0$$ $$0.8 \times 2 = 1.6 \Rightarrow 1$$ $$0.6 \times 2 = 1.2 \Rightarrow 1$$ $$0.2 \times 2 = 0.4 \Rightarrow 0 \quad \text{(重複!)}$$

所以 $0.1_{10} = 0.0\overline{0011}_2$——一個無限循環二進位小數, 就像 $\frac{1}{3}$ 在十進位裡寫不完一樣。 float64 只有 52 個 fraction 位元,必須在某一位截斷, 存進去的實際上是離 $0.1$ 最近、但不完全相等的值: 

>>> format(0.1, '.55f')
'0.1000000000000000055511151231257827021181583404541015625'

這個值和 $0.1$ 的誤差約 $5.5 \times 10^{-18}$——極小,但確實存在。 $0.1$ 加 $0.2$ 的誤差累積之後,就和 $0.3$ 的誤差不一樣,所以比較結果是 False。

機器精度(Machine Epsilon)與 ulp

機器精度(machine epsilon) $\varepsilon_m$ 是「1.0 與它相鄰的下一個可表示浮點數之間的距離」, 也就是相對捨入誤差的最大上界:$|fl(x)-x|/|x| \le \varepsilon_m/2$。

$$\varepsilon_m = 2^{-52} \approx 2.22 \times 10^{-16} \quad \text{(float64)}$$ 
import sys
print(sys.float_info.epsilon)   # 2.220446049250313e-16
# 驗證: 1.0 和下一個 float64 的差
import math
print(math.nextafter(1.0, 2.0) - 1.0)  # 2.220446049250313e-16

ulp(unit in the last place) 是某個數 $x$ 附近兩個相鄰浮點數的間距。 不同大小的數有不同的 ulp:靠近 $1.0$ 的 ulp 是 $\varepsilon_m$, 靠近 $10^{15}$ 的 ulp 大得多,靠近 $0.001$ 的 ulp 小得多。 這反映了浮點數「靠近零越密、遠離零越稀」的本質。

捨入模式

當一個實數無法精確表示時,IEEE 754 規定如何捨入。預設模式是 就近捨入——雙數優先(round to nearest, ties to even),也叫「銀行家捨入」: 精確落在兩個相鄰浮點數正中間時,選偶數尾數的那個。 這能讓大量捨入誤差在統計上相互抵消,比「遇五入」的累積偏差小。

不要用 == 比較浮點數

第 55 章在談數值誤差時已經指出這個原則。浮點數的正確比較方式是給定一個容忍範圍: 

import math

# 錯誤:直接比較
print(0.1 + 0.2 == 0.3)          # False

# 正確:用 math.isclose
print(math.isclose(0.1 + 0.2, 0.3))               # True
# isclose 預設 rel_tol=1e-9, abs_tol=0.0
# 含義: |a-b| <= max(rel_tol * max(|a|,|b|), abs_tol)

# 當比較對象接近 0 時,要同時給 abs_tol
print(math.isclose(1e-15, 0.0, abs_tol=1e-12))    # True
⚠️
永遠不要用 == 比較浮點數

唯一的例外:比較是否為 NaN 時用 math.isnan(x), 比較是否為無窮大時用 math.isinf(x)。 若真的需要精確小數(金融計算),改用 Python 的 decimal.Decimal 模組。

浮點陷阱:大數吃小數、相減抵銷、累加順序

浮點誤差不只是「小小的精度問題」——在特定情況下,它會讓計算結果大錯特錯。以下是幾個經典陷阱。

陷阱一:大數吃小數(Absorption)

把一個非常小的數加到非常大的數上時,小數「消失」了: 

big   = 1e16    # 10 的 16 次方
small = 1.0

result = big + small - big
print(result)   # 0.0,不是 1.0!

# 原因:big 的 ulp 遠大於 small
import math
print(math.ulp(big))   # 2.0 — big 附近相鄰浮點數的間距是 2,加 1 根本沒反應

在大量數值求和時,這個問題尤其嚴重。解法是用 Kahan 補償求和(Kahan summation)或 Python 的 math.fsum: 

import math

nums = [1.0, 1e16, -1e16]          # 理想結果 = 1.0
print(sum(nums))                    # 0.0  ← 錯誤
print(math.fsum(nums))              # 1.0  ← 正確(Kahan 補償)

陷阱二:相減抵銷(Catastrophic Cancellation)

兩個幾乎相等的數相減,有效位數會大量消失——因為前幾位完全抵消,剩下的都是捨入誤差: 

a = 1.00000001
b = 1.00000000
diff = a - b
print(diff)                # 1.0000000116860974e-08
print(1e-8)                # 1e-08
# 差了 1.17e-16,相對誤差約 1.17%——遠超 float64 本身的 ulp 精度

# 更嚴重的例子:sqrt(x+1) - sqrt(x) 當 x 很大
import math
x = 1e15
naive  = math.sqrt(x + 1) - math.sqrt(x)
better = 1.0 / (math.sqrt(x + 1) + math.sqrt(x))   # 有理化分母
print(f'直接算: {naive}')    # 1.4901161193847656e-08 (不準)
print(f'有理化: {better}')   # 1.5811388300842022e-08 (準確)

修法:改用數學等價但數值更穩定的公式。例如 $\sqrt{x+1} - \sqrt{x} = \frac{1}{\sqrt{x+1}+\sqrt{x}}$。

陷阱三:累加順序影響結果

浮點加法不滿足結合律——$(a + b) + c$ 不一定等於 $a + (b + c)$: 

a, b, c = 1e15, -1e15, 1.0

print((a + b) + c)   # 1.0   ← 正確
print(a + (b + c))   # 0.0   ← 錯誤:b+c 先算,1.0 被 1e15 吃掉

這也解釋了為什麼並行浮點運算(GPU、多執行緒)的結果可能不具可重複性—— 執行緒的完成順序不同,累加順序就不同,結果就可能有微小差異。

陷阱四:NaN 的傳染性

NaN 會「感染」它參與的所有運算,產生更多 NaN: 

nan = float('nan')
print(nan + 1)     # nan
print(nan * 0)     # nan
print(nan > 0)     # False
print(nan < 0)     # False
print(nan == nan)  # False  ← 用 == 永遠抓不到 NaN!

因為 nan != nan,任何用 == 偵測 NaN 的程式都是 bug。 正確作法是 math.isnan(x) 或 x != x(後者雖然有效但不推薦,難讀)。

⛔
NaN 靜靜地傳播

NaN 不會丟出例外——它靜靜地傳播,污染後續所有計算結果,最終你才發現輸出全是 NaN。 在進行複雜的數值計算前後,加上 assert not any(math.isnan(v) for v in results) 是防禦性編程的好習慣。

✏️ 練習 101.1 思考

手算:把 −0.75 編碼成 IEEE 754 float32。 給出符號位、指數欄(8 位元二進位)、尾數欄(23 位元二進位),以及最終的 4-byte 十六進位表示。

看解答

步驟 1:轉二進位

$0.75_{10} = 0.11_2$（$0.75 \times 2 = 1.5 \to 1$；$0.5 \times 2 = 1.0 \to 1$）

步驟 2:正規化

$0.11_2 = 1.1 \times 2^{-1}$

步驟 3:編碼

  • 符號:負數 → S = 1
  • 指數欄:$-1 + 127 = 126 = 01111110_2$
  • 尾數欄:$1_2$ 之後補 22 個 0 → 10000000000000000000000

完整 32 位元:1 01111110 10000000000000000000000

十六進位:0xBF400000

Python 驗證:

import struct
struct.pack('>f', -0.75).hex()   # 'bf400000'

解讀:$(-1)^1 \times 1.1_2 \times 2^{-1} = -1.5 \times 0.5 = -0.75$ ✓

✏️ 練習 101.2 實作

預測以下每一段 Python 程式的輸出,並解釋原因: 

# (a)
x = 0.1 + 0.1 + 0.1
print(x == 0.3)

# (b)
import math
big = 2.0 ** 53          # float64 最大連續整數
print(big + 1 == big)

# (c)
inf = float('inf')
nan = float('nan')
print(inf - inf == nan)
看解答

(a) False

0.1 存進去已有誤差,三個誤差累積後和精確 0.3 的誤差樣式不同。用 math.isclose(x, 0.3) 才會得 True。

(b) True

$2^{53}$ 是 float64 連續整數的上限。在這個量級,ulp = 2,所以 $2^{53} + 1$ 會被捨入回 $2^{53}$。因此 big + 1 == big 為 True。這正是大數吃小數的典型案例。

(c) False

inf - inf 確實等於 nan——但 nan == nan 永遠是 False!所以整個運算式為 False。要偵測 NaN 要用 math.isnan(inf - inf)。

✏️ 練習 101.3 挑戰

以下這個函式計算兩數的調和平均數(harmonic mean):$H(a,b) = \frac{2ab}{a+b}$。 

def harmonic_mean(a, b):
    return 2 * a * b / (a + b)

(1) 若 a = 1e308、b = 1e308,呼叫 harmonic_mean(a, b) 會得到什麼?為什麼?
(2) 想一個數學等價但不會溢位的改寫方式。

看解答

(1) 結果是 inf。原因:2 * 1e308 * 1e308 超出 float64 最大值($\approx 1.8 \times 10^{308}$),產生溢位成為 inf。inf / (a + b) 仍然是 inf。

實際正確答案應為 1e308($H(x,x) = x$)。

(2) 化簡可得:

$$H(a,b) = \frac{2ab}{a+b} = \frac{2}{\frac{1}{a}+\frac{1}{b}}$$ 
def harmonic_mean_safe(a, b):
    return 2.0 / (1.0/a + 1.0/b)

print(harmonic_mean_safe(1e308, 1e308))   # 1e308 ✓

先做倒數讓數值縮小,避免中間結果溢位。這種「數學等價但數值更穩定的重寫」是數值計算的核心技巧,第 55 章中也有更多例子。

把這一章串起來

我們從一個讓人困惑的 Python 輸出出發,走過了整個 IEEE 754 的世界。回顧幾個核心路標:

  • 浮點數 = 有限位元的妥協:不是所有實數都能精確表示;多數情況下存的是「最近的浮點數」。
  • IEEE 754 三欄位:符號(1位)+ 偏移指數(8/11位)+ 尾數(23/52位),加上隱含前導 1,float32 有 24 位有效位元、float64 有 53 位。
  • 偏移碼(bias):指數存 $e + 127$(float32)或 $e + 1023$(float64),讓整個浮點數可以當無號整數比大小。
  • 特殊值:指數全 0 → 零/次正規數;指數全 1 → Inf/NaN。次正規數讓下溢漸進化;NaN 是傳染性的「毒」。
  • 0.1 存不進去是結構性問題,不是 bug——$0.1_{10}$ 在二進位是無限循環小數,被截斷後有微小誤差。
  • 實務鐵則:浮點比較用 math.isclose;NaN 偵測用 math.isnan;累加大量數字用 math.fsum;數學等價不代表數值等價。

這一章是第 20 章(整數二補數)的浮點對應:那裡我們看懂了整數在位元層的面貌,這裡我們看懂了小數。 而在第 55 章(數值方法)中,我們用這個知識去分析誤差的累積與演算法穩定性—— 如果你還沒讀那一章,現在帶著這章的理解回去,很多東西會豁然開朗。
