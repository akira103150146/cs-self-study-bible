延伸專案怎麼用

核心 Lab 做完之後,挑一個往下挖。每個專案都有評分規準;做得好可以累積成期末專題。

專案 1 · 一支程式穿過的所有層 C1.1C1.4

目標

親眼看到一支普通的程式在執行時經過了哪些層:你的程式碼 → C 函式庫 → 系統呼叫 → 作業系統核心。

規格

  1. 寫一支小程式:讀一個文字檔、數出行數、把結果寫到另一個檔案。
  2. 用 ltrace 記錄它呼叫了哪些函式庫函式,用 strace 記錄它發出了哪些系統呼叫。
  3. 畫一張圖(可以用 Mermaid 或手繪掃描),把「你的一行程式碼 → 對應的函式庫呼叫 → 對應的系統呼叫」連起來,至少追三條(開檔、讀檔、寫檔)。
  4. 寫一頁報告:哪些系統呼叫是你沒想到會出現的?程式啟動時(main 之前)作業系統做了哪些事?

評分規準

項目配分通過標準
追蹤紀錄30附上 ltrace 與 strace 的輸出,並標出與你的程式碼對應的部分
分層圖40至少三條完整的「程式碼 → 函式庫 → 系統呼叫」路徑,且正確
報告30至少指出兩個意料之外的系統呼叫並解釋用途

延伸方向

比較同一支程式用 Python 寫時,strace 看到的系統呼叫數量差多少,並解釋原因(直譯器本身的啟動成本)。

專案 2 · 自己的開發容器 C1.5

目標

把「我的電腦上可以跑」變成「任何人的電腦上都可以跑」。

規格

  1. 為你自己的一個小專案(任何語言)寫一個 Dockerfile,固定作業系統版本、編譯器或直譯器版本、所有相依套件。
  2. 寫一個 Makefile 或腳本,讓別人 clone 下來後只要一個指令就能建好映像檔並執行測試。
  3. 加上 .devcontainer/devcontainer.json,讓 VS Code 可以直接在容器裡開發。
  4. 找一位同學在他的電腦上照 README 操作,紀錄他遇到的問題並修正。

評分規準

項目配分通過標準
可重現50同學在另一台電腦上一個指令就能跑完測試
版本固定20基底映像檔與套件都有明確版本
文件30README 清楚,並記錄同學試跑時遇到的問題與修正

延伸方向

加上 GitHub Actions,讓每次 push 都自動在容器裡跑測試(CI)。

專案 3 · 抽象層的代價 C1.2

目標

量測抽象不是免費的:你的 KVStore 讓使用者好用,但每次操作讀寫了多少區塊?

規格

  1. 利用 RawDisk 的 reads 與 writes 計數器,量測你的 KVStore 在 1、10、100、1000 筆資料時,每次 put 與 get 平均讀寫幾個區塊。
  2. 畫出「資料筆數 vs 每次操作的區塊讀寫數」的圖。
  3. 改進你的實作(例如只改寫有變動的區塊、在記憶體裡保留索引),讓大量資料時的區塊寫入數明顯下降,並維持原本所有測試通過。
  4. 寫一頁報告比較改進前後,並討論你的改進讓介面或可靠度付出了什麼代價(例如當機時資料是否一致)。

評分規準

項目配分通過標準
量測30四種資料量都有數據與圖
改進401000 筆時的平均寫入區塊數至少降為原本的一半,且原測試全部通過
分析30清楚說明取捨,至少討論一種失敗情境

延伸方向

設計一個「寫到一半當機」的測試(在第 k 次 write_block 時丟例外),讓你的 KVStore 在重新開啟後仍能讀到一致的資料(提示:第 11 章的 journaling)。
